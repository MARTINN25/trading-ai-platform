# Git Workflow

**Статус:** Утверждён
**Владелец:** Product Owner
**Дата последнего изменения:** 2026-08-05
**Назначение:** определить безопасный процесс работы с Git и GitHub.

Настоящий документ детализирует раздел 9 «Правила работы с Git» документа [`PROJECT_CHARTER.md`](../../PROJECT_CHARTER.md). При расхождении между документами приоритет имеет `PROJECT_CHARTER.md` как утверждённый устав проекта (см. раздел 8.1 устава).

---

## 1. Цель процесса

Обеспечить предсказуемую, безопасную и воспроизводимую работу с историей репозитория так, чтобы ветка `main` всегда отражала проверенное и принятое состояние проекта, а любое изменение можно было проследить до конкретной задачи.

---

## 2. Область применения

Документ применяется ко всем изменениям в репозитории `trading-ai-platform` — документации, конфигурации и (начиная с Этапа 4) программного кода — независимо от того, вносит их Product Owner, Solution Architect или Claude.

---

## 3. Роли и ответственность

| Роль | Ответственность в Git-процессе |
|---|---|
| **Product Owner** | Утверждает результат задачи; даёт отдельное разрешение на commit, push, merge и на любые операции, изменяющие опубликованную историю. |
| **Solution Architect / CTO** | Проводит архитектурное ревью изменений перед их принятием. |
| **Senior Software Engineer (Claude)** | Вносит изменения в рабочей ветке, выполняет проверки, показывает diff; не выполняет commit, push, merge и другие управляющие Git-операции без отдельного явного разрешения в задании. |

---

## 4. Основная ветка main

`main` — единственная долгоживущая ветка репозитория. Она содержит только проверенное и принятое состояние проекта и всегда должна оставаться в рабочем, непротиворечивом состоянии.

---

## 5. Запрет прямой работы в main

Прямые изменения в `main` запрещены. Любое изменение вносится через отдельную рабочую ветку и попадает в `main` только через слияние после проверки и принятия.

---

## 6. Правила создания короткоживущих веток

1. Ветка создаётся от актуального состояния `main`.
2. Ветка существует ровно столько, сколько требуется для одной задачи, и удаляется (по отдельному разрешению) после слияния.
3. Долгоживущие параллельные ветки не создаются — проект использует простой trunk-based подход.

---

## 7. Префиксы веток

- `docs/` — документация;
- `feature/` — новая функциональность;
- `fix/` — исправление дефекта;
- `refactor/` — рефакторинг без изменения поведения;
- `chore/` — вспомогательные технические задачи.

---

## 8. Формат имени ветки

```
<тип>/<краткое-название>
```

Пример: `docs/engineering-foundation`, `fix/price-normalization`.

---

## 9. Одна ветка — одна задача

Одна ветка соответствует одной задаче или одному логически целостному изменению. Смешивание нескольких независимых задач в одной ветке не допускается.

---

## 10. Один коммит — одно изменение

Один коммит содержит одно логически целостное изменение. Коммит должен быть понятен без необходимости смотреть соседние коммиты.

---

## 11. Стиль сообщений коммитов

Рекомендуемые префиксы сообщений коммитов:

- `docs:` — изменения документации;
- `feat:` — новая функциональность;
- `fix:` — исправление дефекта;
- `refactor:` — рефакторинг без изменения поведения;
- `chore:` — вспомогательные технические изменения;
- `test:` — изменения, относящиеся к тестам;
- `ci:` — изменения конфигурации CI.

Формат: `<префикс>: <краткое описание сути изменения>`.

---

## 12. Жизненный цикл задачи

1. Переключение на `main`.
2. `git pull` — получение актуального состояния.
3. Создание рабочей ветки от `main`.
4. Внесение изменений в рамках поставленной задачи.
5. Выполнение проверок (раздел 19).
6. Архитектурное и/или продуктовое ревью.
7. `commit` — только после ревью, отдельным разрешением.
8. `push` — только после commit, отдельным разрешением.
9. `merge` в `main` — только после проверки результата (раздел 20).
10. Обновление локального `main` (`git pull`) после слияния.

---

## 13. Правила pull request

1. Pull request открывается из рабочей ветки в `main`.
2. Описание PR отражает суть задачи и перечисляет затронутые файлы.
3. PR не объединяет несколько несвязанных задач.
4. PR остаётся открытым до получения ревью и принятия результата Product Owner.

---

## 14. Условия слияния

Слияние в `main` допускается только когда:

1. Изменения прошли предусмотренные проверки (раздел 20).
2. Архитектурное ревью пройдено, если задача его требует.
3. Product Owner явно принял результат.
4. В ветке нет конфликтов с текущим состоянием `main`.

---

## 15. Запрещённые операции

Без прямого разрешения Product Owner запрещены:

- `force push`;
- `hard reset`;
- переписывание опубликованной истории;
- прямой commit в `main`;
- commit секретов, ключей, токенов и конфиденциальных данных;
- массовое удаление файлов или веток без согласования.

---

## 16. Правила отката

1. Откат вносится новым коммитом (`git revert`), а не переписыванием истории.
2. Откат опубликованных изменений выполняется только по отдельному разрешению Product Owner.
3. Причина отката фиксируется в сообщении коммита.

---

## 17. Правила конфликтов merge

1. Конфликт разрешается в рабочей ветке до слияния в `main`, а не в самой `main`.
2. Разрешение конфликта не должно молча отбрасывать чужие изменения — при неоднозначности решение выносится на Product Owner и/или Solution Architect.
3. После разрешения конфликта обязательно повторное выполнение проверок (раздел 20).

---

## 18. Правила работы Claude с Git

1. Claude проверяет текущую ветку и `git status` до внесения любых изменений.
2. Claude не выполняет `git add`, `git commit`, `git push`, `git merge`, `git rebase`, `git reset`, `git checkout`, `git switch` без отдельного явного разрешения в конкретном задании.
3. Claude не удаляет файлы и ветки без отдельного разрешения.
4. Claude не выполняет `force push`, `hard reset` и переписывание истории ни при каких обстоятельствах, кроме прямого разрешения Product Owner.
5. Claude показывает фактический diff и список затронутых файлов перед тем, как задача может считаться готовой к ревью.

---

## 19. Минимальный набор проверок перед commit

1. `git status --short` — подтверждён ожидаемый список изменённых файлов.
2. `git diff --check` — отсутствуют конфликтные маркеры и ошибки пробелов.
3. `git diff` — изменения соответствуют задаче и не содержат посторонних правок.
4. Для Markdown-файлов — структурная корректность (заголовки, списки, таблицы).
5. Отсутствуют секреты, ключи и конфиденциальные данные в изменённых файлах.
6. Для полностью неотслеживаемых (новых) файлов: `git diff` их содержимое не показывает. Порядок проверки:
   - сначала `git status --short --untracked-files=all` — получить полный список новых файлов;
   - для просмотра diff нового файла допустимо `git add -N <путь>` (intent-to-add) с последующим `git diff -- <путь>`;
   - `git add -N` фиксирует сам факт существования файла для Git, но не добавляет его содержимое в staged-коммит;
   - полноценный `git add` (без `-N`) выполняется только после ревью и отдельного разрешения.

---

## 20. Минимальный набор проверок перед merge

1. Все проверки из раздела 19 пройдены в финальном состоянии ветки.
2. Ветка актуализирована относительно `main` (нет расхождения, требующего разрешения конфликтов).
3. Архитектурное ревью пройдено, если задача его требует.
4. Product Owner явно принял результат.

---

## 21. Definition of Done для Git-задачи

Git-задача считается завершённой только когда:

1. Изменения внесены в отдельной короткоживущей ветке с корректным именем и префиксом.
2. Проверки разделов 19 и 20 пройдены.
3. Diff и список изменённых файлов показаны для ревью.
4. Solution Architect провёл ревью (если применимо).
5. Product Owner явно принял результат.
6. Commit, push и merge выполнены только после принятия — не ранее.

---

## 22. Примеры безопасных команд PowerShell

Команды ниже иллюстрируют типовые шаги жизненного цикла (раздел 12) и выполняются только с явного разрешения Product Owner в рамках конкретной задачи.

> **Примеры ниже нельзя выполнять дословно.** Перед запуском необходимо заменить все значения в угловых скобках на данные текущей утверждённой задачи и проверить текущую ветку командой `git branch --show-current`.

```powershell
# Переключение на main и получение актуального состояния
git switch main
git pull

# Создание рабочей ветки от main
git switch -c <тип>/<краткое-название>

# Просмотр состояния и изменений перед commit
git status --short --untracked-files=all
git diff --check
git diff

# Commit одного логически целостного изменения
git add <путь-к-проверенному-файлу>
git commit -m "docs: описать выполненное изменение"

# git diff --cached показывает именно то содержимое, которое попадёт в коммит
git diff --cached --check
git diff --cached

# Публикация ветки
git push -u origin <тип>/<краткое-название>

# Обновление локального main после слияния через PR
git switch main
git pull
```

## 23. Типовые ошибки и безопасные действия при них

| Ошибка | Безопасное действие |
|---|---|
| Изменения ещё не закоммичены, и вы случайно оказались в `main` | 1. Не выполнять commit.<br>2. Проверить `git status`.<br>3. Создать новую ветку из текущего состояния: `git switch -c <тип>/<краткое-название>`.<br>4. Убедиться, что незакоммиченные изменения остались в рабочем дереве.<br>5. Продолжить только после проверки ветки и статуса.<br>`git stash` используется только при отдельной необходимости и с пониманием риска конфликтов при `stash pop` — это не основной сценарий. |
| Обнаружен конфликт при слиянии | Разрешить конфликт в рабочей ветке (раздел 17), повторить проверки, не использовать `git checkout --theirs/--ours` без понимания последствий. |
| Коммит случайно содержит секрет | Не выполнять `push`; сообщить Product Owner; секрет считается скомпрометированным и подлежит замене, а не только удалению из истории. |
| Локальный `main` отстал от удалённого | Выполнить `git pull` перед созданием новой ветки; не использовать `git reset --hard` без явного разрешения. |
| Ветка создана не от актуального `main` | 1. Не удалять ветку.<br>2. Не выполнять `reset`, `rebase` или `cherry-pick` самостоятельно.<br>3. Остановиться.<br>4. Показать: `git status`, `git branch -vv`, `git log --oneline --decorate --all -10`.<br>5. Выбрать способ исправления только после отдельного решения Product Owner и/или Solution Architect. |
| PowerShell отображает UTF-8-файл повреждёнными символами | Использовать `Get-Content <путь> -Encoding UTF8`. Не считать файл повреждённым только по неправильному отображению в консоли. |
| Непонятно, можно ли выполнять операцию | Остановиться и запросить отдельное разрешение Product Owner — не действовать по предположению. |
