## 11. Контекст

Продуктовый фундамент, логическая архитектура и инженерные принципы платформы утверждены (см. связанные документы, раздел 7). `TECHNOLOGY_EVALUATION.md` (раздел 4.1, утверждён) зафиксировал предварительную, необязывающую рекомендацию Solution Architect — Python как backend runtime — и явно указал, что выбор конкретной версии и политика её обновления являются предметом настоящего ADR.

Архитектурная форма MVP, в рамках которой действует решение:

- модульный монолит со строгими логическими границами (`LOGICAL_ARCHITECTURE.md`, раздел 3);
- Application Layer / Use Cases, координирующий доменные модули (`MODULE_BOUNDARIES.md`, модуль `application`);
- отдельные доменные модули (`identity`, `market`, `instruments`, `sources`, `ingestion`, `normalization`, `data_quality`, `provenance`, `analysis`, `llm_gateway`, `insights`, `evaluations`, `journal`, `notes`, `alerts`, `settings`, `audit`, `jobs`);
- отдельный внешний API adapter (предмет `ADR-0002`, не выбирается здесь);
- отдельный worker-процесс для критичных фоновых задач (`TECHNOLOGY_EVALUATION.md`, раздел 8);
- значительное число внешних HTTP API (рыночные данные, новости, календарь, LLM-провайдер);
- `llm_gateway` как единственная точка обращения к LLM (`LOGICAL_ARCHITECTURE.md`, раздел 9);
- локальная разработка на Windows, production deployment на Linux (`PRODUCT_SCOPE.md`, раздел 18);
- один основной владелец и разработчик платформы (`PRODUCT_SCOPE.md`, раздел 5);
- ограниченный бюджет (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-028).

Дата проверки технологических данных, использованных в настоящем ADR: 2026-08-05 (см. раздел 30 «Источники исследования»).

## 12. Проблема

Какой язык программирования и runtime использовать для исполнения Application Layer / Use Cases, доменных модулей, `llm_gateway` и worker-процесса критичных фоновых задач, чтобы решение соответствовало утверждённой логической архитектуре, поддерживалось одним разработчиком, эффективно работало с большим числом внешних HTTP API и не создавало избыточной сложности на этапе MVP.

Выбор backend API adapter, frontend, хранилища, очереди фоновых задач, SDK LLM-провайдера и инфраструктуры deployment в эту задачу не входит — эти вопросы рассматриваются отдельными ADR (`TECHNOLOGY_EVALUATION.md`, раздел 15).

## 13. Ограничения

- решение принимается до появления бизнес-кода — миграционная стоимость на этом этапе минимальна;
- один разработчик отвечает за весь объём backend — простота сопровождения важнее теоретической производительности;
- локальная разработка ведётся на Windows, production — на Linux; runtime должен быть одинаково пригоден на обеих платформах;
- бюджет ограничен — рассматриваются только open source runtime без лицензионных отчислений;
- решение не должно предполагать конкретный API adapter framework (`ADR-0002`) — оценивается язык/runtime как таковой;
- решение не должно принимать пред-релизные версии языка в production (`ENGINEERING_PRINCIPLES.md`, пункт 4 — безопасность по умолчанию не предполагает нестабильные ветки).

## 16. Выбранное решение

**CPython 3.14 — как язык/реализация runtime backend платформы для MVP.**

### Реализация runtime

- выбранная реализация — CPython, эталонная реализация языка Python (см. раздел 30);
- альтернативные реализации Python (например, PyPy и подобные) **не являются** выбранным runtime настоящего ADR;
- применение другой реализации Python для отдельного компонента платформы требует отдельной оценки совместимости с зависимостями проекта и отдельного управляемого решения — не молчаливой замены CPython.

### Политика версии

- production MVP использует стандартную **GIL-enabled сборку** CPython 3.14 (см. подраздел «Режим GIL и free-threaded сборка» ниже);
- используется последний совместимый patch-релиз линии 3.14.x, прошедший тесты проекта;
- точный patch-релиз не хардкодится в настоящем ADR навсегда — он задаётся централизованной конфигурацией проекта (раздел 23);
- pre-release версии Python не используются в production;
- переход на новую minor-линию Python требует проверки зависимостей, полного набора тестов и отдельного управляемого изменения;
- смена языка/реализации backend требует нового ADR, заменяющего ADR-0001 (`ADR_PROCESS.md`, раздел 18).

По данным официального исследования на 2026-08-05 (раздел 30), актуальным стабильным patch-релизом линии 3.14 является **CPython 3.14.7**; линия 3.14 находится в фазе `bugfix`. Python 3.15 находится в статусе `prerelease` (запланированный первый релиз — 2026-10-01) и **не выбирается** для production, пока не перейдёт в стабильную фазу.

### Режим GIL и free-threaded сборка

- CPython 3.14 имеет официально поддерживаемую free-threaded сборку (см. раздел 30, PEP 703, PEP 779);
- free-threaded режим **не является** стандартным режимом production MVP;
- MVP выбирает стандартную GIL-enabled сборку CPython 3.14 из-за более предсказуемой совместимости экосистемы и нативных расширений — на дату исследования free-threaded сборка официально поддерживается как опциональная альтернатива, но не заменяет GIL-enabled сборку по умолчанию (раздел 30, PEP 779);
- переход на free-threaded build может быть рассмотрен позднее — только после проверки совместимости всех критичных зависимостей платформы и отдельного benchmark, а не автоматически при обновлении patch-релиза;
- GIL-enabled CPython ограничивает параллельное исполнение Python-байткода потоками в рамках одного процесса — истинный многопоточный параллелизм CPU-bound кода на нескольких ядрах в одном процессе не гарантирован;
- GIL **не является** гарантией потокобезопасности бизнес-логики — доступ к общему изменяемому состоянию из нескольких потоков по-прежнему требует явной синхронизации;
- I/O concurrency платформы обеспечивается `asyncio` (раздел 15, критерий 4); CPU-bound работа изолируется от event loop независимо от режима GIL (раздел 21, мера 1);
- введение free-threaded режима для production — управляемое изменение runtime-конфигурации, требующее отдельного архитектурного ревью и, при значимом изменении risk-профиля, отдельного ADR-преемника (`ADR_PROCESS.md`, раздел 18), а не автоматическое следствие обновления patch-релиза.

## 17. Обоснование

Python выбран по совокупности критериев раздела 15, а не по единственному показателю:

- **соответствие архитектуре и сопровождение одним разработчиком** (критерии 1–2): Python архитектурно оценивается как быстрый путь от утверждённой логической архитектуры (`LOGICAL_ARCHITECTURE.md`, `MODULE_BOUNDARIES.md`) к работающему модульному монолиту при минимальном объёме кода, что критично при единственном разработчике (не измерено в рамках ADR);
- **работа с внешними API, асинхронный I/O** (критерии 3–4): `asyncio` — официальная, предназначенная для I/O-bound нагрузки модель, полностью покрывающая профиль платформы (много внешних HTTP-вызовов: источники данных, новости, календарь, LLM);
- **экосистема данных и LLM-интеграций** (критерии 5–6): решающее преимущество Python перед TypeScript/Node.js и Go для платформы, ядро которой — обработка данных и обращение к LLM-провайдерам (`llm_gateway`, `analysis`);
- **CPU-bound и runtime-производительность** (критерии 15, 18): Go превосходит Python по производительности и параллелизму, но платформа на этапе MVP не имеет обоснованной, названной CPU-bound задачи, которая перевешивала бы потери в критериях 1, 2, 5, 6 (`ENGINEERING_PRINCIPLES.md`, пункт 67 — технология не вводится без конкретной проблемы); при появлении такой задачи в будущем возможен точечный вынос компонента без замены всего backend (раздел 26);
- **типизация и тестируемость** (критерии 7–8): Python поддерживает статическую проверку через type hints при production-дисциплине (раздел 19), что признано достаточным относительно преимуществ в критериях 5–6;
- **риск блокировки event loop** (критерий 17): у Go риск ниже архитектурно (горутины и рантайм-планировщик), у Python и Node.js риск сопоставим и управляется дисциплиной (раздел 19), а не выбором языка как таковым;
- TypeScript/Node.js рассмотрен как жизнеспособная альтернатива (общий язык с frontend), но уступает Python по критериям 5–6, которые для этой платформы весомее выгоды единого языка.

Ни один вариант не выбран по признаку «популярности» или «современности» — оценка велась исключительно по критериям раздела 15.

## 18. Положительные последствия

- сильная экосистема анализа данных, применимая к `ingestion`/`normalization`/`data_quality`/`analysis`;
- зрелая экосистема HTTP- и LLM-интеграций, применимая к `sources` и `llm_gateway`;
- высокая скорость разработки MVP силами одного разработчика;
- один runtime для API-логики (за адаптером, `ADR-0002`), worker-процесса и аналитического pipeline — единая модель сопровождения и мониторинга;
- официальная поддержка Windows (разработка) и Linux (production);
- стандартная модель `async`/`await` для I/O-bound операций;
- широкий пул специалистов для возможного будущего привлечения.

## 19. Отрицательные последствия

- более низкая CPU-производительность по сравнению с Go в отдельных сценариях;
- более высокое потребление памяти в сопоставимых сценариях по сравнению с Go;
- реальный риск блокирующего кода внутри `asyncio`-pipeline при недостаточной дисциплине;
- необходимость строгой типизации (type hints) и статических проверок как процессной, а не языковой гарантии;
- неоднородное качество части сторонних библиотек Python-экосистемы;
- выбранная GIL-enabled сборка CPython 3.14 ограничивает истинный потоковый параллелизм CPU-bound кода в рамках одного процесса; free-threaded сборка существует как официально поддерживаемая альтернатива (раздел 16), но не выбрана для MVP и потребовала бы отдельной проверки совместимости зависимостей и benchmark перед переходом;
- динамическая природа языка требует дисциплины явных контрактов между модулями (`ENGINEERING_PRINCIPLES.md`, пункт 7).

## 20. Риски

1. Блокировка event loop блокирующим кодом внутри `asyncio`-pipeline.
2. Появление CPU-bound нагрузки, для которой Python-производительности окажется недостаточно.
3. Несовместимые между собой зависимости при росте числа интеграций.
4. Нативные зависимости, ведущие себя по-разному на Windows и Linux.
5. Supply-chain risk сторонних пакетов.
6. Устаревшие или брошенные библиотеки в отдельных интеграциях.
7. Неявные типовые ошибки при недостаточной дисциплине type hints.
8. Чрезмерная связанность доменного кода с конкретным web-фреймворком (риск для будущего `ADR-0002`).
9. Поздно обнаруженная необходимость выделить высокопроизводительный компонент в отдельный runtime.
10. Ошибочное предположение, что GIL гарантирует потокобезопасность бизнес-логики, ведущее к состояниям гонки при работе с общим изменяемым состоянием из нескольких потоков.

## 21. Меры снижения рисков

1. Блокировка event loop → блокирующие вызовы выполняются только в изолированных исполнителях (пул потоков/процессов), явное правило раздела 19; проверяется критерием раздела 25.
2. CPU-bound нагрузка → при выявлении конкретной, названной задачи — точечный вынос компонента в отдельный процесс/сервис без замены всего backend (раздел 26), в соответствии с `ENGINEERING_PRINCIPLES.md`, пунктом 13 (возможность последующего выделения модулей).
3. Несовместимые зависимости → воспроизводимая фиксация зависимостей (раздел 19), проверка перед обновлением.
4. Нативные зависимости Windows/Linux → приоритет платформонезависимым библиотекам; проверка совместимости на обеих платформах как часть критериев проверки (раздел 25).
5. Supply-chain risk → автоматизированная проверка уязвимостей зависимостей (раздел 25, последний пункт).
6. Устаревшие библиотеки → выбор зависимостей с активным сопровождением как часть будущих задач по каркасу проекта (раздел 23).
7. Неявные типовые ошибки → type hints обязательны для production-кода (раздел 19), проверяются статическим анализом.
8. Связанность с web-фреймворком → доменные модули не импортируют API framework (раздел 19); граница закрепляется правилом импортов, обязательна к проверке в `ADR-0002`.
9. Поздний вынос компонента → соблюдение строгих модульных границ (`MODULE_BOUNDARIES.md`) с самого начала делает такое выделение технически возможным без переписывания бизнес-логики (`ENGINEERING_PRINCIPLES.md`, пункт 13).
10. Ошибочное предположение о потокобезопасности → GIL прямо не считается гарантией потокобезопасности бизнес-логики (раздел 16); доступ к общему изменяемому состоянию из нескольких потоков защищается явной синхронизацией; критичные фоновые операции выполняются в отдельном worker-процессе (`TECHNOLOGY_EVALUATION.md`, раздел 8), а не через неявное разделение памяти между потоками внутри процесса.

## 22. Влияние на нефункциональные характеристики

- **безопасность:** официальная политика security-релизов Python (раздел 30) обеспечивает предсказуемое закрытие уязвимостей рантайма; secrets и конфигурация остаются вне кода независимо от языка (`ENGINEERING_PRINCIPLES.md`, пункты 40–41).
- **надёжность:** `asyncio` подходит для I/O-bound профиля платформы; надёжность фоновых операций обеспечивается отдельным worker-процессом (`TECHNOLOGY_EVALUATION.md`, раздел 8), а не выбором языка.
- **масштабируемость:** строгие модульные границы (раздел 21, мера 9) сохраняют возможность последующего выделения отдельных модулей в сервисы независимо от выбранного языка (`ENGINEERING_PRINCIPLES.md`, пункт 13).
- **производительность:** архитектурно ожидается достаточной для MVP-профиля нагрузки (один пользователь, I/O-bound backend, GIL-enabled сборка CPython 3.14, раздел 16); числовые NFR не утверждены (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-005–NFR-006) и будут измерены на реальном каркасе (раздел 25); CPU-bound нагрузка при GIL-enabled сборке требует выноса из основного процесса (раздел 21, мера 2).
- **стоимость:** open source, без лицензионных отчислений; несколько более высокое потребление ресурсов сервера относительно Go архитектурно учтено как некритичное при MVP-нагрузке одного пользователя, не измерено в рамках ADR (`TECHNOLOGY_EVALUATION.md`, раздел 16).
- **сопровождение:** архитектурная оценка — ожидаемо высокая скорость сопровождения одним разработчиком среди рассмотренных вариантов (раздел 15, критерий 2); не измерено в рамках ADR.
- **наблюдаемость:** Python не ограничивает возможность структурированного логирования и корреляционных идентификаторов (`FAILURE_MODEL.md`, раздел 11) — реализация определяется отдельно.
- **данные:** архитектурная оценка — ожидаемо более широкая экосистема среди рассмотренных вариантов для нормализации, проверки качества и анализа данных (раздел 15, критерий 5); не измерено в рамках ADR.
- **обратную совместимость:** политика версий (раздел 16) и правило раздела 24 обеспечивают управляемый переход между версиями и, при необходимости, между языками.

## 24. План отката

**До появления бизнес-кода:** откат означает замену настоящего ADR новым решением без миграции кода — стоимость отката минимальна.

**После появления кода:**

- требуется новый ADR, заменяющий ADR-0001 (`ADR_PROCESS.md`, раздел 18);
- обязательна оценка стоимости миграции перед принятием нового ADR;
- миграция выполняется модуль за модулем либо как полная замена — конкретный способ решается новым ADR;
- обязательно сохранение совместимости данных и внешних контрактов на всём протяжении миграции (`ENGINEERING_PRINCIPLES.md`, пункт 27);
- ADR-0001 получает статус «Заменён» с указанием ADR-преемника (`ADR_PROCESS.md`, раздел 19).

## 25. Критерии проверки решения

Решение проверяется, когда появится каркас проекта (без создания этих проверок в рамках настоящей задачи):

1. поддерживаемая версия CPython (GIL-enabled сборка) запускается на Windows;
2. та же линия версии запускается на Linux;
3. асинхронные HTTP-вызовы не блокируют event loop;
4. типизация (type hints) применяется к публичным интерфейсам модулей;
5. unit-тесты выполняются;
6. worker запускается отдельно от web-процесса (`TECHNOLOGY_EVALUATION.md`, раздел 8);
7. доменные модули не импортируют API framework (раздел 19, `ADR-0002`);
8. зависимости фиксируются воспроизводимо;
9. уязвимости зависимостей могут быть обнаружены автоматизированной проверкой.

## 26. Условия пересмотра

ADR-0001 пересматривается, если:

- Python не обеспечивает утверждённые NFR после фактических измерений (раздел 25);
- стоимость ресурсов сервера, обусловленная выбором языка, становится неприемлемой;
- критичный компонент требует существенно другой runtime-модели (например, выраженно CPU-bound задача без приемлемого пути изоляции);
- ключевая зависимость экосистемы прекращает поддержку Python;
- требования, близкие к real-time, или объём данных существенно меняются относительно текущего продуктового фундамента;
- поддержка Windows или Linux конкретной версией Python становится проблемной;
- существенные ограничения безопасности рантайма нельзя устранить в рамках официальной политики поддержки (раздел 30);
- появляется обоснованная необходимость разделить отдельные компоненты платформы по разным runtime.

Пересмотр не означает автоматическую замену всего backend. Точечный компонент может использовать другой runtime без замены ADR-0001, если основной backend платформы остаётся на CPython. Введение любого дополнительного production runtime — в том числе для отдельного компонента — требует отдельного нового ADR: этот новый ADR обязан обосновать границу компонента, эксплуатационную стоимость, deployment, наблюдаемость и способ обмена данными с остальной платформой (соблюдение модульных границ, раздел 21, мера 9, делает такое выделение технически возможным, но не заменяет требование отдельного ADR). Бесконтрольное смешивание языков без такого ADR запрещено. Если основной backend платформы перестаёт использовать CPython, соответствующий новый ADR заменяет ADR-0001 целиком (`ADR_PROCESS.md`, раздел 18).

## 27. Открытые вопросы

- точная поддерживаемая версия CPython в конфигурации проекта будет определена на шаге 3 плана внедрения (раздел 23), не в тексте настоящего ADR;
- конкретный набор инструментов статической типизации и linting не выбирается этим ADR — предмет отдельной задачи (раздел 23, шаг 5);
- влияние выбора backend runtime на итоговую стоимость эксплуатации будет уточнено после появления фактических измерений (`TECHNOLOGY_EVALUATION.md`, раздел 16).
