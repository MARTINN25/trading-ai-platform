## 11. Контекст

`ADR-0001` (утверждён) зафиксировал CPython 3.14 (GIL-enabled сборка) как backend runtime. `ADR-0002` (утверждён) зафиксировал FastAPI как внешний HTTP/ASGI API adapter и явно установил: backend является единственной границей бизнес-операций; application/domain не зависят от frontend; критичные фоновые задачи не выполняются ни frontend, ни FastAPI `BackgroundTasks`.

Логическая архитектура (`LOGICAL_ARCHITECTURE.md`, разделы 7, 9, 10, 21) требует:

- Web UI обращается только к Application API;
- frontend не обращается напрямую к БД, рыночным/новостным источникам или LLM;
- бизнес-анализ выполняется backend (`analysis`, `llm_gateway`);
- рыночные разделы данных изолированы (`PRODUCT_SCOPE.md`, раздел 11);
- весь интерфейс и пользовательские сообщения — на русском языке (`PRODUCT_SCOPE.md`, раздел 8);
- веб-приложение — первый и на этапе MVP единственный клиент (`PRODUCT_SCOPE.md`, раздел 19);
- desktop/mobile-клиенты рассматриваются как возможные будущие клиенты (`PRODUCT_SCOPE.md`, раздел 20).

`TECHNOLOGY_EVALUATION.md` (раздел 5, утверждён) зафиксировал предварительную, необязывающую рекомендацию — TypeScript + Next.js (App Router) — и явно указал, что выбор конкретного стека, его границ и правил взаимодействия с backend является предметом настоящего ADR.

Дата проверки технологических данных, использованных в настоящем ADR: 2026-08-05 (см. раздел 40 «Источники исследования»).

## 12. Проблема

Какой язык, UI-библиотеку и frontend-framework использовать для первого веб-клиента платформы, чтобы решение соответствовало утверждённой логической архитектуре и границам ADR-0001/ADR-0002, оставалось строго отделённым от FastAPI Application API как единственной границы бизнес-операций, поддерживалось одним разработчиком, подходило для интерфейса со сложной торговой панелью (несколько рыночных разделов, инсайты, дневник, история) и не создавало риска превращения frontend во второй backend.

Настоящий ADR не выбирает: UI component library, CSS framework, charting library, state-management library, data-fetching library, WebSocket library, authentication provider, frontend testing libraries, package manager, конкретный Node.js runtime, hosting provider, CDN, reverse proxy, desktop/mobile framework.

## 13. Ограничения

- решение принимается до появления frontend-кода — миграционная стоимость на этом этапе минимальна;
- frontend обязан оставаться отдельным клиентом FastAPI Application API (`ADR-0002`, раздел 17) — не второй границей бизнес-операций;
- backend остаётся единственным источником истины для бизнес-данных и бизнес-правил (`ADR-0002`, раздел 30);
- решение не должно предполагать выбор UI/CSS/state/data-fetching/testing библиотек, package manager или Node.js runtime — эти вопросы выходят за рамки задачи;
- один разработчик отвечает за весь frontend — простота и предсказуемость важнее числа неиспользуемых возможностей framework;
- интерфейс полностью на русском языке (`PRODUCT_SCOPE.md`, раздел 8);
- официальные источники на дату исследования (раздел 40) не подтверждают совместимость конкретной версии набора TypeScript/React/Next.js как окончательно зафиксированной — точные версии не фиксируются в этом ADR (раздел 16).

## 14. Движущие факторы решения

Критерии сравнения (раздел 15) выведены из `ENGINEERING_PRINCIPLES.md`, `LOGICAL_ARCHITECTURE.md`, `PRODUCT_SCOPE.md`/`USER_JOURNEYS.md` и контекста задачи (раздел 11): соответствие утверждённой архитектуре, пригодность для сложного trading dashboard, строгое разделение frontend/backend, TypeScript, маршрутизация, layouts, loading/error states, client-side и server-side rendering, static generation, Server Components, streaming, data loading, формы и mutations, будущий OpenAPI-generated client, обработка realtime-данных, browser-only APIs, локальное и серверное состояние, тестируемость, безопасность, риск дублирования backend, риск framework lock-in, производительность, размер клиентского JavaScript, сложность deployment, Windows-разработка, Linux deployment, документация, сопровождение одним разработчиком, скорость разработки MVP, будущие desktop/mobile клиенты, обратимость решения.

## 15. Рассмотренные варианты

Рассмотрены ровно три варианта:

- **Вариант A — TypeScript + React + Next.js App Router**
- **Вариант B — TypeScript + React Router Framework Mode**
- **Вариант C — TypeScript + React SPA на Vite с отдельным routing/data-fetching набором**

Pages Router упоминается только внутри анализа Next.js (раздел 20) как поддерживаемый legacy-роутер, а не как отдельный вариант или выбранное направление. Angular, Vue, Svelte, Solid, Create React App и desktop/mobile framework не рассматривались — они не входят в утверждённый экосистемный контекст (React как UI-библиотека) и не были частью предварительной рекомендации `TECHNOLOGY_EVALUATION.md`.

Качественные оценки ниже — архитектурная оценка на основании официальной документации (раздел 40), а не результат benchmark. Неподтверждённые абсолюты («самый быстрый», «лучший», «минимальный всегда», «максимальный», «гарантированно») не используются.

## 16. Выбранное решение

**TypeScript + React + Next.js App Router** — как язык, UI-библиотека и framework первого веб-клиента платформы.

- используется TypeScript в режиме `strict` (раздел 18);
- React — как UI-библиотека для композиции интерфейса (раздел 19);
- Next.js App Router — как frontend-framework (раздел 20–22);
- веб-приложение является отдельным frontend-клиентом FastAPI Application API (`ADR-0002`) — не вторым backend (раздел 17).

### Версия

- точная версия TypeScript/React/Next.js **не фиксируется навсегда** в настоящем ADR;
- совместимые стабильные версии фиксируются воспроизводимой конфигурацией проекта (раздел 33);
- обновления проходят тестирование перед принятием;
- security updates применяются приоритетно (раздел 25);
- major/minor обновления выполняются как управляемое изменение, а не автоматическое обновление;
- compatibility matrix React/Next.js/TypeScript/Node.js проверяется до обновления любого из компонентов;
- переход на `next@canary` или другие экспериментальные версии Next.js запрещён без отдельного решения (см. также раздел 20).

Официальные источники, проверенные на 2026-08-05 (раздел 40), фиксируют отдельные факты — минимальная поддерживаемая версия TypeScript для Next.js указана как v5.1.0, документация Next.js на дату исследования соответствует версии 16.3.0. Поэтому точная версия каждого компонента не фиксируется в этом ADR; выбор происходит на шаге 2 плана внедрения (раздел 33) после явной проверки совместимости. Точный Node.js runtime этим ADR не выбирается (раздел 3).

**Факт Next.js:** официальная документация Next.js указывает минимальную версию Node.js 20.9 (раздел 40). Это технический минимум framework, а не production-рекомендация проекта.

**Факт Node.js:** линия Node.js 20 находится в статусе EOL на дату исследования (раздел 40). Production должен использовать поддерживаемую Active LTS или Maintenance LTS линию. Точная линия Node.js не выбирается настоящим ADR — выбор Node.js runtime и политика обновлений должны быть оформлены отдельным решением до создания frontend-каркаса (раздел 33, шаг 2).

**Факт React Canary в App Router:** официальная документация Next.js сообщает, что App Router использует встроенные React Canary-релизы (включающие стабильные изменения React 19 и валидируемые framework-функции, раздел 40). Это управляемая интеграция внутри стабильного релиза Next.js — проект не устанавливает произвольные React canary-пакеты самостоятельно. Стабильная совместимая комбинация Next.js/React/React DOM фиксируется lock-файлом и конфигурацией проекта (раздел 33). Обновление Next.js может менять встроенную React Canary-линию и поэтому требует полного frontend-набора тестов перед принятием (см. также раздел 29 «Отрицательные последствия», раздел 30 «Риски»).

## 17. Границы frontend

Frontend отвечает за:

- представление;
- навигацию;
- пользовательский ввод;
- отображение loading/error/empty/partial states;
- локальное UI-состояние;
- визуализацию данных;
- перевод транспортных DTO в view models;
- отправку команд/запросов в FastAPI API;
- отображение источников, рисков, уверенности и ограничений (`FUNCTIONAL_REQUIREMENTS.md`, область 14);
- русскоязычный интерфейс;
- accessibility;
- безопасное хранение только допустимого клиентского состояния.

Frontend **не должен**:

- обращаться напрямую к БД;
- обращаться напрямую к market/news API;
- обращаться напрямую к xAI или другому LLM;
- содержать API-ключи поставщиков;
- выполнять бизнес-анализ;
- вычислять итоговую торговую рекомендацию как источник истины;
- сохранять инсайт в обход backend;
- подменять backend-валидацию;
- принимать окончательные authorization-решения;
- выполнять критичные фоновые задачи;
- становиться вторым бизнес-backend.

## 18. Правила TypeScript

- `strict` mode обязателен (раздел 40 — официально рекомендованный флаг, объединяющий полный набор строгих проверок TypeScript);
- будущие версии TypeScript могут добавлять новые проверки под флагом `strict` и порождать новые ошибки сборки при обновлении (раздел 40);
- обновление версии TypeScript проходит type-check и полный набор тестов перед принятием (раздел 33);
- отдельные strict-флаги, входящие в `strict`, нельзя отключать без документированного обоснования;
- запрещено использовать `any` как обычный способ обхода типов;
- `unknown` проверяется перед использованием;
- публичные интерфейсы типизированы;
- transport DTO отделены от view models;
- domain-модели backend не копируются как frontend domain source of truth;
- generated API types могут появиться позднее (раздел 22.2);
- runtime validation внешних данных не заменяется TypeScript — типы существуют только на этапе компиляции;
- типы не являются security boundary (раздел 25);
- подавление ошибок TypeScript требует объяснения;
- версии TypeScript фиксируются воспроизводимо (раздел 16).

## 19. Правила React

- React используется для UI-композиции;
- компоненты не содержат backend business logic;
- effects не используются как универсальный механизм orchestration;
- derived state не дублируется без необходимости;
- состояние поднимается только до минимально необходимого владельца;
- компоненты должны быть тестируемыми;
- render не выполняет побочные эффекты (раздел 40 — официально: мутации не должны быть побочным эффектом рендера ни в Server, ни в Client Components);
- данные и действия передаются явными контрактами;
- сложные trading views разбиваются на изолированные компоненты;
- ошибки визуализации не должны рушить всё приложение без локальной границы (раздел 24).

## 20. Правила Next.js App Router

- App Router выбран для нового приложения;
- Pages Router не используется для новых модулей — упоминается только как поддерживаемый legacy-роутер Next.js (раздел 40: App Router использует React canary-сборки, Pages Router использует версию React из `package.json` — это разные модели, не смешиваемые в одном модуле);
- file-system routing не определяет доменные границы платформы (`MODULE_BOUNDARIES.md`) — только структуру UI;
- route groups/layouts используются для UI-структуры, не как backend-модули;
- `loading.tsx`/`error.tsx`/`not-found` используются осознанно (раздел 40);
- framework conventions не заменяют архитектуру проекта;
- Next.js не является владельцем бизнес-данных (`ADR-0002`, раздел 30);
- custom server не вводится без отдельного решения;
- experimental/canary features Next.js не используются в production без отдельного решения; переход на `next@canary` или иные экспериментальные версии самого Next.js запрещён без отдельного решения — это отдельный вопрос от встроенных в стабильный релиз App Router React Canary-сборок (раздел 16, раздел 40), которыми проект не управляет напрямую;
- framework-specific возможности изолируются, где это возможно.

## 21. Server Components и Client Components

### 21.1 Общие правила

- по умолчанию layouts и pages — Server Components (раздел 40) — это поведение framework, а не требование проекта использовать server-side data fetching на каждом экране;
- Server Components используются только там, где дают доказанную пользу, а не по умолчанию для каждого экрана;
- для интерактивной торговой панели значительная часть динамических областей (котировки в реальном времени, интерактивные элементы, локальные фильтры) архитектурно ожидаемо остаётся Client Components;
- фактическая граница server/client определяется по результатам первого vertical slice и измерения bundle/rendering (раздел 26, 33), а не по идеологии «всё server» или «всё client»;
- Client Components используются для интерактивности, browser APIs, realtime UI и локального состояния (раздел 40: `useState`, `onClick`, `useEffect`, `localStorage`/`window` и подобное — только в Client Components);
- директива `use client` не ставится на крупные поддеревья без необходимости — официально рекомендуется отмечать конкретные интерактивные компоненты, а не целые layouts (раздел 40);
- props через server/client boundary должны быть сериализуемыми (раздел 40);
- секреты не передаются Client Components;
- Server Components не обращаются напрямую к БД, market/news API или LLM (раздел 17) — это правило проекта, более строгое, чем базовая возможность framework (Server Components технически способны обращаться к БД напрямую, раздел 40, но в этом проекте им это запрещено);
- Server Components обращаются только к утверждённому FastAPI Application API, если серверный fetch действительно нужен (раздел 22.2);
- server-only код не импортируется в client bundle — обеспечивается пакетом `server-only` и внутренними механизмами Next.js (раздел 40);
- размер клиентской границы измеряется (раздел 26);
- React Server Components не считаются обязательными для каждого экрана;
- использование Server Components не должно превращать Next.js в второй backend (раздел 17, 22).

### 21.2 Realtime и клиентские границы

Realtime-обновления (котировки, статус анализа) обрабатываются Client Components — Server Components по своей модели рендерятся один раз на сервере/при запросе и не подходят для потокового клиентского realtime UI без явного клиентского компонента (раздел 40).

## 22. Взаимодействие с backend

### 22.1 Server Actions и Route Handlers

- Server Actions **не являются** владельцами business use cases;
- Route Handlers **не дублируют** FastAPI endpoints;
- business validation и authorization выполняются backend (`ADR-0002`, раздел 17–18);
- разрешены только тонкие frontend-specific операции, если они обоснованы;
- проксирование всех FastAPI endpoints через Next.js запрещено без измеримой причины;
- BFF-слой не создаётся автоматически — введение полноценного BFF требует отдельного ADR;
- server action/route handler не обращается к БД;
- не обращается к LLM;
- не обращается напрямую к внешним рыночным источникам;
- не хранит провайдерские API-ключи для бизнес-интеграций;
- mutation должна сохранять idempotency и correlation ID backend;
- CSRF, cookies и origin-checking учитываются для server-side mutations. Официально: Server Actions в Next.js вызываются только методом `POST`, что снижает часть CSRF-рисков в современных браузерах при `SameSite`-cookies по умолчанию; дополнительно Next.js сравнивает заголовки `Origin`/`Host` (или `X-Forwarded-Host`) и отклоняет запрос при несовпадении; для reverse proxy/multi-domain сценариев предусмотрена конфигурация `serverActions.allowedOrigins` (раздел 40);
- официально: любой экспортированный Server Action технически достижим прямым `POST`-запросом, даже если нигде не импортирован в UI; Next.js применяет secure action ID и dead code elimination неиспользуемых actions, но официальная документация прямо указывает — аутентификация и авторизация должны проверяться внутри каждого action, а не только на уровне страницы (раздел 40) — это правило проекта прямо усиливает данный официальный совет: authorization не считается выполненной только потому, что UI скрыл элемент или проверка была на уровне страницы.

### 22.2 Взаимодействие с FastAPI Application API

- FastAPI является источником публичного Application API (`ADR-0002`);
- frontend использует документированный HTTP-контракт;
- OpenAPI может стать основой generated client позднее (`ADR-0002`, раздел 18.4);
- ручные типы не должны незаметно расходиться с API;
- все запросы имеют correlation ID, где это предусмотрено;
- transport errors преобразуются в безопасные пользовательские состояния (раздел 24);
- retry не выполняется автоматически для небезопасных mutations;
- timeout и cancellation контролируются;
- устаревшие ответы не должны перезаписывать новые;
- authorization не считается выполненной только потому, что UI скрыл элемент;
- прямой импорт backend Python-кода невозможен (разные runtime — `ADR-0001` CPython, frontend — Node.js/browser);
- API base URL задаётся конфигурацией.

## 23. Состояние приложения

### Локальное UI-состояние

- выбранная вкладка;
- раскрытые панели;
- фильтры, ещё не отправленные backend;
- состояние модального окна;
- краткий/полный режим (`FUNCTIONAL_REQUIREMENTS.md`, FR-021/FR-022).

### URL-состояние

- рыночный раздел;
- выбранный инструмент;
- timeframe/horizon;
- фильтры истории, если они должны быть bookmarkable (`USER_JOURNEYS.md`, UJ-030).

### Серверное состояние

- инсайты;
- рыночные данные;
- календарь;
- журнал;
- заметки;
- оценки;
- результаты проверки.

Правила:

- серверное состояние не копируется бесконтрольно в глобальный store;
- конкретная state/data-fetching library выбирается позднее (раздел 33, шаг 9);
- cache invalidation должна иметь явную политику;
- optimistic updates допустимы только при понятном откате;
- realtime updates не должны нарушать порядок данных;
- финансовые данные имеют timestamp и freshness (`ENGINEERING_PRINCIPLES.md`, пункт 23; `FAILURE_MODEL.md`, раздел 3).

## 24. Ошибки и деградация

- loading, empty, stale, partial, unavailable и error — разные состояния (`FAILURE_MODEL.md`, раздел 3);
- partial success отображается явно;
- stale data помечаются;
- frontend не придумывает данные при отсутствии ответа;
- ошибка одного widget не обязана рушить весь экран;
- глобальная ошибка используется только для действительно глобального отказа;
- пользовательские сообщения полностью на русском языке (`PRODUCT_SCOPE.md`, раздел 8);
- технические детали и stack traces не показываются (`ENGINEERING_PRINCIPLES.md`, пункт 39);
- retry доступен только там, где безопасен;
- несохранённый инсайт явно помечается (`FAILURE_MODEL.md`, раздел 13);
- network offline отображается отдельно;
- восстановление после reconnection не должно дублировать mutations.

## 25. Безопасность

- переменные с префиксом `NEXT_PUBLIC_` могут попасть в клиентский bundle и считаются публичными (раздел 40); серверные секреты **не должны** иметь этот префикс;
- отсутствие префикса `NEXT_PUBLIC_` само по себе **не гарантирует** безопасность: серверный секрет нельзя передавать через props, сериализуемые данные, Route Handlers или Server Actions без необходимости (раздел 21.1, 22.1);
- Client Components не имеют доступа к server-only secrets (раздел 40);
- environment validation и конкретный механизм конфигурации выбираются позднее (раздел 33);
- переменные, доступные клиенту, считаются публичными;
- HTML не вставляется без sanitization;
- внешние ссылки и контент источников считаются недоверенными;
- CSP должна быть спроектирована при deployment;
- XSS и supply-chain риски учитываются;
- cookies/token strategy выбирается отдельно;
- localStorage не используется для долгоживущих чувствительных секретов;
- authorization всегда проверяется backend, а для Server Actions — дополнительно внутри самого action, а не только на уровне страницы (раздел 22.1; официально рекомендуется паттерн Data Access Layer — выделенный `server-only` модуль, инкапсулирующий авторизацию и доступ к данным, раздел 40);
- source maps production управляются безопасно;
- dependency updates и security advisories отслеживаются;
- React/Next.js security patches применяются приоритетно;
- React Server Components увеличивают серверную поверхность и требуют своевременных обновлений. Официальные React и Next.js advisories документируют несколько уязвимостей React Server Components и связанных механизмов, включая критическую уязвимость удалённого выполнения кода, а также последующие DoS и раскрытие исходного кода (раздел 40) — это не гипотетический, а документированный класс риска. Количество advisories не фиксируется этим ADR, поскольку оно меняется со временем; ADR использует конкретные advisories как подтверждение существования риска, а не как постоянную характеристику framework; проверка security advisories выполняется при каждом обновлении, используемая версия должна содержать опубликованные исправления;
- Server Actions не считаются автоматически безопасными — встроенные меры Next.js (secure action ID, dead code elimination, Origin/Host проверка) снижают, но не устраняют необходимость собственной проверки авторизации внутри каждого action (раздел 22.1, 40).

## 26. Производительность

- производительность измеряется, а не предполагается;
- клиентский JavaScript контролируется;
- крупные charting-компоненты загружаются только при необходимости;
- виртуализация используется для больших списков после измерений;
- realtime updates агрегируются, чтобы не вызывать лишние render;
- Server Components применяются только после оценки пользы (раздел 21.1);
- dynamic import используется осознанно;
- изображения и шрифты не должны блокировать торговый интерфейс;
- Web Vitals могут измеряться позднее;
- бюджет bundle определяется после первого vertical slice (раздел 33, шаг 17);
- преждевременная оптимизация запрещена (`ENGINEERING_PRINCIPLES.md`, пункт 67, по аналогии).

## 27. Локализация

- интерфейс полностью русский (`PRODUCT_SCOPE.md`, раздел 8);
- пользовательские ошибки полностью русские;
- системные коды ошибок могут оставаться машинными;
- текст не разбрасывается хаотично по компонентам;
- формат дат, времени, чисел, валют и процентов централизован;
- UTC и локальное время различаются явно (`ENGINEERING_PRINCIPLES.md`, пункт 24);
- исходный английский контент переводится backend/analysis pipeline или отдельным управляемым слоем (`FUNCTIONAL_REQUIREMENTS.md`, FR-060);
- frontend не должен самостоятельно менять смысл аналитического текста;
- будущая многоязычность не утверждается, но структура не должна делать её невозможной.

## 28. Положительные последствия

- TypeScript и строгие контракты;
- зрелая React-модель UI, официально рекомендуемая самим React для новых приложений (раздел 40);
- App Router с layouts/loading/error conventions «из коробки»;
- возможность смешивать server/client rendering;
- потенциальное уменьшение client JS при дисциплинированном использовании Server Components;
- архитектурно подходящий путь для сложного dashboard (раздел 15, критерий 2);
- единый frontend-framework;
- возможность будущего SEO/public pages, хотя это не цель MVP;
- активная официальная документация;
- Web UI остаётся отдельным клиентом backend при соблюдении границ раздела 17.

## 29. Отрицательные последствия

- высокая сложность server/client mental model;
- риск превращения Next.js во второй backend при нарушении границ раздела 17, 22;
- framework lock-in (раздел 15, критерий 23);
- сложнее deployment, чем статический Vite SPA — требует Node.js runtime (раздел 40);
- риск hydration/server-client несоответствий;
- cache и rendering semantics могут быть сложными;
- обновления React/Next.js могут приносить breaking/security changes — подтверждено официальными advisories (раздел 25, 40);
- Server Components и Server Actions увеличивают поверхность безопасности (раздел 25);
- требуется Node.js runtime для части сценариев deployment;
- bundle может вырасти при неправильных client boundaries (раздел 21.1);
- разработчик должен понимать browser/server execution contexts;
- часть возможностей Next.js может остаться неиспользованной;
- App Router использует встроенные React Canary-сборки (раздел 16, 40) — это управляемая, но внешняя зависимость: обновление Next.js может изменить встроенную React Canary-линию и потребовать полного прогона frontend-тестов перед принятием обновления.

## 30. Риски

1. Frontend становится вторым backend.
2. Route Handlers дублируют FastAPI.
3. Server Actions содержат бизнес-логику.
4. Секрет попадает в client bundle.
5. Слишком широкие `use client` boundaries.
6. Hydration mismatch.
7. Stale cache.
8. Unsafe automatic retry.
9. Race conditions запросов.
10. Нарушение порядка realtime events.
11. Глобальный store превращается в свалку.
12. Ручные API-типы расходятся с OpenAPI.
13. XSS через новости/заметки/социальные данные.
14. Уязвимости RSC/Next.js (подтверждены конкретными официальными advisories, раздел 40; количество не фиксируется этим ADR).
15. Использование EOL-линии Node.js (например, минимальной версии, указанной Next.js как технический минимум, а не production-рекомендацию) вместо поддерживаемой Active/Maintenance LTS линии.
16. Обновление Next.js меняет встроенную React Canary-линию без прогона полного набора frontend-тестов.
17. Большой JavaScript bundle.
18. Chart rendering блокирует UI.
19. Потеря состояния при navigation.
20. Timezone/formatting ошибки.
21. Русский текст размазан по компонентам.
22. Framework-specific код невозможно заменить.
23. Next.js deployment требует лишней инфраструктуры.
24. Server Components напрямую вызывают внешние бизнес-API.
25. Frontend скрывает, но не защищает запрещённое действие.

## 31. Меры снижения рисков

1. Frontend становится вторым backend → границы раздела 17 и правило «backend — единственная граница бизнес-операций» (`ADR-0002`); проверяется критерием раздела 35.
2. Route Handlers дублируют FastAPI → запрет проксирования всех endpoints без измеримой причины (раздел 22.1); BFF требует отдельного ADR.
3. Server Actions содержат бизнес-логику → business validation/authorization выполняются backend, action остаётся тонким (раздел 22.1).
4. Секрет в client bundle → серверные секреты не имеют префикса `NEXT_PUBLIC_` и не передаются через props/Route Handlers/Server Actions без необходимости (раздел 25, 40); server-only модули изолируются пакетом `server-only`.
5. Широкие `use client` boundaries → директива ставится на конкретные интерактивные компоненты, не на layouts целиком (раздел 21.1).
6. Hydration mismatch → props через server/client границу сериализуемы и детерминированы (раздел 21.1).
7. Stale cache → явная политика cache invalidation (раздел 23).
8. Unsafe automatic retry → retry не выполняется автоматически для небезопасных mutations (раздел 22.2).
9. Race conditions запросов → устаревшие ответы не перезаписывают новые (раздел 22.2).
10. Нарушение порядка realtime events → realtime updates не должны нарушать порядок данных (раздел 23).
11. Глобальный store — свалка → серверное состояние не копируется бесконтрольно в глобальный store (раздел 23).
12. Ручные типы расходятся с OpenAPI → миграция на generated client рассматривается по мере готовности backend-контракта (раздел 22.2, `ADR-0002` раздел 18.4).
13. XSS через новости/заметки → HTML не вставляется без sanitization, внешний контент недоверен (раздел 25).
14. Уязвимости RSC/Next.js → security patches применяются приоритетно, конкретные advisories проверяются при каждом обновлении, используемая версия должна содержать опубликованные исправления (раздел 25).
15. Использование EOL-линии Node.js → выбор Node.js runtime и политика обновлений оформляются отдельным решением до создания frontend-каркаса; production использует поддерживаемую Active или Maintenance LTS линию, а не только технический минимум Next.js (раздел 16).
16. Смена встроенной React Canary-линии при обновлении Next.js → стабильная комбинация фиксируется lock-файлом; обновление Next.js проходит полный набор frontend-тестов перед принятием (раздел 16, 33).
17. Большой bundle → бюджет bundle после vertical slice, измерение, а не предположение (раздел 26).
18. Chart rendering блокирует UI → крупные charting-компоненты загружаются по необходимости, виртуализация после измерений (раздел 26).
19. Потеря состояния при navigation → URL-состояние и layouts, сохраняющие состояние при навигации, используются осознанно (раздел 20, 23).
20. Timezone/formatting ошибки → формат дат/времени централизован, UTC и локальное время различаются явно (раздел 27).
21. Размазанный русский текст → текст не разбрасывается хаотично по компонентам (раздел 27).
22. Framework-specific код невозможно заменить → framework-specific возможности изолируются, где возможно (раздел 20); view models/API client отделяются от framework-specific компонентов (раздел 34).
23. Next.js deployment требует инфраструктуры → учитывается в разделе 26 «сложность deployment»; конкретная инфраструктура — предмет отдельного решения, не этого ADR.
24. Server Components вызывают внешние бизнес-API напрямую → явный запрет (раздел 17, 21.1) — Server Components обращаются только к FastAPI.
25. Frontend скрывает, но не защищает действие → authorization не считается выполненной только потому, что UI скрыл элемент (раздел 22.2, 25).

## 32. Влияние на нефункциональные характеристики

- **безопасность:** секреты не попадают в client bundle; Server Actions требуют собственной проверки авторизации (раздел 25); официальные advisories RSC/Next.js отслеживаются приоритетно.
- **надёжность:** frontend не выполняет критичные фоновые задачи (раздел 17); ошибки одного widget не рушат весь экран (раздел 24).
- **масштабируемость:** строгая граница frontend/FastAPI (раздел 22.2) сохраняет возможность последующей замены frontend без изменения backend (`ENGINEERING_PRINCIPLES.md`, пункт 13).
- **производительность:** архитектурно ожидается достаточной для MVP-профиля; числовые NFR не утверждены (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-005) и не измерены в рамках настоящего ADR; измерение — часть плана внедрения (раздел 26, 33).
- **стоимость:** open source компоненты, без лицензионных отчислений; deployment Next.js требует Node.js runtime, что может увеличивать инфраструктурную стоимость относительно статического SPA (раздел 15, критерий 26) — не измерено в рамках ADR.
- **сопровождение:** архитектурная оценка — единая framework-документация снижает число независимых решений для одного разработчика (раздел 15, критерий 30); не измерено в рамках ADR.
- **наблюдаемость:** correlation ID запросов к FastAPI закладывается на уровне frontend (раздел 22.2), в соответствии с `FAILURE_MODEL.md`, раздел 11.
- **данные:** frontend не владеет бизнес-данными (раздел 17); серверное состояние явно отделено от локального/URL-состояния (раздел 23).
- **обратную совместимость:** изменение публичного HTTP-контракта FastAPI отслеживается через `ADR-0002`, раздел 18.4; frontend не должен незаметно расходиться с API (раздел 22.2).

## 35. Критерии проверки решения

Решение проверяется, когда появится каркас frontend (без создания этих проверок в рамках настоящей задачи):

1. TypeScript `strict` включён;
2. приложение использует App Router;
3. Pages Router отсутствует;
4. frontend обращается только к FastAPI API;
5. нет прямых вызовов market/news/LLM API;
6. секретов нет в browser bundle;
7. FastAPI/OpenAPI контракт отделён от view models;
8. Server Components не обращаются к БД;
9. Route Handlers не дублируют backend;
10. Server Actions не содержат бизнес-правил и проверяют авторизацию внутри себя;
11. Client Components ограничены интерактивными областями;
12. loading/error/empty/stale states различаются;
13. русский интерфейс соблюдён;
14. даты и timezone форматируются централизованно;
15. frontend не принимает authorization-решения;
16. критичные mutations защищены backend;
17. RSC/Next.js security updates отслеживаются;
18. production build проходит;
19. bundle измерим;
20. один vertical slice работает через FastAPI;
21. используемая линия Node.js runtime — поддерживаемая Active или Maintenance LTS, а не EOL-линия;
22. версии React/React DOM, зафиксированные lock-файлом, соответствуют встроенной React Canary-линии используемой версии Next.js.

## 36. Условия пересмотра

ADR-0003 пересматривается, если:

- Next.js перестаёт поддерживать выбранную линию Node.js или React;
- React/Next.js теряет активное официальное сопровождение;
- security model Server Components неприемлем после оценки реальных advisories (раздел 25, 40);
- framework вынуждает системно дублировать backend вопреки правилам раздела 17, 22;
- deployment-стоимость становится неприемлемой;
- сложность App Router объективно превышает пользу для проекта;
- static SPA объективно лучше после измерения (раздел 26);
- измеренная (не архитектурно предполагаемая) производительность не достигает утверждённых NFR;
- будущий desktop/mobile клиент требует общего UI-слоя иной формы, чем предполагает App Router;
- framework lock-in мешает развитию платформы;
- критичные требования realtime невозможно реализовать в рамках модели Server/Client Components;
- обновления React/Next.js регулярно ломают проект.

Дополнительный frontend-клиент (например, для desktop/mobile) может быть создан отдельным ADR без замены ADR-0003, если Next.js остаётся основным Web UI.

## 37. Открытые вопросы

- точные совместимые версии TypeScript/React/Next.js/Node.js будут определены на шаге 2 плана внедрения (раздел 33) — официальные источники на дату исследования не содержат единого заявления о зафиксированной навсегда совместимой комбинации (раздел 16, 40);
- выбор package manager не входит в этот ADR;
- выбор UI component library, CSS framework, charting library, state-management и data-fetching библиотек не входит в этот ADR (раздел 12) — предмет отдельных задач/ADR по мере готовности vertical slice;
- выбор конкретного Node.js runtime для production не входит в этот ADR;
- необходимость полноценного BFF-слоя остаётся открытой — вводится только отдельным ADR при обоснованной необходимости (раздел 22.1);
- итоговая структура realtime-транспорта (WebSocket или иной механизм) не выбирается этим ADR.
