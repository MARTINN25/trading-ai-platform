## 11. Контекст

`ADR-0001` (утверждён) зафиксировал CPython 3.14 (стандартная GIL-enabled сборка) как язык/runtime backend. Логическая архитектура (`LOGICAL_ARCHITECTURE.md`, раздел 7) выделяет Application API как внешний входной адаптер веб-клиента — транспорт и граничную проверку доступа, — явно отделённый от Application Layer / Use Cases и доменных модулей (`MODULE_BOUNDARIES.md`, правило «Application API — внешний адаптер, зависящий только от application»). `TECHNOLOGY_EVALUATION.md` (раздел 4.2, утверждён) зафиксировал предварительную, необязывающую рекомендацию — FastAPI — и явно указал, что выбор конкретного adapter framework и его границ является предметом настоящего ADR.

Архитектурные условия, в рамках которых действует решение:

- backend построен как модульный монолит (`ADR-0001`, раздел 11);
- Application Layer / Use Cases координирует доменные модули и не зависит от внешнего адаптера (`MODULE_BOUNDARIES.md`, модуль `application`);
- доменные модули не зависят от web-фреймворка (`ADR-0001`, раздел 19);
- критичные фоновые задачи выполняются отдельным worker-процессом, а не внутри web-процесса (`TECHNOLOGY_EVALUATION.md`, раздел 8; `ADR-0001`, план внедрения);
- Web UI обращается только к Application API (`LOGICAL_ARCHITECTURE.md`, раздел 21);
- Application API преобразует транспортный запрос в команду/query для Application Layer и не оркестрирует доменные области самостоятельно (`LOGICAL_ARCHITECTURE.md`, раздел 7).

Дата проверки технологических данных, использованных в настоящем ADR: 2026-08-05 (см. раздел 32 «Источники исследования»).

## 12. Проблема

Какой HTTP/ASGI adapter framework использовать в качестве внешнего входного адаптера (Application API), чтобы решение соответствовало утверждённой логической архитектуре и границам модулей, оставалось тонким транспортным слоем без проникновения framework-специфичных типов в Application Layer / Use Cases и доменные модули, поддерживалось одним разработчиком и обеспечивало типизированную валидацию, OpenAPI, dependency injection, обработку ошибок и жизненный цикл технических ресурсов adapter-слоя.

Настоящий ADR не выбирает: основное хранилище, ORM, очередь фоновых задач, frontend, LLM SDK, deployment, ASGI server, библиотеки observability, authentication provider, CORS-политику production, reverse proxy.

## 13. Ограничения

- решение принимается до появления endpoint-кода — миграционная стоимость на этом этапе минимальна;
- adapter обязан оставаться тонким транспортным слоем в соответствии с ролью Application API (`LOGICAL_ARCHITECTURE.md`, раздел 7) — не оркестрировать доменные области самостоятельно;
- доменные модули и Application Layer не должны зависеть от выбранного framework (`ADR-0001`, раздел 19; правило раздела 17 настоящего ADR);
- решение не должно предполагать выбор ASGI server, ORM, хранилища, очереди, authentication provider, CORS production-политики или reverse proxy — эти вопросы выходят за рамки задачи;
- один разработчик отвечает за весь adapter-слой — простота и предсказуемость важнее числа встроенных возможностей, не используемых MVP;
- решение действует в рамках CPython 3.14, GIL-enabled сборки (`ADR-0001`) — adapter не должен требовать альтернативной реализации Python или free-threaded сборки;
- официальные источники на дату исследования (раздел 32) не содержат явного подтверждения точной версии рассматриваемых framework, совместимой с CPython 3.14 — точная версия не фиксируется в этом ADR (раздел 16).

## 14. Движущие факторы решения

Критерии сравнения (раздел 15) выведены из `ENGINEERING_PRINCIPLES.md`, `LOGICAL_ARCHITECTURE.md`/`MODULE_BOUNDARIES.md` и контекста задачи (раздел 11): соответствие утверждённой архитектуре, пригодность как тонкого HTTP adapter, поддержка ASGI и async I/O, типизированная валидация, OpenAPI, dependency injection, middleware, lifecycle/lifespan, обработка исключений, WebSocket, тестируемость и подмена зависимостей в тестах, безопасность по умолчанию, риск проникновения framework в application/domain, объём boilerplate, скорость разработки MVP, зрелость, сопровождение одним разработчиком, документация, расширяемость, vendor/framework lock-in, обратимость, совместимость с модульным монолитом, пригодность для одного API и будущих клиентов.

## 15. Рассмотренные варианты

Рассмотрены ровно четыре варианта:

- **Вариант A — FastAPI**
- **Вариант B — Starlette напрямую**
- **Вариант C — Litestar**
- **Вариант D — Django как ASGI/API framework** (без Django REST Framework — DRF не рассматривается отдельным вариантом)

Качественные оценки ниже — архитектурная оценка на основании официальной документации (раздел 32), а не результат benchmark; превосходные степени без измерения («самый быстрый», «лучший») не используются.

## 16. Выбранное решение

**FastAPI — как внешний HTTP/ASGI API adapter backend платформы.**

FastAPI применяется только в interface/transport-слое (Application API, `LOGICAL_ARCHITECTURE.md`, раздел 7).

FastAPI **не является**:

- бизнес-ядром платформы;
- Application Layer / Use Cases;
- системой фоновых задач;
- источником данных;
- persistence layer;
- контейнером всей архитектуры.

### Версия FastAPI

- точная версия FastAPI **не фиксируется навсегда** в настоящем ADR;
- используется совместимая стабильная версия, закреплённая воспроизводимой конфигурацией проекта (раздел 25);
- обновление версии проходит тестирование перед принятием;
- major/minor обновления с несовместимыми изменениями являются управляемым изменением, а не автоматическим обновлением;
- совместимость с поддерживаемой линией CPython (`ADR-0001`) проверяется до обновления версии FastAPI/Starlette/Pydantic.

Официальные источники, проверенные на 2026-08-05 (раздел 32), не содержат явного, прямого заявления о совместимости конкретной версии FastAPI/Starlette/Pydantic с CPython 3.14 — точная версия поэтому не фиксируется в этом ADR; совместимость проверяется отдельно на шаге плана внедрения (раздел 25, шаг 2) до фактической установки зависимости.

## 17. Границы решения

FastAPI adapter отвечает только за:

- приём HTTP-запроса;
- разбор path/query/header/cookie/body;
- транспортную валидацию;
- authentication context на границе;
- вызов application command/query;
- преобразование application result в HTTP response;
- преобразование ошибок в безопасную транспортную модель;
- correlation ID;
- публикацию OpenAPI;
- lifecycle технических ресурсов adapter-слоя.

FastAPI adapter **не должен**:

- обращаться к repository напрямую;
- обращаться к БД напрямую;
- обращаться к внешним market/news API напрямую;
- обращаться к LLM напрямую;
- выполнять бизнес-анализ;
- сохранять инсайты;
- управлять транзакциями доменных модулей;
- запускать критичные фоновые задачи in-process;
- содержать бизнес-правила;
- импортироваться application/domain-модулями.

## 18. Архитектурные правила adapter-слоя

### 18.1 Dependency Injection

- FastAPI DI используется только для wiring adapter-зависимостей;
- разрешены application use-case interfaces, authentication context, configuration views и технические adapter dependencies;
- FastAPI `Depends` не проникает в application/domain;
- application services не должны принимать FastAPI `Request`, `Response`, `Depends` или framework-specific types;
- доменные интерфейсы создаются независимо от FastAPI;
- подмена зависимостей должна быть возможна без изменения бизнес-кода (см. `app.dependency_overrides`, раздел 32);
- framework DI не является глобальным service locator.

### 18.2 DTO и валидация

- transport DTO отделены от domain entities и application commands;
- внешний JSON не передаётся напрямую в domain;
- transport validation не заменяет бизнес-валидацию;
- ошибки transport и domain имеют разные категории;
- domain entities не обязаны быть моделями framework validation library (Pydantic);
- schema generation не должна раскрывать внутренние модели или секретные поля;
- API versioning и конкретные DTO будут определены позже (не этим ADR).

### 18.3 Async

- async endpoints используются для I/O-bound use cases;
- блокирующие вызовы не выполняются в event loop (`ADR-0001`, раздел 19);
- sync endpoint не является автоматической ошибкой, если операция действительно синхронна и изолирована;
- **факт официальной документации (раздел 32):** `BackgroundTasks` выполняются в процессе приложения после формирования ответа; официальная документация рекомендует более крупные внешние инструменты (например, Celery) для тяжёлых вычислений, не требующих выполнения в том же процессе;
- **архитектурное решение проекта:** in-process выполнение не предоставляет платформе необходимой долговечности задания при падении или перезапуске web-процесса — поэтому `BackgroundTasks` запрещены для критичных, долгих и требующих гарантированного выполнения заданий; такие задания выполняются отдельным worker-процессом (`TECHNOLOGY_EVALUATION.md`, раздел 8);
- `BackgroundTasks` допустимы только для коротких, некритичных best-effort действий;
- application layer не зависит от механики async конкретного web-framework;
- cancellation и timeout должны передаваться контролируемо;
- disconnect клиента не должен автоматически оставлять бизнес-операцию в неопределённом состоянии.

### 18.4 OpenAPI

- OpenAPI является транспортным контрактом adapter-слоя;
- схема генерируется из внешних DTO;
- OpenAPI не является доменной моделью;
- документация API не должна раскрывать внутренние ошибки, секреты и служебные поля;
- production-доступ к интерактивной документации (Swagger UI/ReDoc, раздел 32) определяется конфигурацией безопасности;
- изменение публичного контракта требует contract-тестов и управляемого versioning;
- OpenAPI snapshot может использоваться в quality gates позднее (`ADR-0010` по дорожной карте `TECHNOLOGY_EVALUATION.md`).

### 18.5 Ошибки и безопасность

- единый безопасный формат ошибок;
- correlation ID в ответе и логах;
- внутренний stack trace не возвращается пользователю (`ENGINEERING_PRINCIPLES.md`, пункт 39);
- validation error не раскрывает секретные входные значения;
- authentication и authorization различаются;
- rate limiting реализуется на подходящей границе позднее;
- trusted hosts, CORS, proxy headers и TLS termination определяются deployment-решениями (вне этого ADR);
- секреты не находятся в dependency defaults;
- framework exception handler не заменяет audit trail (`MODULE_BOUNDARIES.md`, модуль `audit`);
- обязательная audit-запись критичного действия не должна теряться (`FAILURE_MODEL.md`, раздел 17.1).

### 18.6 Lifecycle

- startup/shutdown реализуются через поддерживаемый lifespan-механизм (раздел 32);
- lifecycle adapter не выполняет необратимые бизнес-операции;
- подключение технических ресурсов должно корректно закрываться;
- schema migration не запускается скрыто при старте API;
- планировщик критичных задач не запускается внутри каждого web-процесса (`TECHNOLOGY_EVALUATION.md`, раздел 8; `ADR-0001`);
- запуск нескольких web workers не должен дублировать scheduled jobs;
- readiness отличается от liveness;
- конкретная реализация health endpoints определяется позднее.

## 19. Обоснование

FastAPI выбран по совокупности критериев раздела 15, а не по единственному показателю:

- **соответствие архитектуре и роль тонкого адаптера** (критерии 1–2): FastAPI архитектурно оценивается как естественно укладывающийся в роль Application API — декларативные роуты и встроенная валидация/DI/OpenAPI без обязательного использования ORM, шаблонов или админ-панели, в отличие от Django (критерий 1, 15, 22), которая структурно провоцирует более широкую связанность и рискует implicit-выбором ORM, явно исключённого из области этого ADR (раздел 12);
- **ASGI, async I/O, типизированная валидация, OpenAPI, DI** (критерии 3–7): FastAPI официально предоставляет все перечисленное «из коробки» (раздел 32), тогда как Starlette (основа FastAPI) не предоставляет встроенную валидацию, DI и OpenAPI — их пришлось бы собирать вручную или подключать сторонние библиотеки, увеличивая объём кода и решений, которые пришлось бы принимать за рамками одного ADR;
- **риск проникновения framework в domain** (критерий 15): риск существует у всех рассмотренных ASGI-фреймворков (FastAPI, Starlette, Litestar) в сопоставимой степени и управляется дисциплиной границ (разделы 17–18), а не выбором конкретного framework; у Django риск структурно выше из-за укоренённости ORM/admin/settings в самой модели framework;
- **зрелость, документация, сопровождение одним разработчиком** (критерии 18–20): FastAPI архитектурно оценивается как обладающий наиболее полной, ориентированной на практические сценарии официальной документацией среди рассмотренных вариантов на дату исследования (раздел 32) — не измерено в рамках ADR, но снижает риск для единственного разработчика платформы;
- **Litestar как жизнеспособная альтернатива**: Litestar официально предоставляет сопоставимый набор возможностей (DI, OpenAPI, валидация, middleware) и архитектурно мог бы быть выбран вместо FastAPI без изменения границ раздела 17–18; выбор FastAPI сделан по совокупности зрелости и документации (критерии 18, 20), а не из-за отсутствия жизнеспособности Litestar — это отражено как открытый вопрос обратимости (раздел 26, 28);
- **Django как full-stack framework** (критерии 2, 15, 22, 24): Django официально имеет частичную/гибридную поддержку async (ORM и транзакции не полностью асинхронны, раздел 32) и структурно ориентирован на full-stack сценарии, что делает удержание роли «только тонкий адаптер» архитектурно более затратным, чем у остальных вариантов; поэтому Django не выбран.

Ни один вариант не выбран по признаку «популярности» или без учёта критериев раздела 15.

## 20. Положительные последствия

- минимальный объём transport boilerplate;
- типизированная транспортная валидация;
- автоматическая OpenAPI;
- встроенная DI для adapter wiring;
- ASGI/async;
- удобное тестирование API boundary (`TestClient`, `dependency_overrides`, раздел 32);
- архитектурно ожидаемо быстрый MVP (не измерено в рамках ADR);
- совместимость с выбранным CPython (`ADR-0001`), подлежащая проверке при внедрении (раздел 25);
- возможность держать framework вне domain при соблюдении правил раздела 17–18.

## 21. Отрицательные последствия

- риск проникновения FastAPI/Pydantic типов в application/domain при недостаточной дисциплине;
- framework-specific DI может стать service locator при неосторожном использовании;
- автоматическая OpenAPI может ошибочно восприниматься как полноценный contract governance, хотя таковым не является (раздел 18.4);
- неправильное использование async приводит к блокировке event loop (`ADR-0001`, раздел 19);
- тесная связь с Pydantic/Starlette требует управления совместимостью версий (раздел 16);
- слишком много логики может оказаться в route handlers вместо Application Layer;
- framework upgrades могут иметь breaking changes, требующие управляемого перехода (раздел 16);
- `BackgroundTasks` легко использовать для задач, которым нужна надёжность при падении/перезапуске процесса, хотя официальная документация рекомендует для тяжёлых вычислений отдельные инструменты (раздел 32); в проекте такие задачи для `BackgroundTasks` запрещены отдельным архитектурным решением, а не требованием официальной документации (раздел 18.3).

## 22. Риски

1. Fat controllers — накопление бизнес-логики в route handlers.
2. Framework leakage — проникновение FastAPI/Pydantic типов в application/domain.
3. DTO/domain coupling — смешение transport DTO и domain entities.
4. Service locator — использование DI framework как глобального локатора зависимостей.
5. Блокирующий код внутри async endpoint, блокирующий event loop.
6. Недостоверная OpenAPI — схема не отражает фактическое поведение API.
7. Утечка внутренних ошибок пользователю через стандартные обработчики исключений.
8. Дублирование scheduled jobs при запуске нескольких web workers.
9. Потеря `BackgroundTasks` при падении/перезапуске процесса.
10. Несовместимость версий FastAPI/Starlette/Pydantic между собой или с CPython.
11. Чрезмерное использование middleware, усложняющее диагностику запроса.
12. Отсутствие idempotency при повторных запросах/ретраях клиента.
13. Client disconnect во время выполнения операции, оставляющий бизнес-состояние неопределённым.
14. Неограниченный размер request body, ведущий к исчерпанию ресурсов.
15. Загрузка файлов и связанное с ней потребление памяти/диска.

## 23. Меры снижения рисков

1. Fat controllers → route handler ограничен вызовом application use case и преобразованием результата (раздел 17); проверяется критерием раздела 27.
2. Framework leakage → domain/application не импортируют FastAPI/Starlette/Pydantic transport-модели (раздел 18.1–18.2); проверяется критерием раздела 27.
3. DTO/domain coupling → transport DTO явно отделены от domain entities и application commands (раздел 18.2).
4. Service locator → FastAPI DI используется только для adapter wiring, не как глобальный service locator (раздел 18.1).
5. Блокировка event loop → блокирующие вызовы изолируются от event loop, в соответствии с правилами `ADR-0001` (раздел 18.3).
6. Недостоверная OpenAPI → схема генерируется из фактических DTO, изменение контракта требует contract-тестов (раздел 18.4, раздел 27).
7. Утечка внутренних ошибок → единый безопасный формат ошибок, stack trace не возвращается пользователю (раздел 18.5).
8. Дублирование scheduled jobs → планировщик критичных задач не запускается внутри web-процесса; несколько web workers не инициируют дублирующиеся задания (раздел 18.6).
9. Потеря `BackgroundTasks` → критичные операции не используют `BackgroundTasks`, выполняются отдельным worker-процессом (раздел 18.3; `TECHNOLOGY_EVALUATION.md`, раздел 8).
10. Несовместимость версий → воспроизводимая фиксация версий, тестирование перед обновлением, проверка совместимости с CPython до обновления (раздел 16).
11. Чрезмерное middleware → middleware вводится только при конкретной названной необходимости (`ENGINEERING_PRINCIPLES.md`, пункт 67), а не по умолчанию.
12. Отсутствие idempotency → критичные операции защищаются idempotency-механизмом на уровне application layer (`ENGINEERING_PRINCIPLES.md`, пункт 16) — вне зоны ответственности adapter, но adapter не должен ей препятствовать.
13. Client disconnect → cancellation/timeout передаются контролируемо, бизнес-операция не остаётся в неопределённом состоянии (раздел 18.3).
14. Неограниченный размер request body → ограничение размера тела запроса определяется конфигурацией adapter-слоя как часть будущей задачи внедрения (раздел 25).
15. Загрузка файлов → обработка загрузки файлов проектируется с явным ограничением размера/потребления ресурсов как часть будущей задачи, не в рамках настоящего ADR.

## 24. Влияние на нефункциональные характеристики

- **безопасность:** единый безопасный формат ошибок и запрет раскрытия stack trace (раздел 18.5) снижают поверхность утечки данных; конкретный authentication provider не выбирается этим ADR (раздел 12).
- **надёжность:** критичные операции не зависят от `BackgroundTasks` (раздел 18.3, 22–23); надёжность фоновых операций обеспечивается отдельным worker-процессом (`TECHNOLOGY_EVALUATION.md`, раздел 8), а не adapter-слоем.
- **масштабируемость:** тонкий adapter-слой (раздел 17) сохраняет возможность последующей замены adapter без переписывания domain/application (`ENGINEERING_PRINCIPLES.md`, пункт 13).
- **производительность:** архитектурно ожидается достаточной для MVP-профиля нагрузки (один пользователь, I/O-bound backend); числовые NFR не утверждены (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-005–NFR-006) и не измерены в рамках настоящего ADR.
- **стоимость:** open source, без лицензионных отчислений; конкретное влияние на стоимость эксплуатации не измерено в рамках ADR.
- **сопровождение:** архитектурная оценка — единая, практико-ориентированная официальная документация FastAPI снижает нагрузку на единственного разработчика (раздел 15, критерии 19–20); не измерено в рамках ADR.
- **наблюдаемость:** correlation ID и структурированная обработка ошибок закладываются на уровне adapter-слоя (раздел 18.5) в соответствии с `FAILURE_MODEL.md`, раздел 11.
- **данные:** adapter не владеет бизнес-данными и не обращается к хранилищу напрямую (раздел 17) — влияние на модель данных отсутствует.
- **обратную совместимость:** изменение публичного HTTP-контракта требует contract-тестов и управляемого versioning (раздел 18.4); версия самого adapter управляется политикой раздела 16.

## 25. План внедрения

Без кода на этом этапе. Зафиксированные будущие шаги:

1. принять ADR-0002;
2. определить поддерживаемую версию FastAPI в конфигурации проекта, предварительно проверив совместимость с поддерживаемой версией CPython (`ADR-0001`);
3. определить структуру adapter-пакета;
4. определить application ports (интерфейсы, вызываемые adapter-слоем);
5. определить transport DTO;
6. определить error mapping (transport ↔ domain);
7. определить auth boundary;
8. определить lifecycle (startup/shutdown технических ресурсов adapter-слоя);
9. определить contract-тесты;
10. создать минимальный health endpoint отдельной задачей;
11. проверить локальный запуск на Windows и Linux (в соответствии с `ADR-0001`);
12. проверить отсутствие импортов FastAPI в application/domain (раздел 27).

## 26. План отката

**До появления endpoint-кода:** откат означает замену настоящего ADR новым решением без миграции кода — стоимость отката минимальна.

**После появления API:**

- требуется новый ADR, заменяющий ADR-0002;
- application interfaces (application ports, раздел 25, шаг 4) сохраняются — именно они делают замену adapter технически возможной без переписывания domain;
- adapter заменяется постепенно, route за route либо как полная замена — конкретный способ решается новым ADR;
- публичные HTTP-контракты сохраняются либо выпускается новая версия API (раздел 18.4);
- выполняются contract-тесты перед завершением перехода;
- прежний ADR получает статус «Заменён» с указанием ADR-преемника (`ADR_PROCESS.md`, раздел 19).

## 27. Критерии проверки решения

Решение проверяется, когда появится каркас adapter-слоя (без создания этих проверок в рамках настоящей задачи):

1. FastAPI запускается на поддерживаемой версии CPython (`ADR-0001`);
2. route handler вызывает application use case, а не доменные модули напрямую;
3. domain/application не импортируют FastAPI, Starlette или Pydantic transport-модели;
4. repository не вызывается route handler напрямую;
5. transport DTO отделены от domain entities;
6. OpenAPI генерируется и отражает фактические DTO;
7. внутренние ошибки (stack trace, секреты) не раскрываются в ответе;
8. correlation ID проходит через весь запрос;
9. блокирующий I/O не выполняется в event loop;
10. `BackgroundTasks` не используется для критичных операций;
11. lifecycle корректно освобождает технические ресурсы adapter-слоя при shutdown;
12. `dependency_overrides` позволяет тестировать adapter boundary без вызова реальных внешних зависимостей;
13. contract-тесты обнаруживают несогласованное изменение схемы API;
14. несколько web workers не дублируют выполнение scheduled jobs.

## 28. Условия пересмотра

ADR-0002 пересматривается, если:

- FastAPI не поддерживает выбранную линию CPython (`ADR-0001`);
- framework теряет активное официальное сопровождение;
- критичные требования API невозможно реализовать без системных обходов границ раздела 17–18;
- модель OpenAPI/валидации становится препятствием для реальных сценариев платформы;
- измеренная (не архитектурно предполагаемая) производительность не достигает утверждённых NFR после их принятия;
- framework leakage (раздел 22, риск 2) не удаётся контролировать дисциплиной и правилами раздела 18;
- требуется другой протокол или транспорт помимо HTTP/ASGI;
- приложение перестаёт быть HTTP API;
- стоимость сопровождения framework становится неприемлемой.

Другой protocol adapter (например, для отдельного канала интеграции) может быть добавлен отдельным ADR без замены ADR-0002, если FastAPI остаётся основным HTTP adapter платформы.

## 29. Открытые вопросы

- точная версия FastAPI (и совместимых Starlette/Pydantic) будет определена на шаге 2 плана внедрения (раздел 25) после явной проверки совместимости с поддерживаемой версией CPython — официальные источники на дату исследования не содержат прямого подтверждения совместимости конкретной версии с CPython 3.14 (раздел 16, раздел 32);
- выбор конкретного ASGI server (например, для локального запуска и production) не входит в этот ADR — предмет отдельного решения;
- выбор authentication provider и конкретной схемы авторизации не входит в этот ADR;
- ограничения на размер request body и загружаемых файлов будут определены отдельной задачей (раздел 23, меры 14–15);
- структура API versioning и конкретные DTO будут определены отдельно (раздел 18.2).

## 30. Решение Product Owner

Product Owner утверждает FastAPI как внешний HTTP/ASGI API adapter backend платформы.

Утверждение распространяется только на adapter-слой. Application Layer, domain-модули, persistence, очередь фоновых задач, ASGI server, authentication provider, frontend и deployment остаются независимыми решениями и предметом отдельных ADR или задач.

FastAPI не допускается импортировать в application/domain, а критичные фоновые задачи не допускается выполнять через BackgroundTasks.

## 32. Источники исследования

Исследование выполнено 2026-08-05 исключительно по официальным первичным источникам (fastapi.tiangolo.com, starlette.io, docs.litestar.dev, docs.djangoproject.com, asgi.readthedocs.io), без использования блогов, рейтингов, Medium, Reddit, неофициальных benchmark и маркетинговых статей.

**FastAPI:**
- [fastapi.tiangolo.com](https://fastapi.tiangolo.com/) — официально ASGI-фреймворк, построен на Starlette (веб-часть) и Pydantic (валидация данных); полная поддержка `async`/`await`; встроенная DI-система (`Depends`); автоматическая генерация OpenAPI (Swagger UI, ReDoc); поддержка WebSocket, middleware, background tasks, OAuth2/HTTP Basic security utilities. Маркетинговые количественные заявления о скорости разработки и производительности, приведённые на официальном сайте, не используются в этом ADR как измеренный факт (раздел 15).
- [fastapi.tiangolo.com/advanced/events](https://fastapi.tiangolo.com/advanced/events/) — официальный `lifespan`-механизм (async context manager) для startup/shutdown; код до `yield` — startup, после — shutdown; устаревший `@app.on_event` не комбинируется с `lifespan`.
- [fastapi.tiangolo.com/tutorial/background-tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/) — `BackgroundTasks` выполняются в том же процессе, что и приложение, после формирования ответа; официальная документация рекомендует для тяжёлых вычислений, не требующих выполнения в том же процессе (без необходимости разделять память/переменные), отдельные инструменты (например, Celery). Официальный источник не использует термин «ненадёжные» и не формулирует это как гарантию — вывод о недостаточной долговечности задания при падении процесса сделан архитектурно самим ADR (раздел 18.3), а не приписан источнику.
- [fastapi.tiangolo.com/tutorial/testing](https://fastapi.tiangolo.com/tutorial/testing/) — `TestClient` на основе `httpx`, прямая интеграция с `pytest`.
- [fastapi.tiangolo.com/advanced/testing-dependencies](https://fastapi.tiangolo.com/advanced/testing-dependencies/) — `app.dependency_overrides` — официальный механизм подмены зависимостей в тестах без вызова оригинальной зависимости.
- [fastapi.tiangolo.com/tutorial/handling-errors](https://fastapi.tiangolo.com/tutorial/handling-errors/) — `HTTPException`, `@app.exception_handler`, переопределение стандартных обработчиков валидации и HTTP-ошибок.

**Starlette:**
- [starlette.io](https://www.starlette.io/) — официально «легковесный ASGI-фреймворк/toolkit» для async веб-сервисов; поддержка WebSocket, in-process background tasks, встроенный `TestClient` на `httpx`, CORS/GZip/сессии, роутинг и middleware; заявлено «100% test coverage» и полная типизация кода; совместим с `asyncio` и `trio`.
- [starlette.io/lifespan](https://www.starlette.io/lifespan/) — официальная страница описывает `lifespan` (async context manager) как актуальный документируемый механизм startup/shutdown, включая управление состоянием и тестирование; отдельные устаревшие `on_startup`/`on_shutdown` handlers на этой странице не упоминаются как основной подход.

**Litestar:**
- [docs.litestar.dev](https://docs.litestar.dev/latest/) — официально «мощный, гибкий, производительный, opinionated ASGI-фреймворк»; встроенные DI, генерация OpenAPI (несколько UI-вариантов), валидация через Pydantic/dataclasses/другие библиотеки, WebSocket, background tasks, testing-утилиты, встроенный набор middleware (CORS, CSRF, rate-limiting, аутентификация, логирование, компрессия), интеграции с SQLAlchemy/Tortoise/Piccolo; документация указывает пять сопровождающих проекта на дату исследования. На дату исследования документация не содержит явного заявления о числе поддерживаемых версий Python сверх примеров, использующих возможности 3.8+/3.9+.

**Django:**
- [docs.djangoproject.com/en/stable/topics/async](https://docs.djangoproject.com/en/stable/topics/async/) — официально: Django поддерживает async views и «полностью асинхронный стек запроса при запуске под ASGI», но транзакции официально «пока не работают в async-режиме» (рекомендуется `sync_to_async()`), персистентные соединения с БД должны быть отключены в async-режиме, полностью асинхронный стек требует end-to-end async middleware.

**ASGI:**
- [asgi.readthedocs.io](https://asgi.readthedocs.io/en/latest/) — официально: ASGI — «духовный преемник WSGI», стандартный интерфейс между async-совместимыми Python web-серверами, фреймворками и приложениями; сохраняет обратную совместимость с WSGI-приложениями через отдельную реализацию.
