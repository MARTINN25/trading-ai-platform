## 11. Контекст

`ADR-0002` (раздел 18.5) уже требует correlation ID в ответе и логах, не определяя его формат. `ADR-0004` (раздел 29) требует наблюдаемости slow queries, не определяя механизм. `ADR-0005` (раздел 28) требует наблюдаемости retrieval, не определяя набор полей. `ADR-0006` (раздел 43) зафиксировал минимальный набор наблюдаемых полей и метрик для jobs. `ADR-0007` (раздел 48) зафиксировал минимальный набор наблюдаемых полей для LLM-вызовов и полный список provenance-полей (раздел 46). `ADR-0008` (раздел 39–40) явно отложил централизованный лог-стек и monitoring stack к настоящему ADR, оставив логи контейнеров нативно доступными через Docker.

Ни один из предыдущих ADR не определил: стандартизированный формат trace ID и правила его совместного использования с уже требуемыми request/correlation ID, минимальный набор обязательных полей структурированных логов, уровни логирования, правила redaction/PII masking, границы observability по компонентам (backend/frontend/worker/PostgreSQL/reverse proxy/LLM), метрики RED/USE, sampling/cardinality/retention, минимальный набор health endpoints сверх контейнерного health check, поведение observability при graceful shutdown/rollback, порядок incident investigation. Это предмет настоящего ADR.

Дата проверки технологических данных, использованных в настоящем ADR: 2026-08-05 (см. раздел 62 «Источники исследования»).

## 12. Проблема

Как обеспечить наблюдаемость платформы (backend, frontend, worker, PostgreSQL, reverse proxy, LLM-вызовы, очередь фоновых задач) — логирование, метрики, трассировку, аудит, health checks — так, чтобы инциденты можно было расследовать через структурированные диагностические сигналы и корреляцию, деградацию можно было заметить при ручной проверке health/diagnostic-сигналов и логов, секреты и PII не попадали в логи, а платформа не вводила monitoring-инфраструктуру, не обоснованную объёмом MVP. Проактивное автоматическое обнаружение деградации до обращения пользователя (alerting) этим ADR не обещается — см. раздел 18, 49, 51.

Настоящий ADR не выбирает: Prometheus, Grafana, Loki, ELK, OpenSearch, Tempo, Jaeger, OpenTelemetry Collector, Datadog, New Relic, Sentry, CloudWatch, Azure Monitor, GCP Operations или любой другой monitoring provider. Настоящий ADR не создаёт Dockerfile, Docker Compose, конфигурацию Prometheus/Grafana/Loki/OpenTelemetry Collector, alert rules, CI/CD, Terraform, Helm, Kubernetes-манифесты.

## 13. Ограничения

- решение принимается до появления кода инструментирования — миграционная стоимость на этом этапе минимальна;
- `ADR-0002`/`ADR-0004`/`ADR-0005`/`ADR-0006`/`ADR-0007`/`ADR-0008` уже зафиксировали частичные observability-требования (раздел 11) — настоящий ADR согласует их в единую архитектуру, а не пересматривает;
- один разработчик отвечает за эксплуатацию — полноценная observability platform не вводится без доказанной необходимости (`ENGINEERING_PRINCIPLES.md`, пункт 67);
- MVP разворачивается на одном сервере (`ADR-0008`) — объём телеметрии должен соответствовать этому масштабу;
- решение не должно предполагать выбор конкретного monitoring provider — это выходит за рамки задачи;
- официальные источники (раздел 62) подтверждают, что FastAPI не имеет отдельной официальной страницы логирования и что Uvicorn не выводит структурированный JSON access log по умолчанию — эти пробелы отражены честно, а не восполнены предположением (раздел 62).

## 14. Движущие факторы решения

## 15. Термины

**Structured logging** — запись лог-события в виде набора именованных полей (не свободного текста), пригодного для программной обработки.

**Request ID** — идентификатор одного HTTP request/response цикла, порождаемый на границе платформы.

**Correlation ID** — идентификатор бизнес-операции, который может охватывать несколько технических вызовов (уже введён `ADR-0002`, раздел 18.5; `ADR-0006`, раздел 43; `ADR-0007`, раздел 48) — настоящий ADR не переопределяет его назначение и не вводит заново; correlation ID остаётся самостоятельным, provider-neutral application-level идентификатором (раздел 23), формат которого не унифицируется с trace ID.

**Trace ID** — идентификатор всего распределённого графа вызовов одной операции (reverse proxy → backend → worker → внешние API/LLM → PostgreSQL) в формате, совместимом с W3C Trace Context (раздел 24, 62). Только trace ID обязан соответствовать этому стандарту.

Request ID, correlation ID и trace ID — три различных идентификатора с разным охватом (один HTTP-запрос; одна бизнес-операция; один распределённый граф вызовов соответственно). Их значения могут совпадать в тривиальном случае (например, один синхронный запрос без вложенных вызовов) и могут логироваться совместно для одной операции (раздел 22), но не обязаны быть одним и тем же значением и не обязаны иметь общий формат.

**Span** — единица работы внутри trace с собственным временем начала/окончания, атрибутами и родительской связью (концептуальный термин W3C/OpenTelemetry, раздел 62) — не вводит обязательство использовать конкретный tracing backend.

**Job ID** — уникальный идентификатор конкретной durable job record (`ADR-0006`, раздел 15, 43).

**Provenance** — воспроизводимый контекст формирования результата (модель, provider, версия prompt, источники и т.д. — уже определён `ADR-0007`, раздел 46; `ADR-0004`, раздел 23).

**Audit event** — запись о критичном, авторизационно-значимом действии, отличная от диагностического лога по назначению (раздел 62 — OWASP официально разделяет эти категории).

**Redaction** — удаление или маскирование чувствительных данных перед записью в лог.

**Cardinality** — количество уникальных комбинаций значений измерений (labels/tags) метрики или лог-поля; высокая cardinality увеличивает стоимость хранения и обработки.

**Sampling** — сохранение только части событий/трасс вместо всех, для контроля объёма и стоимости.

**RED-метрики** — Rate (throughput), Errors (error rate), Duration (latency) — архитектурная категоризация метрик запросов, используемая этим ADR как удобная таксономия, не как обязательство внедрить конкретный инструмент.

**USE-метрики** — Utilization, Saturation, Errors — архитектурная категоризация метрик ресурсов, аналогично используемая только как таксономия.

## 16. Рассмотренные варианты

Рассмотрены ровно четыре варианта:

- **Вариант A — только application logs.**
- **Вариант B — Logs + metrics.**
- **Вариант C — Logs + metrics + tracing.**
- **Вариант D — полноценная observability platform.**

Качественные оценки — архитектурная оценка на основании официальной документации (раздел 62), а не результат benchmark.

## 17. Критерии сравнения

| № | Критерий | A. Только logs | B. Logs + metrics | C. Logs + metrics + tracing | D. Полноценная platform |
|---|---|---|---|---|---|
| 1 | Соответствие объёму MVP (5 контейнеризованных сервисов, `ADR-0008`) | достаточно для минимального старта, но недостаточно для количественной деградации | архитектурно достаточно для MVP при пяти сервисах | избыточно детально для MVP, но closes gap корреляции между сервисами дёшево (раздел 62 — W3C Trace Context не требует backend) | избыточно для объёма MVP — требует отдельной инфраструктуры хранения/визуализации |

## 18. Выбранная стратегия

Ни один вариант не принимается целиком «как есть» — фиксируется собственная архитектурная позиция платформы, синтезирующая пункты вариантов B и C без введения backend варианта D:

- **structured logging** внедряется во всех компонентах с самого начала (элемент варианта A/B);
- **trace ID**, совместимый с W3C Trace Context (раздел 24), стандартизируется и распространяется через все компоненты — это архитектурная практика варианта C, принимаемая немедленно, поскольку она бесплатна и vendor-neutral (раздел 62), не требует backend трассировки; **request ID** и **correlation ID** (раздел 15, 23) остаются отдельными, уже частично требуемыми идентификаторами platform-/application-уровня — их формат не унифицируется с trace ID, но они могут логироваться совместно с ним для одной операции;
- **значения RED/USE-метрик** (latency, throughput, error rate, saturation) вычисляются в коде приложения и через уже нативно доступные источники (`pg_stat_activity`, access log reverse proxy, Docker resource-метрики; `pg_stat_statements` — только как возможный будущий кандидат, раздел 32) — элемент варианта B; эти значения фиксируются в структурированных логах и/или диагностических ответах как оперативные, вычисляемые за ограниченное окно сигналы, не как долговременная история (раздел 38), и не в отдельном хранилище временных рядов;
- **полноценная tracing-визуализация** (span-граф, UI) и **полноценная observability platform** (вариант D — сбор/хранение/визуализация логов, метрик, трасс через выбранный продукт) **не вводятся** этим ADR;
- **проактивное автоматическое обнаружение деградации до обращения пользователя не гарантируется** этой MVP-стратегией: без alerting и без постоянного time-series хранилища деградация обнаруживается либо при ручной проверке диагностических/health-сигналов и логов, либо постфактум при расследовании инцидента (раздел 48); это осознанный, явно принятый компромисс MVP-объёма (раздел 51), а не случайный пробел;
- **alerting** (проактивное автоматическое уведомление об аномалии) и **долговременная агрегированная история метрик** не вводятся этим ADR и остаются одним из условий перехода к отдельному observability stack (раздел 49);
- переход к отдельному observability stack (вариант D) рассматривается **отдельным ADR** только при доказанных, измеренных условиях (раздел 49).

## 19. Observability границы

- observability — сквозная (cross-cutting) архитектурная забота, не отдельный домен `MODULE_BOUNDARIES.md`;
- каждый компонент платформы (backend, frontend, worker, PostgreSQL, reverse proxy, LLM-вызовы через `llm_gateway`) отвечает за собственное инструментирование в соответствии с настоящим ADR;
- observability не заменяет audit (`ADR-0006`, раздел 44; `ADR-0007`, раздел 49) — это разные, официально различаемые (раздел 62 — OWASP) категории записей;
- observability не является source of truth бизнес-данных — PostgreSQL остаётся source of truth (`ADR-0004`);
- observability-данные (логи, вычисленные метрики) считаются оперативными, не критичными бизнес-данными — их временная потеря не эквивалентна потере бизнес-данных, но систематическое отсутствие наблюдаемости — операционный риск (раздел 51);
- границы того, что явно НЕ входит в этот ADR: выбор monitoring provider, конфигурация сбора/хранения телеметрии, alert rules, дашборды, SLO/error budget policy (не утверждены `NON_FUNCTIONAL_REQUIREMENTS.md`).

## 20. Structured logging

- каждый компонент платформы использует структурированное логирование — именованные поля, а не произвольный текст;
- Python-компоненты (backend, worker) официально поддерживают структурированные поля через параметр `extra` стандартного модуля `logging`, который добавляет пользовательские ключи в `LogRecord` (раздел 62);
- официальный список стандартных атрибутов `LogRecord` (`name`, `levelname`, `levelno`, `message`, `asctime`, `created`, `filename`, `funcName`, `lineno`, `pathname`, `process`, `processName`, `thread`, `threadName`, `taskName` — раздел 62) используется как основа, дополняемая обязательными полями платформы (раздел 22);
- FastAPI официально не имеет отдельной страницы документации по логированию и не предоставляет собственного логирующего механизма поверх стандартного `logging` — платформа полагается на возможности Python (раздел 62, честно отражённый пробел документации);
- Uvicorn не выводит структурированный JSON access log по умолчанию (документационный пробел/архитектурная данность — раздел 62, источник не подтверждён прямым fetch, помечено как ограничение исследования) — платформа не полагается на формат access log Uvicorn как единственный источник структурированных данных, а инструментирует собственный middleware (аналогично официальному примеру `call_next`/замера времени, раздел 62);
- Docker по умолчанию (`json-file` driver) официально нативно захватывает логи контейнера в структурированном JSON на уровне движка (раздел 62) — это используется как базовый транспортный уровень, не заменяющий структурирование внутри самого приложения;
- Nginx (или выбранный позже reverse proxy продукт) поддерживает `log_format` с параметром `escape=json` для JSON-совместимого экранирования access log (раздел 62) — конкретная конфигурация не создаётся этим ADR;
- PostgreSQL поддерживает структурированные форматы вывода лога (`csvlog`, `jsonlog`) через `log_destination` при включённом `logging_collector` (раздел 62) — конкретная конфигурация не создаётся этим ADR;
- frontend (Next.js) официально предоставляет `instrumentation.ts` с функцией `register()`, вызываемой один раз при старте сервера до приёма запросов, и `onRequestError(error, request, context)` для отчёта серверных ошибок «любому кастомному observability provider» — официально vendor-neutral формулировка (раздел 62); конкретный provider не выбирается этим ADR.

## 21. Уровни логирования

- используется стандартная пятиуровневая модель Python `logging` — `DEBUG`/`INFO`/`WARNING`/`ERROR`/`CRITICAL` с официальной семантикой (раздел 62): `DEBUG` — подробная диагностическая информация; `INFO` — подтверждение штатной работы; `WARNING` — неожиданное событие или потенциальная будущая проблема при продолжающейся работе; `ERROR` — компонент не смог выполнить функцию; `CRITICAL` — серьёзная ошибка, программа может не суметь продолжить работу;
- в качестве стандартов-body уровня референса приняты 8 уровней важности RFC 5424 (`Emergency`=0…`Debug`=7, раздел 62) — используются как концептуальная шкала при сопоставлении уровней разных компонентов (Python/Nginx/PostgreSQL), не как обязательный формат логов приложения;
- `DEBUG` не включается в production по умолчанию — соответствует общему принципу платформы не раскрывать избыточные внутренние детали (`ADR-0002`, раздел 18.5);
- уровень `ERROR`/`CRITICAL` для критичных операций связывается с обязательной audit-записью, где применимо (раздел 28, согласуется с `FAILURE_MODEL.md`, раздел 17.1);
- Nginx использует собственную независимую шкалу `error_log` (`debug`/`info`/`notice`/`warn`/`error`/`crit`/`alert`/`emerg`, раздел 62) — не переопределяется этим ADR, сопоставляется по смыслу при агрегации.

## 22. Минимальный набор обязательных полей логов

Каждая структурированная лог-запись обязана содержать как минимум:

- timestamp (с timezone, согласуется с `ADR-0004`, раздел 21 — UTC);
- уровень логирования (раздел 21);
- компонент/сервис-источник (backend/frontend/worker/PostgreSQL/reverse proxy);
- сообщение;
- correlation ID и/или trace ID, если применимо к операции (раздел 23–24);
- job ID, если событие связано с durable job (`ADR-0006`, раздел 43);
- имя логгера/модуля-источника;
- для ошибок — класс/тип ошибки, без утечки внутреннего stack trace пользователю (`ADR-0002`, раздел 18.5), но с диагностической информацией во внутреннем логе.

Полный список специфичных для LLM-вызовов полей уже зафиксирован `ADR-0007`, раздел 48, и не переопределяется здесь — настоящий раздел устанавливает минимум, применимый ко всем компонентам, а не замену этому списку.

## 23. Correlation ID / Request ID

- **request ID** порождается на границе платформы (reverse proxy или backend, конкретная точка — предмет реализации) для каждого HTTP request/response цикла;
- **correlation ID** — уже требуемый `ADR-0002` (раздел 18.5), `ADR-0006` (раздел 43), `ADR-0007` (раздел 48) идентификатор бизнес-операции; настоящий ADR не вводит его заново и не переопределяет его назначение; correlation ID остаётся отдельным, provider-neutral application-level идентификатором — его формат не обязан соответствовать W3C Trace Context (этому стандарту соответствует только trace ID, раздел 24);
- correlation ID и trace ID — разные идентификаторы разного охвата (раздел 15): correlation ID может логироваться совместно с trace ID для одной операции (раздел 22), но приравнивание их значений или форматов не является требованием этого ADR;
- correlation ID передаётся через все внутренние вызовы одной операции — backend → worker (`ADR-0006`), backend/worker → LLM provider (`ADR-0007`), backend → PostgreSQL (через лог-контекст, не через сетевой протокол);
- в Python-компонентах распространение correlation ID через асинхронный код выполняется через `contextvars.ContextVar`, который официально нативно поддерживается `asyncio` «без дополнительной настройки» и рекомендован официальной документацией именно для такого сценария вместо `threading.local()` (раздел 62) — конкретная реализация (middleware, filter) не создаётся этим ADR;
- значение correlation ID может быть внедрено в каждую лог-запись через `logging.Filter`, официально предназначенный для добавления контекстных полей до вывода записи (раздел 62);
- correlation ID не является секретом и не содержит PII (раздел 27) — генерируется случайным образом, не выводится из пользовательских данных.

## 24. Trace ID

- trace ID стандартизируется в формате, совместимом с официальным W3C Trace Context (`traceparent`): `version-trace_id-parent_id-trace_flags`, где `trace_id` — 16-байтовое (32 hex-символа) глобально уникальное случайное значение, `parent_id` — 8-байтовый (16 hex-символов) идентификатор span (раздел 62);
- официально сервис, принимающий запрос, обязан передавать `traceparent` в исходящие запросы, сохраняя `trace_id` неизменным на всём пути, при этом допускается изменение `parent_id`/флагов (раздел 62) — этот принцип принимается платформой для внутреннего распространения между backend, worker, LLM-вызовами;
- span, как концептуальная единица работы с именем, временными метками, атрибутами и родительской связью (терминология OpenTelemetry, раздел 15, 62), используется только как единица описания в логах (например, «начало/окончание LLM-вызова с данным trace ID»), не подразумевает обязательного backend для сбора/визуализации span-графа;
- официально W3C Trace Context структурно отделяет универсальный конверт (`traceparent`) от vendor-specific данных (`tracestate`) именно для того, чтобы стандарт можно было принять без обязательства перед конкретным backend (раздел 62) — это прямое основание принять trace ID формат сейчас, отложив backend трассировки (раздел 18, 49);
- trace ID, полученный на границе платформы (от клиента или сгенерированный заново), сопровождает всю цепочку: reverse proxy → backend → worker (через job record, `ADR-0006`) → внешние вызовы (LLM provider, `ADR-0007`) → отражается в логах PostgreSQL-уровня через контекст приложения (не сетевой протокол PostgreSQL);
- полноценная агрегация/визуализация trace-графа (сопоставление всех span одного trace ID в UI) — предмет отдельного observability stack (вариант D, раздел 49), не реализуется этим ADR;
- trace ID остаётся самостоятельным идентификатором, отличным от correlation ID (раздел 23) — совместное присутствие обоих в одной лог-записи не означает их идентичность или единый формат; только trace ID/`traceparent` обязан соответствовать W3C Trace Context.

## 25. Job ID и observability очередей

- job ID — уникальный идентификатор durable job record, уже определён `ADR-0006` (раздел 15);
- минимальный набор observability-полей job (job ID, job type, status, attempt, created_at/scheduled_at/claimed_at/started_at/finished_at, duration, worker ID, correlation ID, error class, retry reason, next retry time) и метрик очереди (queue depth, oldest pending age, success/failure rate, retry rate, execution/wait duration, stuck jobs count, dead-letter count, доступность worker'ов, конфликты claim'ов, давление на пул соединений) уже зафиксированы `ADR-0006`, раздел 43 — настоящий ADR не переопределяет их;
- job record связывается с trace ID инициировавшего запроса, если job создан синхронной операцией пользователя (раздел 24) — это расширяет, а не заменяет уже установленную связь job↔correlation ID;
- логи worker-процесса (раздел 30) обязаны включать job ID и correlation/trace ID как часть минимального набора полей (раздел 22).

## 26. LLM observability и provenance

- минимальный набор наблюдаемых полей LLM-вызова (request count, success/failure, provider/model, latency, time to first token, usage, estimated/reported cost, rate-limit события, timeout, retry, refusal, invalid schema, cancellation, queue wait, correlation ID) уже зафиксирован `ADR-0007`, раздел 48 — настоящий ADR не переопределяет их;
- полный список provenance-полей LLM-вызова (provider, model ID, prompt version, source references, schema version, usage, finish reason, retries и т.д.) уже зафиксирован `ADR-0007`, раздел 46 — provenance рассматривается настоящим ADR как специализированная, более широкая форма observability-контекста для LLM-домена, не дублируется;
- LLM-вызов, инициированный в рамках HTTP-запроса или durable job, связывается с тем же trace/correlation ID, что и инициировавшая операция (раздел 23–25);
- полный чувствительный prompt не записывается в обычные логи/метрики (уже установлено `ADR-0007`, раздел 48) — настоящий ADR подтверждает это правило как частный случай общего правила redaction (раздел 27).

## 27. Redaction, PII masking и секреты в логах

- официальная рекомендация OWASP Logging Cheat Sheet: пароли, session identifiers (в открытом виде), access tokens, encryption keys и прочие первичные секреты, данные платёжных карт, строки подключения к БД, исходный код приложения не должны записываться в логи; правило сформулировано официально как «никогда не логировать данные, если это не санкционировано legally» (раздел 62);
- API-ключи LLM-провайдера (`ADR-0007`, раздел 45) и credentials PostgreSQL (`ADR-0004`, раздел 28) не логируются — согласуется с уже установленными правилами;
- чувствительные персональные данные (PII) должны быть де-идентифицированы (удаление, скремблирование, псевдонимизация), где идентичность не требуется для диагностики; менее чувствительные PII (имя, телефон, email) также могут требовать особой обработки перед записью (официальная рекомендация OWASP, раздел 62);
- официальная рекомендация по предотвращению log injection: пользовательские данные, помещаемые в лог, должны быть очищены от символов-разделителей (CR/LF и подобных) до записи (раздел 62) — учитывается при инструментировании каждого компонента;
- correlation/trace ID (раздел 23–24) не считаются PII — генерируются случайно, не выводятся из пользовательских данных;
- redaction применяется одинаково к логам, вычисляемым метрикам и любому будущему observability-каналу — правило не привязано к конкретному инструменту.

## 28. Audit logging vs диагностическое логирование

- официально audit/security-событийное логирование и обычный процесс-мониторинг/диагностическое логирование собираются для разных целей и «часто должны храниться раздельно» (OWASP, раздел 62) — платформа принимает это разделение;
- audit events платформы уже определены `ADR-0006` (раздел 44) и `ADR-0007` (раздел 49) для соответствующих доменов — настоящий ADR не переопределяет их, а фиксирует общий принцип для всех остальных компонентов;
- официальный список категорий событий, которые должны фиксироваться как audit/security-значимые (аутентификация success/failure, отказы авторизации, отказы input/output validation, ошибки приложения и системные события, действия администрирования пользователей, доступ к чувствительным данным, криптографические операции — раздел 62), используется как архитектурная база для будущего определения конкретных audit-точек платформы (не создаётся этим ADR);
- обязательные атрибуты security-события — when (timestamp, идентификатор взаимодействия), where (имя/версия приложения, адрес сервера, URL/место), who (адрес источника, идентичность пользователя, если аутентифицирован), what (тип события, важность, описание, действие, затронутый объект, статус результата, причина, HTTP-статус) — официальная рекомендация OWASP (раздел 62), принимается как минимальная структура audit-записи;
- audit не заменяется обычными observability-логами (уже установлено `ADR-0006`, раздел 44; `ADR-0007`, раздел 49) — настоящий раздел подтверждает это правило как общее для платформы, не только для jobs/LLM.

## 29. Backend observability

- backend (`ADR-0002`) логирует каждый обработанный HTTP-запрос со структурированными полями (раздел 22), включая correlation/trace ID (раздел 23–24);
- официальный паттерн FastAPI middleware — оборачивание `call_next()` для измерения времени обработки (пример: заголовок `X-Process-Time`, раздел 62) — используется как основа для вычисления latency без выбора конкретного metrics backend;
- backend readiness/liveness уже определены на уровне контейнера (`ADR-0008`, раздел 26–27) — observability backend дополняет это вычисляемыми значениями (текущая нагрузка, латентность недавних запросов), не переопределяет health check механику;
- ошибки backend логируются с полным внутренним контекстом во внутренний лог и с безопасным сообщением — пользователю (уже установлено `ADR-0002`, раздел 18.5);
- worker-инициированные LLM/DB-вызовы, происходящие через тот же application use case, что и backend (`ADR-0006`, раздел 21), используют тот же формат логирования.

## 30. Frontend observability

- frontend (Next.js) официально предоставляет `instrumentation.ts` (`register()`) для интеграции наблюдаемости на старте сервера и `onRequestError` для отчёта серверных ошибок (раздел 20, 62) — оба официально vendor-neutral, конкретный provider не выбирается этим ADR;
- frontend не логирует напрямую в PostgreSQL или на файловую систему backend — соответствует уже установленной границе frontend/backend (`ADR-0003`, раздел 17);
- клиентские (browser-side) ошибки не являются предметом server-side observability этого ADR в MVP — архитектурно отложены, поскольку `onRequestError` в официальной документации описан именно для серверных ошибок (раздел 62, честно отражённое ограничение области);
- frontend передаёт correlation/trace ID, полученный от backend (или порождённый на границе), в исходящие запросы к FastAPI Application API, чтобы сохранить сквозную корреляцию (раздел 23–24);
- секреты (`ADR-0003`, раздел 25 — `NEXT_PUBLIC_`-переменные) не логируются frontend-observability механизмом.

## 31. Worker observability

- worker (`ADR-0006`) использует тот же формат структурированного логирования, что backend (раздел 20, 22);
- job-специфичные поля (раздел 25) обязательны в каждой лог-записи, связанной с обработкой job;
- worker логирует claim/start/success/failure/retry/dead-letter переходы job (согласуется с `ADR-0006`, раздел 25 — job state machine) как структурированные события, а не только финальный результат;
- worker распространяет correlation/trace ID из job record (раздел 25) во все внутренние и внешние вызовы, инициированные этой job;
- graceful shutdown worker (раздел 46) генерирует явные лог-события о начале остановки, освобождении lease и завершении.

## 32. PostgreSQL observability

- `log_min_duration_statement` официально позволяет логировать длительность любого выполненного запроса, превышающего заданный порог (раздел 62) — используется для обнаружения slow queries (уже требуется `ADR-0004`, раздел 29); конкретное числовое значение порога не устанавливается этим ADR;
- `log_destination` официально поддерживает `csvlog`/`jsonlog` при включённом `logging_collector` (раздел 62) — предпочтительный формат для последующей программной обработки, конкретная конфигурация не создаётся этим ADR;
- `log_line_prefix` официально предоставляет поля timestamp, PID, session ID, пользователь/БД/приложение/хост, SQLSTATE, идентификаторы транзакции, номер строки в рамках сессии, тип backend-процесса, query ID (раздел 62) — используются для сопоставления с общими обязательными полями (раздел 22), где это применимо к SQL-логу;
- `pg_stat_activity` официально предоставляет текущий запрос, `query_id`, состояние сессии (`active`/`idle`/`idle in transaction` и другие), время начала запроса, метаданные подключения и wait events (раздел 62) — используется как источник runtime observability без отдельного экспортёра метрик;
- `pg_stat_statements` — официальный contrib-модуль (требует `shared_preload_libraries` и `CREATE EXTENSION`), предоставляющий агрегированную статистику по calls/rows/времени выполнения/планированию/I/O/WAL на уровне отдельного запроса (раздел 62); настоящий ADR рассматривает его исключительно как возможного **кандидата** источника для будущих вычисляемых метрик БД — **включение `pg_stat_statements` не утверждается этим ADR**; отсутствие расширения не считается нарушением принятого решения; конкретное решение о включении принимается отдельно, на основании проверки фактической нагрузки, privacy/security-оценки (расширение сохраняет текст запросов) и эксплуатационной стоимости (раздел 55);
- PostgreSQL graceful shutdown (`ADR-0008`, раздел 35) генерирует собственные лог-записи через `log_line_prefix`/`log_destination` — не требует отдельного инструментирования приложением.

## 33. Reverse proxy observability

- reverse proxy (продукт не выбран, `ADR-0008` раздел 32) поддерживает настраиваемый `log_format` с полями, аналогичными официальному предопределённому формату `combined` (адрес клиента, пользователь, время, запрос, статус, размер ответа, referer, user-agent — раздел 62 применительно к исследованному продукту);
- переменная времени обработки запроса (аналог `$request_time`) и переменные времени взаимодействия с upstream (аналоги `$upstream_response_time`/`$upstream_connect_time`/`$upstream_header_time`/`$upstream_queue_time`, раздел 62) используются как источник latency-наблюдаемости на границе платформы без выбора конкретного продукта;
- reverse proxy официально поддерживает JSON-совместимое экранирование формата лога через параметр `escape=json` (в исследованном продукте, раздел 62) — используется, если выбранный позднее продукт это поддерживает;
- reverse proxy логирует запросы с trace ID, если он передан клиентом или порождается на этой границе (раздел 24);
- error log reverse proxy использует собственную независимую шкалу важности (раздел 21) — сопоставляется по смыслу с общей моделью платформы, не переопределяется.

## 34. Метрики: latency

- latency вычисляется на каждом слое, где это осмысленно: reverse proxy (время обработки запроса и время ответа upstream, раздел 33), backend (время обработки HTTP-запроса, официальный паттерн middleware, раздел 29), worker (execution duration job, `ADR-0006` раздел 43), PostgreSQL (`log_min_duration_statement`, `pg_stat_statements`, раздел 32), LLM-вызов (latency, time to first token, `ADR-0007` раздел 48);
- latency фиксируется в структурированных логах и/или вычисляемых значениях, доступных diagnostic-эндпоинту (раздел 41) — не обязательно в отдельном хранилище временных рядов на этапе MVP;
- вычисляемые значения latency (включая любые p50/p95-подобные оценки) подчиняются ограничениям раздела 38 — вычисляются за ограниченное локальное окно, сбрасываются при рестарте процесса, не образуют глобальную историю без отдельного backend;
- числовые пороги latency не устанавливаются этим ADR — не утверждены `NON_FUNCTIONAL_REQUIREMENTS.md`.

## 35. Метрики: throughput

- throughput (запросов/операций в единицу времени) вычисляется агрегированием structured logs по временным окнам на уровне каждого компонента;
- throughput очереди фоновых задач уже частично покрыт `ADR-0006` (queue depth, success/failure rate, раздел 43);
- throughput LLM-вызовов уже частично покрыт `ADR-0007` (request count, раздел 48);
- вычисляемые значения throughput подчиняются ограничениям раздела 38 — окно и алгоритм агрегирования не выбираются этим ADR, значения сбрасываются при рестарте процесса;
- отдельная time-series-система для throughput не вводится этим ADR (раздел 18) — числа вычисляются по требованию из логов на этапе MVP.

## 36. Метрики: error rate

- error rate вычисляется как доля неуспешных операций от общего числа за период, на каждом уровне (HTTP-статусы на reverse proxy/backend, job failure rate — `ADR-0006` раздел 43, LLM error taxonomy — `ADR-0007` раздел 39/48);
- error rate — один из RED-показателей (раздел 15), используемых как таксономия при проектировании структурированных логов, не как обязательство внедрить конкретную metrics-систему;
- вычисляемые значения error rate подчиняются ограничениям раздела 38 — вычисляются за ограниченное локальное окно на уровне отдельного процесса/контейнера, не образуют глобальную агрегированную историю без отдельного backend;
- рост error rate — один из триггеров условий перехода к отдельному observability stack (раздел 49), если превышает возможности ручного анализа логов.

## 37. Метрики: saturation

- saturation (насыщение ресурса — CPU/память/соединения/очередь) наблюдается через: `ADR-0008` resource limits и Docker-уровневые метрики контейнера (раздел 41 ADR-0008), `pg_stat_activity` для соединений/wait events PostgreSQL (раздел 32), queue depth/worker availability для worker'ов (`ADR-0006`, раздел 43);
- saturation — USE-показатель (раздел 15), используемый как таксономия;
- отдельная система сбора ресурсных метрик времени (например, для построения графиков насыщения во времени) не вводится этим ADR.

## 38. Минимальный набор обязательных метрик

Минимум вычисляемых значений, которые должны быть доступны (через логи и/или диагностический эндпоинт, раздел 41), без обязательства отдельного хранилища:

- per-компонент: request/operation count, error count, error rate, приближённая (approximate) оценка latency в стиле p50/p95;
- backend: количество активных запросов, приближённое среднее время ответа за последнее окно;
- worker: queue depth, active/claimed job count, retry rate, dead-letter count (уже установлено `ADR-0006`, раздел 43);
- PostgreSQL: количество активных соединений, наличие/количество slow queries за период (`pg_stat_activity`/`log_min_duration_statement`, раздел 32);
- LLM: request count, error rate, latency, usage/cost (уже установлено `ADR-0007`, раздел 48);
- reverse proxy: request count, error rate (4xx/5xx), latency (раздел 33).

**Ограничения, применимые ко всем вычисляемым значениям разделов 34–38:**

- значения вычисляются за ограниченное локальное окно (скользящее временное окно или ограниченное число последних операций) в пределах одного процесса;
- конкретный алгоритм накопления/агрегации (например, гистограмма, приближённые квантильные структуры, простой кольцевой буфер) и размер окна **не выбираются этим ADR** — предмет реализации;
- значения могут сбрасываться при рестарте процесса — они не являются устойчивой историей;
- значения разных процессов/контейнеров (например, нескольких backend или worker-процессов, `ADR-0008` раздел 37) **не образуют единую агрегированную историю** без отдельного backend сбора метрик (вариант D, раздел 49) — каждый процесс/контейнер предоставляет собственный локальный снимок;
- такие значения являются **оперативными диагностическими сигналами** для ручной проверки и troubleshooting, а не долговременной SLI/SLO-записью;
- точные p50/p95-квантили **нельзя обещать** без определённого алгоритма накопления и агрегации, который не выбирается этим ADR; при реализации допустима приближённая оценка, но она должна быть **явно маркирована как approximate** (например, в имени поля ответа или в сопроводительной документации endpoint'а), чтобы не создавать ложное впечатление точного квантиля.

Числовые пороги/алертинг не устанавливаются этим ADR.

## 39. Tracing

- полноценная распределённая трассировка (сбор span, построение графа вызовов, визуализация) **не вводится** этим ADR (раздел 18);
- принимается только формат идентификатора (trace ID, раздел 24), совместимый с W3C Trace Context, и практика его распространения через компоненты;
- span как концептуальная единица (раздел 15, 24) используется исключительно как способ структурировать лог-записи о начале/завершении операций с общим trace ID, не подразумевает обязательного backend;
- переход к полноценному сбору/визуализации трасс — предмет отдельного ADR (вариант D, раздел 49).

## 40. Logging (сводно)

- structured logging (раздел 20), уровни (раздел 21), минимальный набор полей (раздел 22), correlation/trace ID (раздел 23–24) образуют единую, обязательную с самого начала MVP основу наблюдаемости платформы;
- логи каждого контейнеризованного компонента доступны нативно через Docker (`ADR-0008`, раздел 39 — `json-file` driver официально захватывает логи в структурированном JSON на уровне движка, раздел 62) — это транспортный, не прикладной уровень структурирования;
- централизованная агрегация логов (поиск, долгосрочное хранение, полнотекстовый анализ через специализированный продукт) **не вводится** этим ADR — условия перехода см. раздел 49.

## 41. Health checks, readiness, liveness и минимальный набор health endpoints

- механика контейнерного health check (`HEALTHCHECK`/Compose `healthcheck`, статусы `starting`/`healthy`/`unhealthy`) уже полностью определена `ADR-0008`, раздел 26–27 — настоящий ADR не переопределяет её;
- каждый сервис, обслуживающий HTTP (backend, frontend, reverse proxy), обязан предоставлять минимум одну health-точку, отражающую readiness (готовность обслуживать трафик) отдельно от liveness (факт, что процесс жив), в соответствии с уже установленным различием (`ADR-0008`, раздел 27);
- **liveness endpoint не должен выполнять тяжёлые проверки зависимостей** (например, полноценный запрос к PostgreSQL или внешнему API) — он отвечает только на вопрос «процесс жив и не завис», не «вся система здорова»;
- **readiness endpoint может проверять только зависимости, действительно необходимые для приёма трафика** (например, доступность PostgreSQL для backend) — не более широкий, произвольный набор проверок;
- worker и PostgreSQL, не обслуживающие HTTP напрямую, предоставляют эквивалентный сигнал состояния через механизм, соответствующий их природе (job record для worker — `ADR-0006`, раздел 25; `pg_isready`-подобная проверка для PostgreSQL — уже отражено `ADR-0008`, раздел 26);
- **health endpoint (readiness/liveness) и diagnostic endpoint (раздел 38) — разные точки с разной чувствительностью:** health endpoint отвечает минимальным сигналом состояния (готов/не готов, жив/не жив) и предназначен для reverse proxy/оркестрации; diagnostic endpoint, возвращающий вычисляемые значения раздела 38 в структурированном виде, **не должен автоматически публиковаться через внешний публичный endpoint** — он обязан быть внутренним (доступным только из внутренней сети платформы, `ADR-0008` раздел 31) или защищённым (аутентификация/авторизация доступа) — конкретный механизм защиты не фиксируется этим ADR;
- **ни health, ни diagnostic endpoint не заменяют monitoring и alerting** (раздел 18, 49) — они являются точкой опроса состояния по запросу, а не источником проактивного уведомления;
- **ни health, ни diagnostic endpoint не должны раскрывать** секреты, внутренние сетевые адреса, SQL-запросы, stack traces или иные чувствительные данные — согласуется с общим правилом redaction (раздел 27) и запретом на утечку внутренних деталей пользователю (`ADR-0002`, раздел 18.5);
- конкретные пути/имена endpoint'ов не устанавливаются этим ADR — предмет реализации.

## 42. Sampling

- полное логирование каждого события — базовая политика MVP при текущем предполагаемом объёме нагрузки (один пользователь, `PRODUCT_SCOPE.md`, раздел 5) — sampling логов не требуется на этом этапе;
- trace ID (раздел 24) генерируется для каждой операции без сэмплирования на этапе MVP — при объёме одного пользователя стоимость 100%-го покрытия минимальна;
- если объём логов/трасс вырастет настолько, что полное сохранение станет обременительным, вводится явная политика sampling — не автоматически, а как управляемое решение (раздел 49, 51);
- sampling не применяется к error/critical-уровню логов и к audit-событиям (раздел 21, 28) — эти категории сохраняются полностью независимо от общей политики sampling.

## 43. Cardinality

- correlation/trace/job ID (раздел 23–25) — высококардинальные значения по своей природе (уникальны на операцию), но используются как поля лог-записи, а не как label агрегируемой метрики с высокой cardinality — это разграничение снижает риск, документированный как общая проблема cardinality метрических систем (архитектурная оценка, не измерено в рамках ADR);
- метрики, вычисляемые платформой (раздел 38), проектируются с ограниченным набором измерений (компонент, тип операции, класс ошибки) — не включают unbounded-значения (например, полный текст запроса, конкретный ID пользователя) как label;
- при будущем внедрении backend метрик (вариант D) cardinality-бюджет должен быть спроектирован отдельно — не решается этим ADR.

## 44. Retention

- retention логов на этапе MVP управляется нативными средствами Docker/PostgreSQL/reverse proxy (ротация файлов, встроенные механизмы компонентов) — официальная документация Docker отмечает, что `json-file` driver по умолчанию не выполняет ротацию логов, что создаёт риск исчерпания диска при отсутствии явной настройки (раздел 62) — учитывается как известное ограничение (раздел 51);
- audit-записи (раздел 28) следуют retention-политике, согласованной с их значимостью, отдельной от диагностических логов — конкретный срок не устанавливается этим ADR;
- retention PostgreSQL-логов (`csvlog`/`jsonlog`) управляется средствами файловой системы/`logging_collector` (раздел 32) — конкретная политика не создаётся этим ADR;
- retention wider observability-данных при переходе к варианту D (раздел 49) проектируется отдельно, с учётом стоимости хранения.

## 45. Observability для контейнеров

- логи контейнеров нативно доступны через `docker logs`/`json-file` driver (уже установлено `ADR-0008`, раздел 39; раздел 62 этого ADR подтверждает, что данные внутри `json-file` структурированы как JSON на уровне движка);
- health check-статусы контейнеров (`ADR-0008`, раздел 26) — обязательный минимальный сигнал состояния платформы; официальное подтверждение возможности программного опроса статуса health check через инструмент управления контейнерами не было получено напрямую в ходе исследования (раздел 62 — честно отражённый пробел, не выведено за пределы форумного обсуждения) — при реализации это должно быть подтверждено заново по актуальной документации;
- resource-метрики контейнеров (CPU/память, `ADR-0008` раздел 41) — источник USE-наблюдаемости (раздел 37), не дублируется отдельным инструментом на этапе MVP;
- observability самого контейнерного runtime (например, событий Docker daemon) не является предметом настоящего ADR — не входит в границы (раздел 19).

## 46. Observability при graceful shutdown

- graceful shutdown каждого компонента (уже определён `ADR-0008`, раздел 35 — backend/worker через `SIGTERM`, PostgreSQL через Smart Shutdown, reverse proxy через собственный механизм) сопровождается явными лог-событиями о начале и завершении остановки;
- worker явно логирует освобождение lease активных jobs при остановке (раздел 31, согласуется с `ADR-0006`, раздел 41);
- backend явно логирует отказ от приёма новых запросов и завершение in-flight запросов при остановке (согласуется с `ADR-0002`, раздел 18.6 — lifespan shutdown);
- health check переводит сервис в состояние, отражающее недоступность, до фактического завершения процесса, чтобы reverse proxy не направлял новый трафик на завершающийся контейнер (согласуется с `ADR-0008`, раздел 27);
- отсутствие лог-события о штатном завершении при последующем перезапуске контейнера трактуется как признак аварийного (не штатного) завершения — используется при troubleshooting (раздел 48).

## 47. Observability при rollback

- откат на предыдущий образ (уже определён `ADR-0008`, раздел 45) сопровождается явным лог-событием о смене версии (например, версия/тег образа, время перехода) на уровне, доступном в структурированных логах старта каждого сервиса;
- health check новой (откатной) версии должен подтвердить готовность (раздел 41) до того, как rollback считается завершённым;
- метрики error rate (раздел 36) до и после rollback используются как критерий его успешности — числовой порог не устанавливается этим ADR;
- откат PostgreSQL-данных (`ADR-0004`, раздел 37) сопровождается собственными observability-требованиями backup/restore-процесса (`ADR-0008`, раздел 25) — не дублируется здесь.

## 48. Incident investigation и troubleshooting

- расследование инцидента начинается с trace/correlation ID (раздел 23–24) конкретной пострадавшей операции, если он известен (например, из жалобы пользователя или из error-лога);
- по trace ID вручную сопоставляются записи разных компонентов (reverse proxy → backend → worker → LLM/PostgreSQL) — на этапе MVP это ручной процесс без визуализации графа (раздел 39);
- минимальный набор метрик (раздел 38) используется для локализации деградировавшего компонента до детального анализа логов;
- audit-записи (раздел 28) используются отдельно от диагностических логов при расследовании инцидентов, связанных с авторизацией/критичными действиями;
- health check-история (там, где доступна, раздел 41, 45) используется для определения момента начала деградации;
- отсутствие корреляции между компонентами (например, из-за пропущенного trace ID на одном из этапов) — известное ограничение ручного troubleshooting на этапе MVP, снижаемое дисциплиной распространения ID (раздел 51).

## 49. Условия перехода к отдельному observability stack

Переход к варианту D (раздел 16) — то есть внедрение специализированного продукта для сбора/хранения/визуализации логов, метрик и/или трасс — рассматривается **отдельным ADR**, только если измерения или опыт эксплуатации покажут одно или несколько из:

- ручной анализ структурированных логов перестаёт справляться с объёмом инцидентов или временем расследования;
- отсутствие визуализации trace-графа (раздел 39) систематически замедляет troubleshooting сверх приемлемого;
- объём логов делает нативную ротацию/retention (раздел 44) недостаточной;
- требуется алертинг (проактивное уведомление об аномалии) — не покрывается ручным просмотром логов/метрик;
- число компонентов/инстансов превышает то, что разумно анализировать вручную (например, при горизонтальном масштабировании — `ADR-0008`, раздел 38);
- требуется SLO/error budget policy, для которой нужна количественная история метрик за длительный период;
- эксплуатационная польза специализированного стека измеримо превышает его стоимость и сложность (раздел 17, критерии 5–6).

Сам факт роста числа компонентов или пользователей **не является автоматическим** основанием для введения observability platform.

## 50. Положительные последствия

- стандартизированный формат trace ID (W3C Trace Context, раздел 24) внедряется сразу, бесплатно, без блокировки на конкретном vendor, наряду с уже существующим отдельным correlation ID (раздел 23) — устраняет необходимость ретрофита при будущем переходе к варианту D;
- structured logging и redaction-правила (раздел 20, 27) закладываются архитектурно с первого дня, а не добавляются постфактум;
- уже существующие частичные observability-требования (`ADR-0002`/0004/0005/0006/0007/0008) согласуются в единую модель без противоречий и без их пересмотра;
- MVP не несёт стоимости и сложности отдельной observability-инфраструктуры, которая ему не нужна при текущем объёме (`ENGINEERING_PRINCIPLES.md`, пункт 67);
- честно задокументированные пробелы официальной документации (отсутствие логирующей страницы у FastAPI, неподтверждённый JSON access log Uvicorn, неподтверждённая программная опрашиваемость health-статуса контейнера) снижают риск скрытых сюрпризов при реализации.

## 51. Отрицательные последствия

- ручное сопоставление логов по trace ID без визуализации — трудоёмкий процесс при усложнении графа вызовов (раздел 39, 48);
- отсутствие retention-политики логов по умолчанию (`json-file` driver, раздел 44) создаёт риск исчерпания диска без явной настройки;
- **отсутствие автоматического alerting — осознанное отрицательное последствие принятого MVP-компромисса** (раздел 18): деградация может остаться незамеченной до обращения пользователя или ручной проверки логов/health/diagnostic-сигналов; это принято сознательно ради избежания преждевременной observability-инфраструктуры (раздел 49), а не является случайным недосмотром;
- дисциплина распространения correlation/trace ID через все компоненты требует последовательного соблюдения на этапе реализации — пропуск на одном из этапов ломает корреляцию (раздел 48);
- вычисляемые метрики (раздел 34–38) не дают исторического тренда без отдельного хранилища — представляют собой снимок на момент запроса, не временной ряд.

## 52. Риски

1. Секреты попадают в логи.
2. PII попадает в логи без redaction.
3. Log injection через пользовательский ввод (CR/LF/разделители).
4. Correlation/trace ID не распространяется через один из компонентов, ломая корреляцию.
5. Trace ID генерируется предсказуемо/не случайно, создавая риск подмены.
6. Отсутствие ротации логов приводит к исчерпанию диска.
7. Уровень логирования `DEBUG` включён в production, раскрывая избыточные детали.
8. Audit-события смешиваются с диагностическими логами.
9. Критичное действие не сопровождается audit-записью.
10. Health check не отражает реальную готовность сервиса (уже частично покрыто `ADR-0008`, но наблюдаемость этого факта — предмет данного ADR).
11. Метрики error rate вычисляются некорректно из-за неполных данных.
12. Высокая cardinality вычисляемых значений создаёт риск при будущем переходе к варианту D.
13. Slow query threshold PostgreSQL не настроен, скрывая деградацию.
14. Решение о включении `pg_stat_statements` не принято осознанно (ни в ту, ни в другую сторону) до момента реальной необходимости в детальной query-статистике.
15. Reverse proxy access log не включает latency-переменные, скрывая деградацию на границе.
16. LLM-вызовы логируются без учёта уже установленных правил `ADR-0007`.
17. Job-логи не содержат correlation ID, разрывая связь job↔исходный запрос.
18. Frontend server-side ошибки не репортируются через `onRequestError`.
19. Graceful shutdown не сопровождается лог-событиями, усложняя различение штатного и аварийного завершения.
20. Rollback не проверяется по метрикам/health check перед признанием успешным.
21. Incident investigation невозможен из-за отсутствия минимального набора обязательных полей (раздел 22).
22. Ручной troubleshooting не масштабируется при росте нагрузки, но переход к observability stack откладывается без объективных оснований.
23. Наблюдатель ошибочно вводит monitoring provider «на будущее» без выполнения условий раздела 49.
24. Логи разных компонентов используют несовместимые форматы timestamp/timezone.
25. Structured logging применяется частично — часть компонентов логирует произвольным текстом.
26. Диагностическая точка (раздел 41) раскрывает внутренние детали инфраструктуры внешнему пользователю.
27. Sampling ошибочно применяется к error/audit-событиям, теряя критичные записи.
28. Observability-данные ошибочно трактуются как источник истины бизнес-данных.
29. Официально неподтверждённые факты (JSON access log Uvicorn, health-статус через инструмент управления контейнерами) используются в реализации как если бы они были документированы.
30. Retention audit-записей не согласован с их значимостью, приводя к преждевременному удалению.

## 53. Меры снижения рисков

1. Секреты в логах → правило redaction (раздел 27), основанное на официальном списке OWASP; ревью инструментирования каждого компонента.
2. PII без redaction → де-идентификация чувствительных данных перед записью (раздел 27).
3. Log injection → очистка пользовательских данных от разделителей перед записью в лог (раздел 27, официальная рекомендация OWASP).
4. Разрыв корреляции → `contextvars`-based распространение ID в Python-компонентах (раздел 23), явная проверка распространения как часть критериев проверки (раздел 57).
5. Предсказуемый trace ID → официальное требование W3C Trace Context к случайной глобальной уникальности `trace-id` соблюдается при реализации (раздел 24, 62).
6. Исчерпание диска → явная политика ротации логов определяется на этапе реализации, с учётом официально документированного отсутствия ротации по умолчанию у `json-file` driver (раздел 44, 62).
7. `DEBUG` в production → уровень логирования по умолчанию в production выше `DEBUG` (раздел 21).
8. Смешение audit и диагностических логов → официально обоснованное разделение (раздел 28) соблюдается архитектурно и на этапе реализации.
9. Отсутствие audit-записи → критичные действия связываются с audit trail (уже установлено `ADR-0006`, раздел 44; `ADR-0007`, раздел 49; раздел 28 настоящего ADR).
10. Health check не отражает готовность → наблюдаемость health-статуса явно фиксируется как часть минимального набора (раздел 41), несоответствие обнаруживается через сопоставление с реальными ошибками.
11. Некорректный error rate → error rate вычисляется из полного набора структурированных записей, не выборочно (раздел 36, 42).
12. Высокая cardinality → метрики проектируются с ограниченным набором измерений с самого начала (раздел 43).
13. Slow query threshold не настроен → явное требование настроить `log_min_duration_statement` как часть плана внедрения (раздел 54).
14. Неосознанное решение о `pg_stat_statements` → явный шаг плана внедрения (раздел 54) с оценкой нагрузки, privacy/security и эксплуатационной стоимости перед принятием решения о включении; включение не утверждается этим ADR, отсутствие расширения не считается нарушением решения (раздел 32).
15. Отсутствие latency-переменных в access log → явное требование включить эти переменные в `log_format` при реализации reverse proxy (раздел 33, 54).
16. Нарушение правил `ADR-0007` при логировании LLM → настоящий ADR явно ссылается и не переопределяет эти правила (раздел 26).
17. Job-логи без correlation ID → обязательность поля закреплена в минимальном наборе (раздел 22, 25).
18. Frontend-ошибки не репортируются → явное требование реализовать `onRequestError` (раздел 30, 54).
19. Graceful shutdown без лог-событий → явное требование логировать начало/завершение остановки для каждого компонента (раздел 46, 54).
20. Rollback без проверки → health check и метрики error rate как обязательное условие завершения rollback (раздел 47).
21. Невозможность investigation → минимальный набор обязательных полей закреплён как архитектурное требование (раздел 22), проверяется критериями раздела 57.
22. Немасштабируемый troubleshooting без перехода → условия перехода зафиксированы явно и объективно (раздел 49), не оставлены на усмотрение момента.
23. Преждевременный monitoring provider → раздел 49 требует доказанных условий, а не предположений; ADR прямо запрещает выбор provider без отдельного решения.
24. Несовместимые timestamp/timezone → UTC и общий формат обязательны для всех компонентов (раздел 22, согласуется с `ADR-0004`, раздел 21).
25. Частичное structured logging → архитектурное требование применяется ко всем компонентам без исключения (раздел 20), проверяется критериями раздела 57.
26. Утечка внутренних деталей через диагностическую точку → diagnostic endpoint внутренний или защищённый, не публикуется автоматически наружу; формат ответа не раскрывает секреты, внутренние адреса, SQL, stack traces или иные чувствительные данные (раздел 41), согласуется с `ADR-0002`, раздел 18.5.
27. Sampling теряет error/audit → явное исключение error/critical и audit из sampling (раздел 42).
28. Observability как источник истины → явное архитектурное разграничение (раздел 19) — PostgreSQL остаётся source of truth.
29. Неподтверждённые факты трактуются как документированные → честно помечены как пробелы исследования (раздел 62), подлежат отдельной проверке перед реализацией.
30. Retention audit не согласован → отдельная retention-политика audit, отличная от диагностических логов (раздел 28, 44).

## 54. NFR impact

Числовые NFR, связанные с observability (retention сроки, пороги latency/error rate для алертинга, cardinality-бюджет, SLO), не утверждены `NON_FUNCTIONAL_REQUIREMENTS.md` и не устанавливаются этим ADR — определяются при измерениях после реализации и/или при переходе к варианту D (раздел 49). Structured logging, correlation/trace ID, redaction и разделение audit/диагностических логов закладываются архитектурно с самого начала (разделы 20–28).

## 55. План внедрения

Без кода на этом этапе. Зафиксированные будущие шаги:

1. принять ADR-0009;
2. определить конкретный формат генерации/передачи trace ID (библиотека или собственная реализация, совместимая с W3C Trace Context) отдельным решением;
3. определить middleware/filter для backend, инжектирующий correlation/trace ID в каждую лог-запись (`contextvars`, `logging.Filter`);
4. определить аналогичный механизм для worker;
5. определить `instrumentation.ts`/`onRequestError` реализацию для frontend;
6. определить конкретный формат структурированных логов (JSON-схему полей раздела 22) как отдельный артефакт;
7. настроить `log_min_duration_statement` и оценить необходимость `pg_stat_statements` для PostgreSQL;
8. настроить `log_destination`/`log_line_prefix` PostgreSQL под структурированный формат;
9. настроить `log_format` reverse proxy с latency-переменными и, если доступно, JSON-совместимым экранированием;
10. определить redaction-механизм (фильтр/маскирование) для каждого компонента на основании раздела 27;
11. определить audit-точки платформы за пределами уже установленных `ADR-0006`/`ADR-0007` доменов;
12. определить минимальный диагностический endpoint формат для backend/frontend/reverse proxy (раздел 41);
13. определить политику ротации логов контейнеров с учётом отсутствия ротации по умолчанию у `json-file` driver;
14. проверить корректность распространения trace ID через полный путь одного запроса (reverse proxy → backend → worker → LLM/PostgreSQL) как часть первого vertical slice;
15. проверить, что secrets/PII не попадают в логи ни одного компонента;
16. проверить graceful shutdown/rollback лог-события (раздел 46–47);
17. провести первый incident investigation drill на тестовом сценарии, используя только структурированные логи и trace ID;
18. только после этого — production-развёртывание наблюдаемости MVP.

## 56. План отката

**Если элемент observability не используется (например, откат к чисто произвольному текстовому логированию):**

- откат не влияет на бизнес-данные (PostgreSQL остаётся source of truth, раздел 19);
- потеря структурированности логов снижает возможность troubleshooting, но не создаёт риска для целостности платформы;
- correlation/trace ID может быть временно отключён без нарушения функциональности — это ухудшает наблюдаемость, не работоспособность;
- новый ADR фиксирует замену настоящего решения, если решение об архитектуре наблюдаемости пересматривается целиком.

**Если позже принят отдельный observability stack (переход к варианту D) и требуется откат от него:**

- structured logging и trace ID формат (уже принятые этим ADR) остаются действительными независимо от наличия/отсутствия backend — откат от backend не требует пересмотра формата;
- сбор/хранение через внешний продукт прекращается, платформа возвращается к модели раздела 18–19 (логи, вычисляемые метрики, ручной troubleshooting);
- откат документируется соответствующим будущим ADR, не настоящим.

## 57. Критерии проверки решения

После будущей реализации (без создания этих проверок в рамках настоящей задачи):

1. каждый компонент (backend, frontend, worker, PostgreSQL, reverse proxy) генерирует структурированные логи с минимальным набором полей (раздел 22);
2. trace ID в формате, совместимом с W3C Trace Context, распространяется через полный путь одного запроса;
3. correlation ID, уже требуемый `ADR-0002`/`ADR-0006`/`ADR-0007`, присутствует в логах наряду с trace ID как отдельный идентификатор, без требования единого формата (раздел 15, 23);
4. job-логи содержат job ID и correlation/trace ID;
5. LLM-вызовы логируются в соответствии с уже установленными правилами `ADR-0007`, раздел 48;
6. секреты и PII не обнаруживаются в логах ни одного компонента (проверка redaction);
7. log injection невозможен через пользовательский ввод;
8. audit-события отделены от диагностических логов;
9. критичные действия сопровождаются audit-записью там, где это уже требуется `ADR-0006`/`ADR-0007`;
10. `DEBUG`-уровень не активен в production;
11. slow query threshold PostgreSQL настроен и работает;
12. reverse proxy access log содержит latency-переменные;
13. минимальный health endpoint возвращает readiness/liveness раздельно, без тяжёлых проверок в liveness (согласуется с `ADR-0008`, раздел 27); отдельный diagnostic endpoint, если реализован, является внутренним/защищённым (раздел 41);
14. graceful shutdown и rollback сопровождаются явными лог-событиями;
15. incident investigation drill успешно проходит с использованием только структурированных логов и trace ID, без внешнего monitoring provider;
16. ротация логов контейнеров настроена, диск не переполняется при нормальной нагрузке;
17. ни один monitoring provider не выбран без отдельного ADR.

## 58. Условия пересмотра

ADR-0009 пересматривается, если:

- выполнены условия перехода к отдельному observability stack (раздел 49) и требуется выбор конкретного продукта;
- структурированное логирование или формат trace ID перестают удовлетворять требованиям расследования инцидентов после практического опыта;
- официальная документация используемых компонентов (FastAPI, Uvicorn, Next.js, PostgreSQL, reverse proxy, Docker) существенно меняет описанные в этом ADR механизмы;
- W3C Trace Context или иной использованный стандарт корреляции пересматривается стандартизирующим органом существенным образом;
- требования compliance/аудита существенно меняют требования к retention или redaction;
- горизонтальное масштабирование (`ADR-0008`, раздел 38) делает ручную корреляцию логов недостаточной;
- количественные NFR (`NON_FUNCTIONAL_REQUIREMENTS.md`) устанавливаются и требуют observability-возможностей, не покрываемых текущей моделью;
- LLM provider (`ADR-0007`) или queue-модель (`ADR-0006`) меняются существенным образом, затрагивающим уже установленные наборы observability-полей.

## 59. Открытые вопросы

- конкретная библиотека/реализация генерации и распространения trace ID (совместимого с W3C Trace Context) не выбирается этим ADR — предмет отдельного implementation-решения;
- конкретный monitoring provider (Prometheus/Grafana/Loki/ELK/OpenSearch/Tempo/Jaeger/OpenTelemetry Collector/Datadog/New Relic/Sentry/CloudWatch/Azure Monitor/GCP Operations или иной) не выбирается этим ADR — предмет отдельного ADR при выполнении условий раздела 49;
- конкретный формат/схема JSON структурированных логов не фиксируется этим ADR;
- программная опрашиваемость health-статуса контейнера через инструмент управления контейнерами не подтверждена официальной документацией в рамках этого исследования (раздел 62) — требует отдельной проверки перед реализацией;
- официальный формат access log Uvicorn (структурированный/JSON вывод) не подтверждён прямым обращением к официальной странице в рамках этого исследования — требует переподтверждения перед реализацией (раздел 62);
- клиентская (browser-side) наблюдаемость frontend не рассмотрена этим ADR — architecturally отложена, так как официальный `onRequestError` Next.js документирован именно для серверных ошибок (раздел 30);
- конкретная политика ротации/retention логов контейнеров не устанавливается этим ADR;
- необходимость `pg_stat_statements` как обязательного расширения (а не опционального) остаётся открытым вопросом реализации.

**W3C / OpenTelemetry (vendor-neutral стандарты корреляции):**
- [w3.org/TR/trace-context](https://www.w3.org/TR/trace-context/) — официальная W3C Recommendation; формат `traceparent` (`version-trace_id-parent_id-trace_flags`), обязательная случайная глобальная уникальность `trace-id`/`parent-id`, обязательность передачи `traceparent` в исходящие запросы с сохранением `trace-id`, структурное отделение universal-конверта от vendor-specific `tracestate`.
- [opentelemetry.io/docs/concepts/signals/traces](https://opentelemetry.io/docs/concepts/signals/traces/), [opentelemetry.io/docs/what-is-opentelemetry](https://opentelemetry.io/docs/what-is-opentelemetry/) — определения trace/span/span context/context propagation; официальное подтверждение vendor-neutrality спецификации и её отличия от OpenTelemetry Collector как отдельного, не выбираемого этим ADR компонента.

**OWASP / IETF (redaction, audit, уровни):**
- [cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) — список данных, запрещённых к логированию; рекомендации по PII/де-идентификации; предотвращение log injection; обязательные атрибуты security-события (when/where/who/what); официальное разделение audit/security-логов и диагностических логов; список событий, подлежащих обязательному логированию.
- [rfc-editor.org/rfc/rfc5424](https://www.rfc-editor.org/rfc/rfc5424) — официальные 8 уровней важности syslog (Emergency…Debug) с определениями, §6.2.1.

**Python:**
- [docs.python.org/3/library/logging.html](https://docs.python.org/3/library/logging.html) — 5 уровней (`DEBUG`/`INFO`/`WARNING`/`ERROR`/`CRITICAL`) с официальной семантикой; параметр `extra` для структурированных полей; стандартные атрибуты `LogRecord`; `logging.Filter` для инъекции контекстных полей.
- [docs.python.org/3/library/contextvars.html](https://docs.python.org/3/library/contextvars.html) — нативная поддержка `asyncio` без дополнительной настройки; официальная рекомендация `ContextVar` вместо `threading.local()` для распространения контекстных значений в конкурентном/асинхронном коде.

**FastAPI / Uvicorn:**
- [fastapi.tiangolo.com/tutorial/middleware](https://fastapi.tiangolo.com/tutorial/middleware/) — официальный паттерн измерения времени обработки через `call_next()` (`X-Process-Time`); подтверждённое отсутствие отдельной официальной страницы логирования FastAPI.
- Uvicorn access log формат (`%(levelprefix)s %(client_addr)s - "%(request_line)s" %(status_code)s`) — сведения получены через поисковые сниппеты официальной страницы; прямой fetch `uvicorn.org`/`uvicorn.dev` не удался (DNS timeout/403) в рамках этого исследования — честно отражено как ограничение, не как прямо процитированный официальный источник.

**Next.js:**
- [nextjs.org/docs/app/guides/instrumentation](https://nextjs.org/docs/app/guides/instrumentation/) — официальное описание `instrumentation.ts`/`register()`; vendor-neutral формулировка примера с OpenTelemetry как иллюстрации, не требования.
- [nextjs.org/docs/app/api-reference/file-conventions/instrumentation](https://nextjs.org/docs/app/api-reference/file-conventions/instrumentation/) — `onRequestError(error, request, context)`, официально описан как отчёт серверных ошибок «любому кастомному observability provider»; стабилен с версии 15.0.0.

**PostgreSQL:**
- [postgresql.org/docs/current/runtime-config-logging.html](https://www.postgresql.org/docs/current/runtime-config-logging.html) — `log_min_duration_statement`, `log_destination` (включая `csvlog`/`jsonlog`), `logging_collector`, поля `log_line_prefix`.
- [postgresql.org/docs/current/monitoring-stats.html](https://www.postgresql.org/docs/current/monitoring-stats.html) — `pg_stat_activity`: query/query_id/state/wait_event_type/wait_event и метаданные подключения.
- [postgresql.org/docs/current/pgstatstatements.html](https://www.postgresql.org/docs/current/pgstatstatements.html) — официальный contrib-модуль `pg_stat_statements`, агрегированная статистика по запросам.

**Docker (переиспользовано и дополнено относительно `ADR-0008`, раздел 61):**
- [docs.docker.com/engine/logging/configure](https://docs.docker.com/engine/logging/configure/) — `json-file` driver по умолчанию, официально нативный структурированный JSON-захват на уровне движка; официально документированное отсутствие ротации по умолчанию.
- [docs.docker.com/engine/logging](https://docs.docker.com/engine/logging/) — `docker logs` читает stdout/stderr по умолчанию.
- Программная опрашиваемость статуса `HEALTHCHECK` через `docker inspect` не подтверждена официальной страницей docs.docker.com в рамках этого исследования — только форумное обсуждение сообщества, не использовано как источник факта (честно отражённый пробел).

**Reverse proxy (переиспользовано и дополнено относительно `ADR-0008`, раздел 61):**
- [nginx.org/en/docs/http/ngx_http_log_module.html](https://nginx.org/en/docs/http/ngx_http_log_module.html) — `log_format`, параметр `escape` (включая `json`), предопределённый формат `combined`, `$request_time`.
- [nginx.org/en/docs/http/ngx_http_upstream_module.html](https://nginx.org/en/docs/http/ngx_http_upstream_module.html) — `$upstream_response_time`/`$upstream_connect_time`/`$upstream_header_time`/`$upstream_queue_time`.
- [nginx.org/en/docs/ngx_core_module.html](https://nginx.org/en/docs/ngx_core_module.html) — 8 уровней `error_log` (`debug`…`emerg`).
