## 11. Контекст

`ADR-0004` (утверждён) зафиксировал PostgreSQL как основное транзакционное хранилище и явно не утвердил ни pgvector, ни отдельную vector database — оставив стратегию векторного поиска предметом настоящего ADR (`ADR-0004`, раздел 40 «Открытые вопросы»). `TECHNOLOGY_EVALUATION.md` (раздел 7, утверждён) зафиксировал предварительную рекомендацию — не вводить отдельную векторную СУБД в MVP, рассматривать расширение возможностей уже выбранной реляционной СУБД только при появлении конкретной задачи.

Логическая архитектура требует: факты отделены от AI-интерпретации (`ENGINEERING_PRINCIPLES.md`, пункт 59); LLM не является источником фактов (пункт 57); provenance сохраняется (`LOGICAL_ARCHITECTURE.md`, раздел 9, 14); инсайты неизменяемы (раздел 14); модульный монолит не усложняется без доказанной необходимости (пункт 12, 67); стоимость инфраструктуры должна оставаться управляемой (пункт 52); дополнительные сервисы не вводятся заранее (пункт 67).

Дата проверки технологических данных, использованных в настоящем ADR: 2026-08-05 (см. раздел 47 «Источники исследования»).

## 12. Проблема

Требуется ли платформе векторный/семантический поиск на этапе MVP; если да — при каких условиях; какой вариант реализации является первым кандидатом при подтверждённой необходимости; при каких условиях потребуется отдельная vector database; как отделить структурированный поиск, полнотекстовый поиск, семантический поиск и генерацию LLM друг от друга; как контролировать качество, стоимость, безопасность, версионирование embeddings и путь миграции между вариантами.

Настоящий ADR не выбирает: конкретную embedding-модель, embedding provider, размерность vectors, distance metric, параметры HNSW/IVFFlat, chunking library, reranking model, hybrid-search библиотеку, версию pgvector, версию Qdrant, managed vector provider, значения retention, числовые пороги latency/recall без измерений.

## 13. Ограничения

- решение принимается до появления embeddings и кода — миграционная стоимость на этом этапе минимальна;
- PostgreSQL уже утверждён как основное хранилище (`ADR-0004`) — любой вариант векторного поиска оценивается относительно этого факта, а не в вакууме;
- один разработчик отвечает за эксплуатацию — дополнительный сервис не вводится без доказанной необходимости (`ENGINEERING_PRINCIPLES.md`, пункт 67);
- MVP разворачивается на одном сервере (`PRODUCT_SCOPE.md`, раздел 22);
- решение не должно предполагать выбор embedding-модели/provider, конкретных параметров индексов или конкретной vector database — это выходит за рамки задачи;
- официальные источники (раздел 47) не подтверждают, что vector database обязательна для AI-платформы — это утверждение прямо не используется как основание решения.

## 14. Движущие факторы решения

Критерии сравнения (раздел 16) выведены из `ENGINEERING_PRINCIPLES.md`, `LOGICAL_ARCHITECTURE.md`, `ADR-0004` и контекста задачи (раздел 11): необходимость для утверждённого MVP, соответствие принципу «не добавлять технологию без конкретной проблемы» (YAGNI), стоимость, инфраструктурная сложность, эксплуатация одним разработчиком, локальный Windows-запуск, Linux production, необходимость дополнительного сервиса, транзакционная связь с PostgreSQL, consistency, backup/restore, disaster recovery, metadata filtering, exact/approximate search, HNSW/IVFFlat, lexical search, hybrid search, масштабирование, объём vectors, latency, recall, обновление и версионирование embeddings, удаление пользовательских данных, provenance, аудит, безопасность, vendor lock-in, обратимость, независимое масштабирование, устойчивость к сетевым сбоям, будущий рост.

## 15. Термины и виды поиска

### Структурированный поиск

Поиск по нормализованным полям: instrument, market, timeframe, timestamps, status, tags, source, user, evaluation status и другим. Выполняется средствами PostgreSQL (реляционные запросы, индексы) и **не требует embeddings**.

### Полнотекстовый поиск

Лексический поиск по тексту через встроенные возможности PostgreSQL (`tsvector`/`tsquery`, раздел 47). **Не равен** semantic vector search — находит совпадения по словоформам (лексемам), а не по смысловой близости.

### Semantic vector search

Поиск по близости embeddings (векторных представлений) в многомерном пространстве. **Не гарантирует** фактическую правильность или релевантность результата — обеспечивает только близость по смыслу согласно конкретной embedding-модели.

### Hybrid search

Комбинация lexical (полнотекстового), vector и metadata filtering поиска, обычно с последующим слиянием результатов (например, Reciprocal Rank Fusion — официально документированный подход Qdrant, раздел 47). **Не вводится автоматически** этим ADR.

### Reranking

Дополнительное переупорядочивание кандидатов после первичного поиска (например, более точной, но более дорогой моделью). **Не выбирается** этим ADR.

## 16. Рассмотренные варианты

Рассмотрены ровно три стратегии:

- **Вариант A — без vector search в первоначальном MVP** (structured + full-text search PostgreSQL)
- **Вариант B — pgvector внутри PostgreSQL**
- **Вариант C — отдельная Qdrant vector database**

Качественные оценки ниже — архитектурная оценка на основании официальной документации (раздел 47), а не результат benchmark.

## 17. Выбранная стратегия

Стратегия — поэтапная, с явными условиями перехода между фазами.

### Фаза 1 — первоначальный MVP

- vector search не является обязательной функцией;
- embeddings не создаются заранее;
- Qdrant не разворачивается;
- pgvector extension не устанавливается автоматически;
- поиск реализуется через PostgreSQL: структурированные фильтры, реляционные запросы, полнотекстовый поиск — если это необходимо конкретному утверждённому пользовательскому сценарию;
- LLM получает только явно собранный application context (не через retrieval);
- отсутствие vector search **не считается техническим долгом** — это осознанное состояние, соответствующее принципу «не добавлять технологию без конкретной проблемы» (`ENGINEERING_PRINCIPLES.md`, пункт 67).

### Фаза 2 — подтверждённая необходимость semantic retrieval

После выполнения всех условий активации (раздел 19):

- первым кандидатом является **pgvector внутри PostgreSQL**;
- включение pgvector требует отдельной implementation-задачи и проверки инфраструктуры (совместимость сборки/платформы, память, дисковое пространство);
- exact search используется как baseline там, где объём позволяет (раздел 47 — exact search даёт полный recall);
- HNSW или IVFFlat выбираются только после измерений на конкретных данных, а не заранее;
- конкретный индекс, distance metric и параметры **не выбираются настоящим ADR**;
- embeddings остаются производными данными — исходные данные остаются source of truth (раздел 24).

### Фаза 3 — специализированное хранилище

Отдельная vector database (первый кандидат — Qdrant) рассматривается **отдельным ADR** только при доказанных, измеренных ограничениях pgvector/PostgreSQL (раздел 21). Настоящий ADR **не утверждает Qdrant** ни сейчас, ни автоматически в будущем.

## 18. Состояние MVP

MVP платформы работает полностью без vector-инфраструктуры:

- поиск и фильтрация истории инсайтов, дневника, заметок выполняются структурированными запросами PostgreSQL (`USER_JOURNEYS.md`, UJ-029, UJ-030);
- при необходимости полнотекстового поиска (например, поиск по тексту заметок или инсайтов) используется встроенный полнотекстовый поиск PostgreSQL — `tsvector`/`tsquery` с GIN-индексами (раздел 47);
- ни одно утверждённое требование MVP (`FUNCTIONAL_REQUIREMENTS.md`) не предполагает semantic retrieval;
- LLM-вызовы (`llm_gateway`, `ADR-0002`) получают контекст, явно собранный application layer, а не через retrieval-механизм;
- отсутствие vector search не блокирует ни один сценарий MVP.

## 19. Условия активации vector search

Vector search допускается только при одновременном наличии:

1. утверждённого пользовательского сценария, требующего semantic retrieval;
2. определения корпуса данных (что именно индексируется);
3. доказательства, что structured/full-text search недостаточен для этого сценария;
4. выбранной embedding-модели через отдельное решение (не этим ADR);
5. правил chunking (раздел 25);
6. правил metadata (раздел 26);
7. правил provenance (раздел 30);
8. правил доступа и удаления (раздел 31);
9. offline evaluation dataset;
10. baseline без embeddings (structured + full-text);
11. метрик качества retrieval (раздел 28, без фиксированных числовых порогов в этом ADR);
12. утверждённого бюджета (раздел 32);
13. оценки объёма vectors;
14. оценки времени обновления embeddings;
15. плана переиндексации;
16. плана смены embedding-модели;
17. backup/restore плана (раздел 34);
18. явного решения Product Owner об активации.

До выполнения **всех** перечисленных условий vector search не реализуется.

## 20. Первый вариант реализации

При подтверждённой необходимости (раздел 19) первым и единственным предварительно рекомендованным вариантом реализации является **pgvector внутри уже утверждённого PostgreSQL** (`ADR-0004`):

- устанавливается как обычное PostgreSQL extension через `CREATE EXTENSION` (раздел 47) — требует прав, соответствующих официальной модели extensions PostgreSQL;
- поддерживает несколько типов векторов и как минимум шесть distance-функций (L2, inner product, cosine, L1, Hamming, Jaccard — раздел 47);
- exact nearest-neighbor search доступен по умолчанию (последовательное сканирование, полный recall);
- approximate search доступен через HNSW (выше точность/скорость запроса, дороже построение и память) или IVFFlat (быстрее построение, ниже память, ниже эффективность запроса) — официально документированный компромисс (раздел 47);
- фильтрация поддерживается через обычные `WHERE`-условия; официальная документация отмечает «iterative scanning» для случаев, когда фильтр отсекает слишком много кандидатов approximate-индекса (раздел 47);
- обновление embeddings выполняется стандартными SQL-операциями (`INSERT`/`UPDATE`/`DELETE`/`ON CONFLICT`, раздел 47);
- backup/restore входит в общий lifecycle PostgreSQL (раздел 34).

Точная версия pgvector, конкретный индекс и его параметры не выбираются настоящим ADR — определяются на шаге плана внедрения (раздел 40) после измерений.

## 21. Условия выделения отдельной vector database

Отдельная Qdrant-инфраструктура (или аналог) рассматривается **отдельным ADR**, если измерения показывают одно или несколько из:

- объём vectors создаёт неприемлемую нагрузку на primary PostgreSQL;
- построение/перестроение vector-индекса мешает OLTP-нагрузке (`ADR-0004`, раздел 29);
- требуются независимые ресурсы и независимое масштабирование vector-компонента отдельно от транзакционной нагрузки (официально сильная сторона Qdrant — шардирование и репликация, раздел 47);
- filtering и retrieval не достигают утверждённых требований на pgvector;
- rebuild индексов мешает production-доступности;
- необходимы специализированные hybrid/multivector возможности, официально предоставляемые Qdrant «из коробки» (Query API, RRF/DBSF fusion, раздел 47), которые нецелесообразно воспроизводить вручную поверх pgvector;
- backup lifecycle vectors должен быть независим от backup lifecycle транзакционных данных;
- latency pgvector не достигает утверждённых NFR после измерений;
- эксплуатационная польза измеримо превышает стоимость эксплуатации второго сервиса (раздел 32).

Сам факт существования embeddings **не является** основанием для отдельной БД.

## 22. Категории данных

Потенциально могут индексироваться (только после выполнения условий раздела 19):

- пользовательские заметки;
- дневник сделок;
- сохранённые инсайты;
- уроки и ошибки (Future);
- новостные материалы;
- экономические события;
- текстовые описания инструментов;
- проверенные аналитические фрагменты.

**Не индексируются автоматически:**

- секреты;
- API keys;
- credentials;
- необработанные персональные данные;
- весь raw provider payload;
- каждый tick;
- Order Book;
- технические логи;
- audit trail целиком;
- любые данные без утверждённого сценария использования (раздел 19, пункт 1).

## 23. Embedding pipeline

- embeddings создаются только backend worker/application pipeline (`TECHNOLOGY_EVALUATION.md`, раздел 8) — не FastAPI route handler (`ADR-0002`, раздел 17) и не frontend (`ADR-0003`, раздел 17);
- LLM gateway не владеет хранением embeddings (`MODULE_BOUNDARIES.md`, модуль `llm_gateway` — не владеет фактами);
- embedding-вызов отделён от открытой DB-транзакции (`ADR-0004`, раздел 19 — внешние вызовы не выполняются внутри открытой транзакции);
- исходный объект сохраняется независимо от успеха embedding-вызова;
- embedding может быть пересоздан из исходного текста при наличии модели и правил (embeddings — производные данные);
- сбой embedding не уничтожает исходные данные (`FAILURE_MODEL.md`, раздел 13, по аналогии);
- pipeline идемпотентен (`ENGINEERING_PRINCIPLES.md`, пункт 16);
- retry только для классифицированных временных ошибок (`FAILURE_MODEL.md`, раздел 4);
- rate limits и стоимость наблюдаемы (`ENGINEERING_PRINCIPLES.md`, пункты 53–55);
- batch processing не блокирует web request;
- конкретный embedding provider выбирается отдельным решением, не этим ADR.

## 24. Версионирование embeddings

Каждый embedding связывается с:

- source object ID;
- source object version;
- embedding model/provider identifier;
- embedding model version;
- dimensions;
- distance metric, если применимо;
- preprocessing version;
- chunking version (раздел 25);
- language;
- creation timestamp;
- pipeline version;
- content checksum.

Правила:

- embeddings разных несовместимых моделей **не смешиваются** в одном поиске;
- смена embedding-модели создаёт новую версию, а не перезаписывает старую;
- старый индекс не удаляется до проверки нового (staged migration);
- dual-read или staged migration между версиями проектируется отдельно при активации;
- embeddings являются производными данными — их можно перестроить из исходного текста при наличии модели и зафиксированных правил (раздел 23).

## 25. Chunking

- chunking не выполняется автоматически «по N символов» без оценки;
- предпочтительны смысловые границы текста;
- оригинальный документ не теряется — chunk связан с source (раздел 30);
- overlapping chunks увеличивают стоимость и дублирование — вводятся осознанно;
- слишком большие chunks ухудшают точность retrieval;
- слишком маленькие chunks теряют контекст;
- таблицы, даты, числа и финансовые обозначения требуют осторожной обработки (риск потери смысла при разбиении);
- русский и английский тексты учитываются (`PRODUCT_SCOPE.md`, раздел 8 — русский интерфейс, но источники могут быть на английском, `FUNCTIONAL_REQUIREMENTS.md`, FR-060);
- конкретная стратегия chunking выбирается по результатам offline evaluation dataset (раздел 19, пункт 9), не в этом ADR.

## 26. Metadata и полнотекстовый/hybrid search

### Metadata и filtering

Обязательные metadata-фильтры, где применимо:

- user;
- market;
- instrument;
- language;
- source;
- document type;
- timestamp range;
- visibility;
- status;
- embedding version.

**Vector similarity не заменяет authorization filter.** Фильтрация по правам пользователя выполняется до выдачи данных, а не полагается на релевантность similarity-скора.

### Полнотекстовый и hybrid search

- полнотекстовый поиск использует встроенные возможности PostgreSQL — `tsvector`/`tsquery`, официально предпочтительны GIN-индексы (выше эффективность запроса; GiST — lossy, требует recheck строк, раздел 47);
- hybrid search (комбинация lexical + vector + metadata filtering) **не вводится автоматически** — при активации Фазы 2 (раздел 17) hybrid-логика на уровне pgvector реализуется вручную поверх FTS + pgvector, конкретный механизм не выбирается этим ADR;
- если в будущем будет обоснован переход к отдельной vector database (раздел 21), официально встроенные hybrid-возможности Qdrant (Query API, RRF/DBSF, раздел 47) рассматриваются как один из факторов такого решения, но не активируются этим ADR.

## 27. Качество retrieval

- качество не оценивается субъективным впечатлением;
- создаётся offline evaluation dataset до активации (раздел 19, пункт 9);
- используются утверждённые метрики (без фиксированных числовых порогов в этом ADR);
- baseline: structured search и full-text search (раздел 18);
- vector search должен доказать измеримый прирост относительно baseline, а не приниматься по умолчанию;
- approximate index (HNSW/IVFFlat) сравнивается с exact search baseline (раздел 47 — recall approximate-индексов официально зависит от параметров и не гарантирован);
- recall/precision/latency измеряются, а не предполагаются;
- пользовательская оценка не является единственной метрикой;
- retrieval result **не считается фактом** (раздел 29);
- отсутствие релевантного результата допускается и явно отражается — не подставляется нерелевантный контекст только для заполнения prompt (`ENGINEERING_PRINCIPLES.md`, пункт 60, по аналогии).

Конкретные числовые пороги recall/precision/latency не утверждаются этим ADR.

## 28. Влияние на нефункциональные характеристики

Отдельный раздел учтён внутри разделов 30–34; сводно:

- **безопасность:** доступ к vectors ограничивается так же, как доступ к source (раздел 31); отдельный сервис (Фаза 3) увеличивает поверхность атаки.
- **надёжность:** сбой embedding pipeline не уничтожает исходные данные (раздел 23); рассинхронизация PostgreSQL/Qdrant — ожидаемый класс отказа при Фазе 3 (раздел 30).
- **масштабируемость:** Фаза 2 масштабируется вместе с PostgreSQL; Фаза 3 предоставляет независимое масштабирование ценой дополнительной сложности (раздел 16, критерии 20, 33).
- **производительность:** архитектурно ожидается управляемой при измеренном подходе (exact baseline → approximate только после измерений); числовые NFR не утверждены и не измеряются в рамках настоящего ADR.
- **стоимость:** контролируется поэтапной активацией — embeddings не создаются «на будущее» (раздел 32).
- **данные:** provenance retrieval сохраняется (раздел 30); embeddings — производные, восстановимые данные (раздел 24).

## 29. Связь с LLM

- vector store **не является** памятью LLM;
- vector result **не является** источником истины (`ENGINEERING_PRINCIPLES.md`, пункт 57);
- LLM получает документы с provenance (раздел 30), а не «сырые» векторные совпадения без контекста;
- retrieved context отделяется от user prompt и system instructions;
- prompt injection из документов учитывается — retrieved text считается недоверенным (аналогично внешним данным, `ENGINEERING_PRINCIPLES.md`, пункт 57);
- LLM не определяет authorization;
- LLM не получает документы другого пользователя (раздел 26 — фильтрация по правам выполняется до передачи в LLM);
- citations/reference сохраняются вместе с ответом;
- отсутствие retrieval **не разрешает** LLM домысливать факты (`ENGINEERING_PRINCIPLES.md`, пункт 57, 60);
- vector search может работать без generation (например, для отображения похожих прошлых инсайтов пользователю напрямую);
- generation может работать без vector search для всех уже утверждённых сценариев MVP (раздел 18).

## 30. Provenance

Для результата поиска сохраняются или доступны:

- идентификатор исходного объекта;
- версия исходного объекта;
- source;
- chunk (раздел 25);
- embedding version (раздел 24);
- similarity score;
- применённые filters (раздел 26);
- query representation/version;
- retrieval timestamp;
- search strategy (structured/full-text/vector/hybrid);
- index type/version, если применимо.

Сохранённый инсайт, если он использует retrieval, должен знать, какой retrieval context был использован при его формировании (`ENGINEERING_PRINCIPLES.md`, пункт 29 — воспроизводимость аналитического вывода).

## 31. Безопасность

- embeddings могут раскрывать характеристики исходных данных даже без прямого доступа к исходному тексту — учитывается при классификации данных;
- доступ к vectors ограничивается так же строго, как доступ к исходным (source) данным;
- удаление пользовательских данных включает удаление или перестроение соответствующих vectors, а не только исходной записи;
- metadata filtering **не заменяет** authorization (раздел 26);
- отдельная vector database (Фаза 3) увеличивает attack surface — дополнительный сетевой сервис, отдельные credentials (раздел 47 — Qdrant поддерживает HTTP/gRPC интерфейсы);
- credentials не попадают в репозиторий (`ENGINEERING_PRINCIPLES.md`, пункт 6);
- сетевой доступ к любому vector-компоненту ограничивается;
- embedding provider не получает лишний текст сверх необходимого для конкретного запроса;
- чувствительные данные классифицируются перед решением об индексации (раздел 22 — что не индексируется автоматически);
- prompt injection и «отравленные» (poisoned) документы учитываются как класс риска (раздел 29);
- backup vectors защищается на том же уровне, что и backup исходных данных (раздел 34);
- multi-user isolation проектируется до расширения числа пользователей (`PRODUCT_SCOPE.md`, раздел 6 — multi-tenant не утверждён).

## 32. Стоимость

Учитываемые категории затрат при активации (без фиксированных сумм — соответствует `TECHNOLOGY_EVALUATION.md`, раздел 16, «не добавлять выдуманные суммы»):

- embedding API (стоимость по токенам/запросам);
- переиндексация при смене модели;
- хранение vectors (дополнительное место на диске PostgreSQL или отдельного сервиса);
- построение и хранение индексов (HNSW официально требует больше памяти при построении, раздел 47);
- RAM и CPU;
- backup;
- сеть (существенно для Фазы 3);
- отдельный сервис (Фаза 3) — собственные вычислительные ресурсы;
- мониторинг;
- обновление модели;
- повторная генерация embeddings при изменении pipeline.

**Embeddings не создаются «на будущее»** — стоимость возникает только после явной активации (раздел 19).

## 33. Производительность

- построение и обновление vector-индекса имеет измеримую стоимость по времени и памяти — HNSW официально дороже при построении и в потреблении памяти, но эффективнее при запросе; IVFFlat — обратный компромисс (раздел 47);
- exact search используется как baseline и ориентир качества до внедрения approximate-индекса;
- approximate search (HNSW/IVFFlat) вводится только после того, как объём данных и измеренная latency exact-поиска обосновывают это;
- влияние построения/перестроения индекса на OLTP-нагрузку PostgreSQL оценивается перед активацией (`ADR-0004`, раздел 29);
- числовые пороги latency/recall не устанавливаются этим ADR — определяются в рамках критериев качества (раздел 27) при активации;
- при Фазе 3 сетевая задержка между backend и отдельным vector-сервисом учитывается как дополнительный компонент latency.

## 34. Backup и восстановление

### pgvector (Фаза 2)

- vectors находятся в PostgreSQL и входят в его уже утверждённый backup lifecycle (`ADR-0004`, раздел 27);
- extension должно присутствовать на сервере восстановления для корректного восстановления объектов, зависящих от типов pgvector;
- восстановление проверяется в рамках уже утверждённой практики restore drills (`ADR-0004`, раздел 27);
- embeddings можно перестроить из исходного текста, но это не заменяет backup metadata и связей provenance (раздел 30) — восстановление backup остаётся основным путём.

### Отдельная vector database (Фаза 3)

- требует собственного backup/restore процесса (например, snapshots, раздел 47);
- требует синхронизации состояния с PostgreSQL после восстановления;
- рассинхронизация между PostgreSQL и vector database является ожидаемым классом отказа, а не исключительной ситуацией;
- PostgreSQL остаётся source of truth в любом случае;
- vector storage может быть перестроено из исходных данных при необходимости, если embedding pipeline и версии сохранены (раздел 24).

## 35. Положительные последствия

- MVP не несёт стоимости и сложности vector-инфраструктуры, которая ему не нужна;
- поэтапная активация снижает риск преждевременной инвестиции (`ENGINEERING_PRINCIPLES.md`, пункт 67);
- pgvector как первый кандидат сохраняет единую транзакционную границу и единый backup lifecycle с уже утверждённым PostgreSQL (`ADR-0004`);
- exact search как обязательный baseline снижает риск принятия approximate-результатов без понимания их recall;
- явные условия перехода к Фазе 3 предотвращают преждевременное внедрение отдельного сервиса;
- provenance и версионирование embeddings заложены с самого начала, а не добавляются постфактум;
- решение оставляет понятный путь роста (pgvector → специализированное хранилище) без блокировки на одном варианте.

## 36. Отрицательные последствия

- отсутствие vector search в MVP означает, что semantic-сценарии (если они появятся раньше, чем ожидалось) потребуют дополнительного цикла активации, а не немедленной реализации;
- pgvector — младшее по времени существования расширение относительно PostgreSQL ядра — совместимость и зрелость конкретной сборки требует проверки при внедрении;
- approximate search официально не гарантирует recall — неправильная настройка HNSW/IVFFlat может дать плохие результаты незаметно для пользователя (раздел 47);
- chunking и версионирование embeddings добавляют операционную сложность при активации;
- переход к Фазе 3 (если потребуется) добавляет отдельный сервис, сетевую границу и риск рассинхронизации;
- многоэтапная модель принятия решения требует дисциплины — риск, что кто-то в будущем активирует vector search без прохождения условий раздела 19.

## 37. Риски

1. Vector search реализован без доказанной пользовательской пользы.
2. Embeddings создаются для всех данных без разбора.
3. Стоимость embedding API растёт неконтролируемо.
4. Смена embedding-модели ломает совместимость.
5. Несовместимые dimensions между версиями.
6. Смешивание версий embeddings в одном поиске.
7. Плохой chunking снижает качество retrieval.
8. Нерелевантный retrieval передаётся в LLM.
9. Approximate recall недостаточен без ведома пользователя.
10. Stale embeddings (не обновлены после изменения source).
11. Удалён source, но vector остался.
12. Vector потерян, source сохранён (несогласованность).
13. Source потерян, vector остался.
14. Нарушение user isolation в результатах поиска.
15. Prompt injection через retrieved-документы.
16. Poisoned content в источниках, используемых для embeddings.
17. Отсутствие provenance у результата поиска.
18. Vector similarity result принят за подтверждённый факт.
19. PostgreSQL перегружен vector-нагрузкой.
20. HNSW rebuild мешает OLTP-доступности.
21. Индекс занимает избыточный объём RAM.
22. Отдельный Qdrant усложняет эксплуатацию сверх пользы.
23. Рассинхронизация PostgreSQL/Qdrant (Фаза 3).
24. Backup vector-компонента не восстанавливается.
25. Provider lock-in по embedding API.
26. Отсутствие evaluation dataset перед активацией.
27. Метрики качества не определены до активации.
28. Full-text baseline не проверен перед внедрением vector search.
29. Embedding pipeline блокирует web request.
30. Повторная индексация дублирует записи.

## 38. Меры снижения рисков

1. Без доказанной пользы → условия активации раздела 19 обязательны и все выполняются одновременно.
2. Embeddings для всех данных → раздел 22 явно ограничивает категории данных и запрещает индексацию по умолчанию.
3. Рост стоимости API → стоимость наблюдаема (раздел 23, 32), бюджет утверждается до активации (раздел 19, пункт 12).
4. Смена модели ломает совместимость → версии embeddings не смешиваются (раздел 24).
5. Несовместимые dimensions → dimensions фиксируются как часть версии embedding (раздел 24).
6. Смешивание версий → поиск учитывает embedding version как обязательный metadata-фильтр (раздел 26).
7. Плохой chunking → стратегия выбирается по evaluation dataset, не произвольно (раздел 25).
8. Нерелевантный retrieval в LLM → retrieval должен доказать прирост над baseline (раздел 27); retrieved text считается недоверенным (раздел 29).
9. Недостаточный approximate recall → exact search — обязательный baseline для сравнения (раздел 20, 27, 33).
10. Stale embeddings → embedding pipeline идемпотентен и привязан к source version (раздел 23, 24).
11. Source удалён, vector остался → удаление данных включает vector (раздел 31).
12. Vector потерян, source цел → embeddings — производные, восстановимы из source (раздел 24).
13. Source потерян, vector остался → provenance и backup поддерживают восстановление source как приоритет (раздел 30, 34).
14. Нарушение user isolation → metadata-фильтр user обязателен, vector similarity не заменяет authorization (раздел 26, 31).
15. Prompt injection → retrieved text считается недоверенным, отделяется от system instructions (раздел 29).
16. Poisoned content → источники классифицируются, provenance сохраняется для аудита (раздел 22, 30).
17. Отсутствие provenance → provenance — обязательный элемент результата поиска (раздел 30).
18. Vector result принят за факт → явное разделение AI-интерпретации и фактов (раздел 29, `ENGINEERING_PRINCIPLES.md`, пункт 59).
19. Перегрузка PostgreSQL vector-нагрузкой → влияние на OLTP оценивается перед активацией (раздел 21, 33); переход к Фазе 3 предусмотрен именно для этого случая.
20. HNSW rebuild мешает OLTP → построение/перестроение индекса измеряется и планируется отдельно (раздел 33).
21. Избыточный RAM индекса → выбор HNSW/IVFFlat — после измерений, с учётом официального компромисса памяти (раздел 20, 47).
22. Qdrant усложняет сверх пользы → активация Фазы 3 требует доказанных условий раздела 21, а не предположений.
23. Рассинхронизация PostgreSQL/Qdrant → признаётся ожидаемым классом отказа, PostgreSQL остаётся source of truth (раздел 34).
24. Backup vector-компонента не восстанавливается → restore drills для vector-компонента так же обязательны, как для PostgreSQL (раздел 34).
25. Provider lock-in → embedding provider выбирается отдельным решением с учётом обратимости (раздел 23).
26. Отсутствие evaluation dataset → обязательное условие активации (раздел 19, пункт 9).
27. Метрики не определены → обязательное условие активации (раздел 19, пункт 11).
28. Full-text baseline не проверен → обязателен как часть плана внедрения перед активацией vector search (раздел 40).
29. Pipeline блокирует web request → embedding-вызов выполняется вне request-цикла, в worker (раздел 23).
30. Повторная индексация дублирует записи → идемпотентность pipeline на основе content checksum (раздел 23, 24).

## 39. Влияние на NFR

См. раздел 28 (сведено в единый раздел с производительностью/безопасностью/масштабируемостью — по требованию структуры документа раздел 39 подтверждает отсутствие дополнительных, не упомянутых выше эффектов): числовые NFR, связанные с retrieval (latency, recall), не утверждены `NON_FUNCTIONAL_REQUIREMENTS.md` и не устанавливаются этим ADR — они будут определены как часть условий активации (раздел 19, пункт 11) и измерены при внедрении (раздел 27, 33).

## 41. План отката

**Если pgvector включён (Фаза 2):**

- прекратить создание новых embeddings;
- сохранить исходные данные без изменений;
- отключить semantic retrieval через feature flag;
- удалить зависимость от embeddings из read path приложения;
- сохранить или удалить существующие embeddings согласно принятой retention-политике;
- PostgreSQL structured/full-text search остаётся доступным без каких-либо изменений.

**Если используется отдельная vector database (Фаза 3):**

- переключить retrieval на baseline (Фаза 1/2);
- PostgreSQL остаётся source of truth на всём протяжении отката;
- прекратить синхронизацию с отдельным сервисом;
- экспортировать необходимые metadata перед выключением сервиса;
- удалить сервис только после подтверждения, что откат не требует отмены;
- новый ADR фиксирует фактическую замену/понижение стратегии, обновляя статус ADR-0005 при необходимости (`ADR_PROCESS.md`, раздел 18).

## 42. Критерии проверки решения

После будущей реализации (без создания этих проверок в рамках настоящей задачи):

1. MVP работает полностью без vector-инфраструктуры;
2. structured search работает корректно;
3. full-text baseline измерен, если используется;
4. semantic user journey утверждён перед активацией;
5. evaluation dataset существует до активации;
6. метрики качества retrieval определены до активации;
7. vector search доказал измеримую пользу относительно baseline;
8. embeddings версионированы (раздел 24);
9. source/chunk/provenance связаны для каждого результата поиска;
10. user isolation в retrieval проверена;
11. удаление source корректно обрабатывает связанный vector;
12. сбой embedding pipeline не приводит к потере source;
13. exact search baseline доступен наряду с approximate;
14. approximate search сравнён с exact на измерениях;
15. backup/restore vector-компонента проверен;
16. стоимость embedding/vector-инфраструктуры наблюдаема;
17. web request не блокируется batch-генерацией embeddings;
18. LLM не принимает vector result за подтверждённый факт;
19. документы другого пользователя недоступны через retrieval;
20. semantic retrieval можно отключить через feature flag;
21. Qdrant (или другая отдельная vector DB) отсутствует без отдельного принятого ADR.

## 43. Условия пересмотра

ADR-0005 пересматривается, если:

- утверждён конкретный semantic-search user journey, требующий выполнения плана внедрения (раздел 40);
- PostgreSQL full-text search признан недостаточным для конкретного утверждённого сценария;
- pgvector не достигает измеримых требований после реализации Фазы 2;
- vector-нагрузка (построение индекса, объём) мешает OLTP-производительности PostgreSQL;
- переход к Фазе 3 (Qdrant) становится обоснованным по условиям раздела 21;
- embedding provider/модель меняется существенным образом;
- требования приватности/compliance запрещают использование внешнего embedding API;
- появляется требование offline-only работы, несовместимое с внешним embedding provider;
- объём vectors существенно растёт сверх первоначальных оценок;
- требуется multivector или специализированный hybrid retrieval, недоступный в разумной форме на pgvector;
- стоимость vector-инфраструктуры превышает утверждённый бюджет;
- vector search после внедрения не показывает измеримой пользы относительно baseline;
- PostgreSQL перестаёт быть основной transactional system of record (потребовало бы пересмотра `ADR-0004`, что каскадно затронуло бы и этот ADR).

## 44. Открытые вопросы

- конкретный embedding provider и модель не выбираются этим ADR — предмет отдельного решения при выполнении условий активации (раздел 19, пункт 4);
- конкретные числовые пороги latency/recall/precision не устанавливаются — определяются в момент активации на основании измерений (раздел 27, 33);
- конкретная версия pgvector и её совместимость с выбранной версией PostgreSQL (`ADR-0004`) — определяется на шаге плана внедрения (раздел 40, шаг 15);
- официальная кросс-платформенная поддержка pgvector на Windows для локальной разработки не подтверждена в рамках этого исследования — требует проверки при внедрении (раздел 16, критерий 6);
- итоговый механизм hybrid search (структурированный + lexical + vector) на pgvector не определён — потребует отдельного проектирования при активации (раздел 26);
- бюджет embedding/vector-инфраструктуры не утверждён (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-028).

## 45. Решение Product Owner

Product Owner утверждает трёхфазную стратегию развития поиска платформы: Фаза 1 — PostgreSQL structured/full-text search в MVP без embeddings; Фаза 2 — pgvector как первый кандидат для semantic retrieval только после подтверждения необходимости и выполнения условий активации (раздел 19); Фаза 3 — отдельная vector database рассматривается только отдельным ADR при доказанной недостаточности pgvector (раздел 21).

Утверждение относится к стратегии и порядку принятия решений, а не к конкретной реализации. Embedding provider/model, конкретная версия pgvector, параметры индексов и отдельная vector database (если потребуется) выбираются отдельными решениями при выполнении условий активации, определённых настоящим ADR.

## 47. Источники исследования

Исследование выполнено 2026-08-05 исключительно по официальным первичным источникам (postgresql.org, github.com/pgvector/pgvector, qdrant.tech/documentation), без использования блогов, Reddit, Medium, рейтингов, неофициальных benchmark, маркетинговых сравнительных статей и пользовательских issues как нормативного источника решения.

**PostgreSQL:**
- [postgresql.org/docs/current/textsearch-indexes.html](https://www.postgresql.org/docs/current/textsearch-indexes.html) — официально: GIN и GiST — два типа индексов полнотекстового поиска; GIN официально предпочтителен для производительности запросов (инвертированный индекс, эффективен для многословных запросов); GiST — lossy-индекс, требующий recheck строк, что снижает производительность при случайном доступе к таблице.
- [postgresql.org/docs/current/datatype-textsearch.html](https://www.postgresql.org/docs/current/datatype-textsearch.html) — официально: `tsvector` — отсортированный список лексем (нормализуется через `to_tsvector()`), поддерживает позиции слов и веса (A/B/C/D); `tsquery` — булево выражение над лексемами с операторами `&`/`|`/`!`/`<->`.
- [postgresql.org/docs/current/contrib.html](https://www.postgresql.org/docs/current/contrib.html) и [postgresql.org/docs/current/sql-createextension.html](https://www.postgresql.org/docs/current/sql-createextension.html) — официально: расширения (включая сторонние, такие как pgvector) устанавливаются через `CREATE EXTENSION`; обычно требуют прав суперпользователя (кроме «доверенных» расширений); файлы расширения должны быть установлены на сервере; стандартное поведение `pg_dump` включает команды `CREATE EXTENSION` в дамп, обеспечивая восстановление расширения вместе с БД.

**pgvector:**
- [github.com/pgvector/pgvector](https://github.com/pgvector/pgvector) (официальный README проекта) — официально: типы `vector`/`halfvec`/`bit`/`sparsevec`; шесть distance-функций (L2, inner product, cosine, L1, Hamming, Jaccard); exact nearest-neighbor search через последовательное сканирование даёт полный recall; approximate search — HNSW (выше точность/скорость запроса, дороже построение и память) и IVFFlat (быстрее построение, ниже память, ниже эффективность запроса); фильтрация через `WHERE`, включая iterative scanning для сильно фильтрующих запросов к approximate-индексу; обновление — стандартные `INSERT`/`UPDATE`/`DELETE`/`ON CONFLICT`; официально явно указано, что approximate-индексы дают иные результаты запросов относительно точного поиска, а recall зависит от параметров (`hnsw.ef_search`, `ivfflat.probes`); NULL- и нулевые (для cosine) векторы не индексируются.

**Qdrant:**
- [qdrant.tech/documentation/overview](https://qdrant.tech/documentation/overview/) — официально: специализированная векторная СУБД, клиент-серверная архитектура (HTTP/gRPC, официальные клиенты для нескольких языков), поддержка dense и sparse векторов, hybrid retrieval, шардирование и репликация.
- [qdrant.tech/documentation/concepts/indexing](https://qdrant.tech/documentation/concepts/indexing/) — официально: HNSW как основной векторный индекс; payload indexes для ускорения фильтрации; «filterable HNSW» — расширение графа HNSW дополнительными рёбрами на основе индексированных payload-значений; рекомендуется создавать payload-индексы до загрузки данных.
- [qdrant.tech/documentation/concepts/filtering](https://qdrant.tech/documentation/concepts/filtering/) — официально: булевы условия (`must`/`should`/`must_not`) применяются к payload наряду с векторным поиском; рекомендуется создавать payload-индексы для полей фильтрации до загрузки данных.
- [qdrant.tech/documentation/concepts/hybrid-queries](https://qdrant.tech/documentation/concepts/hybrid-queries/) — официально: Query API с `prefetch`, методы слияния Reciprocal Rank Fusion и Distribution-Based Score Fusion, многоступенчатые запросы (сначала дешёвое приближение, затем точное переранжирование).
- [qdrant.tech/documentation/concepts/storage](https://qdrant.tech/documentation/concepts/storage/) — официально: сегментированное хранение, memory-mapped файлы векторов с режимами `cached`/`cold`, Write-Ahead Log для восстановления после сбоя, отдельный от PostgreSQL lifecycle снятия снапшотов.

Выводы, использованные в разделах 15–21, 26–27, 33–34 настоящего ADR, основаны на перечисленных источниках; длинные цитаты в текст ADR намеренно не включены. Пользовательские GitHub issues не использовались как нормативный источник ни для одного вывода этого документа.
