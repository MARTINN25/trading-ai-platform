## 11. Контекст

`ADR-0001` (утверждён) зафиксировал CPython 3.14 как backend runtime. `ADR-0002` (утверждён) зафиксировал FastAPI как внешний HTTP/ASGI adapter, явно запретив route handlers обращаться к БД напрямую и закрепив, что FastAPI не является persistence layer. `ADR-0003` (утверждён) зафиксировал frontend, обращающийся исключительно к FastAPI Application API — не к БД. Backend построен как модульный монолит с отдельным worker-процессом для критичных фоновых задач (`ADR-0001`, `TECHNOLOGY_EVALUATION.md`, раздел 8) — то есть несколько процессов (web + worker, потенциально несколько web workers) обращаются к одному хранилищу.

Логическая архитектура (`MODULE_BOUNDARIES.md`) требует хранения: пользователей и настроек (`identity`, `settings`); инструментов и рыночных контекстов (`market`, `instruments`); метаданных источников (`sources`); нормализованных фактов (`normalization`, `data_quality`); provenance (`provenance`); инсайтов (`insights`); версий входного контекста инсайтов (`ENGINEERING_PRINCIPLES.md`, пункт 29); пользовательских оценок и результатов проверки прогнозов (`evaluations`); уроков и ошибок (Future, `FUNCTIONAL_REQUIREMENTS.md`, область 29); дневника сделок (`journal`); заметок (`notes`); алертов (`alerts`); состояния фоновых заданий (`jobs`); аудита критичных действий (`audit`); идемпотентности операций (`ENGINEERING_PRINCIPLES.md`, пункт 16).

Основное хранилище не обязано содержать абсолютно все сырые high-frequency market data навсегда (раздел 24).

`TECHNOLOGY_EVALUATION.md` (раздел 6, утверждён) зафиксировал предварительную, необязывающую рекомендацию — PostgreSQL — и явно указал, что выбор конкретной СУБД, её границ и правил использования является предметом настоящего ADR.

Дата проверки технологических данных, использованных в настоящем ADR: 2026-08-05 (см. раздел 43 «Источники исследования»).

## 12. Проблема

Какую СУБД использовать в качестве основного транзакционного хранилища платформы, чтобы решение соответствовало утверждённой логической архитектуре и модульным границам, поддерживало несколько одновременно работающих процессов (web + worker) в рамках модульного монолита на одном сервере, обеспечивало транзакционную целостность для инсайтов/оценок/аудита/идемпотентности, поддерживало неизменяемую историю (provenance, инсайты) и не требовало от единственного разработчика чрезмерной эксплуатационной сложности.

Настоящий ADR не выбирает: ORM, migration library, Python database driver, connection pool, managed PostgreSQL provider, cloud, конкретный сервер, TimescaleDB, отдельную векторную СУБД, pgvector, Redis, Kafka, объектное хранилище, стратегию хранения всех high-frequency тиков, точную схему таблиц.

## 13. Ограничения

- решение принимается до появления схемы и кода — миграционная стоимость на этом этапе минимальна;
- backend — модульный монолит с несколькими процессами (web + worker), обращающимися к одному хранилищу (`ADR-0001`, `TECHNOLOGY_EVALUATION.md`, раздел 8) — хранилище должно поддерживать многопроцессный конкурентный доступ, а не только один процесс;
- MVP разворачивается как один сервер (`PRODUCT_SCOPE.md`, раздел 22 — без Kubernetes/распределённой инфраструктуры);
- один разработчик отвечает за эксплуатацию хранилища — простота и предсказуемость важнее числа неиспользуемых возможностей;
- решение не должно предполагать выбор ORM/driver/migration tool/connection pool/managed provider/TimescaleDB/pgvector — эти вопросы выходят за рамки задачи;
- инсайты и provenance должны оставаться неизменяемыми после сохранения (`LOGICAL_ARCHITECTURE.md`, раздел 14; `ADR-0002`, раздел 30, по аналогии) — хранилище должно естественно поддерживать этот инвариант;
- официальные источники на дату исследования (раздел 43) явно указывают, что PostgreSQL 19 находится в статусе beta — beta-версия не выбирается для production (раздел 16).

## 15. Рассмотренные варианты

Рассмотрены ровно три варианта:

- **Вариант A — PostgreSQL**
- **Вариант B — SQLite**
- **Вариант C — MongoDB**

Качественные оценки ниже — архитектурная оценка на основании официальной документации (раздел 43), а не результат benchmark; неподтверждённые абсолюты не используются.

### Сравнительная таблица

| № | Критерий | A. PostgreSQL | B. SQLite | C. MongoDB |
|---|---|---|---|---|
| 1 | Соответствие логической архитектуре | архитектурная оценка: подходит — реляционная модель естественно отражает связи модулей (`insights`→`evaluations`, `journal`→`insights`, `provenance`) | архитектурная оценка: транзакционная модель подходит, но многопроцессный доступ — архитектурное ограничение (раздел 25) | архитектурная оценка: документная модель требует пересмотра части связей как встраиваемых/денормализованных структур |
| 2 | Транзакционность | полная поддержка ACID-транзакций на уровне SQL (раздел 43) | поддерживает ACID-транзакции для одного файла БД (раздел 43) | поддерживает multi-document ACID-транзакции на replica set/sharded cluster, но официально описаны как более дорогие относительно записи одного документа, и официально не рекомендуются как замена схемному проектированию (раздел 43) |
| 3 | ACID | официально полная поддержка (раздел 43) | официально полная поддержка в границах одного файла (раздел 43) | официально поддерживается для multi-document операций при соблюдении конфигурации (write/read concern), раздел 43 |
| 4 | MVCC | официально MVCC — читатели не блокируют писателей и наоборот, даже на уровне Serializable через SSI (раздел 43) | не MVCC в классическом смысле — используется блокировочная модель файла; WAL-режим даёт readers/writers без взаимной блокировки, но только один writer одновременно (раздел 43) | использует WiredTiger storage engine с MVCC на уровне документа (архитектурная оценка на основании официальной архитектуры хранения, не измерено в рамках ADR) |
| 5 | Уровни изоляции | Read Committed (по умолчанию), Repeatable Read, Serializable — официально документированы, с чёткими правилами retry (раздел 43) | сериализуемость по умолчанию в рамках одной транзакции (snapshot-изоляция чтения), явные SQL-уровни isolation ANSI не предоставляются как отдельная настраиваемая шкала (архитектурная оценка) | read concern/write concern настраиваются отдельно (local/majority/snapshot) — модель отличается от классических SQL isolation levels (раздел 43) |
| 6 | Ограничения и внешние ключи | полная поддержка FK, CHECK, UNIQUE, NOT NULL на уровне СУБД (общеизвестная реляционная модель, архитектурная оценка) | поддерживает FK/CHECK/UNIQUE, но enforcement FK исторически требует явного включения (`PRAGMA foreign_keys`) — архитектурная оценка, требует проверки при внедрении | не является реляционной СУБД — по умолчанию нет декларативных foreign keys между коллекциями; целостность связей обеспечивается на уровне приложения или schema validation (раздел 43) |
| 7 | Уникальность | UNIQUE constraints на уровне СУБД (архитектурная оценка) | UNIQUE constraints поддерживаются | unique index поддерживается на уровне коллекции (архитектурная оценка) |
| 8 | Идемпотентность | естественно поддерживается через UNIQUE/ON CONFLICT на уровне транзакции (архитектурная оценка) | поддерживается аналогично в границах одного writer'а | поддерживается через unique index, но конфликтная семантика в multi-document сценариях сложнее из-за модели транзакций (раздел 43) |
| 9 | Конкурентные записи (несколько процессов) | официально поддерживает много одновременных клиентов/процессов без ограничения на одного writer'а (общая архитектура клиент-серверной СУБД) | официально: «only one writer any instant in time»; несколько процессов, пишущих одновременно, сериализуются на уровне файла (раздел 43) | поддерживает конкурентные записи из нескольких процессов на уровне сервера (архитектурная оценка на основании клиент-серверной модели) |
| 10 | Несколько процессов | официально спроектирован как клиент-серверная СУБД для множества клиентских процессов (раздел 43) | официально не рекомендуется, когда «много клиентских программ отправляют SQL к одной БД по сети» — прямо описан как конкурент `fopen()`, а не клиент-серверных СУБД (раздел 43) | официально спроектирован как клиент-серверная СУБД (раздел 43) |
| 11 | Модульный монолит (web + worker процессы) | подходит — стандартный сценарий нескольких клиентов одного сервера БД | архитектурно проблематично для сценария web-процесс + отдельный worker-процесс, обращающихся к одной БД одновременно (раздел 43, критерий 9-10) | подходит — стандартный сценарий нескольких клиентов |
| 12 | Миграции схемы | зрелая экосистема миграций поверх декларативной схемы (архитектурная оценка, инструмент не выбирается этим ADR) | миграции возможны, но ALTER TABLE исторически ограничен относительно полной СУБД (архитектурная оценка, требует проверки при внедрении) | «миграции» в классическом смысле не требуются для гибкой схемы, но schema validation (если используется) версионируется отдельно (раздел 43) |
| 13 | Сложные связи | сильная сторона — JOIN, FK, нормализация (архитектурная оценка) | поддерживает SQL JOIN в границах одного файла | документная модель официально поощряет денормализацию/встраивание вместо сложных связей между коллекциями (раздел 43) |
| 14 | История инсайтов | реляционная модель с FK на provenance/evaluations естественно подходит | подходит технически, но ограничена сценарием одного writer'а | подходит при денормализованном дизайне документа инсайта |
| 15 | Provenance | связи через FK, неизменяемость обеспечивается на уровне приложения + constraints (раздел 20, 23) | аналогично технически возможно | возможно через встраивание, но целостность ссылок обеспечивается приложением, а не СУБД по умолчанию (раздел 43) |
| 16 | Аудит | подходит — append-only таблица с FK на инициатора действия | подходит технически | подходит — append-only коллекция |
| 17 | Дневник сделок | подходит — реляционная модель с опциональной FK на инсайт | подходит технически | подходит |
| 18 | Заметки | подходит | подходит | подходит, документная модель естественна для свободного текста с метаданными |
| 19 | JSON | JSONB — бинарный, индексируемый (GIN), официально рекомендован для большинства случаев вместо `json` (раздел 43) | встроенные JSON-функции (с версии 3.38.0), включая проприетарный формат JSONB, несовместимый с форматом PostgreSQL (раздел 43) | документ — нативно JSON-подобная модель (BSON) по построению |

| 35 | Vendor lock-in | низкий — open source, широкая экосистема драйверов/инструментов | низкий — файл-based, широко читаемый формат | умеренный — специфичная query-модель (aggregation pipeline), миграция на другую СУБД требует переосмысления схемы |
| 36 | Обратимость | высокая на этапе до появления данных; после появления — миграция потребует нового ADR и оценки стоимости (раздел 37) | высокая на этапе до появления данных, аналогично | высокая на этапе до появления данных, аналогично |
| 37 | Будущий рост | архитектурная оценка: партиционирование, репликация, логическая репликация дают понятный путь роста без смены СУБД (не измерено в рамках ADR) | архитектурная оценка: путь роста для многопроцессного производственного сценария потребовал бы перехода на другую СУБД | архитектурная оценка: путь роста существует (шардинг), но требует production HA-топологии с самого начала (раздел 43) |

## 16. Выбранное решение

**PostgreSQL — как основное транзакционное хранилище платформы.**

### Версионная политика

- production использует поддерживаемую стабильную major-линию PostgreSQL;
- **PostgreSQL 19 beta не выбирается** — на дату исследования (раздел 43) 19-я линия находится в статусе beta, официальная документация прямо не рекомендует beta-версии в production;
- точная major- и patch-версия **не фиксируется навсегда** этим ADR;
- версия фиксируется воспроизводимой конфигурацией проекта (раздел 36);
- перед обновлением проверяются release notes, совместимость расширений, драйвера, миграций и backup/restore;
- major upgrade является управляемым изменением, а не автоматическим обновлением;
- security и bugfix patch-релизы применяются после тестов;
- неподдерживаемые EOL-линии запрещены для production — официальная политика версионирования (раздел 43) даёт каждой major-линии 5 лет поддержки; на дату исследования линии 14–18 официально поддерживаются, линия 14 приближается к завершению поддержки (12 ноября 2026) и не рекомендуется для нового production-развёртывания без плана обновления.

Настоящее утверждение относится к продукту (выбору PostgreSQL как СУБД), а не к конкретной версии — конкретная поддерживаемая версия выбирается на шаге плана внедрения (раздел 36) после проверки актуального состояния официальной политики версионирования непосредственно перед развёртыванием.

## 17. Границы решения

PostgreSQL является:

- источником истины для транзакционных данных платформы;
- хранилищем пользователей и настроек;
- хранилищем метаданных инструментов;
- хранилищем конфигурации источников без секретных значений;
- хранилищем нормализованных фактов, если их объём соответствует принятой retention-политике;
- хранилищем provenance;
- хранилищем инсайтов;
- хранилищем оценок и результатов проверок;
- хранилищем уроков и ошибок;
- хранилищем дневника сделок;
- хранилищем заметок;
- хранилищем алертов;
- хранилищем состояния фоновых заданий, если это будет утверждено ADR очереди (`ADR-0006` по дорожной карте `TECHNOLOGY_EVALUATION.md`);
- хранилищем audit trail или его транзакционной части согласно отдельному проектированию.

PostgreSQL **не является** автоматически:

- хранилищем каждого сырого тика навсегда;
- high-frequency order book engine;
- message broker;
- cache;
- object storage;
- vector database;
- поисковым движком для всех случаев;
- хранилищем секретов;
- системой логирования observability;
- системой резервного копирования сам по себе.

## 18. Категории данных

PostgreSQL хранит следующие категории данных платформы (`MODULE_BOUNDARIES.md`):

- пользователи и настройки владельца (`identity`, `settings`);
- инструменты и рыночные контексты (`market`, `instruments`);
- метаданные источников без секретных значений (`sources`);
- нормализованные факты в рамках retention-политики (`normalization`, `data_quality`);
- provenance (`provenance`);
- инсайты и версии их входного контекста (`insights`; `ENGINEERING_PRINCIPLES.md`, пункт 29);
- пользовательские оценки и результаты проверки прогнозов (`evaluations`);
- уроки и ошибки (Future, `FUNCTIONAL_REQUIREMENTS.md`, область 29);
- дневник сделок (`journal`);
- заметки (`notes`);
- алерты (`alerts`);
- состояние фоновых заданий, если утверждено отдельным ADR (`jobs`);
- аудит критичных действий (`audit`);
- записи идемпотентности операций (`ENGINEERING_PRINCIPLES.md`, пункт 16).

Каждая категория владеется соответствующим доменным модулем (`MODULE_BOUNDARIES.md`) — настоящий ADR не переопределяет владение данными, только физическое хранилище.

## 19. Транзакции

- application use case (`application`, `ADR-0002`) определяет логическую транзакционную границу;
- HTTP route не управляет бизнес-транзакцией напрямую (`ADR-0002`, раздел 17);
- domain-модуль не зависит от PostgreSQL (`ADR-0001`, раздел 19, по аналогии; `MODULE_BOUNDARIES.md`);
- repository abstractions находятся на соответствующей границе (application/infrastructure), не в domain;
- транзакция должна быть короткой;
- внешние API и LLM не вызываются внутри открытой DB-транзакции без отдельного обоснования (`FAILURE_MODEL.md`, раздел 5 — retry/timeout правила);
- network call не удерживает блокировки;
- критичные записи выполняются атомарно (например, сохранение инсайта с контекстом — единая логическая операция, `LOGICAL_ARCHITECTURE.md`, раздел 18);
- partial success проектируется явно (`FAILURE_MODEL.md`, раздел 8);
- retry транзакции допускается только для классифицированных временных ошибок (`FAILURE_MODEL.md`, раздел 4), включая PostgreSQL serialization failures при Repeatable Read/Serializable (раздел 43);
- идемпотентность не заменяется транзакцией — это разные механизмы;
- distributed transaction не вводится в MVP.

Уровень изоляции по умолчанию — Read Committed (официальное значение по умолчанию PostgreSQL, раздел 43); более строгие уровни (Repeatable Read, Serializable) рассматриваются точечно для операций, где это обосновано, с обязательной retry-логикой на уровне application layer (раздел 43).

## 20. Целостность

- ограничения БД дополняют domain validation, а не заменяют её;
- обязательные поля, уникальность и ссылки обеспечиваются на уровне БД там, где это является инвариантом (PostgreSQL официально поддерживает FK/CHECK/UNIQUE/NOT NULL, раздел 43);
- foreign keys не запрещаются ради удобства;
- soft delete не вводится автоматически;
- физическое удаление пользовательских данных проектируется отдельно;
- insight record не переписывается задним числом (`LOGICAL_ARCHITECTURE.md`, раздел 14);
- исправление создаёт новую версию или связанную запись, а не перезапись;
- provenance не удаляется молча;
- audit-запись критичного действия связана с транзакцией там, где требуется (`FAILURE_MODEL.md`, раздел 17.1);
- optimistic concurrency может использоваться после отдельного проектирования;
- нельзя полагаться только на ORM validation — ORM не выбирается этим ADR и не является заменой ограничениям СУБД.

## 21. Время и временные зоны

- все серверные временные метки хранятся в UTC, с использованием `timestamp with time zone` — официально рекомендованного PostgreSQL типа для timezone-aware данных (раздел 43: значение конвертируется в UTC при записи и обратно при выводе);
- timezone-aware значения обязательны — `timestamp without time zone` не используется для событийных меток;
- различаются: event time; source publication time; source ingestion time; normalization time; insight creation time; evaluation time; user-local display time (`ENGINEERING_PRINCIPLES.md`, пункт 24);
- время источника не заменяется временем загрузки;
- исходный timezone сохраняется при необходимости (отдельно от внутреннего UTC-представления);
- frontend форматирует время для пользователя (`ADR-0003`, раздел 27) — не backend/БД;
- ordering не основывается только на времени клиента;
- database clock и application clock не считаются полностью взаимозаменяемыми;
- политика точности времени определяется данными источника;
- naive timestamps (без временной зоны) запрещены.

## 22. JSON и полуструктурированные данные

- реляционные поля используются для устойчивых инвариантов и связей;
- JSON/JSONB используется только для действительно вариативных атрибутов, исходных payload или версионируемых дополнительных данных;
- используется тип `jsonb`, а не `json` — официальная рекомендация PostgreSQL для большинства приложений (раздел 43: бинарное хранение, поддержка GIN-индексов, более быстрые запросы);
- JSON не становится способом избежать проектирования схемы — официальная документация PostgreSQL прямо рекомендует, чтобы даже гибкие JSON-документы имели «somewhat fixed structure» (раздел 43);
- критичные поля, фильтры и связи не прячутся бесконтрольно в JSONB;
- JSON payload имеет schema/version identifier, если формат меняется;
- исходный payload может храниться отдельно от нормализованных данных;
- секреты и избыточные персональные данные не сохраняются в payload;
- индексы JSONB (GIN, включая `jsonb_path_ops`, раздел 43) добавляются только после измерения запросов;
- обновление JSONB-документа приобретает блокировку на уровне всей строки (раздел 43) — учитывается при проектировании конкурентного доступа (раздел 25).

## 23. Provenance и неизменяемая история

- важный нормализованный факт связан с источником;
- сохраняются source identifier, source URL/reference, timestamps, retrieval metadata и parser/normalizer version (`ENGINEERING_PRINCIPLES.md`, пункт 32);
- исходный факт и AI-интерпретация разделены (`ENGINEERING_PRINCIPLES.md`, пункт 59);
- сохранённый инсайт неизменяем (`LOGICAL_ARCHITECTURE.md`, раздел 14) — обеспечивается на уровне application layer и, где применимо, ограничениями/правами доступа БД (конкретный механизм — предмет реализации, не этого ADR);
- повторный анализ создаёт новый результат, а не перезаписывает существующий;
- пользовательская оценка не переписывает исходный прогноз (`evaluations` хранится отдельно от `insights`, `MODULE_BOUNDARIES.md`);
- результат автоматической проверки хранится отдельно;
- урок связан с прогнозом, фактическим результатом и версией анализа (Future, `FUNCTIONAL_REQUIREMENTS.md`, область 29–31);
- удаление источника не должно делать историю необъяснимой — provenance сохраняется даже если внешний источник становится недоступен;
- исправления provenance прослеживаются, а не перезаписываются молча;
- ретроспективный анализ должен знать временной срез данных (раздел 21).

## 24. Рыночные и временные ряды

- PostgreSQL может хранить агрегированные свечи, события календаря, funding, open interest и ограниченные нормализованные временные ряды;
- решение о полном потоке тиков, order book snapshots и Time & Sales принимается отдельно после оценки объёма — вне рамок настоящего ADR;
- retention обязателен;
- partitioning может быть применён после анализа нагрузки — официальная рекомендация PostgreSQL: партиционирование оправдано, когда таблица существенно превышает физическую память сервера (раздел 43); правило не применяется механически;
- partitioning не включается механически для всех таблиц;
- raw payload может иметь отдельный срок хранения относительно нормализованных данных;
- агрегированные данные не заменяют исходные данные без явной политики;
- late-arriving data и corrections учитываются в модели данных;
- уникальность временной точки зависит от source/instrument/timeframe;
- high-frequency storage не является автоматически задачей основной OLTP-БД;
- **TimescaleDB не выбирается настоящим ADR** — рассматривается только как возможное будущее отдельное решение при обоснованной необходимости;
- специализированные time series collections (в духе MongoDB, раздел 43) официально накладывают существенные ограничения на изменение полей вне метаданных — архитектурно хуже соответствуют требованию проекта явно фиксировать исправления как новые версии (раздел 20, 23), а не полагаться на update-ограниченную модель.

## 25. Конкурентный доступ

- несколько web/worker процессов могут обращаться к одной БД (`ADR-0001`, план внедрения; `TECHNOLOGY_EVALUATION.md`, раздел 8) — PostgreSQL официально спроектирован для этого сценария (раздел 43), в отличие от SQLite, для которого официальная документация прямо не рекомендует множественный клиентский доступ по сети и ограничивает запись одним writer'ом одновременно (раздел 43, раздел 15, критерии 9–11);
- блокировки и уровни изоляции используются осознанно (раздел 19);
- `SELECT FOR UPDATE` не применяется повсеместно — PostgreSQL предоставляет несколько уровней строгости блокировки строк (`FOR UPDATE`/`FOR NO KEY UPDATE`/`FOR SHARE`/`FOR KEY SHARE`, раздел 43), выбираемых по месту;
- длинные транзакции запрещены;
- deadlocks считаются ожидаемым классом отказа (`FAILURE_MODEL.md`, раздел 2) и корректно обрабатываются — PostgreSQL официально обнаруживает deadlock автоматически и прерывает одну из транзакций (раздел 43); приложение обязано иметь retry-логику для этого случая;
- background job claiming требует атомарной модели (например, через `UPDATE ... RETURNING` с соответствующим уровнем блокировки);
- duplicate processing предотвращается не только памятью процесса — идемпотентность обеспечивается на уровне данных (UNIQUE/ON CONFLICT);
- sequence/order нельзя гарантировать только временем — используются явные идентификаторы порядка, где это критично;
- connection exhaustion должен быть обнаруживаемым (`FAILURE_MODEL.md`, раздел 2, класс «Нехватка ресурсов»);
- конкретный pool выбирается позднее (раздел 40).

## 26. Миграции схемы

- schema changes выполняются только управляемыми миграциями;
- ручное изменение production schema запрещено;
- миграции версионируются вместе с кодом;
- миграция должна быть воспроизводимой;
- destructive changes требуют backup и плана отката;
- expand/migrate/contract применяется для несовместимых изменений;
- migration не запускается скрыто каждым web worker (`ADR-0003`, раздел 20, по аналогии — миграция не является частью старта отдельного процесса приложения);
- rollback миграции не всегда технически возможен;
- forward fix может быть безопаснее rollback;
- конкретный migration tool выбирается отдельно (раздел 36, 40).

## 27. Резервное копирование и восстановление

- backup без проверенного восстановления не считается рабочим;
- определяются RPO/RTO после измерений и решения Product Owner (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-022, NFR-023, NFR-041 — статус «требуется решение/измерение»);
- локальная разработка не заменяет production backup;
- production требует регулярных backup;
- PITR рассматривается как production-требование — официально поддерживается PostgreSQL через continuous archiving WAL-файлов и `pg_basebackup`, с восстановлением на произвольный момент времени через `recovery_target_time` (раздел 43);
- резервные копии хранятся отдельно от основного сервера;
- backup шифруется;
- доступ ограничен;
- restore drills выполняются периодически (`ENGINEERING_PRINCIPLES.md`, пункт 50);
- retention backup определяется отдельно;
- секреты подключения не попадают в backup scripts;
- конкретный механизм backup (например, `pg_basebackup` в сочетании с WAL-архивированием, раздел 43) выбирается детально при deployment ADR (`ADR-0008` по дорожной карте `TECHNOLOGY_EVALUATION.md`).

## 28. Безопасность

- отдельный DB user для приложения;
- principle of least privilege (`ENGINEERING_PRINCIPLES.md`, пункт 5);
- production superuser не используется приложением;
- разные окружения изолированы;
- секреты подключения не хранятся в репозитории (`ENGINEERING_PRINCIPLES.md`, пункт 6);
- TLS определяется deployment-архитектурой;
- SQL injection предотвращается параметризованными запросами;
- динамический SQL ограничивается;
- audit доступа к БД определяется отдельно;
- персональные и чувствительные данные классифицируются;
- encryption at rest зависит от инфраструктуры и не считается автоматически предоставленным PostgreSQL;
- row-level security не включается без реальной модели multi-user access (`PRODUCT_SCOPE.md`, раздел 6 — multi-tenant не утверждён);
- backup имеет собственную модель доступа (раздел 27).

## 29. Производительность

- индексы создаются под измеренные запросы;
- каждый индекс имеет стоимость записи и хранения;
- N+1 рассматривается как дефект доступа к данным;
- query plans анализируются для критичных запросов;
- pagination должна быть устойчивой;
- offset pagination не используется механически для больших историй (`USER_JOURNEYS.md`, UJ-029, UJ-030 — история и фильтрация инсайтов);
- bulk ingestion проектируется отдельно;
- большие payload не загружаются без лимитов;
- connection pool не маскирует медленные запросы;
- slow queries измеряются;
- autovacuum не отключается без отдельного решения — стандартный механизм обслуживания PostgreSQL;
- нагрузочные пределы не придумываются до тестов — числовые NFR не утверждены (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-005–NFR-006).

## 30. Масштабирование

- MVP использует один primary PostgreSQL instance;
- это логическое решение, а не обязательный managed service;
- read replica не вводится заранее;
- sharding не вводится заранее;
- отдельная analytical DB не вводится заранее;
- масштабирование начинается со схемы, запросов, индексов, retention и ресурсов сервера — не с горизонтального масштабирования СУБД;
- репликация (физическая или логическая, раздел 43) рассматривается при реальной необходимости;
- извлечение отдельного хранилища допускается для high-volume market data (раздел 24);
- разделение хранилищ требует отдельного ADR;
- приложение не зависит от vendor-specific managed features без отдельного решения.

## 31. Положительные последствия

- полная поддержка ACID-транзакций и MVCC без взаимной блокировки читателей и писателей (раздел 43);
- зрелая система ограничений (FK, CHECK, UNIQUE) для отражения инвариантов домена;
- официально рекомендованная поддержка JSONB для вариативных атрибутов наряду с реляционными данными;
- зрелые механизмы backup/PITR/логической репликации «из коробки»;
- полноценный SQL для сложных запросов и агрегатов;
- индексация, включая GIN для JSONB и полнотекстовый поиск;
- официально спроектирован для множества одновременных клиентских процессов — соответствует архитектуре модульного монолита с web + worker процессами;
- единый источник истины MVP для транзакционных данных;
- расширяемость через систему extensions;
- open source, без обязательной зависимости от одного облачного провайдера;
- возможность начать с одного сервера без предустановленной необходимости в кластере (в отличие от production-топологии MongoDB, раздел 43).

## 32. Отрицательные последствия

- требуется отдельный серверный процесс — не встроенная в приложение база, в отличие от SQLite;
- эксплуатация сложнее SQLite (нет варианта «файл рядом с приложением»);
- backup, vacuum, обновления и мониторинг требуют дисциплины;
- schema migrations требуют процесса и инструмента (выбирается отдельно, раздел 36);
- плохая схема и запросы приводят к деградации производительности;
- JSONB можно злоупотребить, превратив его в способ избежать проектирования схемы (раздел 22);
- большие временные ряды могут потребовать разделения хранилища (раздел 24, 30);
- major upgrade требует подготовки (совместимость расширений, драйверов, миграций, раздел 16);
- восстановление требует практики (restore drills, раздел 27);
- доступность одного primary ограничена до внедрения репликации/восстановления (раздел 30);
- PostgreSQL не решает автоматически cache, queue, search и observability — эти области остаются предметом отдельных ADR;
- ошибка retention может дорого увеличить объём хранения (раздел 24, 29);
- один сервер остаётся точкой отказа до внедрения восстановления/репликации.

## 34. Меры снижения рисков

1. Потеря данных → регулярный backup и проверенный restore (раздел 27); транзакционная атомарность критичных записей (раздел 19).
2. Backup не восстанавливается → restore drills выполняются периодически (раздел 27).
3. Переполнение диска → retention-политика и мониторинг объёма (раздел 24, 29); observability подключается отдельным решением.
4. Слишком большие raw payload → отдельный срок хранения raw payload, лимиты на размер (раздел 22, 24).
5. Неконтролируемый рост временных рядов → retention обязателен, partitioning — по результатам анализа нагрузки, не механически (раздел 24).
6. Отсутствие retention → retention определяется явно для каждой категории данных перед вводом в эксплуатацию (раздел 24, план внедрения раздел 36).
7. Медленные запросы → query plans анализируются для критичных путей, slow queries измеряются (раздел 29).
8. Неправильные индексы → индексы создаются под измеренные запросы, а не заранее (раздел 29).
9. N+1 → рассматривается как дефект доступа к данным, выявляется на этапе review/тестирования (раздел 29).
10. Длинные транзакции → транзакция должна быть короткой, внешние вызовы не выполняются внутри открытой транзакции (раздел 19).
11. Deadlock → консистентный порядок блокировок, retry-логика на классифицированных serialization failures (раздел 19, 25, `FAILURE_MODEL.md`, раздел 4).
12. Connection exhaustion → обнаруживается через observability (`FAILURE_MODEL.md`, раздел 2); конкретный pool и лимиты — предмет реализации (раздел 40).
13. Duplicate job processing → атомарная модель job claiming (раздел 25).
14. Нарушение идемпотентности → UNIQUE/ON CONFLICT на уровне данных, а не только в памяти процесса (раздел 25).
15. JSONB как свалка → JSON используется только для вариативных атрибутов с версионированным форматом (раздел 22).
16. Ручные изменения schema → только управляемые миграции, ручное изменение production запрещено (раздел 26).
17. Destructive migration → обязателен backup и план отката перед destructive-изменением (раздел 26, 27).
18. Несовместимый major upgrade → проверка release notes/расширений/драйверов/миграций/backup перед обновлением, управляемый процесс (раздел 16).
19. EOL-линия PostgreSQL → версия проверяется по официальной политике версионирования перед развёртыванием и при каждом major upgrade (раздел 16).
20. Утечка DB credentials → секреты вне репозитория, конфигурация вне кода (`ENGINEERING_PRINCIPLES.md`, пункты 40–41).
21. Работа от superuser → отдельный DB user приложения с минимальными привилегиями (раздел 28).
22. SQL injection → параметризованные запросы, ограничение динамического SQL (раздел 28).
23. Ошибки часовых поясов → обязательный `timestamp with time zone`, UTC на сервере, форматирование — на frontend (раздел 21).
24. Потеря provenance → provenance не удаляется молча, исправления прослеживаются (раздел 23).
25. Переписывание инсайта → неизменяемость инсайта обеспечивается на уровне application layer и ограничений (раздел 20, 23).
26. Недоступность primary → восстановление из backup/PITR (раздел 27); репликация рассматривается при реальной необходимости (раздел 30).
27. Блокировка API тяжёлой аналитикой → длинные транзакции запрещены, тяжёлые запросы изолируются от критичного пути (раздел 19, 29).
28. БД как очередь без модели → состояние фоновых заданий получает утверждённую модель только через отдельный ADR (раздел 17; `ADR-0006` по дорожной карте).
29. Отсутствие observability запросов → slow queries измеряются, наблюдаемость — предмет отдельного ADR наблюдаемости (`ADR-0009` по дорожной карте).
30. High-frequency данные перегружают OLTP → полный поток тиков не хранится в основной OLTP-БД по умолчанию, решается отдельно после оценки объёма (раздел 24).

## 35. Влияние на нефункциональные характеристики

- **безопасность:** отдельный DB user с минимальными привилегиями, секреты вне кода (раздел 28); официальная политика PostgreSQL по security-патчам применяется приоритетно (раздел 16).
- **надёжность:** ACID-транзакции и MVCC снижают риск рассогласования данных (раздел 43); PITR и backup обеспечивают восстановимость (раздел 27).
- **масштабируемость:** партиционирование, индексация и логическая репликация дают понятный путь роста без немедленной смены СУБД (раздел 24, 30); числовые пределы не утверждены (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-008).
- **производительность:** архитектурно ожидается достаточной для MVP-профиля нагрузки (один пользователь); числовые NFR не утверждены и не измерены в рамках ADR (раздел 29).
- **стоимость:** open source, без лицензионных отчислений; требует отдельного серверного процесса относительно встроенного варианта (раздел 32) — не измерено в рамках ADR.
- **сопровождение:** архитектурная оценка — предсказуемая, зрелая документация снижает нагрузку на единственного разработчика (раздел 15, критерий 33); не измерено в рамках ADR.
- **наблюдаемость:** slow query-логирование и метрики закладываются как требование (раздел 29), конкретная реализация — предмет отдельного ADR наблюдаемости.
- **данные:** provenance и неизменяемость инсайтов поддерживаются на уровне модели данных и ограничений (раздел 20, 23).
- **обратную совместимость:** миграции версионируются вместе с кодом, expand/migrate/contract для несовместимых изменений (раздел 26).

## 37. План отката

**До появления схемы и кода:** откат означает замену настоящего ADR новым решением без миграции — стоимость отката минимальна.

**После появления данных:**

- требуется новый ADR, заменяющий ADR-0004;
- экспорт данных;
- проверка целостности;
- параллельная запись допускается только при отдельном плане;
- миграция по сущностям;
- сверка количества записей и контрольных сумм;
- переключение приложения на новое хранилище;
- период read-only проверки старого хранилища;
- план возврата на случай неудачи миграции;
- прежний ADR получает статус «Заменён» с указанием ADR-преемника (`ADR_PROCESS.md`, раздел 19).

Простой откат после накопления production-данных **не обещается** — стоимость миграции растёт с объёмом накопленных данных.

## 38. Критерии проверки решения

Решение проверяется, когда появится реализация (без создания этих проверок в рамках настоящей задачи):

1. PostgreSQL использует поддерживаемую стабильную версию;
2. EOL-линия не используется;
3. приложение не подключается от имени superuser;
4. миграции воспроизводимы;
5. schema создаётся с нуля без ручных шагов;
6. backup создаётся;
7. restore проверен;
8. используются timezone-aware timestamps;
9. инсайт неизменяем после сохранения;
10. evaluation хранится отдельно от insight;
11. provenance связан с нормализованными фактами;
12. constraints защищают заявленные инварианты;
13. route handler не обращается к БД напрямую (`ADR-0002`, раздел 17);
14. внешние API не вызываются внутри открытой транзакции;
15. критичные операции идемпотентны;
16. slow queries наблюдаемы;
17. retention определён для каждой категории данных;
18. raw data не растут бесконтрольно;
19. несколько процессов (web + worker) работают корректно с одной БД;
20. deadlock/retry обрабатываются корректно;
21. восстановление после рестарта не теряет подтверждённые (закоммиченные) данные.

## 39. Условия пересмотра

ADR-0004 пересматривается, если:

- PostgreSQL перестаёт удовлетворять NFR после фактических измерений (раздел 35, 38);
- high-frequency market data перегружают OLTP-нагрузку основной БД (раздел 24, 33);
- объём данных требует отдельного time-series/analytical storage;
- требования multi-region делают один primary неприемлемым;
- стоимость эксплуатации становится неприемлемой;
- резервное копирование и восстановление не достигают утверждённых RPO/RTO после их принятия;
- появляется обязательное требование offline-only embedded storage (например, для отдельного desktop-клиента, `PRODUCT_SCOPE.md`, раздел 20);
- основная модель данных становится преимущественно документной, и реляционные связи теряют архитектурное значение;
- технология теряет официальную поддержку;
- выбранная версия достигает EOL без своевременного плана обновления;
- необходима managed-specific функция с существенным vendor lock-in;
- требования compliance требуют иной модели хранения.

Дополнительное специализированное хранилище (например, для high-volume рыночных данных или векторного поиска) может быть добавлено отдельным ADR без замены ADR-0004, если PostgreSQL остаётся основной transactional system of record.

## 40. Открытые вопросы

- точная поддерживаемая версия PostgreSQL будет определена на шаге 2 плана внедрения (раздел 36) — официальная политика версионирования (раздел 43) показывает несколько одновременно поддерживаемых линий (14–18 на дату исследования), конкретный выбор не входит в этот ADR;
- выбор Python driver, ORM/data-access approach, migration tool, connection pool не входит в этот ADR (раздел 12) — предмет отдельных задач;
- выбор конкретной deployment-модели PostgreSQL (managed provider, self-hosted, контейнеризация) — предмет будущего `ADR-0008`;
- необходимость TimescaleDB, pgvector или отдельного time-series/vector storage остаётся открытой — решается отдельными ADR при появлении конкретной, обоснованной задачи (`ADR-0005` по дорожной карте `TECHNOLOGY_EVALUATION.md` для векторного поиска);
- окончательная модель хранения состояния фоновых заданий и очереди решается `ADR-0006`;
- числовые RPO/RTO и другие количественные NFR, связанные с хранилищем, остаются неутверждёнными (`NON_FUNCTIONAL_REQUIREMENTS.md`).

## 43. Источники исследования

Исследование выполнено 2026-08-05 исключительно по официальным первичным источникам (postgresql.org, sqlite.org, mongodb.com/docs), без использования блогов, Reddit, Medium, рейтингов, неофициальных benchmark, маркетинговых сравнительных статей и документации ORM как доказательства возможностей самой СУБД.

**PostgreSQL:**
- [postgresql.org/support/versioning](https://www.postgresql.org/support/versioning/) — официальная политика версионирования: major-версия ежегодно, minor — не реже раза в квартал (только исправления); каждая major-линия поддерживается 5 лет; на дату исследования поддерживаются линии 18 (до 2030-11-14), 17 (до 2029-11-08), 16 (до 2028-11-09), 15 (до 2027-11-11), 14 (до 2026-11-12, приближается к завершению поддержки).
- [postgresql.org](https://www.postgresql.org/) — официально: последний стабильный релиз PostgreSQL 18.4 (2026-05-14); PostgreSQL 19 Beta 2 опубликован 2026-07-16, официально не рекомендован для production («While we do not advise you to run beta versions in production environments...»).
- [postgresql.org/docs/current/mvcc-intro.html](https://www.postgresql.org/docs/current/mvcc-intro.html) — официально: MVCC — чтение никогда не блокирует запись и наоборот, включая строгий уровень Serializable через Serializable Snapshot Isolation (SSI).
- [postgresql.org/docs/current/transaction-iso.html](https://www.postgresql.org/docs/current/transaction-iso.html) — официально: уровни Read Committed (по умолчанию, retry не требуется), Repeatable Read и Serializable (оба требуют retry-логики приложения при serialization failure).
- [postgresql.org/docs/current/datatype-json.html](https://www.postgresql.org/docs/current/datatype-json.html) — официально: `jsonb` рекомендован для большинства приложений; GIN-индексы (`jsonb_ops`, `jsonb_path_ops`); официальная рекомендация сохранять «somewhat fixed structure» даже для гибких документов; обновление JSON-документа блокирует всю строку.
- [postgresql.org/docs/current/ddl-partitioning.html](https://www.postgresql.org/docs/current/ddl-partitioning.html) — официально: партиционирование оправдано, когда таблица существенно превышает физическую память сервера; три встроенные стратегии (range/list/hash); явное предупреждение не считать «больше партиций — всегда лучше».
- [postgresql.org/docs/current/continuous-archiving.html](https://www.postgresql.org/docs/current/continuous-archiving.html) — официально: continuous archiving (WAL) + `pg_basebackup` дают point-in-time recovery через `recovery_target_time`; описан полный процесс backup/restore и таймлайнов восстановления.
- [postgresql.org/docs/current/logical-replication.html](https://www.postgresql.org/docs/current/logical-replication.html) — официально: publish/subscribe модель, транзакционная согласованность применения изменений на подписчике, применимо для консолидации БД и репликации между версиями/платформами.
- [postgresql.org/docs/current/textsearch-intro.html](https://www.postgresql.org/docs/current/textsearch-intro.html) — официально: встроенный полнотекстовый поиск на основе `tsvector`/`tsquery` с лингвистической нормализацией и ранжированием.
- [postgresql.org/docs/current/datatype-datetime.html](https://www.postgresql.org/docs/current/datatype-datetime.html) — официально: `timestamp with time zone` рекомендован для timezone-aware данных, хранится в UTC внутренне, конвертируется при выводе по сессионной timezone.
- [postgresql.org/docs/current/explicit-locking.html](https://www.postgresql.org/docs/current/explicit-locking.html) — официально: четыре режима row-level locking (`FOR UPDATE`/`FOR NO KEY UPDATE`/`FOR SHARE`/`FOR KEY SHARE`); автоматическое обнаружение deadlock и прерывание одной из транзакций; рекомендации — консистентный порядок блокировок, retry-логика.
- [postgresql.org/docs/current/ddl-generated-columns.html](https://www.postgresql.org/docs/current/ddl-generated-columns.html) — официально: generated columns (stored/virtual) вычисляются из других колонок, используют только immutable-функции, не могут быть частью partition key.

**SQLite:**
- [sqlite.org/whentouse.html](https://www.sqlite.org/whentouse.html) — официально: SQLite спроектирован для локального хранения, конкурирует с `fopen()`, а не с клиент-серверными СУБД; прямая рекомендация не использовать SQLite, когда «много клиентских программ отправляют SQL к одной БД по сети»; поддерживает неограниченное число одновременных читателей, но только одного writer'а одновременно.
- [sqlite.org/wal.html](https://www.sqlite.org/wal.html) — официально: WAL-режим — читатели и писатели не блокируют друг друга, но одновременно может быть только один writer; WAL требует общей разделяемой памяти между процессами и не работает через сетевые файловые системы между разными хостами; плохая производительность для транзакций больше нескольких десятков МБ.
- [sqlite.org/lockingv3.html](https://www.sqlite.org/lockingv3.html) — официально: только один процесс может писать в БД в любой момент времени; пять состояний блокировки файла (UNLOCKED/SHARED/RESERVED/PENDING/EXCLUSIVE); EXCLUSIVE-блокировка при коммите блокирует всех читателей.
- [sqlite.org/json1.html](https://www.sqlite.org/json1.html) — официально: богатый набор JSON-функций (с версии 3.38.0), включая проприетарный бинарный формат JSONB (с 3.45.0), не совместимый с форматом JSONB PostgreSQL.
- [sqlite.org/backup.html](https://www.sqlite.org/backup.html) — официально: Online Backup API поддерживает горячее резервное копирование работающей БД инкрементально, без блокировки на всё время операции.
- [sqlite.org/lang_transaction.html](https://www.sqlite.org/lang_transaction.html) — официально: множественные одновременные read-транзакции, но только одна write-транзакция; snapshot-изоляция чтения; транзакции не вкладываются (используется `SAVEPOINT`).

**MongoDB:**
- [mongodb.com/docs/manual/core/transactions](https://www.mongodb.com/docs/manual/core/transactions/) — официально: multi-document ACID-транзакции поддерживаются на replica set (fcv 4.0+) и sharded cluster (fcv 4.2+); официальная документация прямо указывает на больший performance-cost относительно записи одного документа и рекомендует денормализованное схемное проектирование как основную стратегию, а не транзакции.
- [mongodb.com/docs/manual/core/schema-validation](https://www.mongodb.com/docs/manual/core/schema-validation/) — официально: schema validation через JSON Schema — opt-in, не включена по умолчанию; может быть настроена на предупреждение вместо отклонения (`warn` level) или обойдена.
- [mongodb.com/docs/manual/core/timeseries-collections](https://www.mongodb.com/docs/manual/core/timeseries-collections/) — официально: специализированные time series collections оптимизированы для хранения, но match-выражения в update ограничены только `metaField` — обновление прочих полей документа официально ограничено; есть отдельные ограничения sharding.
- [mongodb.com/docs/manual/changeStreams](https://www.mongodb.com/docs/manual/changeStreams/) — официально: change streams требуют replica set/sharded cluster и WiredTiger; не поддерживаются на time series collections.
- [mongodb.com/docs/manual/core/replica-set-members](https://www.mongodb.com/docs/manual/core/replica-set-members/) — официально: рекомендуемая production-топология — минимум три data-bearing узла (1 primary + 2 secondary); PSA-топология (с arbiter) предупреждается как риск потери доступности.
- [mongodb.com/docs/manual/reference/program/mongodump](https://www.mongodb.com/docs/manual/reference/program/mongodump/) — официально: standalone-дамп без `--oplog` не даёт консистентного снимка на единый момент времени при продолжающейся записи; на replica set для консистентности требуется `--oplog` + `mongorestore --oplogReplay`; `--oplog` не работает для sharded cluster.
