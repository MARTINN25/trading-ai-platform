## 11. Контекст

`ADR-0002` (утверждён) запретил использовать FastAPI `BackgroundTasks` для критичных, долгих или требующих гарантированного выполнения задач и указал, что такие задачи выполняются отдельным worker-процессом. `ADR-0004` (утверждён) зафиксировал PostgreSQL как основное транзакционное хранилище и transactional system of record, явно не утвердив его как message broker, но оставив возможность использовать PostgreSQL для очереди через отдельное решение. `ADR-0005` (утверждён) указал, что future embedding-задачи выполняются backend worker/application pipeline и не блокируют web request.

Логическая архитектура включает области `application`, `jobs`, `evaluations`, `alerts`, `ingestion`, `analysis`, `llm_gateway`, `insights`, `audit`, `observability` (`LOGICAL_ARCHITECTURE.md`, `MODULE_BOUNDARIES.md`, модуль 19 `jobs`). Ни один механизм фоновых задач, очереди или worker-процесса ещё не выбран — это предмет настоящего ADR.

Дата проверки технологических данных, использованных в настоящем ADR: 2026-08-05 (см. раздел 60 «Источники исследования»).

## 12. Проблема

Какие операции платформы должны выполняться синхронно в рамках HTTP-запроса, какие допустимы как in-process фоновые операции внутри web-процесса, а какие требуют durable-задачи в отдельном worker-процессе; нужна ли отдельная message broker инфраструктура в MVP; как обеспечиваются долговечность задач, retry, идемпотентность, дедупликация, планирование, отмена, наблюдаемость, аудит, безопасность и восстановление после рестарта; при каких условиях появление отдельного брокера сообщений становится оправданным.

Настоящий ADR не выбирает: Celery, Dramatiq, RQ, ARQ, Taskiq, Huey, Redis, RabbitMQ, Kafka, конкретную PostgreSQL job library, конкретный scheduler, конкретную retry library, конкретный connection pool, конкретные числовые timeout/retry значения, exactly-once delivery, конкретную схему таблицы jobs.

## 13. Ограничения

- решение принимается до появления кода worker/scheduler — миграционная стоимость минимальна;
- PostgreSQL уже утверждён как основное хранилище (`ADR-0004`) и оценивается как первый кандидат для durable-очереди, а не выбирается заново с нуля;
- FastAPI `BackgroundTasks` уже запрещены для критичных/долгих задач (`ADR-0002`) — это ограничение принимается как данность, не пересматривается;
- один разработчик отвечает за эксплуатацию — дополнительный сервис (broker) не вводится без доказанной необходимости (`ENGINEERING_PRINCIPLES.md`, пункт 67);
- MVP разворачивается на одном сервере (`PRODUCT_SCOPE.md`, раздел 22);
- решение не должно предполагать выбор конкретной библиотеки/broker/scheduler — это выходит за рамки задачи;
- официальные источники (раздел 60) не подтверждают exactly-once delivery ни для одного из рассмотренных broker-вариантов без дополнительных условий — это утверждение не используется как основание решения.

## 15. Термины

**Синхронная операция** — пользователь ожидает результат в рамках текущего HTTP-запроса.

**In-process background operation** — операция выполняется после отправки ответа, но внутри lifecycle web-процесса; **не является** durable-задачей.

**Durable background job** — persisted job, переживающий рестарт web/worker процесса.

**Worker** — отдельный процесс, получающий и выполняющий durable jobs.

**Scheduler** — компонент, создающий jobs по расписанию; не обязан выполнять jobs сам.

**Broker** — отдельная инфраструктура доставки сообщений/задач (например, Redis, RabbitMQ, Kafka).

**Job record** — persisted source of truth о задаче: состояние, попытки, время, результат.

**At-least-once** — задача может быть доставлена или выполнена повторно.

**Exactly-once** — не обещается настоящим ADR ни для одного варианта; официальные источники нескольких broker-технологий (раздел 60) документируют exactly-once только как опциональную, условную возможность, а не универсальную гарантию. Бизнес-эффект обеспечивается идемпотентностью и уникальными ограничениями (раздел 26), а не транспортной гарантией.

## 17. Рассмотренные варианты

Рассмотрены ровно четыре стратегии:

- **Вариант A — только синхронное выполнение и FastAPI `BackgroundTasks`**
- **Вариант B — PostgreSQL-backed durable queue + отдельный worker**
- **Вариант C — отдельный Redis/RabbitMQ broker + worker framework**
- **Вариант D — Kafka-based event/log инфраструктура**

Kafka рассмотрена честно, но не как обычная task queue по умолчанию — официально Kafka позиционируется как персистентный, воспроизводимый лог событий, в отличие от модели удаления сообщений традиционных очередей (раздел 60). Качественные оценки — архитектурная оценка на основании официальной документации, а не benchmark.

## 18. Выбранная стратегия

### MVP

- критичные и долгие задачи (раздел 16, классы 3–4, 7–12) выполняются отдельным worker-процессом;
- job record сохраняется в PostgreSQL;
- PostgreSQL является source of truth состояния jobs;
- web-процесс создаёт job через application use case (`ADR-0002`, раздел 17);
- worker атомарно claim'ит job;
- выполнение отделено от HTTP-request/response цикла;
- рестарт web-процесса не теряет durable job;
- отдельный Redis/RabbitMQ/Kafka broker **не вводится**;
- конкретная библиотека очереди **не выбирается** этим ADR;
- scheduler создаёт durable jobs, но не выполняет бизнес-работу сам;
- короткие некритичные операции могут выполняться in-process (раздел 20) только при явном признании допустимости потери результата;
- критичные `BackgroundTasks` запрещены (уже установлено `ADR-0002`, подтверждается здесь).

### Будущее

Отдельный broker (Вариант C) или event/log-инфраструктура (Вариант D) рассматриваются **отдельным ADR** только после доказанных, измеренных ограничений PostgreSQL-backed queue (раздел 23).

## 19. Синхронные операции

Выполняются в рамках HTTP-запроса без постановки в очередь: выбор рынка/инструмента/горизонта, запрос полного анализа (`DATA_FLOWS.md`, DF-001 — клиентский запрос MVP синхронно ожидает результат), сохранение инсайта, оценка инсайта, создание записи дневника/заметки, скальпинг-вердикт (DF-017). Синхронная операция может внутренне использовать асинхронный I/O (`ADR-0001`, `asyncio`), но остаётся частью одного запрос-ответного цикла — это не является durable job.

## 20. In-process фоновые операции

**Факт официальной документации (`ADR-0002`, раздел 18.3, 40; подтверждено повторно в рамках этого ADR):** FastAPI `BackgroundTasks` выполняются в процессе приложения после формирования ответа; официальная документация рекомендует для тяжёлых вычислений, не требующих выполнения в том же процессе, отдельные инструменты (раздел 60).

**Архитектурное решение проекта:** in-process background operations (включая `BackgroundTasks`) теряются при падении или рестарте web-процесса — это не гипотеза, а прямое следствие отсутствия персистентности состояния вне памяти процесса. Поэтому:

- in-process операции допустимы **только** для коротких, некритичных, best-effort действий, где потеря результата явно приемлема;
- критичные, долгие, повторяемые, плановые и требующие гарантированного выполнения задачи **никогда** не реализуются как in-process операции (раздел 16, классы 3–12);
- решение о допустимости конкретной операции как in-process принимается явно на этапе проектирования, а не по умолчанию.

## 21. Отдельный worker-процесс

- worker — отдельный от web ОС-процесс (`multiprocessing`-подобная модель изоляции процессов, раздел 60 — официально рекомендуется для CPU-bound и требующих изоляции сценариев, в отличие от `asyncio`, эффективного для I/O-bound задач в одном процессе);
- worker обращается к тому же PostgreSQL, что и web-процесс (`ADR-0004`);
- несколько worker-процессов могут выполняться конкурентно (раздел 22, 35);
- worker не выполняет транспортную логику FastAPI (`ADR-0002`, раздел 17 — route handler не владеет бизнес-логикой; аналогично worker не является HTTP-adapter'ом);
- конкретный runtime worker (asyncio-based, process pool, gevent-подобный и т.д.) не выбирается этим ADR — только факт необходимости отдельного процесса.

## 22. PostgreSQL-backed job queue

- job — persisted record в PostgreSQL;
- claiming выполняется атомарно; `SELECT ... FOR UPDATE SKIP LOCKED` официально предназначен именно для «избежания конкуренции блокировок при множественных потребителях, обращающихся к queue-like таблице» (раздел 60) и может быть одним из механизмов, но **не утверждается как единственная реализация**;
- официально: `SKIP LOCKED` даёт «несогласованное представление данных», что признано неприемлемым для general-purpose работы, но подходящим именно для queue-подобного доступа (раздел 60) — это ограничение учитывается при проектировании;
- несколько worker'ов могут работать конкурентно над разными job без взаимной блокировки строк;
- статус и lease/ownership job проектируются явно (раздел 25);
- worker не держит транзакцию открытой во время выполнения внешнего вызова (раздел 38);
- claim и business execution разделены на разные транзакции;
- завершение job записывается отдельной короткой транзакцией;
- heartbeat может применяться для долгих jobs, чтобы обнаруживать «зависшие» lease;
- потерянный (просроченный) lease позволяет другому worker'у забрать job повторно;
- `LISTEN`/`NOTIFY` может ускорять пробуждение worker (снижает задержку относительно чистого polling), но официально **не является** durable-механизмом: «если ни один клиент не слушает в момент `NOTIFY`, уведомление теряется» (раздел 60) — соответственно не может быть source of truth;
- polling остаётся допустимым fallback-механизмом обнаружения новых jobs;
- job payload не содержит секреты (раздел 45);
- большие payload не хранятся бесконтрольно (раздел 46);
- job связан с инициатором и correlation ID (`FAILURE_MODEL.md`, раздел 11);
- конкретная схема таблицы jobs и индексы проектируются отдельно (раздел 53).

## 23. Условия отдельного broker

Отдельный broker (Redis/RabbitMQ — Вариант C, или Kafka-подобная event/log инфраструктура — Вариант D) рассматривается **отдельным ADR**, только если измерения показывают одно или несколько из:

- PostgreSQL-backed queue создаёт неприемлемую OLTP-нагрузку на primary (`ADR-0004`, раздел 29);
- throughput не достигает утверждённых NFR;
- latency (включая задержку пробуждения worker) не достигает утверждённых NFR;
- нужен независимый от PostgreSQL lifecycle очереди;
- требуется routing по множеству логически разных очередей;
- требуется специализированная delivery topology (fan-out, приоритетные очереди на уровне broker и подобное);
- требуется значительно большее число worker'ов, чем разумно обслуживать через одну БД-таблицу;
- polling создаёт неприемлемую нагрузку, а `LISTEN`/`NOTIFY` не решает проблему из-за собственных официальных ограничений (раздел 60 — потеря уведомлений, лимит очереди уведомлений 8 ГБ, риск сбоя commit при переполнении);
- broker-специфичная семантика (например, официально документированные consumer groups и `XACK`/PEL Redis Streams, или партиционированный упорядоченный лог Kafka, раздел 60) даёт измеримую пользу, которую нецелесообразно воспроизводить вручную;
- эксплуатационная стоимость второго сервиса измеримо оправдана пользой;
- recovery и наблюдаемость PostgreSQL-подхода признаны недостаточными после реализации и измерений.

Сам факт существования фоновых задач **не является** основанием для broker.

## 24. Job lifecycle

Job проходит путь: создание (application use case, раздел 37) → ожидание (`pending`/`scheduled`) → атомарный захват worker'ом (`claimed`) → выполнение (`running`) → завершение с одним из терминальных или промежуточных исходов (`succeeded`, `retry_wait`, `failed`, `cancelled`, `dead_letter`/`terminal_failed`). Каждый переход состояния фиксируется в job record с временной меткой (раздел 43), обеспечивая полную историю без стирания предыдущих попыток (раздел 26 — идемпотентность опирается именно на эту историю).

## 25. Job state machine

Минимальные состояния:

- `pending` — job создан, ожидает claim;
- `scheduled` — job создан с отложенным временем начала (`scheduled_at`, раздел 31);
- `claimed` — job атомарно захвачен конкретным worker'ом (lease активен);
- `running` — worker выполняет бизнес-логику job;
- `succeeded` — job завершён успешно, результат сохранён;
- `retry_wait` — временная ошибка классифицирована, job ожидает повторной попытки (раздел 28–29);
- `failed` — job завершился ошибкой, но ещё не исчерпал попытки/не признан terminal;
- `cancelled` — job отменён (раздел 33);
- `dead_letter`/`terminal_failed` — job окончательно не может быть выполнен (раздел 30).

**Правила переходов:**

- переходы состояний явные и документируются как допустимый граф — job не может произвольно «перепрыгивать» между несмежными состояниями;
- job не считается успешным до фактического сохранения результата (не до начала выполнения);
- история попыток не стирается при повторных попытках;
- `failed` job не возвращается в `pending` молча — переход обратно к ожиданию выполнения происходит только через явный, наблюдаемый переход `retry_wait` → `pending`/`scheduled` по правилам retry (раздел 28);
- terminal failure (`dead_letter`) не удаляется без применения отдельной retention-политики (раздел 30, 46).

## 26. Idempotency

- at-least-once (раздел 15) допускает повторную доставку/выполнение — это архитектурная данность, а не дефект;
- каждый durable job обязан иметь явную idempotency-стратегию;
- idempotency key связан с бизнес-операцией (например, «сформировать evaluation для insight X за период Y»), а не только с транспортным идентификатором сообщения;
- уникальные ограничения БД используются там, где они отражают реальный бизнес-инвариант (`ADR-0004`, раздел 20);
- повторное выполнение job не создаёт второй `insight`/`evaluation`/`alert` без явного, осознанного правила, разрешающего это;
- внешний API может не поддерживать идемпотентность на своей стороне — это учитывается отдельно для каждой интеграции;
- side effect (например, вызов внешнего API) выполняется после проверки текущего состояния, а не вслепую;
- exactly-once **не обещается** (раздел 15);
- crash worker'а между внешним side effect и локальным commit — отдельный, явно признанный класс отказа (раздел 29, риск 34);
- reconciliation (сверка состояния) может потребоваться для критичных неидемпотентных эффектов (раздел 38).

## 27. Deduplication

- дедупликация job на входе (например, повторная постановка одной и той же логической задачи) обеспечивается тем же механизмом, что и идемпотентность результата — уникальными ограничениями на idempotency key, а не отдельным недокументированным механизмом;
- scheduler не создаёт дублирующиеся jobs при повторном запуске (раздел 31);
- дублирование job record не эквивалентно дублированию бизнес-эффекта, если idempotency-правила раздела 26 соблюдены — job-level и effect-level дедупликация различаются явно.

## 28. Retry

Retry допустим только для временных ошибок:

- network timeout;
- rate limit;
- временная недоступность provider;
- serialization failure (`ADR-0004`, раздел 19 — PostgreSQL Repeatable Read/Serializable);
- deadlock (`ADR-0004`, раздел 25 — PostgreSQL официально автоматически обнаруживает deadlock и прерывает одну из транзакций);
- временная нехватка ресурса.

**Retry не выполняется автоматически** для:

- validation errors;
- authentication errors;
- authorization errors;
- malformed payload;
- permanent provider rejection;
- unsupported operation;
- domain invariant violation.

Каждая попытка сохраняется в job record (раздел 24–25). Максимальное число попыток определяется конфигурацией, а не этим ADR. Официально: Celery как пример framework поддерживает такую классификацию через `autoretry_for` и не гарантирует exactly-once — задачи должны быть идемпотентны (раздел 60); этот принцип принимается как общий архитектурный урок независимо от того, что Celery этим ADR не выбирается.

## 29. Backoff и jitter

- используется увеличивающаяся (экспоненциальная) задержка между повторными попытками;
- jitter добавляется для предотвращения синхронного «retry storm» при массовом сбое;
- заголовок `Retry-After` внешнего API учитывается, если предоставлен;
- retry-политика зависит от класса ошибки (раздел 28), а не универсальна;
- конкретные числовые значения задержки/множителя выбираются отдельно, не этим ADR;
- пользователь не должен видеть ложный статус успеха во время retry-ожидания;
- долгий retry-цикл не должен бесполезно удерживать worker slot — job переходит в `retry_wait` с отложенным временем следующей попытки, а не блокирует worker активным ожиданием.

## 30. Timeouts

Разделяются явно (единый timeout на всё не используется):

- queue wait timeout — сколько job может ждать взятия в работу;
- claim/lease timeout — после которого lease считается просроченным и job может быть перехвачен;
- execution timeout — максимальная длительность выполнения;
- external HTTP timeout (`ADR-0001`, `ENGINEERING_PRINCIPLES.md`, пункт 17);
- LLM timeout;
- shutdown grace period (раздел 41);
- user-facing wait timeout — для синхронных операций (раздел 19), отличается от timeout durable job.

Истечение timeout **не означает автоматическую отмену** уже начатого внешнего side effect — внешний вызов мог фактически завершиться успешно на стороне provider даже после локального timeout (раздел 29, 38).

## 31. Scheduling

- `scheduled_at` хранится в UTC (`ADR-0004`, раздел 21);
- scheduler создаёт или активирует durable jobs — сам не выполняет бизнес-работу (раздел 15);
- повторный запуск scheduler (например, после рестарта) **не создаёт дубликаты** — обеспечивается тем же idempotency-механизмом, что и в разделе 26/27;
- пропущенные (missed) расписания обрабатываются по явной, документированной политике (например, выполнить один раз при следующем запуске или пропустить с записью в job record), а не произвольно;
- часовой пояс пользователя не хранится как naive time (`ADR-0004`, раздел 21);
- дрейф часов (clock drift) между узлами учитывается как источник неточности планирования;
- расписание не зависит от памяти одного web-процесса — это была бы разновидность in-process операции (раздел 20), неприменимая к durable-планированию;
- конкретный cron-подобный механизм/библиотека выбирается отдельно (раздел 53).

## 32. Periodic jobs

Повторяющиеся jobs (раздел 16, класс 6 — например, плановая проверка результата инсайта, DF-007) создаются scheduler'ом как отдельные durable job-записи на каждый цикл, а не как единая «вечно живущая» задача в памяти процесса. Это обеспечивает: применимость общей job state machine (раздел 25) к каждому запуску; независимое отслеживание истории попыток и результата каждого цикла; отсутствие потери запланированного цикла при рестарте scheduler/worker (раздел 42).

## 33. Cancellation

- `pending`/`scheduled` job может быть отменён напрямую (переход в `cancelled` без выполнения);
- `running` job отменяется **кооперативно** — worker периодически проверяет флаг отмены, немедленная остановка не гарантируется;
- запрос на отмену не гарантирует, что внешний side effect ещё не произошёл (раздел 26, 38);
- итоговый статус явно различает `cancelled` (отменено по запросу) и `failed` (завершилось ошибкой);
- отмена критичной операции аудируется (раздел 44);
- cleanup после отмены (например, откат частично выполненных шагов) проектируется явно для каждого класса задач, а не подразумевается автоматическим.

## 34. Priority

- приоритет вводится только при реальном, названном пользовательском сценарии — не «на будущее» (`ENGINEERING_PRINCIPLES.md`, пункт 67);
- starvation (постоянное откладывание low-priority job) запрещён — механизм приоритизации обязан гарантировать в конечном счёте обработку всех jobs;
- приоритет реализуется на уровне приложения/схемы job record, PostgreSQL не предоставляет встроенной приоритетной очереди — это архитектурное, а не технологическое решение.

## 35. Concurrency

- несколько worker-процессов могут выполняться параллельно, конкурентно забирая разные jobs (раздел 22);
- FIFO-порядок **не обещается** при нескольких worker'ах — параллельное выполнение по природе не сохраняет строгий порядок постановки;
- конкретное число worker-процессов и модель их развёртывания выбираются отдельно (раздел 53).

## 36. Ordering

- глобальный порядок выполнения **не гарантируется** только по timestamp (`ADR-0004`, раздел 21 — аналогичное правило для данных применяется и к jobs);
- если порядок важен для конкретного домена (например, jobs одного инструмента или пользователя), он обеспечивается сериализацией по aggregate/key на уровне приложения, а не глобальной блокировкой;
- глобальная сериализация всех jobs **запрещена** без конкретной, названной необходимости — она уничтожила бы пользу от нескольких worker'ов (раздел 35).

## 37. Transactions

- создание job может быть частью application-транзакции, инициировавшей его (например, атомарное сохранение insight + постановка evaluation-job в одной транзакции), где это архитектурно оправдано;
- outbox pattern может быть рассмотрен позднее как способ гарантировать атомарность «сохранить данные + поставить job» без немедленного выбора конкретной реализации (открытый вопрос, раздел 57);
- worker сначала атомарно фиксирует claim (короткая транзакция), затем выполняет внешний вызов вне открытой транзакции, затем сохраняет результат новой короткой транзакцией (`ADR-0004`, раздел 19);
- transaction rollback (например, отмена claim) **не откатывает** уже выполненный внешний side effect — это разные слои согласованности;
- distributed transaction между PostgreSQL и внешними системами **не вводится**.

## 38. External calls

- внешний API и LLM **не вызываются внутри открытой DB-транзакции** (`ADR-0004`, раздел 19; `FAILURE_MODEL.md`, раздел 5);
- worker обязан завершить/закоммитить транзакцию claim до выполнения сетевого вызова;
- для критичных неидемпотентных внешних side effect'ов (например, куда нельзя безопасно повторить вызов) требуется reconciliation-механизм — сверка фактического состояния у provider с локальным состоянием job при неопределённом исходе (раздел 26, 29, риск 34).

## 39. Failure handling

Для каждого класса отказа определяется ожидаемое поведение (в соответствии с `FAILURE_MODEL.md`):

- worker crash — job остаётся `claimed` с истекающим lease, восстанавливается другим worker'ом после timeout (раздел 42);
- web crash — durable job не затрагивается (job уже сохранён в PostgreSQL независимо от web-процесса);
- DB restart — durable jobs сохраняются благодаря WAL-durability PostgreSQL (раздел 60); активные claim'ы worker'ов, потерявших соединение, истекают по lease;
- network partition — worker не может подтвердить claim/результат, lease истекает, job становится доступен повторно (at-least-once, раздел 26);
- stale lease — обнаруживается по heartbeat/lease timeout (раздел 22, 30);
- duplicate delivery — обрабатывается идемпотентностью (раздел 26), не предотвращается на транспортном уровне;
- timeout — классифицируется как временная ошибка (раздел 28), обрабатывается согласно retry-политике;
- partial result — не считается успехом, job не переходит в `succeeded` без полного сохранения ожидаемого результата;
- invalid payload — классифицируется как постоянная ошибка (раздел 28), не повторяется автоматически;
- внешний side effect выполнен, но локальный commit не удался — явный, распознаваемый класс отказа, требующий reconciliation (раздел 26, 38);
- локальный commit выполнен, но acknowledgement (например, во внешнем broker'е при Фазе Broker) не удался — отдельный класс отказа для варианта C/D, не актуален для PostgreSQL-backed MVP-варианта;
- scheduler создаёт duplicate — предотвращается идемпотентностью планирования (раздел 31);
- clock drift — учитывается при оценке lease timeout и scheduled_at (раздел 21, 31);
- disk full — классифицируется как ресурсный отказ (`FAILURE_MODEL.md`, раздел 2, «Нехватка ресурсов»);
- connection exhaustion — аналогично, обнаруживается через наблюдаемость (раздел 43).

## 40. Dead-letter / terminal failure

- terminal failure (`dead_letter`/`terminal_failed`) **не удаляется молча**;
- причина отказа сохраняется вместе с job record;
- история всех попыток сохраняется, а не только последней;
- пользователь видит безопасное сообщение об ошибке, не раскрывающее внутренние детали (`ENGINEERING_PRINCIPLES.md`, пункт 39);
- оператор (владелец платформы) видит техническую причину через наблюдаемость (раздел 43);
- повторный запуск terminal-failed job требует явного действия (ручного или через отдельный управляемый процесс), а не происходит автоматически;
- повторный запуск после исправления причины создаёт новую попытку в рамках существующего job или новую job — конкретное правило определяется по классу задачи, не универсально этим ADR;
- retention terminal-failed записей определяется отдельно (раздел 46, 53).

## 41. Graceful shutdown

- worker перестаёт забирать (`claim`) новые jobs при получении сигнала остановки;
- worker завершает текущую job или безопасно освобождает её lease для последующего перехвата другим worker'ом;
- lease не остаётся «вечным» — всегда имеет timeout (раздел 22, 30);
- shutdown имеет ограниченный grace period, после которого процесс завершается принудительно;
- `SIGTERM` официально может быть перехвачен приложением для организации корректного завершения — «может быть обработан», в отличие от `SIGKILL`, который официально «не может быть перехвачен, заблокирован или проигнорирован» (раздел 60) — это прямое основание для использования `SIGTERM` как штатного сигнала graceful shutdown и признания, что `SIGKILL` cleanup не выполняет;
- job, прерванная аварийным завершением (`SIGKILL`, сбой питания и подобное), восстанавливается через механизм lease timeout после рестарта (раздел 42), а не через graceful-путь;
- lifecycle web-процесса и worker-процесса управляются раздельно — остановка одного не требует немедленной остановки другого.

## 42. Recovery after restart

- после рестарта worker'а jobs, ранее находившиеся в `claimed`/`running` с этим worker'ом, восстанавливаются по истечении lease timeout и становятся доступны для повторного claim (раздел 22, 25);
- после рестарта web-процесса уже созданные durable jobs не теряются — сохранность обеспечена PostgreSQL WAL durability (раздел 60: «если WAL-записи благополучно на диске, транзакция долговечна и переживёт любой сбой»);
- после рестарта PostgreSQL (например, после сбоя) recovery происходит через официальный механизм roll-forward (REDO) по WAL — уже закоммиченные jobs сохраняются, незакоммиченные — откатываются (раздел 60);
- scheduler после рестарта не порождает дублирующиеся периодические jobs (раздел 27, 31);
- recovery-путь после рестарта явно отличается от graceful shutdown-пути (раздел 41) — recovery предполагает отсутствие штатного cleanup.

## 43. Observability

Для каждой job минимально фиксируются: job ID; job type; status; attempt (номер попытки); created_at; scheduled_at; claimed_at; started_at; finished_at; duration; worker ID; correlation ID (`FAILURE_MODEL.md`, раздел 11); error class; retry reason; next retry time.

Метрики: queue depth; oldest pending age; success/failure rate; retry rate; execution duration; wait duration; количество «зависших» (stuck) jobs; dead-letter count; доступность worker'ов; конфликты claim'ов (contended `SKIP LOCKED`); давление на пул соединений БД.

Логи и метрики **не содержат** секретов и полного чувствительного payload (раздел 45).

## 44. Audit

- не каждая техническая попытка job является audit-событием — это создало бы шум, неотличимый от диагностических логов (`MODULE_BOUNDARIES.md`, модуль `audit`; `ENGINEERING_PRINCIPLES.md`, пункт 28);
- создание критичной пользовательской операции (постановка job, инициированной пользователем с бизнес-значимым эффектом) аудируется;
- отмена критичной job аудируется (раздел 33);
- ручной повторный запуск terminal-failed job аудируется (раздел 40);
- результат критичной job связывается с инициатором в audit trail;
- audit **не заменяется** обычными application-логами (`FAILURE_MODEL.md`, раздел 17.1 — критичное действие не считается завершённым без аудиторской записи);
- отказ подсистемы audit обрабатывается согласно `FAILURE_MODEL.md` (раздел 17.1) — job с критичным эффектом не считается полностью завершённой без аудиторской записи, если она требуется.

## 45. Security

- job payload не содержит plaintext-секретов (`ENGINEERING_PRINCIPLES.md`, пункт 6);
- worker использует минимально необходимые привилегии (`ADR-0004`, раздел 28 — принцип наименьших привилегий распространяется и на worker's DB user);
- job type не может быть подменён произвольным пользовательским вводом — тип job определяется приложением, не десериализуется напрямую из недоверенного источника;
- authorization проверяется **до** создания job, а не только при выполнении;
- worker не доверяет содержимому payload безвольно — критичные инварианты проверяются повторно перед выполнением side effect (аналогично `ADR-0003`, раздел 22.1 — «authorization не считается выполненной только потому, что…»);
- произвольное выполнение кода (arbitrary code execution) через payload запрещено;
- десериализация payload безопасна (не использует небезопасные форматы, допускающие выполнение кода);
- user isolation сохраняется — job одного пользователя не может повлиять на данные другого;
- логи не раскрывают credentials (раздел 43);
- отдельный broker (если будет введён, раздел 23) увеличивает attack surface — дополнительный сетевой сервис и credentials;
- service credentials (доступ worker'а к PostgreSQL, внешним API) выбираются и управляются отдельно, не этим ADR.

## 46. Cost

Учитываемые категории (без выдуманных сумм, аналогично `TECHNOLOGY_EVALUATION.md`, раздел 16):

- CPU/RAM worker-процесса(ов);
- дополнительное хранилище PostgreSQL под job-таблицу и историю попыток;
- стоимость polling (частые короткие запросы) относительно push-модели (`LISTEN`/`NOTIFY`, с учётом её официальных ограничений, раздел 22, 60);
- индексы job-таблицы (стоимость записи, раздел 47);
- retry (повторные внешние вызовы — потенциально повторная стоимость API/LLM);
- внешние API и LLM-вызовы, инициированные из jobs;
- мониторинг;
- backup (использует уже утверждённый backup PostgreSQL, `ADR-0004`, раздел 27 — без дополнительной стоимости на этапе MVP);
- отдельный broker (Вариант C/D) — заметная дополнительная стоимость при активации;
- сеть (актуально только при появлении отдельного broker);
- операционное время разработчика на эксплуатацию.

Отдельный broker **не вводится «на будущее»** — стоимость возникает только при доказанной необходимости (раздел 23).

## 47. Performance

- `SELECT ... FOR UPDATE SKIP LOCKED` официально сохраняет table-level `ROW SHARE` блокировку обычным образом — снимаются только row-level блокировки уже занятых строк (раздел 60) — это учитывается при оценке нагрузки на job-таблицу при большом числе конкурентных worker'ов;
- частый polling создаёт постоянную, измеримую нагрузку на PostgreSQL — компромисс между задержкой обнаружения job и нагрузкой оценивается при внедрении, возможно комбинирование с `LISTEN`/`NOTIFY` как оптимизацией задержки (не заменой durability, раздел 22);
- индексы job-таблицы (по статусу, `scheduled_at`, приоритету) ускоряют выборку claim-кандидатов, но имеют стоимость записи (аналогично `ADR-0004`, раздел 29);
- долгие job-транзакции запрещены (раздел 22, 37) именно из соображений производительности OLTP-нагрузки;
- числовые пороги throughput/latency не устанавливаются этим ADR — определяются при измерениях после реализации (раздел 53, 55).

## 48. Положительные последствия

- критичные фоновые задачи получают устойчивость к падению процесса, чего не может обеспечить `BackgroundTasks` (раздел 20);
- PostgreSQL-backed queue использует уже утверждённую, эксплуатируемую и понятную инфраструктуру (`ADR-0004`) без добавления нового сервиса в MVP;
- единая транзакционная граница с остальными данными платформы упрощает согласованность (раздел 37);
- явная job state machine и история попыток облегчают диагностику и восстановление (раздел 24–25, 43);
- поэтапная модель (broker — только по доказанной необходимости) предотвращает преждевременную инфраструктурную сложность (`ENGINEERING_PRINCIPLES.md`, пункт 67);
- механизм заложен для расширения на многие классы задач (раздел 16) без структурных изменений.

## 49. Отрицательные последствия

- PostgreSQL-backed очередь не предоставляет специализированных broker-возможностей «из коробки» (приоритетные очереди, sophisticated routing, встроенный dead-letter exchange) — их пришлось бы реализовывать вручную при необходимости;
- polling (даже оптимизированный `LISTEN`/`NOTIFY`) создаёт дополнительную, хоть и управляемую, нагрузку на основной OLTP-сервер, разделяемую с транзакционной нагрузкой платформы;
- рост объёма jobs может потребовать партиционирования или архивации job-таблицы (аналогично `ADR-0004`, раздел 24 — для рыночных данных);
- отсутствие встроенной exactly-once семантики требует дисциплины идемпотентности на уровне приложения для каждого класса задач;
- если в будущем потребуется отдельный broker, переход добавит эксплуатационную сложность и риск рассинхронизации (аналогично `ADR-0005`, раздел 21, 30 — для Qdrant).

## 50. Риски

1. Потеря job при рестарте.
2. In-process критичная задача (нарушение раздела 20).
3. Duplicate execution.
4. Неидемпотентный side effect.
5. Retry постоянной (permanent) ошибки.
6. Retry storm.
7. Worker crash во время выполнения.
8. Stale (просроченный, но не обнаруженный) lease.
9. Job «зависла» в `running`.
10. Connection exhaustion.
11. Долгая транзакция блокирует другие операции.
12. Внешний вызов внутри открытой транзакции.
13. Deadlock.
14. Serialization failure.
15. Scheduler создаёт дубликаты периодических jobs.
16. Пропущенное (missed) расписание.
17. Clock drift.
18. Starvation по приоритету.
19. Нарушение требуемого порядка выполнения.
20. Избыточно большой job payload.
21. Секреты в job payload.
22. Обход авторизации через job.
23. «Отравленный» (некорректный/вредоносный) job type.
24. Terminal failures игнорируются и накапливаются незамеченными.
25. Отсутствие наблюдаемости очереди.
26. Неограниченный рост истории job (retention не определён).
27. Рост объёма job-таблицы деградирует производительность.
28. Worker не развёрнут в production (задачи копятся необработанными).
29. Несовместимость версий web и worker.
30. Миграция схемы несовместима с уже существующими pending jobs.
31. Ручное редактирование статуса job в обход приложения.
32. Отдельный broker введён преждевременно.
33. PostgreSQL-очередь перегружает основную OLTP-нагрузку.
34. Неоднозначность acknowledgement (side effect произошёл, подтверждение — нет, или наоборот).
35. Отмена после того, как side effect уже произошёл.

## 51. Меры снижения рисков

1. Потеря job при рестарте → durable job сохраняется в PostgreSQL, WAL обеспечивает durability закоммиченных транзакций (раздел 22, 42, 60).
2. In-process критичная задача → явный запрет для классов 3–12 (раздел 16, 20).
3. Duplicate execution → идемпотентность на уровне бизнес-эффекта, а не только транспорта (раздел 26).
4. Неидемпотентный side effect → idempotency key, проверка состояния перед действием, reconciliation при неопределённости (раздел 26, 38).
5. Retry постоянной ошибки → явная классификация retryable/non-retryable ошибок (раздел 28).
6. Retry storm → экспоненциальный backoff с jitter (раздел 29).
7. Worker crash → lease timeout, job возвращается в пул доступных (раздел 22, 39, 42).
8. Stale lease → heartbeat/lease timeout обнаруживают и освобождают просроченный lease (раздел 22).
9. Job «зависла» → execution timeout и наблюдаемость (queue depth/stuck jobs, раздел 30, 43).
10. Connection exhaustion → наблюдаемость давления на пул соединений (раздел 43); конкретный pool — предмет реализации.
11. Долгая транзакция → явный запрет длинных транзакций (раздел 22, 37).
12. Внешний вызов в транзакции → явное разделение claim-транзакции и выполнения (раздел 22, 38).
13. Deadlock → консистентный порядок блокировок, retry классифицированных ошибок (раздел 28, `ADR-0004` раздел 25).
14. Serialization failure → retry согласно классификации (раздел 28).
15. Дубликаты periodic jobs → идемпотентность планирования (раздел 27, 31).
16. Пропущенное расписание → явная политика обработки missed schedule (раздел 31).
17. Clock drift → учитывается при расчёте lease/scheduled timeout (раздел 21, 31).
18. Starvation → приоритетный механизм обязан гарантировать конечную обработку всех jobs (раздел 34).
19. Нарушение порядка → сериализация по ключу на уровне приложения там, где порядок важен (раздел 36).
20. Избыточный payload → лимиты размера, исходные данные хранятся отдельно от job payload при необходимости (раздел 22, аналогично `ADR-0004` раздел 22).
21. Секреты в payload → job payload не содержит секретов по правилу (раздел 45); ревью схемы payload.
22. Обход авторизации → авторизация проверяется до создания job и повторно перед критичным side effect (раздел 45).
23. Отравленный job type → тип job не десериализуется напрямую из недоверенного ввода (раздел 45).
24. Игнорируемые terminal failures → наблюдаемость dead-letter count, явное отсутствие автоматического удаления (раздел 40, 43).
25. Отсутствие наблюдаемости → обязательный минимальный набор полей и метрик (раздел 43).
26. Неограниченный рост истории → retention-политика определяется на этапе внедрения (раздел 53), не оставляется неопределённой навсегда.
27. Деградация от роста job-таблицы → индексы, при необходимости партиционирование/архивация (аналогично `ADR-0004`, раздел 24), решается по измерениям.
28. Worker не развёрнут → проверка наличия и доступности worker включена в критерии проверки (раздел 55) и observability (worker availability, раздел 43).
29. Несовместимость версий web/worker → payload versioning и совместимость схемы job проверяются как часть процесса деплоя (открытый вопрос, раздел 57, требует отдельной deployment-практики).
30. Несовместимая миграция → миграции схемы job-таблицы планируются с учётом существующих pending jobs (expand/migrate/contract, аналогично `ADR-0004`, раздел 26).
31. Ручное редактирование статуса → операционная дисциплина; при необходимости — ограничение прав доступа к job-таблице (раздел 45).
32. Преждевременный broker → активация только через раздел 23, требующий измерений, а не предположений.
33. Перегрузка OLTP → мониторинг влияния очереди на PostgreSQL, переход к разделу 23 при доказанной перегрузке.
34. Неоднозначность acknowledgement → claim и завершение — отдельные шаги с явной фиксацией в job record (раздел 22, 24); reconciliation для критичных случаев (раздел 38).
35. Отмена после side effect → итоговый статус явно фиксирует это как известное ограничение кооперативной отмены (раздел 33), не выдаётся как гарантированная остановка.

## 52. NFR impact

Числовые NFR, связанные с очередью (throughput, latency, queue depth thresholds), не утверждены `NON_FUNCTIONAL_REQUIREMENTS.md` и не устанавливаются этим ADR — определяются при измерениях после реализации (раздел 30 таблицы сравнения; раздел 47, 55). Надёжность (durable jobs переживают рестарт), безопасность (раздел 45) и наблюдаемость (раздел 43) закладываются архитектурно с самого начала, а не добавляются постфактум.

## 54. План отката

**Если PostgreSQL-backed очередь не используется (откат к синхронному/in-process подходу):**

- остановить создание новых durable jobs;
- завершить или явно отменить pending jobs согласно политике;
- сохранить полную историю job для последующего анализа;
- вернуть операцию в синхронный режим только если это архитектурно безопасно для конкретного сценария (не для критичных классов раздела 16, пункты 3–12);
- durable-требования (раздел 15) не отменяются молча — отказ от них фиксируется явным новым решением;
- новый ADR фиксирует замену.

**Если введён отдельный broker (переход к Варианту C/D):**

- остановить публикацию новых сообщений в PostgreSQL-очередь;
- дренировать (drain) существующих consumer'ов PostgreSQL-подхода;
- сохранить состояние PostgreSQL job до полного подтверждения переноса;
- переключить создание jobs на предыдущий (PostgreSQL-backed) подход в случае отката от broker;
- проверить отсутствие потерянных side effect'ов при переключении в любую сторону;
- удалить неиспользуемую инфраструктуру только после сверки;
- PostgreSQL остаётся system of record бизнес-результатов независимо от выбранного механизма доставки задач.

## 55. Критерии проверки решения

После будущей реализации (без создания этих проверок в рамках настоящей задачи):

1. durable job переживает рестарт web-процесса;
2. durable job переживает рестарт worker-процесса;
3. duplicate delivery не создаёт duplicate бизнес-эффект;
4. постоянная (permanent) ошибка не повторяется бесконечно;
5. история retry сохраняется полностью;
6. «зависшая» (stuck) job восстанавливается автоматически по истечении lease;
7. scheduler не создаёт дубликаты периодических jobs;
8. отмена явно отличима от отказа в статусе;
9. graceful shutdown корректно освобождает активные lease;
10. внешние вызовы не выполняются внутри открытой DB-транзакции;
11. job payload не содержит секретов;
12. авторизация проверена до создания и (при необходимости) повторно перед side effect;
13. queue depth и связанные метрики наблюдаемы;
14. terminal failure видим оператору и не удаляется молча;
15. совместимость версий web/worker проверяется как часть процесса деплоя;
16. web-процесс продолжает отвечать на запросы во время выполнения долгой job;
17. `BackgroundTasks` не используются для критичных классов job (раздел 16, пункты 3–12);
18. exactly-once нигде не заявляется как гарантия;
19. отдельный broker отсутствует без отдельного принятого ADR;
20. PostgreSQL OLTP-производительность не деградирует сверх измеримых, согласованных требований.

## 56. Условия пересмотра

ADR-0006 пересматривается, если:

- PostgreSQL-backed queue не достигает утверждённых NFR после измерений;
- количество jobs существенно растёт сверх первоначальных оценок;
- число необходимых worker-процессов существенно растёт;
- требуется специализированная routing-topology, нецелесообразная поверх PostgreSQL;
- требуется независимый от PostgreSQL lifecycle очереди;
- требования к надёжности (reliability) существенно меняются;
- появляются multi-region требования;
- PostgreSQL становится узким местом (bottleneck) для платформы в целом;
- появляется обоснованная потребность в потоковой (event streaming) обработке, для которой Kafka-подобная модель становится оправданной;
- отдельный broker измеримо снижает суммарную операционную сложность относительно текущего решения;
- выбранная в будущем библиотека/подход теряет поддержку;
- требования compliance меняются;
- обеспечение бизнес-эффекта, эквивалентного exactly-once, оказывается невозможным в рамках текущей модели идемпотентности.

## 57. Открытые вопросы

- конкретная Python-библиотека или собственный data-access подход для очереди не выбираются этим ADR (раздел 53, шаг 16);
- конкретный scheduler-механизм/библиотека не выбирается;
- конкретные числовые значения timeout, retry-лимитов, backoff-множителя и lease-длительности не устанавливаются;
- необходимость outbox pattern для гарантии «сохранить данные + поставить job» остаётся открытой — решается при внедрении (раздел 37);
- точная схема таблицы jobs и индексов не проектируется этим ADR;
- retention-политика для истории jobs и terminal failures не установлена (раздел 40, 46);
- практика совместимости версий web/worker при деплое не определена этим ADR (риск 29, раздел 51).

## 58. Решение Product Owner

Утверждено. Product Owner фиксирует следующую архитектурную стратегию фоновых задач и очереди для MVP:

- критичные, долгие, плановые и требующие гарантированного выполнения задачи выполняются отдельным worker-процессом;
- PostgreSQL job record является source of truth состояния задач;
- отдельный Redis, RabbitMQ или Kafka broker в MVP не вводится;
- FastAPI `BackgroundTasks` не используются для критичных и долговечных задач;
- exactly-once не обещается;
- конкретная Python worker/queue library, scheduler, схема таблиц, retry library и отдельный broker остаются предметом отдельных implementation-решений.

## 60. Источники исследования

Исследование выполнено 2026-08-05 исключительно по официальным первичным источникам (postgresql.org, docs.python.org, redis.io, rabbitmq.com, kafka.apache.org, docs.celeryq.dev, ранее исследованные fastapi.tiangolo.com/starlette.io в рамках `ADR-0002`), без использования блогов, Reddit, Medium, маркетинговых статей, неофициальных benchmark и рейтингов очередей.

**PostgreSQL:**
- [postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE) — официально: `SKIP LOCKED` пропускает строки, которые нельзя немедленно заблокировать; предназначен для «избежания конкуренции блокировок при множественных потребителях, обращающихся к queue-like таблице»; даёт несогласованное представление данных, не подходит для general-purpose работы; table-level `ROW SHARE` блокировка всё равно берётся обычным образом.
- [postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS) — официально: advisory locks — прикладные блокировки вне обычной MVCC-модели; session-level (не следуют транзакционной семантике, требуют явного снятия) и transaction-level (снимаются автоматически при завершении транзакции); типовое применение — эмуляция pessimistic locking.
- [postgresql.org/docs/current/sql-notify.html](https://www.postgresql.org/docs/current/sql-notify.html) — официально: `LISTEN`/`NOTIFY` — IPC-механизм между клиентами одной БД; уведомление доставляется только активно слушающим клиентам в момент отправки; **не гарантирует доставку**, не персистентно (если никто не слушает — уведомление теряется), недоставленные уведомления не сохраняются; очередь уведомлений ограничена 8 ГБ, транзакция может завершиться ошибкой при переполнении.
- [postgresql.org/docs/current/wal-intro.html](https://www.postgresql.org/docs/current/wal-intro.html) — официально: изменения данных записываются на диск только после того, как WAL-записи, описывающие изменения, зафиксированы на постоянном носителе; это даёt durability закоммиченным транзакциям без необходимости немедленно сбрасывать изменённые страницы данных; восстановление после сбоя — roll-forward (REDO) повторным применением WAL-записей.

**Python:**
- [docs.python.org/3/library/signal.html](https://docs.python.org/3/library/signal.html) — официально: `SIGTERM` может быть перехвачен и обработан приложением (`signal.signal()`), что позволяет организовать graceful shutdown; `SIGKILL` официально «не может быть перехвачен, заблокирован или проигнорирован» — принудительное немедленное завершение без возможности cleanup.
- [docs.python.org/3/library/multiprocessing.html](https://docs.python.org/3/library/multiprocessing.html) — официально: `multiprocessing` обеспечивает параллелизм на основе отдельных процессов, минуя GIL; рекомендуется для CPU-bound нагрузки и сценариев, требующих изоляции процессов и отказоустойчивости через перезапуск процесса; `asyncio` эффективнее для I/O-bound задач в одном процессе.

**Redis:**
- [redis.io/docs/latest/develop/data-types/streams](https://redis.io/docs/latest/develop/data-types/streams/) — официально: Redis Streams поддерживают consumer groups, `XREADGROUP`/`XACK`, Pending Entries List (PEL) для отслеживания недоставленных подтверждений, `XCLAIM`/`XAUTOCLAIM` для восстановления «зависших» сообщений; модель по умолчанию — at-least-once; официально заявленная exactly-once семантика (через `XACKDEL`/`XDELEX`) документирована как более новая, опциональная возможность (Redis 8.2+), а не universal-гарантия по умолчанию.

**RabbitMQ:**
- [rabbitmq.com/docs/confirms](https://www.rabbitmq.com/docs/confirms) — официально: подтверждения потребителя (manual/automatic) и publisher confirms — независимые механизмы; automatic ack описан как «fire-and-forget» и небезопасен при разрыве соединения потребителя; неподтверждённые сообщения официально повторно доставляются с флагом `redeliver`, потребители должны обрабатывать их идемпотентно; персистентные сообщения всё равно могут быть потеряны, если узел падает до записи на диск.

**Kafka:**
- [kafka.apache.org/intro](https://kafka.apache.org/intro) — официально: retention настраивается per-topic (события удаляются по истечении заданного срока); порядок событий в пределах partition гарантирован для любого потребителя; официально заявлена поддержка обработки событий exactly-once как возможность платформы (не безусловная гарантия любого потребления).
- [kafka.apache.org/uses](https://kafka.apache.org/uses) — официально: Kafka позиционируется как высокопроизводительная альтернатива традиционным message broker (ActiveMQ/RabbitMQ) с партиционированием, репликацией и отказоустойчивостью, но архитектурно построен вокруг персистентного, воспроизводимого лога событий, а не модели удаления сообщений традиционной очереди — это прямое основание не рассматривать Kafka как обычную task queue по умолчанию.

**Celery** (рассмотрена только как пример framework, не выбирается):
- [docs.celeryq.dev/en/stable/userguide/tasks.html#retrying](https://docs.celeryq.dev/en/stable/userguide/tasks.html#retrying) — официально: retry через `retry()`/`autoretry_for`, поддержка `retry_backoff`; acknowledgement зависит от `acks_late` (по умолчанию `False` — ack до выполнения; `True` — ack после выполнения, требует идемпотентности задач); официально прямо указано — Celery **не гарантирует exactly-once execution**, задачи должны быть идемпотентны.

**FastAPI/Starlette** (факты подтверждены ранее в рамках `ADR-0002`, раздел 32, переиспользованы без повторного полного цитирования): `BackgroundTasks` выполняются в процессе приложения после формирования ответа; официальная документация рекомендует отдельные инструменты для тяжёлых, не требующих того же процесса вычислений.
