## 11. Контекст

`ADR-0001`–`ADR-0007` определили язык/runtime, HTTP adapter, frontend framework, хранилище, стратегию поиска, фоновые задачи и LLM-интеграцию, но ни один из них не выбрал, как эти компоненты физически развёртываются. `ADR-0004` (раздел 40) явно отложил выбор deployment-модели PostgreSQL к настоящему ADR. `ADR-0002` (раздел 12) явно исключил reverse proxy, TLS termination, ASGI server и CORS production-политику из своей области. `ADR-0003` зафиксировал, что Next.js требует Node.js runtime и что deployment Next.js сложнее статического SPA (раздел 26). `ADR-0006` установил отдельный worker-процесс, обращающийся к тому же PostgreSQL, что и web-процесс. `TECHNOLOGY_EVALUATION.md` обозначил `ADR-0008` в дорожной карте как «контейнеризация и single-server deployment».

Итоговый состав компонентов платформы, подлежащих развёртыванию: backend (FastAPI, `ADR-0002`), frontend (Next.js, `ADR-0003`), worker (`ADR-0006`), PostgreSQL (`ADR-0004`), reverse proxy (роль, не выбираемая этим ADR как конкретный продукт).

Дата проверки технологических данных, использованных в настоящем ADR: 2026-08-05 (см. раздел 61 «Источники исследования»).

## 12. Проблема

Как физически развернуть backend, frontend, worker, PostgreSQL и reverse proxy на этапе MVP, чтобы решение было воспроизводимым, переносимым между Windows-разработкой и Linux-production, эксплуатируемым одним разработчиком на одном сервере, безопасным по умолчанию, поддерживало graceful shutdown, health checks, backup/restore PostgreSQL, HTTPS через автоматически продлеваемые сертификаты, и не вводило оркестрационную или облачную сложность, не обоснованную объёмом MVP.

Настоящий ADR не выбирает: cloud provider, Kubernetes, Docker Swarm, Nomad, Helm, Terraform, Ansible, systemd unit files, CI/CD систему, конкретный reverse proxy продукт (Nginx/Caddy/Traefik) и его конфигурацию, конкретный monitoring stack, Redis/RabbitMQ/Kafka.

## 13. Ограничения

- решение принимается до появления Dockerfile/Compose-файлов — миграционная стоимость на этом этапе минимальна;
- backend (`ADR-0001`, `ADR-0002`), worker (`ADR-0006`) и PostgreSQL (`ADR-0004`) уже утверждены — deployment-модель оценивается относительно них, а не выбирается заново;
- Next.js официально требует Node.js runtime в production (`ADR-0003`, раздел 16) — deployment-модель должна это учитывать;
- один разработчик отвечает за эксплуатацию — Kubernetes и multi-node оркестрация не вводятся без доказанной необходимости (`ENGINEERING_PRINCIPLES.md`, пункт 67);
- MVP разворачивается на одном сервере (`PRODUCT_SCOPE.md`, раздел 22);
- решение не должно предполагать выбор конкретного cloud provider — платформа не должна быть заблокирована на одном облаке;
- решение не должно предполагать выбор конкретного reverse proxy продукта, monitoring stack или CI/CD — это выходит за рамки задачи;
- официальные источники (раздел 61) не подтверждают, что снимок тома с работающей БД без соблюдения условий консистентности является валидным backup — это ограничение прямо учитывается (раздел 24).

## 14. Движущие факторы решения

Критерии сравнения (раздел 17) выведены из `ENGINEERING_PRINCIPLES.md`, `PRODUCT_SCOPE.md`, `ADR-0001`–`ADR-0007` и контекста задачи: соответствие MVP, воспроизводимость, портируемость Windows/Linux, эксплуатационная сложность для одного разработчика, стоимость, vendor/cloud lock-in, изоляция процессов, безопасность по умолчанию, graceful shutdown, health checks, backup/restore устойчивых данных, HTTPS/TLS automation, горизонтальное масштабирование, обратимость, будущий рост.

## 15. Термины

**Контейнер** — изолированный процесс с собственной файловой системой, сетью и деревом процессов, порождённый из образа (раздел 61).

**Образ (image)** — неизменяемый, слоистый пакет файлов/бинарников/библиотек/конфигурации, необходимый для запуска контейнера (раздел 61).

**OCI Image Specification** — открытая спецификация, стандартизирующая структуру образа (manifest, index, слои, конфигурация) для интероперабельности инструментов сборки/транспортировки/запуска (раздел 61).

**Compose Specification** — открытая спецификация, стандартизирующая многосервисное приложение через абстракции services/networks/volumes/secrets/configs (раздел 61).

**Volume** — управляемое Docker персистентное хранилище, существующее вне жизненного цикла конкретного контейнера (раздел 61).

**Bind mount** — монтирование конкретного пути хост-системы внутрь контейнера, зависящее от структуры хоста (раздел 61).

**Restart policy** — декларативное правило автоматического перезапуска контейнера при остановке (раздел 61).

**Health check** — механизм, определяющий состояние контейнера (`starting`/`healthy`/`unhealthy`) сверх факта его запуска (раздел 61).

**Readiness** — готовность сервиса принимать трафик; **Liveness** — факт, что процесс сервиса жив и не завис. Настоящий ADR различает эти понятия как разные вопросы (раздел 27), не как синонимы.

**Reverse proxy** — компонент, принимающий внешний HTTP(S)-трафик, терминирующий TLS и перенаправляющий запросы внутренним сервисам (раздел 61).

## 16. Рассмотренные варианты

Рассмотрены ровно четыре варианта:

- **Вариант A — без контейнеров** (процессы разворачиваются напрямую на сервере).
- **Вариант B — Docker Compose single-server.**
- **Вариант C — Kubernetes.**
- **Вариант D — Managed PaaS.**

Качественные оценки — архитектурная оценка на основании официальной документации (раздел 61), а не результат benchmark.

## 18. Выбранная стратегия

- для MVP используется **Docker Compose на одном сервере**;
- Kubernetes **не вводится**;
- multi-node оркестрация **не вводится**;
- конкретный cloud provider **не выбирается** — платформа не создаёт зависимость от одного облака;
- контейнеризуются: backend, frontend, worker, PostgreSQL, reverse proxy (раздел 19);
- конкретный reverse proxy продукт (Nginx/Caddy/Traefik) **не выбирается** этим ADR (раздел 33);
- переход к оркестрации или managed PaaS рассматривается **отдельным ADR** только при доказанных, измеренных ограничениях однохостовой модели (раздел 38).

## 19. Контейнеризуемые компоненты

- **backend** — FastAPI (`ADR-0002`) внутри CPython 3.14 GIL-enabled runtime (`ADR-0001`);
- **frontend** — Next.js App Router (`ADR-0003`), требующий Node.js runtime в контейнере;
- **worker** — отдельный процесс критичных/долгих задач (`ADR-0006`), тот же backend runtime, отдельный контейнер от web-процесса;
- **PostgreSQL** — основное транзакционное хранилище (`ADR-0004`), официальный контейнерный образ как отправная точка (раздел 20, 61);
- **reverse proxy** — принимает внешний трафик, терминирует TLS, направляет запросы backend/frontend (раздел 32–34).

Каждый компонент — отдельный контейнер; ни один компонент не совмещается в одном контейнере с другим (соответствует изоляции процессов, раздел 17, критерий 7).

## 20. Образы

- образ — неизменяемый, слоистый пакет файлов/бинарников/библиотек/конфигурации (раздел 61);
- backend/worker образ строится от официального базового образа Python, соответствующего утверждённой линии CPython (`ADR-0001`) — конкретный тег образа не фиксируется этим ADR;
- frontend образ строится от официального базового образа Node.js, соответствующего утверждённой политике `ADR-0003` (раздел 16 — Active/Maintenance LTS, не EOL-линия);
- PostgreSQL образ — официальный образ, соответствующий утверждённой версионной политике `ADR-0004`;
- reverse proxy образ — официальный образ выбранного (позже) продукта;
- образы должны собираться из воспроизводимого источника (зафиксированные зависимости — `ADR-0001`, `ADR-0003`);
- конкретные Dockerfile не создаются в рамках настоящего ADR.

## 21. Build

- multi-stage build официально позволяет использовать несколько `FROM` в одном Dockerfile, с выборочным копированием артефактов между стадиями (`COPY --from=`), исключая build-инструментарий из финального образа (раздел 61);
- backend/worker и frontend образы используют multi-stage build там, где это уменьшает финальный образ (например, отделение build-зависимостей frontend от production-образа);
- официальная документация FastAPI не описывает обязательность multi-stage build для backend — решение о его использовании для конкретного образа принимается на этапе реализации (раздел 61);
- build cache используется официальным механизмом слоёв — порядок инструкций Dockerfile влияет на эффективность кеша (раздел 61: копирование манифеста зависимостей до кода приложения);
- build не запускает миграции схемы БД или иные необратимые операции (согласуется с `ADR-0004`, раздел 26 — миграция не встроена в старт процесса);
- конкретное содержимое Dockerfile не создаётся в рамках настоящего ADR.

## 22. Runtime

- контейнер — изолированный процесс с собственной файловой системой, сетью и деревом процессов (раздел 61);
- официально `docker run` создаёт и запускает контейнер, среда исполнения обеспечивает изоляцию ресурсов, заданную при создании (раздел 61: память/CPU/block I/O/доступ к устройствам);
- runtime backend/worker — CPython 3.14 GIL-enabled внутри контейнера (`ADR-0001`), не изменяется контейнеризацией;
- каждый контейнер запускает ровно один основной процесс (backend web, worker, PostgreSQL, frontend, reverse proxy — раздел 19);
- PID 1 внутри контейнера отвечает за reaping дочерних процессов; официальная документация Docker явно рекомендует флаг `--init`, вставляющий облегчённый init-процесс как PID 1 именно для этой цели, вместо встраивания полноценной init-системы (раздел 61) — это учитывается при проектировании запуска контейнеров, не как выбор конкретной init-системы, а как факт, требующий решения на этапе реализации.

## 23. Volumes и Persistent data

- официально volume — управляемое Docker персистентное хранилище, существующее вне жизненного цикла конкретного контейнера, в отличие от bind mount, зависящего от структуры хоста (раздел 61);
- PostgreSQL данные хранятся в volume, а не в writable-слое контейнера — официальная документация образа PostgreSQL прямо предупреждает, что монтирование volume не в тот путь (например, родительский каталог вместо каталога данных) не обеспечит персистентность при пересоздании контейнера (раздел 61) — точный путь монтирования фиксируется на этапе реализации в соответствии с используемой версией образа;
- официальная документация отмечает, что volume даёт более предсказуемую производительность и более безопасное совместное использование между контейнерами, чем bind mount (раздел 61);
- bind mount может использоваться для конфигурации, которую разработчик редактирует напрямую на хосте (например, локальная разработка), но не для PostgreSQL-данных production;
- volume для PostgreSQL — критичный persistent-объект платформы; удаление volume эквивалентно потере данных, если не выполнен backup (раздел 24);
- frontend/backend/worker контейнеры архитектурно являются stateless относительно бизнес-данных — устойчивое состояние платформы находится в PostgreSQL (`ADR-0004`), не в файловой системе этих контейнеров.

## 24. Backups

- backup PostgreSQL использует официальные механизмы `ADR-0004` (раздел 27) — `pg_basebackup`/continuous archiving через WAL — независимо от контейнеризации;
- официальная документация PostgreSQL прямо указывает: файловый снимок каталога данных валиден только при полностью остановленном сервере, либо при консистентном атомарном снимке (например, снимок volume), включающем WAL-файлы, с рекомендацией предварительного `CHECKPOINT` (раздел 61) — «сырое» копирование volume работающего контейнера без соблюдения этих условий backup'ом не считается;
- backup не хранится только внутри того же контейнера/хоста, что и сам PostgreSQL-volume;
- backup PostgreSQL-volume следует официальной модели `ADR-0004` (раздел 27) — регулярность, шифрование, ограничение доступа, периодические restore drills;
- backup конфигурации (образы, Compose-модель) обеспечивается воспроизводимостью самой сборки (раздел 20–21), а не отдельным снимком состояния;
- секреты не попадают в backup images или backup scripts (раздел 29).

## 25. Restore

- restore PostgreSQL следует уже утверждённой модели `ADR-0004` (раздел 27) — восстановление проверяется regular restore drills;
- восстановление контейнеризованного PostgreSQL включает: остановку сервиса, замену/восстановление volume, запуск PostgreSQL с восстановленными данными, проверку целостности перед возобновлением трафика;
- restore инфраструктуры (backend/frontend/worker/reverse proxy) сводится к пересборке/перезапуску контейнеров из образов — эти контейнеры не хранят критичное состояние (раздел 23);
- план restore верифицируется как часть критериев проверки (раздел 56), не создаётся в рамках настоящего ADR как исполняемый скрипт.

## 26. Health checks

- официально `HEALTHCHECK`/Compose `healthcheck` даёт контейнеру статус состояния (`starting`/`healthy`/`unhealthy`) сверх факта запуска процесса, с настраиваемыми `interval`/`timeout`/`retries`/`start_period` (раздел 61);
- backend/frontend/worker/PostgreSQL/reverse proxy получают health check, отражающий их реальную готовность, а не только факт существования процесса;
- для PostgreSQL официальный образ не документирует конкретный healthcheck-паттерн на своей странице, но официальная утилита `pg_isready` документирует специально предназначенные для скриптов коды возврата (готов/не готов/нет ответа/ошибка параметров) — пригодность для health check вытекает из документированного назначения утилиты, а не является прямой рекомендацией со страницы образа (раздел 61) — это отражено честно, без приписывания официальной рекомендации, которой не найдено;
- health check зависимого сервиса (например, worker или backend, ожидающего готовности PostgreSQL) использует health-статус зависимости, а не только факт запуска контейнера — Compose Specification официально поддерживает условие ожидания по статусу health check (раздел 61);
- конкретные команды health check не фиксируются этим ADR — определяются на этапе реализации.

## 27. Readiness и Liveness

- readiness и liveness — разные вопросы: готовность принимать трафик vs факт, что процесс жив и не завис;
- backend readiness означает готовность обслуживать HTTP-запросы (включая, при необходимости, доступность PostgreSQL);
- backend liveness означает, что процесс не завис — не обязательно то же самое, что готовность обслуживать все запросы;
- reverse proxy направляет трафик на backend/frontend только при подтверждённой readiness (конкретный механизм — предмет реализации, раздел 61 — пассивная проверка доступности документирована на уровне reverse proxy в открытых версиях исследованных продуктов, активная периодическая проверка в части продуктов доступна только в коммерческих редакциях, раздел 61);
- PostgreSQL readiness проверяется независимо от readiness backend (раздел 26);
- различие readiness/liveness сохраняется даже в отсутствие оркестратора уровня Kubernetes — само по себе оно является архитектурным принципом проектирования сервиса, не механизмом конкретной платформы.

## 28. Restart policy

Официально документированы четыре значения (раздел 61): `no` (без автоперезапуска, по умолчанию), `on-failure[:max-retries]` (перезапуск только при ненулевом коде выхода, с опциональным лимитом попыток), `always` (перезапуск при остановке, включая после перезапуска демона, но не после ручной остановки до следующего перезапуска демона/контейнера), `unless-stopped` (аналогично `always`, но вручную остановленный контейнер не перезапускается автоматически даже после перезапуска демона). Все политики официально вступают в силу только после ≥10 секунд успешной работы контейнера (раздел 61).

- backend/worker/frontend/reverse proxy используют политику, допускающую автоматическое восстановление после сбоя, но не скрывающую постоянно падающий контейнер бесконечным немедленным перезапуском без учёта деградации (конкретное значение — предмет реализации);
- PostgreSQL использует restart policy, совместимую с его собственной моделью graceful shutdown (раздел 35) — автоматический перезапуск не должен интерферировать с уже выполняющимся штатным остановом;
- restart policy не заменяет health check — перезапущенный, но не готовый к работе контейнер не должен считаться исправным только по факту перезапуска.

## 29. Secrets

- официально Compose secrets объявляются на верхнем уровне и предоставляются только явно указанным сервисам, монтируются read-only в `/run/secrets/<name>`, что даёт контроль доступа на уровне файловой системы (раздел 61);
- официальная документация прямо противопоставляет secrets переменным окружения: переменные окружения часто доступны всем процессам контейнера и могут попадать в логи при отладке; секреты не должны храниться в незашифрованном виде в Dockerfile или исходном коде приложения (раздел 61);
- официальный образ PostgreSQL документирует `_FILE`-варианты переменных инициализации (например, вариант для пароля), позволяющие передавать значение через файл, а не напрямую через переменную окружения (раздел 61) — это предпочтительный путь для паролей БД;
- API-ключи LLM-провайдера (`ADR-0007`, раздел 45) и credentials PostgreSQL (`ADR-0004`, раздел 28) следуют одной и той же модели — не встраиваются в образ, не логируются, доступны только тем контейнерам, которым необходимы;
- конкретный механизм хранения секретов на сервере (например, конкретный secrets backend) не выбирается этим ADR.

## 30. Environment variables

- официально Compose поддерживает три механизма передачи переменных: атрибут `environment`, `env_file` (в том числе несколько файлов с приоритетом последнего), и передачу через CLI (раздел 61);
- переменные окружения используются для несекретной конфигурации (например, режим окружения, некритичные флаги);
- секретные значения предпочтительно передаются через механизм secrets (раздел 29), а не через обычные переменные окружения, в соответствии с официальным предупреждением о видимости переменных окружения всем процессам контейнера и логам (раздел 61);
- `.env`-файлы, используемые для интерполяции значений в саму Compose-модель, не путаются с секретами, доступными процессу внутри контейнера — это разные механизмы (раздел 61);
- конкретный список переменных окружения не определяется этим ADR.

## 31. Network и internal communication

- официально контейнеры в default bridge-сети видят друг друга только по IP; пользовательские (user-defined) bridge-сети официально добавляют DNS-based service discovery — контейнеры обращаются друг к другу по имени сервиса через встроенный DNS Docker (раздел 61);
- backend, worker, frontend, PostgreSQL и reverse proxy находятся в общей внутренней сети, позволяющей обращение по имени сервиса;
- порты не публикуются на хост по умолчанию — официально публикация конкретного порта на хост требует явного `--publish`/эквивалента (раздел 61);
- наружу (на хост) публикуются только порты reverse proxy (80/443) — backend, worker, frontend и PostgreSQL не публикуются напрямую на хост; эта топология опирается на подтверждённые официальной документацией Docker возможности публикации портов и внутренних сетей (раздел 61), но сама конкретная схема «наружу — только proxy» является архитектурным решением этого ADR, а не процитированной рекомендацией со страниц исследованных reverse proxy продуктов, которые не содержали официального заявления именно об этом паттерне (раздел 61) — это указано честно, чтобы не приписывать источникам вывод, которого они не содержат;
- worker обращается к PostgreSQL и к внешним API (LLM-провайдер, `ADR-0007`) — не к backend напрямую, если это не требуется конкретным use case;
- frontend обращается только к backend через reverse proxy (`ADR-0003`, раздел 17) — не к PostgreSQL, не к worker напрямую.

## 32. Reverse proxy

- reverse proxy — единственная точка входа внешнего трафика;
- официально роль reverse proxy — приём запроса, перенаправление backend'у (например, через `proxy_pass`-подобный механизм), опционально балансировка нагрузки (раздел 61);
- reverse proxy терминирует TLS (раздел 33) и перенаправляет обычный HTTP внутренним сервисам;
- reverse proxy направляет трафик backend (`ADR-0002`) и frontend (`ADR-0003`) по маршруту, конкретная схема которого — предмет реализации;
- конкретный продукт reverse proxy (Nginx/Caddy/Traefik) **не выбирается** этим ADR — оба исследованных официальных источника (раздел 61) документируют жизнеспособные, но различающиеся по умолчанию модели получения TLS-сертификатов (раздел 33–34), что является входным фактором для отдельного выбора продукта на этапе реализации;
- health check зависимости backend/frontend от reverse proxy учитывается при маршрутизации (раздел 26–27), конкретный механизм не фиксируется.

## 33. HTTPS и TLS

- TLS терминируется на reverse proxy, не на backend/frontend-контейнерах — согласуется с уже зафиксированным в `ADR-0002` (раздел 12) выносом TLS termination за пределы FastAPI adapter, а также с официальной документацией FastAPI, описывающей HTTPS обычно как задачу внешнего TLS Termination Proxy (раздел 61);
- официально исследованные reverse proxy продукты документируют TLS termination через явную конфигурацию сертификата/ключа (один из вариантов) либо через встроенное автоматическое управление сертификатами (другой вариант, раздел 61) — конкретный механизм не выбирается этим ADR (раздел 32);
- backend получает исходную схему запроса (HTTP/HTTPS) через заголовки, передаваемые reverse proxy (в частности, FastAPI-документация упоминает опцию проксирования заголовков — раздел 61) — конкретная реализация не фиксируется этим ADR;
- сертификаты и приватные ключи не хранятся в образе или репозитории — управляются как секреты/volume reverse proxy (раздел 29).

## 34. Let's Encrypt

- официально сертификаты Let's Encrypt имеют срок действия 90 дней (либо 6 дней для короткоживущего варианта), с официальной рекомендацией автоматизированного продления (для 90-дневных — каждые 60 дней) и намеренного случайного распределения времени продления, чтобы избежать синхронизированной нагрузки (раздел 61);
- следовательно, ручное продление сертификатов архитектурно неприемлемо — продление должно быть автоматизировано;
- один из исследованных reverse proxy продуктов официально заявляет автоматическое получение и продление сертификатов «из коробки», по умолчанию обращаясь к Let's Encrypt с официально документированным fallback на альтернативный ACME-совместимый центр сертификации при недоступности (раздел 61); другой требует отдельного ACME-клиента, поскольку сам не занимается выпуском/продлением сертификатов (раздел 61) — это входит в критерии будущего выбора конкретного продукта (раздел 32), не решается этим ADR;
- ACME-протокол — стандартный механизм автоматического получения сертификатов, используемый Let's Encrypt (раздел 61);
- конкретный ACME-клиент не выбирается этим ADR.

## 35. Graceful shutdown

- graceful shutdown разделяется по компонентам, так как их официальная семантика различается:
  - **backend/worker (CPython/Uvicorn):** `SIGTERM` — стандартный, перехватываемый сигнал (официально подтверждено `docs.python.org`, раздел 61); Uvicorn документирует параметр ожидания graceful shutdown перед принудительным завершением (раздел 61); `SIGTERM`/`SIGINT` инициируют штатное завершение lifespan-приложения (`ADR-0002`, раздел 18.6) — конкретное числовое значение таймаута не фиксируется этим ADR;
  - **PostgreSQL:** официально `SIGTERM` соответствует «Smart Shutdown» — новые подключения запрещаются, существующие сессии завершаются штатно, затем сервер останавливается; официально явно не рекомендуется использовать `SIGKILL` для остановки PostgreSQL, поскольку это мешает серверу освободить разделяемую память и семафоры (раздел 61) — это прямое основание требовать, чтобы grace period контейнера PostgreSQL был достаточным для завершения Smart Shutdown до эскалации до `SIGKILL`;
  - **reverse proxy:** graceful shutdown завершает уже принятые соединения перед остановкой — конкретный механизм зависит от продукта (раздел 32), не фиксируется этим ADR;
- официально `docker stop` отправляет `SIGTERM` главному процессу контейнера (переопределяемый через `STOPSIGNAL`/`--stop-signal`), затем — если grace period истёк — принудительно завершает контейнер `SIGKILL`; grace period по умолчанию документирован как 10 секунд для Linux-контейнеров, настраивается (раздел 61);
- grace period для PostgreSQL-контейнера должен учитывать официальное предупреждение о недопустимости `SIGKILL` (выше) — конкретное значение таймаута определяется на этапе реализации с учётом этой рекомендации, не фиксируется числом в этом ADR;
- порядок остановки сервисов (например, сначала прекратить приём трафика на reverse proxy, затем остановить backend/worker, затем PostgreSQL) — архитектурное намерение настоящего раздела, конкретная последовательность/оркестрация не реализуется этим ADR.

## 36. Signal handling

- `SIGTERM` — перехватываемый сигнал, официально позволяющий приложению зарегистрировать обработчик для организации штатного завершения (раздел 61);
- `SIGKILL` — официально не может быть перехвачен, заблокирован или проигнорирован (раздел 61) — используется только как последний, принудительный механизм после истечения grace period;
- официальная документация FastAPI/Uvicorn отмечает важность exec-формы команды запуска контейнера (а не оболочечной), поскольку это необходимо для корректной доставки сигналов и штатного завершения lifespan-событий (раздел 61) — конкретное содержимое команды запуска не фиксируется этим ADR;
- PID 1 внутри контейнера отвечает за reaping завершившихся дочерних процессов; официальная рекомендация Docker — использовать флаг `--init` для лёгкого init-процесса, решающего эту задачу, вместо встраивания полноценной init-системы (раздел 22, 61);
- каждый компонент (backend, worker, PostgreSQL, reverse proxy) обрабатывает `SIGTERM` в соответствии со своей собственной официально документированной семантикой (раздел 35) — единой универсальной политики сигналов для всех компонентов не вводится.

## 37. Scaling

- MVP использует один экземпляр каждого сервиса на одном сервере;
- горизонтальное масштабирование за пределы одного сервера **не вводится** этим ADR;
- вертикальное масштабирование (увеличение ресурсов сервера) остаётся доступным без изменения архитектуры контейнеризации;
- backend/worker архитектурно допускают запуск нескольких процессов в пределах одного контейнера или нескольких контейнеров одного сервиса (`ADR-0001`, `ADR-0002`) — официальная документация FastAPI отдельно описывает модель репликации через несколько процессов на одном сервере как самостоятельный, не требующий Kubernetes путь (раздел 61) — конкретное число процессов не фиксируется этим ADR;
- PostgreSQL остаётся единственным primary-экземпляром (`ADR-0004`, раздел 30) — реплики не вводятся этим ADR;
- переход к оркестрации для горизонтального масштабирования рассматривается только при доказанной необходимости (раздел 38).

## 38. Single-server ограничения

- один сервер — единая точка отказа для всех контейнеризованных сервисов до появления резервирования;
- ресурсы (CPU/RAM/диск) сервера общие для всех пяти сервисов — интенсивная нагрузка одного сервиса может повлиять на остальные без явных resource limits (раздел 41);
- обновление сервера (перезапуск ОС, патчинг) требует окна обслуживания для всех сервисов одновременно, если не спроектирован отдельный механизм отказоустойчивости — не вводимый этим ADR;
- сетевые ограничения одного узла (пропускная способность, публичный IP) разделяются всеми сервисами;
- переход к варианту C (Kubernetes) или D (Managed PaaS, раздел 16) рассматривается **отдельным ADR** только при одном или нескольких из следующих, доказанных измерениями условий:
  - ресурсы одного сервера становятся узким местом после исчерпания вертикального масштабирования;
  - требуется отказоустойчивость на уровне узла (сервер как единая точка отказа становится неприемлемым);
  - требуется независимое горизонтальное масштабирование отдельных сервисов;
  - эксплуатационная сложность single-server модели, вопреки ожиданиям, становится выше сопоставимой оркестрационной модели;
  - появляется обоснованное требование multi-region размещения.

## 39. Логи

- логи контейнеров доступны нативно через сам Docker (раздел 61) — специализированная агрегация/хранение логов не вводится этим ADR;
- backend/worker логи структурированы в соответствии с общими принципами наблюдаемости платформы (`FAILURE_MODEL.md`, раздел 11 — correlation ID);
- логи PostgreSQL и reverse proxy доступны тем же нативным механизмом;
- логи не содержат секретов (раздел 29) — согласуется с общим правилом платформы (`ADR-0004`, раздел 28; `ADR-0007`, раздел 45);
- централизованный лог-стек (например, специализированные решения агрегации/поиска логов) **не выбирается** этим ADR — предмет отдельного ADR наблюдаемости (`ADR-0009` по дорожной карте `TECHNOLOGY_EVALUATION.md`).

## 40. Monitoring

- специализированный monitoring stack **не выбирается** этим ADR;
- health check-статусы контейнеров (раздел 26) — минимальный, нативно доступный сигнал состояния платформы на этапе MVP;
- метрики уровня приложения (задержки LLM-вызовов, состояние очереди jobs и подобное, `ADR-0006` раздел 43, `ADR-0007` раздел 48) определены соответствующими ADR независимо от механизма их сбора/визуализации;
- полноценная observability-инфраструктура — предмет отдельного `ADR-0009` (по дорожной карте `TECHNOLOGY_EVALUATION.md`).

## 41. Resource limits

- официально Docker поддерживает ограничение памяти (жёсткий предел, опциональный мягкий предел, реагирующий на нехватку памяти хоста) и CPU (в том числе дробное выделение ядер, cgroup-квоты, закрепление за конкретными ядрами) на уровне контейнера (раздел 61);
- официальная документация предупреждает, что отсутствие ограничения памяти контейнера создаёт риск исчерпания памяти всего хоста, а не только контейнера (раздел 61);
- каждый из пяти сервисов (раздел 19) получает явные ограничения ресурсов, чтобы один компонент не мог исчерпать ресурсы, необходимые остальным (раздел 38);
- конкретные числовые значения ограничений не устанавливаются этим ADR — определяются при внедрении и измерениях (раздел 59).

## 42. Security

- официальные рекомендации Docker по безопасности образов: минимальные/доверенные базовые образы, разделение build- и production-образов, объединение шагов установки пакетов в один слой с очисткой кеша, закрепление базовых образов по дайджесту (раздел 61);
- контейнеры не хранят секреты в слоях образа (раздел 29);
- сетевой доступ ограничен внутренней сетью, кроме reverse proxy (раздел 31);
- принцип наименьших привилегий (`ADR-0004`, раздел 28; `ENGINEERING_PRINCIPLES.md`, пункт 5) распространяется и на DB-пользователя приложения внутри контейнеризованного PostgreSQL;
- security patch-обновления базовых образов применяются приоритетно, аналогично политике `ADR-0001`/`ADR-0003` для рантаймов;
- дополнительная, более глубокая мера — rootless-режим самого Docker-демона — официально документирована как отдельная, более сильная мера относительно non-root пользователя внутри контейнера (раздел 43, 61); её принятие не фиксируется этим ADR и остаётся открытым вопросом (раздел 60).

## 43. User permissions / root/non-root

- официальная рекомендация Docker: если сервис может работать без привилегий, использовать инструкцию, переключающую процесс на непривилегированного пользователя, с явно заданным UID/GID (а не автоматически назначаемым, что недетерминировано между пересборками), избегая `sudo` внутри контейнера (раздел 61);
- backend/worker/frontend/reverse proxy контейнеры запускаются от non-root пользователя, где это технически возможно;
- официальная документация Uvicorn также упоминает практику запуска production-процесса от non-root пользователя (раздел 61);
- официальный образ PostgreSQL уже реализует собственную модель пользователя процесса — платформа не переопределяет её без отдельного обоснования;
- root внутри контейнера допускается только там, где это технически необходимо (например, отдельные шаги инициализации) и явно обосновано.

## 44. Image pinning и version pinning

- образы фиксируются воспроизводимым тегом/дайджестом, а не плавающим `latest` — согласуется с общей политикой версий платформы (`ADR-0001`, раздел 16; `ADR-0003`, раздел 16; `ADR-0004`, раздел 16);
- обновление базового образа — управляемое изменение, проходящее тестирование, а не автоматическое обновление;
- версии backend/frontend/PostgreSQL runtime внутри образов остаются в границах политик, установленных `ADR-0001`, `ADR-0003`, `ADR-0004` соответственно — настоящий ADR не переопределяет эти политики, а только добавляет требование воспроизводимой фиксации на уровне образа;
- конкретные теги/дайджесты не фиксируются этим ADR.

## 45. Rollback

- откат выполняется переключением на предыдущий воспроизводимый образ (раздел 44) — не ручным изменением работающего контейнера;
- откат backend/frontend/worker/reverse proxy не требует отдельного плана данных (раздел 23 — эти сервисы stateless относительно бизнес-данных);
- откат PostgreSQL (при откате схемы/данных) следует модели `ADR-0004`, раздел 37 — экспорт, проверка целостности, управляемый переход;
- откат конфигурации Compose-модели выполняется тем же способом, что откат кода — через контроль версий, вне рамок этого ADR как исполняемого механизма;
- план отката для настоящего ADR в целом описан отдельно (раздел 58).

## 46. Deployment strategy

- MVP использует единственный экземпляр среды — сложные стратегии (blue-green, canary) не вводятся этим ADR ввиду однохостовой модели и объёма MVP;
- обновление сервиса выполняется путём остановки контейнера старой версии, замены образа, запуска новой версии, с проверкой health check перед возвратом в строй (раздел 26–27);
- graceful shutdown (раздел 35) обязателен при любом обновлении, чтобы не терять in-flight запросы/jobs без необходимости;
- обновление PostgreSQL-образа (minor/patch) следует его собственной версионной политике (`ADR-0004`, раздел 16);
- более сложные стратегии деплоя рассматриваются только при доказанной необходимости (раздел 60), совместно с вопросом горизонтального масштабирования (раздел 38).

## 47. Upgrade strategy

- upgrade базовых образов runtime (Python/Node.js/PostgreSQL) следует версионным политикам соответствующих ADR (`ADR-0001`, `ADR-0003`, `ADR-0004`);
- upgrade reverse proxy-продукта следует его собственному официальному release cycle — конкретный продукт не выбран этим ADR (раздел 32);
- major upgrade любого компонента — управляемое изменение с тестированием перед принятием, не автоматическое обновление (согласуется с `ADR-0001`, раздел 16; `ADR-0004`, раздел 16);
- upgrade Docker/Compose самого по себе (версия движка/спецификации) выполняется отдельно от upgrade образов приложения и не должен неявно менять поведение уже работающих сервисов без тестирования.

## 48. Disaster recovery

- disaster recovery платформы фактически сводится к: (1) восстановлению PostgreSQL из backup (раздел 25, `ADR-0004` раздел 27); (2) пересборке/перезапуску stateless-контейнеров из воспроизводимых образов (раздел 20, 23);
- полная потеря сервера восстанавливается через: получение нового сервера, восстановление PostgreSQL из backup, пересборка/запуск остальных контейнеров из зафиксированных образов и Compose-модели;
- RPO/RTO для этого сценария не утверждены `NON_FUNCTIONAL_REQUIREMENTS.md` и не устанавливаются этим ADR — определяются после измерений (согласуется с `ADR-0004`, раздел 27);
- backup хранится отдельно от единственного сервера (раздел 24) — иначе disaster recovery невозможен при полной потере сервера;
- disaster recovery drill (полное восстановление на новом сервере) выполняется периодически, аналогично restore drills `ADR-0004`.

## 49. Положительные последствия

- воспроизводимость среды через официально стандартизированные образы (OCI) и Compose Specification (раздел 61) вместо ручной настройки сервера;
- изоляция процессов между пятью сервисами без введения кластерной сложности Kubernetes;
- единый инструмент (Docker Compose) для локальной разработки и production, снижающий расхождение окружений (Windows/Linux);
- явное разделение stateless-сервисов и единственного stateful-компонента (PostgreSQL) с собственной, уже утверждённой backup-моделью;
- честно задокументированные, официально подтверждённые ограничения (например, недопустимость `SIGKILL` для PostgreSQL, недопустимость наивного снимка volume) снижают риск скрытых ошибок эксплуатации;
- путь роста к оркестрации/managed PaaS сохранён без блокировки архитектуры на однохостовой модели навсегда.

## 50. Отрицательные последствия

- один сервер остаётся единой точкой отказа до появления резервирования (раздел 38, 48);
- Docker/Compose добавляет прослойку по сравнению с прямым запуском процессов — требует минимальной операционной квалификации;
- отсутствие оркестратора означает отсутствие автоматического failover между узлами — не являлось целью этого ADR, но остаётся ограничением;
- необходимость выбора конкретного reverse proxy продукта остаётся открытым вопросом (раздел 60), требующим отдельного решения перед реализацией;
- ручное соблюдение официальных ограничений (graceful shutdown PostgreSQL, консистентность backup) требует дисциплины, не обеспечиваемой автоматически инструментами.

## 51. Риски

1. Потеря данных PostgreSQL при пересоздании контейнера без правильно смонтированного volume.
2. Наивный снимок volume работающего PostgreSQL без соблюдения условий консистентности.
3. Backup хранится на том же сервере, что и основные данные.
4. `SIGKILL` PostgreSQL до истечения его собственного grace period, ведущий к некорректному завершению.
5. Слишком короткий `docker stop` grace period, не покрывающий Smart Shutdown PostgreSQL.
6. Секреты попадают в образ или Dockerfile.
7. Секреты попадают в обычные переменные окружения, видимые всем процессам контейнера.
8. Секреты попадают в логи.
9. Порты backend/worker/PostgreSQL публикуются на хост напрямую в обход reverse proxy.
10. Отсутствие health check маскирует неработающий сервис как «запущенный».
11. Restart policy маскирует постоянно падающий сервис бесконечным перезапуском.
12. Контейнер работает от root без необходимости.
13. Плавающий тег образа (`latest`) даёт непредсказуемые обновления.
14. Ручное изменение работающего контейнера в обход образов.
15. Отсутствие ограничения ресурсов у одного сервиса исчерпывает ресурсы всего сервера.
16. TLS-сертификат не продлевается автоматически и истекает.
17. Zombie-процессы внутри контейнера из-за отсутствия PID 1 reaping.
18. Frontend или backend получают неверную схему запроса (http/https) из-за отсутствия корректной передачи заголовков от reverse proxy.
19. Единственный сервер как точка отказа без задокументированного disaster recovery.
20. Разные версии PostgreSQL-образа между окружениями (Windows-разработка/Linux-production) дают расхождение путей данных.
21. Миграция схемы конфликтует с уже запущенными несколькими backend-процессами.
22. Восстановление после сбоя сервера занимает неприемлемо долгое время из-за неотработанного disaster recovery drill.
23. Docker/Compose версии расходятся между разработкой и production, создавая скрытую несовместимость.
24. Preview/экспериментальные версии образов используются в production по недосмотру.
25. Недокументированный выбор reverse proxy продукта откладывается до момента, когда решение принимается неосознанно (default-выбор без анализа).

## 52. Меры снижения рисков

1. Потеря данных при пересоздании → volume монтируется в верный путь данных согласно официальной документации используемой версии образа PostgreSQL (раздел 23, 61).
2. Наивный снимок volume → backup выполняется только официальными PostgreSQL-инструментами или атомарным консистентным снимком с WAL и предварительным `CHECKPOINT` (раздел 24, 61).
3. Backup на том же сервере → backup хранится отдельно от единственного production-сервера (раздел 24, 48).
4. `SIGKILL` PostgreSQL до Smart Shutdown → `docker stop` grace period для PostgreSQL-контейнера согласован с ожидаемым временем Smart Shutdown (раздел 35).
5. Короткий grace period → значение grace period определяется на этапе реализации с явным учётом официальной рекомендации не использовать `SIGKILL` для PostgreSQL (раздел 35, 61).
6. Секреты в образе → секреты передаются через secrets-механизм, не встраиваются в Dockerfile/образ (раздел 29).
7. Секреты в переменных окружения → предпочтение secrets-механизму и `_FILE`-вариантам перед обычными переменными для чувствительных значений (раздел 29–30).
8. Секреты в логах → логи не содержат секретов по общему правилу платформы (раздел 39, 45 ADR-0007, 28 ADR-0004).
9. Прямая публикация внутренних портов → наружу публикуются только порты reverse proxy, остальные сервисы — только во внутренней сети (раздел 31).
10. Отсутствие health check → health check обязателен для каждого из пяти сервисов, с семантикой, отражающей реальную готовность (раздел 26).
11. Restart policy маскирует сбой → restart policy сочетается с health check и наблюдаемостью (раздел 28, 39–40), не применяется как единственная мера отказоустойчивости.
12. Root без необходимости → non-root пользователь с явным UID/GID, где технически возможно (раздел 43).
13. Плавающий тег → образы фиксируются воспроизводимым тегом/дайджестом (раздел 44).
14. Ручное изменение контейнера → изменения вносятся только через пересборку образа и управляемый деплой (раздел 45–46).
15. Отсутствие resource limits → явные ограничения ресурсов для каждого сервиса (раздел 41).
16. Непродлённый TLS-сертификат → автоматизированное продление в соответствии с официальной рекомендацией Let's Encrypt (раздел 34).
17. Zombie-процессы → официально рекомендованный `--init`-подход к PID 1 (раздел 22, 36, 61).
18. Неверная схема запроса → корректная передача заголовков схемы от reverse proxy к backend определяется на этапе реализации (раздел 33).
19. Единственный сервер как точка отказа → задокументированный disaster recovery процесс и периодические drills (раздел 48).
20. Расхождение путей данных между окружениями → путь монтирования volume фиксируется в соответствии с документацией конкретной используемой версии образа, единообразно для всех окружений (раздел 23).
21. Конфликт миграции с несколькими backend-процессами → миграция выполняется как отдельный, предшествующий запуску множества процессов шаг (согласуется с `ADR-0004`, раздел 26, и официальной рекомендацией FastAPI выполнять такие шаги одним процессом до старта worker'ов — раздел 61).
22. Долгое восстановление после сбоя → регулярные disaster recovery drills, а не однократная теоретическая проверка (раздел 48).
23. Расхождение версий Docker/Compose → версия Docker/Compose фиксируется как часть воспроизводимой конфигурации проекта, определяется на этапе реализации.
24. Preview-образы в production → используются только стабильные, воспроизводимо зафиксированные образы (раздел 44), preview/experimental запрещены без отдельного решения.
25. Неосознанный выбор reverse proxy → выбор продукта зафиксирован как явный открытый вопрос (раздел 60), требующий отдельного обоснованного решения, а не выбора по умолчанию.

## 53. NFR impact

Числовые NFR, связанные с deployment (RPO/RTO, resource limits, конкретные значения timeout/grace period), не утверждены `NON_FUNCTIONAL_REQUIREMENTS.md` и не устанавливаются этим ADR — определяются при измерениях после реализации (раздел 48, 59). Воспроизводимость, изоляция процессов, graceful shutdown и backup/restore закладываются архитектурно с самого начала (разделы 20–28, 35, 24–25).

## 54. План внедрения

Без кода на этом этапе. Зафиксированные будущие шаги:

1. принять ADR-0008;
2. выбрать конкретный reverse proxy продукт отдельным решением (раздел 32, 60);
3. определить структуру Compose-модели (сервисы/сети/volumes) как отдельный артефакт;
4. определить Dockerfile backend/worker (multi-stage, non-root, точный базовый образ);
5. определить Dockerfile frontend (multi-stage, non-root, соответствие версии Node.js `ADR-0003`);
6. определить точную версию/тег официального образа PostgreSQL согласно версионной политике `ADR-0004`;
7. определить путь монтирования volume PostgreSQL согласно документации выбранной версии образа;
8. определить конкретные health check команды для каждого сервиса;
9. определить конкретные значения resource limits;
10. определить конкретные значения graceful shutdown timeout с учётом раздела 35;
11. определить механизм передачи секретов (раздел 29) конкретной реализацией;
12. определить структуру внутренней сети и правила публикации портов (раздел 31);
13. настроить TLS/Let's Encrypt для выбранного reverse proxy продукта;
14. определить restart policy для каждого сервиса;
15. реализовать backup/restore процесс для контейнеризованного PostgreSQL, основанный на разделе 24–25;
16. проверить локальный запуск полного стека на Windows;
17. проверить production-запуск полного стека на Linux;
18. выполнить disaster recovery drill на тестовом окружении;
19. выполнить restore drill backup PostgreSQL;
20. измерить фактическое потребление ресурсов пятью сервисами на одном сервере;
21. только после этого — production-развёртывание MVP.

## 55. План отката

**Если контейнеризация не используется (откат к варианту A):**

- backend/frontend/worker/PostgreSQL/reverse proxy запускаются напрямую на сервере;
- воспроизводимость окружения обеспечивается иным механизмом (вне рамок этого отката);
- PostgreSQL-данные экспортируются перед переходом стандартными средствами `ADR-0004`;
- новый ADR фиксирует замену настоящего решения.

**Если требуется переход к оркестрации (Kubernetes) или Managed PaaS (варианты C/D):**

- образы, зафиксированные настоящим ADR (раздел 20, 44), переносимы на новую платформу без пересборки бизнес-логики — это прямое следствие использования стандартных OCI-образов;
- PostgreSQL-данные переносятся через backup/restore (раздел 24–25), а не «на лету»;
- переход выполняется поэтапно, с периодом параллельной проверки;
- новый ADR фиксирует конкретную оркестрационную/PaaS-модель и обновляет статус ADR-0008 при необходимости (`ADR_PROCESS.md`, раздел 18).

## 56. Критерии проверки решения

После будущей реализации (без создания этих проверок в рамках настоящей задачи):

1. backend, frontend, worker, PostgreSQL, reverse proxy запускаются как отдельные контейнеры;
2. PostgreSQL данные переживают пересоздание контейнера;
3. backup PostgreSQL создаётся и восстанавливается успешно (restore drill);
4. наивный снимок volume без соблюдения условий консистентности не используется как backup-механизм;
5. health check каждого сервиса отражает реальную готовность, не только факт запуска;
6. readiness и liveness различаются там, где это применимо;
7. graceful shutdown не теряет in-flight запросы/jobs при штатной остановке;
8. PostgreSQL не останавливается через `SIGKILL` при штатном сценарии;
9. секреты не присутствуют в образах, логах или обычных переменных окружения, видимых процессам, которым они не нужны;
10. только reverse proxy публикует порты на хост;
11. контейнеры работают от non-root пользователя, где технически возможно;
12. образы зафиксированы воспроизводимым тегом/дайджестом, не `latest`;
13. resource limits заданы для каждого сервиса;
14. TLS-сертификат продлевается автоматически до истечения срока действия;
15. полный стек запускается локально на Windows и в production на Linux;
16. disaster recovery drill проходит успешно на тестовом окружении;
17. миграция схемы БД не конфликтует с несколькими backend-процессами;
18. откат на предыдущий образ возможен без потери данных PostgreSQL.

## 57. Условия пересмотра

ADR-0008 пересматривается, если:

- один сервер перестаёт справляться с нагрузкой после исчерпания вертикального масштабирования;
- требуется отказоустойчивость на уровне узла;
- требуется независимое горизонтальное масштабирование отдельных сервисов;
- эксплуатационная сложность single-server модели превышает ожидаемую относительно оркестрационной альтернативы;
- появляется обоснованное требование multi-region размещения;
- выбранный (позднее) reverse proxy продукт перестаёт удовлетворять требованиям TLS-автоматизации или health-check-видимости;
- официальные источники, использованные этим ADR, пересматриваются производителями (например, изменение поведения `docker stop`, изменение backup-рекомендаций PostgreSQL) существенным образом;
- Docker/Compose Specification перестают быть жизнеспособным основанием (потеря поддержки, критические ограничения);
- disaster recovery drill систематически не укладывается в приемлемое время;
- состав контейнеризуемых сервисов существенно меняется (например, добавление отдельного message broker по `ADR-0006`, раздел 23).

## 58. Открытые вопросы

- конкретный reverse proxy продукт (Nginx, Caddy, Traefik или иной) не выбирается этим ADR — предмет отдельного решения (раздел 32, план внедрения раздел 54, шаг 2);
- конкретные значения resource limits, health check интервалов и grace period timeout не устанавливаются этим ADR — определяются при внедрении и измерениях;
- необходимость rootless-режима самого Docker-демона (более сильная мера, чем non-root пользователь внутри контейнера) остаётся открытой (раздел 42);
- точный путь монтирования volume PostgreSQL зависит от конкретной версии официального образа, выбираемой на этапе реализации согласно версионной политике `ADR-0004`;
- механизм хранения секретов на конкретном production-сервере (за пределами Compose-абстракции secrets) не выбран этим ADR;
- официальная документация не подтвердила единообразно для reverse proxy продуктов паттерн «наружу — только proxy» — это архитектурное решение проекта, реализация которого проверяется на этапе внедрения (раздел 31).

## 59. Решение Product Owner

Утверждено. Product Owner фиксирует Docker Compose на одном сервере как production deployment-модель MVP.

- backend, frontend, worker, PostgreSQL и reverse proxy разворачиваются как отдельные контейнеризованные сервисы;
- Kubernetes, Docker Swarm, Nomad и multi-node orchestration для MVP не вводятся;
- конкретный cloud provider не выбирается;
- конкретный reverse proxy продукт не выбирается настоящим ADR;
- наружу публикуется только reverse proxy;
- PostgreSQL использует persistent volume и официально поддерживаемую backup/restore-процедуру;
- образы фиксируются воспроизводимыми тегами или дайджестами, а не плавающим `latest`;
- секреты не встраиваются в образы и не коммитятся в репозиторий;
- контейнеры должны поддерживать health checks и graceful shutdown;
- deployment должен поддерживать контролируемое обновление и rollback;
- конкретные Dockerfile, Compose-файл, reverse proxy configuration, cloud/hosting provider, monitoring stack, CI/CD и числовые resource limits остаются отдельными implementation-решениями.
