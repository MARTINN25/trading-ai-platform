# Module Boundaries

**Статус:** Утверждён
**Владелец:** Product Owner
**Дата последнего изменения:** 2026-08-12
**Назначение:** определить логические границы модулей и разрешённые зависимости между ними.

Настоящий документ детализирует раздел 6–7 [`LOGICAL_ARCHITECTURE.md`](./LOGICAL_ARCHITECTURE.md) до уровня отдельных модулей и их зависимостей. Классы, пакеты и физическая реализация этим документом не определяются — это предмет реализации в рамках утверждённой архитектуры. При расхождении приоритет имеет `PROJECT_CHARTER.md`; иерархия источников истины — [`DOCUMENTATION_STANDARD.md`](../processes/DOCUMENTATION_STANDARD.md), раздел 3.

## Application Layer

### 0. application

- **Ответственность:** выполнение use cases; координация доменных модулей; управление границами логической транзакции; проверка результата перед возвратом Application API.
- **Владеемые данные:** не владеет долговременными бизнес-данными; может владеть только временным состоянием выполнения use case (включая Analysis Session Context, см. `LOGICAL_ARCHITECTURE.md`, раздел 13.1).
- **Публичный логический интерфейс:** выполнить use case (команда/query от Application API или триггер от jobs).
- **Разрешённые зависимости:** identity, market, instruments, sources (как публичный фасад над ingestion pipeline), analysis, insights, evaluations, journal, notes, alerts, settings, audit, shared_kernel.
- **Запрещённые зависимости:** внутренние реализации модулей (только публичные интерфейсы); физические хранилища напрямую; llm_gateway напрямую (вызывается только через analysis); внешние источники напрямую (вызываются только через sources).
- **Публикуемые события/команды:** событие «use case выполнен» / «use case завершился ошибкой».
- **Что не входит:** доменные правила, принадлежащие конкретному модулю; транспортная валидация и граничная аутентификация/авторизация (зона Application API — внешний адаптер, не доменный модуль, зависящий только от application).

## Модули

### 1. identity

- **Ответственность:** определение владельца платформы, проверка доступа.
- **Владеемые данные:** учётные данные доступа владельца (логически, без выбора механизма).
- **Публичный логический интерфейс:** проверить доступ; получить сведения о текущем владельце.
- **Разрешённые зависимости:** shared_kernel.
- **Запрещённые зависимости:** все остальные модули.
- **Публикуемые события/команды:** событие «доступ подтверждён» / «доступ отклонён».
- **Что не входит:** multi-tenant модель (не утверждена, `PRODUCT_SCOPE.md`, раздел 6); хранение секретов (зона Configuration and Secrets, `LOGICAL_ARCHITECTURE.md`).

### 2. market

- **Ответственность:** хранение и предоставление текущего рыночного контекста анализа (рынок, инструмент, горизонт).
- **Владеемые данные:** активный контекст анализа на сессию.
- **Публичный логический интерфейс:** установить контекст; получить текущий контекст.
- **Разрешённые зависимости:** instruments, shared_kernel.
- **Запрещённые зависимости:** analysis, llm_gateway, sources, insights.
- **Публикуемые события/команды:** событие «контекст изменён».
- **Что не входит:** хранение исторических данных инструмента; анализ.

### 3. instruments

- **Ответственность:** каталог доступных инструментов по рыночным разделам.
- **Владеемые данные:** список инструментов и их принадлежность к рыночному разделу.
- **Публичный логический интерфейс:** получить список инструментов раздела; проверить существование инструмента.
- **Разрешённые зависимости:** sources (только для сведений о доступности), shared_kernel.
- **Запрещённые зависимости:** analysis, llm_gateway, insights.
- **Публикуемые события/команды:** событие «каталог обновлён».
- **Что не входит:** хранение котировок или новостей.

### 4. sources

- **Ответственность:** взаимодействие с внешними источниками рыночных данных, новостей, календаря.
- **Владеемые данные:** сведения о подключённых источниках и их состоянии доступности.
- **Публичный логический интерфейс:** запросить данные у источника; получить статус доступности источника.
- **Разрешённые зависимости:** shared_kernel, settings (конфигурация источников).
- **Запрещённые зависимости:** analysis (явное правило раздела «Обязательные правила зависимостей»), llm_gateway, insights.
- **Публикуемые события/команды:** событие «источник недоступен» / «данные получены».
- **Что не входит:** нормализация, анализ, интерпретация данных.

### 5. ingestion

- **Ответственность:** приём сырых данных от sources.
- **Владеемые данные:** сырые данные в исходном виде до нормализации.
- **Публичный логический интерфейс:** принять данные от источника; передать данные в normalization.
- **Разрешённые зависимости:** sources, provenance, shared_kernel.
- **Запрещённые зависимости:** analysis, llm_gateway, insights.
- **Публикуемые события/команды:** событие «сырые данные приняты».
- **Что не входит:** интерпретация или анализ данных.

### 6. normalization

- **Ответственность:** приведение сырых данных к единому внутреннему формату.
- **Владеемые данные:** правила и результат нормализации.
- **Публичный логический интерфейс:** нормализовать данные.
- **Разрешённые зависимости:** ingestion, provenance, shared_kernel.
- **Запрещённые зависимости:** analysis, llm_gateway, insights.
- **Публикуемые события/команды:** событие «данные нормализованы».
- **Что не входит:** проверку качества данных (зона data_quality).

### 7. data_quality

- **Ответственность:** проверка согласованности, актуальности, правдоподобия; дедупликация.
- **Владеемые данные:** пометки состояния данных (доступны/устарели/недостоверны/конфликтуют).
- **Публичный логический интерфейс:** проверить качество данных; получить данные с пометкой состояния.
- **Разрешённые зависимости:** normalization, provenance, shared_kernel.
- **Запрещённые зависимости:** analysis (данные предоставляются analysis, а не запрашиваются им напрямую в обход; см. правило раздела «Обязательные правила зависимостей» — analysis не зависит от конкретного внешнего API, но потребляет выход data_quality как формальный вход), llm_gateway, insights.
- **Публикуемые события/команды:** событие «данные проверены».
- **Что не входит:** молчаливое отбрасывание проблемных данных без пометки.

### 8. provenance

- **Ответственность:** фиксация происхождения каждого значимого факта на всём пути данных.
- **Владеемые данные:** записи происхождения, привязанные к фактам и к инсайту.
- **Публичный логический интерфейс:** зафиксировать происхождение; получить происхождение факта/инсайта.
- **Разрешённые зависимости:** shared_kernel.
- **Запрещённые зависимости:** analysis, llm_gateway, insights (эти модули потребляют provenance как атрибут данных, но provenance не зависит от них).
- **Публикуемые события/команды:** отсутствуют — provenance является атрибутируемым, а не событийным модулем.
- **Что не входит:** проверка качества данных (зона data_quality).

### 9. analysis

- **Ответственность:** координация формирования инсайта из проверенных данных и ответа llm_gateway.
- **Владеемые данные:** состояние текущего процесса формирования инсайта (до сохранения в insights).
- **Публичный логический интерфейс:** сформировать инсайт по контексту и проверенным данным.
- **Разрешённые зависимости:** data_quality, provenance, llm_gateway, shared_kernel. Market Context и Instrument Catalog предоставляются analysis как часть входного пакета от вызывающего use case (application), а не запрашиваются analysis напрямую.
- **Запрещённые зависимости:** sources (явное правило), insights — analysis не сохраняет инсайт и не зависит от insights ни в каком виде (см. `LOGICAL_ARCHITECTURE.md`, раздел 7.1); evaluations, journal, application (analysis не вызывает вызвавший её слой — зависимость однонаправленная: application → analysis).
- **Публикуемые события/команды:** логическое событие «результат анализа сформирован», адресованное вызвавшему use case (application). Публикация события не создаёт compile-time зависимости analysis от подписчика (application/insights) — analysis не знает, кто и как сохранит результат.
- **Что не входит:** сбор сырых данных (зона sources/ingestion); прямой вызов внешнего LLM API в обход llm_gateway; сохранение сформированного результата.

### 10. llm_gateway

- **Ответственность:** единственная точка обращения к внешнему LLM-провайдеру.
- **Владеемые данные:** параметры вызова провайдера (модель/версия, промпт, конфигурация вызова) — не факты.
- **Публичный логический интерфейс:** выполнить запрос к LLM с формальным входом; получить AI-интерпретацию.
- **Разрешённые зависимости:** shared_kernel.
- **Запрещённые зависимости:** sources, data_quality, provenance, insights, evaluations, journal, notes — llm_gateway не владеет фактами (явное правило) и не обращается к источникам напрямую.
- **Публикуемые события/команды:** событие «LLM-вызов выполнен» / «LLM недоступен».
- **Что не входит:** владение фактами; хранение provenance; принятие решений об анализе (это зона analysis).

### 11. insights

- **Ответственность:** хранение и предоставление сформированных инсайтов вместе с контекстом их формирования.
- **Владеемые данные:** тексты инсайтов, их контекст формирования, связи с provenance.
- **Публичный логический интерфейс:** сохранить инсайт; получить инсайт по идентификатору; получить историю инсайтов.
- **Разрешённые зависимости:** provenance, shared_kernel.
- **Запрещённые зависимости:** sources, ingestion, normalization, data_quality, analysis (insights не выполняет сбор данных — явное правило; получает готовый инсайт как вход, не запрашивает его формирование самостоятельно), llm_gateway.
- **Публикуемые события/команды:** событие «инсайт сохранён».
- **Что не входит:** сбор данных; изменение содержания уже сохранённого инсайта по существу.

### 12. evaluations

- **Ответственность:** хранение пользовательских оценок и результатов проверки инсайтов.
- **Владеемые данные:** оценки, зафиксированные результаты, связи с исходным инсайтом.
- **Публичный логический интерфейс:** сохранить оценку/результат; получить оценки/результаты по инсайту.
- **Разрешённые зависимости:** insights (только для ссылки на инсайт, не для его изменения), shared_kernel.
- **Запрещённые зависимости:** analysis, llm_gateway, sources, jobs — evaluations не переписывает исходный инсайт (явное правило) и не зависит от планировщика, который её вызывает (jobs предоставляет операции evaluations через её публичный интерфейс — направление зависимости jobs → evaluations, не наоборот; см. также application, который может инициировать запись evaluations в рамках use case).
- **Публикуемые события/команды:** событие «результат зафиксирован».
- **Что не входит:** изменение текста исходного инсайта; **агрегатные вычисления/калибровка по накопленным оценкам и результатам (например, «какая доля high-confidence инсайтов впоследствии оценена как полезная») — этот раздел документирует только хранение отдельных записей, не расчёт статистики по ним. Владение будущей функцией калибровки (расширение ответственности этого модуля либо отдельная концепция) намеренно не решено этим документом — открытый вопрос до Stage 2 стадийной дорожной карты обучения/калибровки** (см. `docs/architecture/TARGET_INTELLIGENCE_CONTEXT.md`). **Дополнено Phase 2.0 (PO-2.0-11):** непрерывное отслеживание состояния тезиса во времени (`DATA_FLOWS.md`, DF-022) также намеренно не отнесено этим документом ни к `evaluations`, ни к `jobs` — см. «Предложение (не принято): логическая граница monitoring» ниже и `docs/decisions/ADR-0012-realtime-and-background-monitoring-runtime.md` (Черновик).

### 13. journal

- **Ответственность:** хранение записей о сделках пользователя.
- **Владеемые данные:** записи дневника, при наличии — ссылка на связанный инсайт.
- **Публичный логический интерфейс:** создать запись; получить записи; запросить разбор сделки (использует insights как источник).
- **Разрешённые зависимости:** insights (только для ссылки), shared_kernel.
- **Запрещённые зависимости:** analysis, llm_gateway — journal не изменяет прошлый инсайт (явное правило).
- **Публикуемые события/команды:** событие «запись дневника создана».
- **Что не входит:** формирование анализа; изменение инсайта.

### 14. notes

- **Ответственность:** хранение личных заметок и диалогов пользователя.
- **Владеемые данные:** тексты заметок и диалогов, необязательные ссылки на инструмент/инсайт.
- **Публичный логический интерфейс:** сохранить заметку; получить заметки; изменить заметку; удалить заметку (**расширено Product Owner, Phase 0** — заметки, в отличие от `insights`/`journal`, editable и deletable).
- **Разрешённые зависимости:** shared_kernel; **insights — только для проверки существования ссылки при сохранении/изменении заметки, не для чтения или изменения содержимого инсайта** (расширено Product Owner, Phase 0, аналогично разрешённой зависимости `journal` §13 — устраняет ранее задокументированное противоречие между этим разделом и «Владеемыми данными» выше, где ссылка на инсайт уже упоминалась как часть владеемых данных без соответствующей разрешённой зависимости).
- **Запрещённые зависимости:** analysis, settings — notes не являются скрытыми глобальными настройками (явное правило): использование заметки как контекста анализа требует явного действия пользователя через application-уровень, а не автоматической зависимости notes → analysis. `insights` не входит в запрещённые (см. выше), но зависимость строго однонаправленная и только для проверки существования — notes не подписывается на изменения инсайта и не кэширует его содержимое.
- **Публикуемые события/команды:** отсутствуют по умолчанию.
- **Что не входит:** изменение поведения анализа без явного действия пользователя; изменение содержимого или provenance связанного инсайта.

### 15. alerts

- **Ответственность:** хранение условий алертов и инициирование уведомлений при их выполнении (Post-MVP).
- **Владеемые данные:** условия алертов, их состояние.
- **Публичный логический интерфейс:** создать условие; проверить условие; получить активные алерты.
- **Разрешённые зависимости:** market, instruments, shared_kernel.
- **Запрещённые зависимости:** analysis, llm_gateway, insights, jobs — alerts не зависит от планировщика, который её вызывает (направление зависимости jobs → alerts, не наоборот).
- **Публикуемые события/команды:** событие «условие алерта выполнено».
- **Что не входит:** доставку уведомлений (канал доставки — вне логической модели данного документа); эксплуатационные алерты владельца (зона observability).

### 16. settings

- **Ответственность:** хранение настроек платформы, управляемых владельцем.
- **Владеемые данные:** настройки источников, языка, отображения.
- **Публичный логический интерфейс:** получить настройки; изменить настройки.
- **Разрешённые зависимости:** shared_kernel.
- **Запрещённые зависимости:** analysis, llm_gateway, insights.
- **Публикуемые события/команды:** событие «настройки изменены» (используется audit).
- **Что не входит:** хранение секретов (зона Configuration and Secrets, вне списка из 20 модулей).

### 17. audit

- **Ответственность:** проверяемый журнал критичных действий.
- **Владеемые данные:** записи аудита (действие, инициатор, время).
- **Публичный логический интерфейс:** зафиксировать критичное действие; получить записи аудита.
- **Разрешённые зависимости:** shared_kernel.
- **Запрещённые зависимости:** все модули, чьи внутренние данные не относятся к самому факту действия — audit фиксирует событие, а не читает внутреннее состояние других модулей; audit не используется как обычное логирование (явное правило — не заменяет observability).
- **Публикуемые события/команды:** отсутствуют — audit является приёмником событий.
- **Что не входит:** диагностическое логирование (зона observability).

### 18. observability

- **Ответственность:** структурированные логи, метрики, диагностика состояния платформы.
- **Владеемые данные:** диагностические события, метрики (не бизнес-состояние).
- **Публичный логический интерфейс:** зафиксировать диагностическое событие; получить состояние диагностики.
- **Разрешённые зависимости:** shared_kernel.
- **Запрещённые зависимости:** не хранит бизнес-состояние ни одного модуля (явное правило) — принимает события, но не становится источником истины по бизнес-данным.
- **Публикуемые события/команды:** отсутствуют — приёмник событий.
- **Что не входит:** аудит критичных действий (зона audit); бизнес-состояние.

### 19. jobs

- **Ответственность:** выполнение асинхронных и плановых операций.
- **Владеемые данные:** расписание и состояние выполнения фоновых заданий.
- **Публичный логический интерфейс:** запланировать задание; получить статус задания.
- **Разрешённые зависимости:** application (инициирование фонового use case, например DF-007/DF-015), evaluations, alerts, shared_kernel.
- **Запрещённые зависимости:** insights напрямую (чтение инсайтов для проверки — через application, см. `DATA_FLOWS.md`, DF-007); llm_gateway напрямую в обход analysis; изменение production-логики автоматически на основании Future-уроков (`FUNCTIONAL_REQUIREMENTS.md`, область 31).
- **Публикуемые события/команды:** событие «задание выполнено» / «задание завершилось ошибкой».
- **Что не входит:** бизнес-логику анализа. **Дополнено Phase 2.0 (PO-2.0-10):** непрерывный фоновый сбор данных (`DATA_FLOWS.md`, DF-019) и обнаружение сигналов/событий (DF-020) концептуально исполняются через тот же плановый субстрат `jobs` + `application`, что и уже утверждённые DF-007/DF-015 — не требуют нового исполняющего модуля. Вопрос, требует ли *логика* мониторинга состояния тезиса (DF-022) отдельной границы `monitoring`, вне этого раздела — см. ниже.

### 20. shared_kernel

- **Ответственность:** минимальный набор общих логических примитивов, используемых несколькими модулями (например, общие идентификаторы, общие правила валидации формата).
- **Владеемые данные:** только сквозные примитивы, не относящиеся к бизнес-данным конкретного модуля.
- **Публичный логический интерфейс:** предоставление общих примитивов.
- **Разрешённые зависимости:** отсутствуют — shared_kernel не зависит ни от одного другого модуля.
- **Запрещённые зависимости:** все модули.
- **Публикуемые события/команды:** отсутствуют.
- **Что не входит:** любая бизнес-логика конкретного модуля; shared_kernel минимален (явное правило) и не должен становиться местом накопления общей логики «на всякий случай».

## Предложение (не принято): логическая граница monitoring (Phase 2.0, PO-2.0-11)

**Статус этого раздела: ПРЕДЛОЖЕНИЕ, не утверждённая архитектура.** Ратификация Phase 2.0 (PO-2.0-11) одобрила только создание черновика ADR, рассматривающего выделение `monitoring` как отдельной логической границы — сам факт написания этого раздела не делает `monitoring` 21-м модулем платформы. `monitoring` **не включён** в список модулей выше, в матрицу зависимостей (раздел «Матрица разрешённых зависимостей») и не имеет присвоенного номера — до отдельного решения Solution Architect/Product Owner.

- **Предлагаемая ответственность (если будет принято):** непрерывный мониторинг состояния ранее сформированных тезисов (`DATA_FLOWS.md`, DF-022), обнаружение рыночных сигналов/событий (DF-020), ранжирование возможностей по актуальности. Не включает сам фоновый сбор данных (DF-019 — остаётся зоной `jobs`+`application`, как и сегодня) и не включает формирование прогноза (DF-021 — остаётся зоной `analysis`/`llm_gateway`).
- **Альтернатива A — расширение `jobs`:** `jobs` уже выполняет плановые/событийные операции (DF-007, DF-015); мониторинг состояния тезиса структурно похож на уже утверждённую DF-007. Довод против: `jobs` по определению (раздел 19 выше) — исполняющий планировщик, не владелец бизнес-состояния; состояние тезиса — бизнес-данные, а не расписание задания.
- **Альтернатива B — расширение `evaluations`:** `evaluations` уже владеет результатами проверки (DF-006/DF-007) и уже содержит открытый вопрос о владении калибровкой (раздел 12 выше). Довод против: состояние тезиса (действителен/ослаблен/инвалидирован) логически предшествует финальному результату проверки — это не то же самое, что зафиксированный факт совпадения/расхождения.
- **Альтернатива C — отдельный модуль `monitoring`:** зависел бы от `insights` (чтение тезисов), `market`/`instruments` (текущие данные через `application`), `evaluations` (передача на финальную проверку) и `shared_kernel`; не зависел бы от `llm_gateway` напрямую. Довод за: изолирует специфичную для мониторинга модель состояний от планировщика и от хранения результатов. Довод против: добавляет 21-й модуль ради функциональности, которая пока нигде не реализована ни в каком виде — риск преждевременной архитектуры (`ENGINEERING_PRINCIPLES.md`, принцип простоты).
- **Почему решение не принимается этим документом:** ни `monitoring`, ни расширение существующих модулей не имеют реализованного прецедента в кодовой базе (в отличие, например, от `notes`, где паттерн `journal` уже был реализован и переиспользован). Решение требует того же уровня обоснования, что и `ADR-0011` (провайдерская стратегия) — фактического опыта или явного архитектурного анализа Solution Architect, а не предположения на этапе документации продукта.
- **Куда ведёт нерешённость:** `docs/decisions/ADR-0012-realtime-and-background-monitoring-runtime.md` (Черновик) фиксирует этот вопрос как явно нерешённую альтернативу и не выбирает между A/B/C. Следующий валидный номер ADR для отдельного решения, если оно потребуется отдельным документом — `ADR-0013` (не создаётся этой задачей).

## Обязательные правила зависимостей

- UI зависит только от Application API (внешний адаптер, вне списка модулей).
- Application API — внешний адаптер, зависящий только от application; не считается доменным модулем и не оркестрирует доменные области самостоятельно.
- application вызывает use case через публичные интерфейсы модулей, а не хранилища напрямую (`LOGICAL_ARCHITECTURE.md`, раздел 12).
- sources не зависит от analysis.
- analysis не зависит от конкретного внешнего API (только от data_quality/provenance как формального входа) и не зависит от insights ни прямо, ни через событие (раздел «11.3»/`LOGICAL_ARCHITECTURE.md`, раздел 7.1).
- llm_gateway не владеет фактами.
- insights не выполняет сбор данных; инсайт в insights сохраняет application, а не analysis.
- journal не изменяет прошлый инсайт.
- evaluations не переписывает исходный инсайт и не зависит от jobs (направление — jobs → evaluations).
- alerts не зависит от jobs (направление — jobs → alerts).
- jobs инициирует операции evaluations/alerts или фоновый use case через application; сам не читает insights напрямую (см. `DATA_FLOWS.md`, DF-007).
- notes не являются скрытыми глобальными настройками.
- доменные модули не зависят от observability напрямую; телеметрия добавляется через инфраструктурные обёртки на границах вызовов (`LOGICAL_ARCHITECTURE.md`, раздел 14.1).
- audit не используется как обычное логирование; критичные действия передаются в audit через application или доменные события, а не через прямую зависимость произвольного модуля от audit.
- observability не хранит бизнес-состояние.
- shared_kernel минимален.
- циклические зависимости запрещены (проверено по всей матрице, не только по парам — см. ниже).
- импорт внутренних деталей другого модуля запрещён — модули взаимодействуют только через публичный логический интерфейс (колонка «Публичный логический интерфейс» выше).
- публикация логического события издателем не создаёт compile-time зависимости издателя от подписчика.

## Матрица разрешённых зависимостей

**Легенда:** строка — модуль-источник (тот, кто вызывает); столбец — модуль назначения (тот, чей публичный интерфейс вызывается). «✓» в ячейке [строка X, столбец Y] означает «X разрешено зависеть от Y» (X вызывает публичный интерфейс Y). Пустая ячейка — зависимость запрещена. `application` — Application Layer / Use Cases (раздел «Application Layer» выше); `Application API` и `Web UI` в матрицу не включены — это внешние адаптеры вне списка доменных модулей, `Web UI` зависит только от `Application API`, `Application API` зависит только от `application` (см. «Обязательные правила зависимостей»).
