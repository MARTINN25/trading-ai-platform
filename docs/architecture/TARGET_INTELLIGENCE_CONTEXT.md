# Target Intelligence Context

**Статус:** На ревью
**Владелец:** Product Owner
**Дата последнего изменения:** 2026-08-11
**Назначение:** определить концептуальный «Analysis Context Package» — что именно собирается и проверяется до синтеза AI-инсайта, — чтобы будущие источники данных не добавлялись бессистемно напрямую в prompt.

---

## 0. Зачем отдельный документ, а не расширение существующего

Это отдельный вопрос от `INFORMATION_ARCHITECTURE.md` (тот документ — о навигации разделов продукта; этот — о том, какие данные вправе достичь LLM и на каких условиях) и отдельный вопрос от `docs/product/FUNCTIONAL_REQUIREMENTS.md` (тот фиксирует обязательные требования; этот — расширяемый инвентарь кандидатов, большинство из которых **не** являются требованиями сегодня). По `DOCUMENTATION_STANDARD.md`, раздел 8 (один источник истины на вопрос) и `PROJECT_CHARTER.md`, раздел 7.1 (одна зона ответственности на документ), смешивание этих трёх вопросов в одном файле создало бы неоднозначность. Настоящий документ детализирует уже утверждённые `LOGICAL_ARCHITECTURE.md` (области Source Integration → Ingestion → Normalization → Data Quality → Provenance → Analysis Orchestration → LLM Gateway) и `ENGINEERING_PRINCIPLES.md`, пункты 54–55 (запрет отправки нефильтрованного сырого потока в LLM) — он не создаёт новых логических областей.

**Ключевой принцип (Product Owner, Phase 0): AI-синтез — один компонент системы, а не вся система.** Ценность продукта — в цепочке «источник → нормализация → качество → отбор релевантности → контекст → provenance → синтез → сохранение → оценка результата» целиком (`MODULE_BOUNDARIES.md`, `LOGICAL_ARCHITECTURE.md`, раздел 7.1). Продукт не документируется и не проектируется как «отправить рыночные данные и новости в LLM».

**Настоящий документ не разрешает реализацию ни одной из перечисленных ниже категорий.** Он существует, чтобы последующие задачи классифицировали новую категорию данных explicitly, а не добавляли её в prompt по факту появления идеи.

## 1. Aналитический контекстный пакет — обзор

Формируется (концептуально, независимо от того, что физически реализовано сегодня) применительно к: **рынку** (`market`), **инструменту** (`identity`), **горизонту** (`horizon`) и **конкретной аналитической задаче** (ручной запрос анализа, FR-016). Ни одна категория ниже не считается автоматически полезной только по факту существования — раздел 3 явно требует классификации «больше данных ≠ лучше анализ».

## 2. Категории контекста

### 2.1 identity — идентичность инструмента

- **Текущая доступность:** доступно (`ticker`, `name`, `exchange`, `currency`, `instrument_type` — через `instruments/search`, `watchlist`).
- **Стадия:** **CURRENT.**
- **Источник:** `market_data` (сегодня), в перспективе `instruments`-каталог (`MODULE_BOUNDARIES.md`, раздел 3).
- **Фильтрация/релевантность:** не требуется.
- **Может входить в LLM-контекст:** да, уже входит (`ticker`).
- **При недоступности:** уже обрабатывается — нераспознанный тикер отклоняется до анализа (`422`, существующее поведение).

### 2.2 market — принадлежность рынку и его семантика

- **Текущая доступность:** отсутствует как явное поле — сегодня подразумевается ровно один рынок (US-listed акции).
- **Стадия:** **MVP FOUNDATION** (нужно до/вместе с многорыночным расширением, `PO-2`); включает семантику часов торгов и 24×7 для крипты.
- **Источник:** зависит от `PO-2`/будущего `ADR-0011`.
- **Фильтрация/релевантность:** не применимо к самой категории; но конкретный рынок определяет, какие остальные категории вообще применимы (например, «часы торгов» неприменимы к крипте).
- **Может входить в LLM-контекст:** **не решено** — нужно ли явно называть модели текущий рыночный режим (открыт/закрыт рынок) — открытый вопрос для `ADR-0011`/будущей задачи горизонта.
- **При недоступности:** не применимо сегодня (один рынок).

### 2.3 horizon — горизонт анализа

- **Текущая доступность:** отсутствует полностью (`grep horizon` — 0 совпадений в коде на момент этой задачи).
- **Стадия:** **MVP REQUIRED** (`FR-006`, `PO-3`) — но **точные временные диапазоны SHORT/MEDIUM/LONG остаются нерешённым Product Owner вопросом** (Clarification 1, эта задача). Утверждён только концепт трёх значений.
- **Источник:** выбор пользователя (Analysis Session Context, `LOGICAL_ARCHITECTURE.md`, раздел 13.1 — уже архитектурно предусмотрено).
- **Фильтрация/релевантность:** горизонт определяет, какой глубины price/history и каких ещё категорий этого списка достаточно для честного вывода — не наоборот.
- **Может входить в LLM-контекст:** да, как только реализовано — обязательное требование `FR-006`: «горизонт передаётся в аналитический запрос и **влияет на структуру инсайта**», не только на текст интерфейса.
- **При недоступности достаточных данных для выбранного горизонта:** **обязательное поведение, а не опция** — уровень уверенности должен быть явно понижен, либо формируется явное состояние недостаточности (см. `FR-019`; прямое указание Product Owner, Clarification 1). Система не должна формировать уверенный LONG-анализ на основании одного месяца истории и нескольких заголовков новостей.
- **Явное разграничение:** SHORT-горизонт **не становится** скальпинг-режимом. Скальпинг (`FR-027`) остаётся отдельным, самостоятельно документированным быстрым режимом со своими правилами (пропуск уточняющих вопросов, упрощённый вывод) — а не синонимом «горизонт = короткий».

### 2.4 price / history — котировка и ценовая история

- **Текущая доступность:** доступно — котировка (OHLC/volume/as_of) и сводка истории за фиксированное окно 1 месяц (первая/последняя/мин/макс цена закрытия, без сырых точек).
- **Стадия:** **CURRENT** (для текущего недифференцированного поведения) / **MVP FOUNDATION** (для горизонт-зависимого окна — фиксированное окно в 1 месяц не масштабируется под LONG-горизонт; см. 2.3).
- **Источник:** `market_data` (Twelve Data).
- **Фильтрация/релевантность:** не требуется сверх существующей суммаризации.
- **Может входить в LLM-контекст:** да, уже входит.
- **При недоступности:** уже обрабатывается (`FR-059`, graceful degradation).

### 2.5 news — новости по инструменту

- **Текущая доступность:** доступно, до 10 полученных / до 5 переданных в модель, необработанный язык источника, без дедупликации, без ранжирования по релевантности.
- **Стадия:** **CURRENT** (сырой список) / **MVP FOUNDATION** (дедупликация `FR-015`, перевод `FR-060`, сигнал релевантности — ни одно не реализовано).
- **Источник:** `market_data`/`news_gateway` (Finnhub).
- **Фильтрация/релевантность:** **требуется до LLM** (`ENGINEERING_PRINCIPLES.md`, пункты 54–55) — сегодня отсутствует сверх собственной привязки провайдера к тикеру.
- **Может входить в LLM-контекст:** да, уже входит.
- **При недоступности:** уже обрабатывается (новости — опциональный источник в анализе).

### 2.6 macro / broad-market context — макро- и общерыночный контекст

- **Текущая доступность:** отсутствует полностью.
- **Стадия:** названо в продуктовом видении (`PRODUCT_SCOPE.md`, раздел 2; `FR-017`), но **UNRESOLVED / REQUIRES PO DECISION** по конкретному источнику — не запланировано ни на один ADR сегодня.
- **Источник:** не выбран.
- **Фильтрация/релевантность:** потребуется обязательно при появлении (риск стоимости/шума, `PRODUCT_SCOPE.md`, раздел 29; `ENGINEERING_PRINCIPLES.md`, пункты 54–55).
- **Может входить в LLM-контекст:** нет, до отдельного решения об источнике.
- **При недоступности:** не применимо сегодня; при появлении обязана деградировать честно (`FR-059`-подобно), не маскироваться.

### 2.7 calendar / events — экономический календарь и события

- **Источник:** не выбран.

### 2.8 earnings / company events — корпоративные события

- **Текущая доступность:** отсутствует.
- **Стадия:** **UNRESOLVED / REQUIRES PO DECISION** — ни один FR не называет эту категорию отдельно; не путать с общим календарём (`FR-010`).

### 2.9 fundamentals — фундаментальные показатели

- **Текущая доступность:** отсутствует.
- **Стадия:** **UNRESOLVED / REQUIRES PO DECISION** — не задокументировано ни в одном FR.
- **Источник:** не выбран.
- **Может входить в LLM-контекст:** нет, требует сначала нового FR — не добавляется по умолчанию только потому, что технически доступно у провайдера.

### 2.10 derived / technical features — производные технические признаки

- **Текущая доступность:** частично — уже вычисляемые min/max/first/last цены закрытия существуют, но намеренно **не** подаются как «технический индикатор».
- **Стадия:** **UNRESOLVED / REQUIRES PO DECISION** для любого признака сверх уже существующей сводки (RSI, скользящие средние и подобное) — только «где обосновано» (прямая формулировка Product Owner), не по умолчанию.
- **Может входить в LLM-контекст:** уже входит в минимальной форме (min/max/first/last); дальнейшее расширение требует явного обоснования конкретной задачей.

### 2.11 sentiment / opinion — настроения/мнения

- **Текущая доступность:** отсутствует; упомянуто только неоперационально («мнения», `PRODUCT_SCOPE.md`, раздел 2).
- **Стадия:** **UNRESOLVED / REQUIRES PO DECISION.**
- **Условие Product Owner, если когда-либо реализуется:** источник и методика формирования оценки должны быть явными — категориальное значение с прослеживаемым происхождением, никогда «голое» число без объяснения (тот же принцип, что уже применён к `confidence`, `ai/types.py`).

- **Стадия:** **UNRESOLVED / REQUIRES PO DECISION**, вероятно Post-MVP при появлении.
- **Может входить в LLM-контекст:** нет.

### 2.13 source quality / freshness — качество и актуальность источника

- **Текущая доступность:** частично — актуальность (`data_freshness`, `FR-012`) реализована и подаётся в модель backend-вычисленной строкой (никогда не запрашивается у самой модели); базовая оценка надёжности источника (`FR-013`) — COULD/Post-MVP, не реализована.
- **Стадия:** **CURRENT** (актуальность) / **Post-MVP** (надёжность источника).
- **Может входить в LLM-контекст:** актуальность — уже входит; надёжность — нет, до Post-MVP.

### 2.14 provenance — происхождение фактов

- **Текущая доступность:** частично — минимальная форма (`KeyFact.source`, метка-строка) реализована и обязательна (`FR-011`); полный набор полей происхождения вызова LLM по `ADR-0007`, раздел 46 (usage, finish_reason, retries, версия снапшота модели) **не персистируется** сегодня — задокументированный, честный пробел (см. checkpoint, часть 7).
- **Стадия:** **CURRENT** (минимальная форма) / **MVP FOUNDATION** (полнота по ADR-0007 §46 — небольшое, аддитивное расширение, не новая архитектура).
- **Может входить в LLM-контекст:** не применимо — provenance описывает вывод модели, не подаётся в модель.

### 2.15 prior insight / outcome evidence — данные прошлых инсайтов и результатов

- **Текущая доступность:** данные существуют и связаны (FK `insight_id` в `insight_evaluations`/`journal_entries`), но **никогда не читаются обратно** ни в один будущий вызов LLM.
- **Стадия:** **FUTURE**, жёстко закрыто условиями `ADR-0005`, раздел 19 (18 условий активации, ни одно не выполнено) — не открывается этой задачей.
- **Может входить в LLM-контекст:** нет, до отдельного явного решения об активации retrieval по `ADR-0005`.
- **При недоступности:** не применимо — концепция ещё не активирована.

## 3. Явное правило: больше данных ≠ лучше анализ

Ни одна категория из раздела 2 не добавляется к тому, что уже отправляется в LLM, без явного прохождения через:

1. нормализацию (`normalization`, `LOGICAL_ARCHITECTURE.md`, раздел 7);
2. проверку качества/актуальности (`data_quality`);
3. отбор релевантности (совместно `data_quality`/`analysis`, `LOGICAL_ARCHITECTURE.md`, раздел 24);
4. привязку provenance (`provenance`).

Категории, помеченные **UNRESOLVED / REQUIRES PO DECISION**, не реализуются впрямую по мере появления идеи или доступности у провайдера — каждая требует отдельного продуктового решения (новый или расширенный FR) до того, как этап реализации станет осмысленным.
