# Data Flows

**Статус:** Утверждён
**Владелец:** Product Owner
**Дата последнего изменения:** 2026-08-12
**Назначение:** определить основные логические потоки данных платформы.

Настоящий документ детализирует [`LOGICAL_ARCHITECTURE.md`](./LOGICAL_ARCHITECTURE.md) и [`MODULE_BOUNDARIES.md`](./MODULE_BOUNDARIES.md) на уровне сквозных потоков данных. Конкретные API-контракты, форматы сообщений и технологии этим документом не определяются. При расхождении приоритет имеет `PROJECT_CHARTER.md`; иерархия источников истины — [`DOCUMENTATION_STANDARD.md`](../processes/DOCUMENTATION_STANDARD.md), раздел 3.

Каждый поток имеет идентификатор `DF-XXX` и описывается через: инициатор, входные данные, последовательность, синхронные шаги, асинхронные шаги, точки сохранения, ошибки и деградацию, аудит, наблюдаемость, результат, связанные FR/NFR/UJ, этап.

**Обязательные сквозные требования** (применяются ко всем потокам ниже, если не указано иное):
- поток не предполагает успешность всех источников;
- невалидные данные не доходят до LLM как подтверждённые факты;
- provenance не теряется на всём протяжении потока;
- исходный инсайт после сохранения не переписывается;
- оценка и результат хранятся отдельно от исходного текста инсайта;
- Future-уроки не изменяют production-логику автоматически;
- LLM-вызов не получает весь необработанный поток данных;
- контекст рынка сохраняется на всём протяжении потока;
- данные одного рынка не попадают в другой без явного действия пользователя;
- Observability — сквозная техническая телеметрия, добавляемая инфраструктурными обёртками на границах вызовов, а не явной зависимостью доменных шагов; Audit вызывается только для критичных бизнес-действий через application; публикация события не создаёт обратной зависимости издателя от подписчика (`LOGICAL_ARCHITECTURE.md`, раздел 14.1).

## DF-001. Ручной запрос анализа

- **Инициатор:** пользователь.
- **Входные данные:** контекст (рынок, инструмент, горизонт).
- **Последовательность:** пользователь → Web UI → Application API → application use case → identity/access check → проверка market/instrument context → ingestion pipeline (sources → ingestion → normalization → data_quality [freshness, дедупликация, релевантность — согласно `LOGICAL_ARCHITECTURE.md` §24 совместно с analysis] → provenance) → analysis (context assembly: сборка отфильтрованного пакета контекста для LLM) → llm_gateway через analysis (LLM-синтез) → analysis возвращает структурированный результат use case (application) → application вызывает insights (сохранение) → Application API → Web UI. Концептуальная последовательность PO-6 (sources → ingestion → normalization → quality/freshness → dedup/relevance → context assembly → provenance/evidence → LLM-синтез → insight persistence) отображена на существующие логические владения без введения новых модулей; provenance сопровождает данные на всех этапах конвейера (не единичный шаг), см. `LOGICAL_ARCHITECTURE.md` §7. Этап evaluation/outcome в PO-6 не входит в этот синхронный поток — это отдельный последующий поток через evaluations (см. `MODULE_BOUNDARIES.md` §12), инициируемый пользователем после сохранения инсайта.
- **Синхронные шаги:** клиентский запрос MVP ожидает итоговый результат синхронно (Application API — Web UI не получает ответ, пока use case не завершится).
- **Асинхронные шаги:** параллельный сбор данных от нескольких источников внутри ingestion pipeline может быть внутренне асинхронным — это не означает, что каждый внутренний шаг (identity check, market/instrument context, ingestion pipeline, analysis, сохранение) выполняется последовательно в одном потоке исполнения; use case координирует их результат, прежде чем вернуть синхронный ответ клиенту.
- **Точки сохранения:** insights (инсайт с контекстом формирования).
- **Ошибки и деградация:** недоступность источника — data_quality помечает данные как отсутствующие, analysis формирует инсайт с явным ограничением (не блокирует поток), см. `FAILURE_MODEL.md`.
- **Аудит:** не является критичным действием — не аудируется; фиксируется observability.
- **Наблюдаемость:** сквозной корреляционный идентификатор от запроса до сохранения инсайта.
- **Результат:** структурированный инсайт (10 обязательных разделов), сохранённый в insights.
- **Связанные FR/NFR/UJ:** FR-005, FR-006, FR-007, FR-014, FR-016–FR-018; NFR-006; UJ-004, UJ-005.
- **Этап:** MVP.

## DF-002. Уточняющие вопросы

- **Инициатор:** analysis (в рамках DF-001), при недостатке существенной информации.
- **Входные данные:** промежуточный контекст анализа, требующий уточнения.
- **Последовательность:** analysis → application use case → Application API → Web UI (вопрос пользователю, максимум 1–3) → пользователь отвечает или пропускает → Application API → application use case (сохраняет ответ в Analysis Session Context конкретного use case) → analysis (продолжение с уточнённым контекстом).
- **Синхронные шаги:** весь поток — часть синхронного DF-001, до продолжения формирования инсайта.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** ответ сохраняется только в Analysis Session Context текущего use case (`LOGICAL_ARCHITECTURE.md`, раздел 13.1) — не в Market Context и не как глобальная настройка (settings).
- **Ошибки и деградация:** при пропуске — analysis продолжает с явными допущениями; при противоречии ответа фактам — analysis отражает противоречие в инсайте, не разрешает его молча.
- **Аудит:** не аудируется.
- **Наблюдаемость:** событие «вопрос задан» / «вопрос пропущен» в рамках корреляционного идентификатора DF-001.
- **Результат:** уточнённый или явно допущенный контекст для продолжения DF-001.
- **Связанные FR/NFR/UJ:** FR-020; UJ-006.
- **Этап:** MVP.

## DF-003. Краткий и полный режим инсайта

- **Инициатор:** пользователь (выбор режима) или Web UI (переключение представления).
- **Входные данные:** идентификатор уже сформированного или формируемого инсайта.
- **Последовательность:** пользователь → Web UI → Application API → insights (получение полного инсайта) → представление в кратком или полном виде.
- **Синхронные шаги:** весь поток.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** не создаёт новую запись — использует уже сохранённый (DF-001) или формируемый инсайт; полный инсайт — единственный сохранённый источник, краткий вид — производное представление.
- **Ошибки и деградация:** отсутствие данных отражается в обоих режимах одинаково, не опускается в кратком виде.
- **Аудит:** не аудируется.
- **Наблюдаемость:** событие «краткий вид запрошен» / «полный вид запрошен».
- **Результат:** отображение инсайта в выбранном режиме без изменения сохранённых данных.
- **Связанные FR/NFR/UJ:** FR-021, FR-022; UJ-007, UJ-008.
- **Этап:** MVP.

## DF-004. Сохранение инсайта

- **Инициатор:** application use case (после получения успешного результата от analysis, в рамках DF-001) или пользователь (явное сохранение, в зависимости от архитектурного решения о поведении по умолчанию).
- **Входные данные:** структурированный результат анализа с контекстом (данные, provenance, модель/промпт, правила), возвращённый analysis use case.
- **Последовательность:** application получает результат analysis → application вызывает insights → insights сохраняет неизменяемый исходный инсайт и контекст как единую логическую операцию (`LOGICAL_ARCHITECTURE.md`, раздел 18). Прямая последовательность analysis → insights отсутствует — analysis не зависит от insights (`MODULE_BOUNDARIES.md`).
- **Синхронные шаги:** запись в insights.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** insights.
- **Ошибки и деградация:** при сбое сохранения — пользователю показывается уже сформированный инсайт на экране без потери (не теряется отображённый результат, повторная попытка сохранения не обязательна для просмотра).
- **Аудит:** не аудируется (сохранение инсайта не является критичным действием в терминах `MODULE_BOUNDARIES.md`, раздел audit).
- **Наблюдаемость:** событие «инсайт сохранён».
- **Результат:** инсайт доступен в истории (DF-... просмотр истории — вне явного перечня DF, реализуется через insights).
- **Связанные FR/NFR/UJ:** FR-034, FR-038; NFR-013, NFR-016; UJ-013.
- **Этап:** MVP.

## DF-005. Пользовательская оценка инсайта

- **Инициатор:** пользователь.
- **Входные данные:** идентификатор инсайта, значение оценки.
- **Последовательность:** пользователь → Web UI → Application API → evaluations (сохранение оценки со ссылкой на insights, без изменения insights).
- **Синхронные шаги:** весь поток.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** evaluations.
- **Ошибки и деградация:** сбой сохранения оценки не влияет на сохранённый инсайт в insights.
- **Аудит:** не аудируется.
- **Наблюдаемость:** событие «оценка сохранена».
- **Результат:** оценка доступна вместе с инсайтом (через ссылку evaluations → insights), исходный текст инсайта не изменён.
- **Связанные FR/NFR/UJ:** FR-035; UJ-014.
- **Этап:** MVP.

## DF-006. Ручная проверка результата инсайта

- **Инициатор:** пользователь.
- **Входные данные:** идентификатор инсайта, фактический результат.
- **Последовательность:** пользователь → Web UI → Application API → application use case → evaluations (сохранение введённого пользователем результата) → (опционально, FR-037) application use case → ingestion pipeline (получение изменения цены за горизонт через sources/ingestion/normalization/data_quality) → application use case → evaluations (дополнение записи расчётным изменением цены). Evaluations не обращается к sources напрямую — получение фактов для проверки координирует application.
- **Синхронные шаги:** весь поток.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** evaluations (результат хранится неразрывно с выводом через ссылку на insights, но как отдельная запись — `MODULE_BOUNDARIES.md`, evaluations не переписывает insights).
- **Ошибки и деградация:** при недоступности данных для расчёта изменения цены — evaluations явно фиксирует невозможность проверки, не подставляет произвольное значение.
- **Аудит:** не аудируется.
- **Наблюдаемость:** событие «результат зафиксирован вручную».
- **Результат:** вывод и результат связаны неразрывно (через ссылку), не рассогласуемы.
- **Связанные FR/NFR/UJ:** FR-036, FR-037, FR-038; NFR-013; UJ-015.
- **Этап:** MVP.

## DF-007. Автоматическая проверка результата (Post-MVP)

- **Инициатор:** jobs (плановое задание или событие существенного движения цены).
- **Входные данные:** истёкший горизонт инсайта или сигнал существенного движения цены.
- **Последовательность:** jobs инициирует application/background use case → application вызывает insights (список инсайтов, требующих проверки) → application вызывает ingestion pipeline (sources → ingestion → normalization → data_quality) → application вызывает evaluations (сохранение результата). insights и evaluations не зависят от jobs (`MODULE_BOUNDARIES.md`) — jobs зависит только от application, который и вызывает insights/evaluations.
- **Синхронные шаги:** отсутствуют (полностью асинхронный поток).
- **Асинхронные шаги:** весь поток, инициируется jobs.
- **Точки сохранения:** evaluations.
- **Ошибки и деградация:** недоступность источника при плановой проверке — jobs фиксирует невозможность проверки в evaluations как явное состояние, не как ложный результат; повторная попытка планируется отдельно (`FAILURE_MODEL.md`, retry).
- **Аудит:** не аудируется как критичное действие; фиксируется observability.
- **Наблюдаемость:** событие «автоматическая проверка выполнена» / «автоматическая проверка не выполнена».
- **Результат:** результат зафиксирован в evaluations без изменения исходного инсайта.
- **Связанные FR/NFR/UJ:** FR-039, FR-040, FR-041; NFR-040; UJ-015.
- **Этап:** Post-MVP.

## DF-008. Формирование урока (Future)

- **Инициатор:** jobs (по результату DF-007, при обнаруженном расхождении).
- **Входные данные:** зафиксированное расхождение между выводом (insights) и результатом (evaluations).
- **Последовательность:** jobs → evaluations (классификация ошибки) → jobs (формирование урока как структурированной записи) → сохранение урока (логически — расширение evaluations/insights-контекста, не изменение текста инсайта).
- **Синхронные шаги:** отсутствуют.
- **Асинхронные шаги:** весь поток.
- **Точки сохранения:** структурированная запись урока, отдельная от исходного инсайта.
- **Ошибки и деградация:** невозможность классифицировать ошибку — урок не формируется, расхождение остаётся видимым без урока (не блокирует просмотр, `USER_JOURNEYS.md`, UJ-016).
- **Аудит:** не аудируется.
- **Наблюдаемость:** событие «урок сформирован».
- **Результат:** урок сохранён как отдельная прослеживаемая запись, не изменяющая production-логику автоматически (`FUNCTIONAL_REQUIREMENTS.md`, FR-046) и не переобучающая веса LLM.
- **Связанные FR/NFR/UJ:** FR-042, FR-043, FR-044, FR-046; UJ-016.
- **Этап:** Future.

## DF-009. Создание записи дневника

- **Инициатор:** пользователь.
- **Входные данные:** данные сделки (инструмент, направление, результат), опциональная ссылка на инсайт.
- **Последовательность:** пользователь → Web UI → Application API → journal (сохранение записи, ссылка на insights при наличии).
- **Синхронные шаги:** весь поток.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** journal.
- **Ошибки и деградация:** некорректный ввод отклоняется до сохранения, с понятным сообщением.
- **Аудит:** не аудируется (обычная пользовательская операция).
- **Наблюдаемость:** событие «запись дневника создана».
- **Результат:** запись доступна в journal; связанный инсайт (если есть) не изменён.
- **Связанные FR/NFR/UJ:** FR-030; UJ-017.
- **Этап:** MVP.

## DF-010. Разбор сделки

- **Инициатор:** пользователь.
- **Входные данные:** идентификатор записи дневника.
- **Последовательность:** пользователь → Web UI → Application API → journal (получение записи и ссылки на инсайт) → insights (получение исходного инсайта, без изменения) → analysis (формирование пояснения, при необходимости через llm_gateway) → ответ пользователю.
- **Синхронные шаги:** весь поток.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** пояснение может быть сохранено как атрибут записи journal (не изменяет insights).
- **Ошибки и деградация:** запись без связанного инсайта — journal явно сообщает об отсутствии основания для разбора, поток не формирует пояснение из ничего.
- **Аудит:** не аудируется.
- **Наблюдаемость:** событие «разбор сделки выполнен».
- **Результат:** пояснение результата сделки, не звучащее как гарантия будущего результата.
- **Связанные FR/NFR/UJ:** FR-031; UJ-018.
- **Этап:** Post-MVP.

## DF-011. Заметки и чат

- **Инициатор:** пользователь.
- **Входные данные:** текст заметки или сообщения чата; опциональная ссылка на инструмент и/или инсайт.
- **Последовательность (создание):** пользователь → Web UI → Application API → application use case → **insights (только проверка существования ссылки, если указана — не чтение содержимого)** → notes (сохранение).
- **Последовательность (изменение, MVP, только заметки):** пользователь → Web UI → Application API → application use case → insights (повторная проверка ссылки, если изменена) → notes (обновление существующей записи, не создание новой).
- **Последовательность (удаление, MVP, только заметки):** пользователь → Web UI → Application API → application use case → notes (удаление записи; исходный инсайт, если был связан, не затрагивается).
- **Синхронные шаги:** весь поток, для всех трёх операций.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** notes.
- **Ошибки и деградация:** сбой сохранения не приводит к потере уже введённого текста на экране (ответственность Web UI); ссылка на несуществующий инсайт отклоняется до сохранения/изменения, с понятным сообщением, а не сохраняется как битая ссылка.
- **Аудит:** не аудируется.
- **Наблюдаемость:** событие «заметка сохранена» / «заметка изменена» / «заметка удалена» / «сообщение чата сохранено».
- **Результат:** заметка/диалог доступны для просмотра, изменения и удаления (заметки — **утверждено Product Owner, Phase 0**; чат — вне scope этого решения); не становятся глобальной памятью или настройкой без отдельного явного действия пользователя (`MODULE_BOUNDARIES.md`, notes); удаление или изменение заметки никогда не изменяет связанный инсайт.
- **Связанные FR/NFR/UJ:** FR-032, FR-033; UJ-019.
- **Этап:** MVP (заметки, включая изменение/удаление), Post-MVP (чат).

## DF-012. Отказ одного источника

- **Инициатор:** sources (обнаружение недоступности при выполнении DF-001 или иного потока, использующего sources).
- **Входные данные:** попытка запроса к недоступному источнику.
- **Последовательность:** sources (таймаут/ошибка) → data_quality (пометка «отсутствуют данные» для затронутой части) → analysis (продолжение с явным ограничением) → observability (диагностическое событие).
- **Синхронные шаги:** в рамках синхронного потока (например, DF-001) — обработка отказа не блокирует остальной поток.
- **Асинхронные шаги:** отсутствуют для самого отказа; возможная фоновая проверка восстановления источника — вне явного перечня DF.
- **Точки сохранения:** пометка состояния данных в data_quality; итоговый инсайт (insights) с явным отражением ограничения.
- **Ошибки и деградация:** это и есть основной сценарий деградации данного потока — не маскируется как достоверные данные (`FAILURE_MODEL.md`).
- **Аудит:** не аудируется как критичное действие пользователя; фиксируется observability.
- **Наблюдаемость:** событие «источник недоступен» с корреляцией к затронутому запросу.
- **Результат:** поток (например, DF-001) продолжается с явно отражённым ограничением, а не прерывается.
- **Связанные FR/NFR/UJ:** FR-059; NFR-004, NFR-010; UJ-010.

## DF-016. Сценарий «Что если»

- **Инициатор:** пользователь.
- **Входные данные:** исходный контекст (рынок, инструмент, ранее сформированный инсайт, если применимо) и гипотетическое условие.
- **Последовательность:** пользователь → Web UI → Application API → application use case → получение исходного контекста и гипотетического условия → analysis → llm_gateway через analysis → analysis возвращает структурированный результат application → application вызывает insights для сохранения результата как отдельного сценарного инсайта, если сохранение предусмотрено → Application API → Web UI. Analysis не вызывает insights — сохранение, если оно предусмотрено, инициирует application после получения результата от analysis (аналогично DF-004).
- **Синхронные шаги:** весь поток.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** insights — сценарный результат сохраняется как отдельная запись с явной пометкой «гипотеза», отличающей её от обычного инсайта; исходный инсайт (если сценарий основан на нём) не изменяется. Provenance исходных фактов, использованных как отправная точка сценария, сохраняется вместе со сценарным результатом.
- **Ошибки и деградация:** гипотетическое условие пользователя помечается отдельно от фактов на всём протяжении потока; гипотеза никогда не отображается как подтверждённый факт — нарушение этого правила считается дефектом потока.
- **Аудит:** не аудируется.
- **Наблюдаемость:** событие «сценарный анализ выполнен».
- **Результат:** явно помеченная гипотетическая оценка. Если сценарий пересекает границы рыночного раздела — требуется явное действие пользователя (`PRODUCT_SCOPE.md`, раздел 11; `LOGICAL_ARCHITECTURE.md`, раздел 20).
- **Связанные FR/NFR/UJ:** FR-049; UJ-020.
- **Этап:** Post-MVP.

## DF-017. Быстрый скальпинг-вердикт

- **Инициатор:** пользователь.
- **Входные данные:** контекст инструмента в разделе «Скальпинг».
- **Последовательность:** пользователь → Web UI → Application API → application use case быстрого анализа → проверка market/instrument context → ограниченный ingestion pipeline (sources → ingestion → normalization) → data_quality → analysis → llm_gateway через analysis, если LLM-вызов допускается этим потоком → analysis возвращает структурированный быстрый результат application → application вызывает insights для сохранения, если результат должен попасть в историю → Application API → Web UI. Analysis не вызывает insights.
- **Синхронные шаги:** весь поток, оптимизированный на скорость.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** insights (только если application решает сохранить результат в историю).
- **Ошибки и деградация:** быстрый режим не обходит data_quality — ограниченный набор данных всё равно проходит проверку качества; необработанные данные не передаются в LLM; уточняющие вопросы (DF-002) не блокируют этот поток (`FUNCTIONAL_REQUIREMENTS.md`, правило уточняющих вопросов); при существенном недостатке данных поток направляется в DF-018; быстрый вердикт не выдаётся с завышенной уверенностью; контекст рынка не смешивается с другим рынком (`LOGICAL_ARCHITECTURE.md`, раздел 20).
- **Аудит:** не аудируется.
- **Наблюдаемость:** событие «скальпинг-вердикт сформирован», с отдельной меткой «быстрый режим» для последующего анализа времени формирования (NFR-006).
- **Результат:** быстрый, явно ограниченный по глубине вердикт.
- **Связанные FR/NFR/UJ:** FR-027; UJ-023.
- **Этап:** MVP.

## DF-018. Недостаток данных для скальпинга

- **Инициатор:** data_quality/analysis (в рамках DF-017).
- **Входные данные:** ограниченный набор данных, недостаточный для уверенного быстрого вердикта.
- **Последовательность:** data_quality (пометка недостаточности) → analysis возвращает application результат «недостаточно данных» или ограниченный результат (явное сообщение об ограничении вместо вердикта с завышенной уверенностью) → application решает, требуется ли сохранение результата → при сохранении application вызывает insights. Analysis не зависит от insights и не вызывает её напрямую — согласовано с DF-017.
- **Синхронные шаги:** в рамках DF-017.
- **Асинхронные шаги:** отсутствуют.
- **Точки сохранения:** insights — только если application решает сохранить ограниченный результат; отражение ограничения сохраняется вместе с (при наличии) частичным вердиктом.
- **Ошибки и деградация:** это и есть сценарий деградации DF-017 — управляется явным отражением ограничения (`ENGINEERING_PRINCIPLES.md`, пункт 60), а не понижением порога уверенности молча; отсутствие данных не превращается в полноценный торговый вердикт.
- **Аудит:** не аудируется.
- **Наблюдаемость:** событие «недостаток данных для скальпинга».
- **Результат:** пользователь не вводится в заблуждение относительно качества быстрого вердикта; может перейти к полному анализу (DF-001).
- **Связанные FR/NFR/UJ:** FR-027, FR-019; UJ-024.
- **Этап:** MVP.

## DF-019. Непрерывный фоновый сбор данных (Future, концептуально, Phase 2.0)

*Добавлено Phase 2.0 (PO-2.0-10). Расширяет уже существующий ingestion pipeline плановым, а не только пользовательским, триггером — не вводит новый модуль сбора.*

- **Инициатор:** jobs (плановое задание, независимо от того, открыт ли браузер пользователя).
- **Входные данные:** список отслеживаемых инструментов и контекстных категорий (watchlist + будущий Market Context, `INFORMATION_ARCHITECTURE.md` §2.12).
- **Последовательность:** jobs (плановый, бюджетируемый по rate-limit триггер) → application background use case → ingestion pipeline (sources → ingestion → normalization → data_quality [freshness/staleness]) → provenance → сохранение состояния «последнее известное хорошее» (last-known-good) в модуле-владельце данных.
- **Синхронные шаги:** отсутствуют.
- **Асинхронные шаги:** весь поток.
- **Точки сохранения:** last-known-good состояние с меткой свежести на источник/инструмент.
- **Ошибки и деградация:** недоступность одного источника не блокирует сбор по остальным; бюджетирование rate-limit предотвращает превышение лимитов провайдера (детализируется `docs/decisions/ADR-0012-realtime-and-background-monitoring-runtime.md`, Черновик); устаревшие данные помечаются явно, не удаляются молча и не выдаются как свежие.
- **Аудит:** не аудируется как критичное действие; фиксируется observability.
- **Наблюдаемость:** событие «плановый сбор выполнен» / «источник пропущен по бюджету или отказу», на каждый запуск задания.
- **Результат:** рыночный контекст остаётся актуальным независимо от активности пользователя в браузере, в рамках задержки, приемлемой для поддержки принятия решения человеком — не тик-уровня и не миллисекундной инфраструктуры (PO-2.0-10, дословно).
- **Связанные FR/NFR/UJ:** cross-ref FR-063; `ADR-0012` (Черновик).
- **Этап:** Future.

## DF-022. Мониторинг состояния тезиса (Future, концептуально, Phase 2.0)

*Расширяет DF-007 явной моделью состояний тезиса — не дублирует уже утверждённую автоматическую проверку результата (FR-039/FR-040).*

- **Инициатор:** jobs (плановая проверка по FR-039/FR-040, либо событийно по DF-020).
- **Входные данные:** ранее сформированный структурированный прогноз (DF-021) с условиями инвалидации.
- **Последовательность:** jobs → application background use case → получение открытых тезисов → ingestion pipeline (текущие данные, как в DF-007) → application сравнивает текущие данные с условиями инвалидации тезиса (`FORECAST_CONTRACT.md`, раздел 3) → application обновляет состояние тезиса (например: действителен / ослаблен / инвалидирован / истёк / готов к оценке) → при истечении или инвалидации может инициировать DF-007 (проверка результата) и, при обнаруженном расхождении, DF-008 (формирование урока).
- **Синхронные шаги:** отсутствуют.
- **Асинхронные шаги:** весь поток.
- **Точки сохранения:** состояние тезиса — отдельная запись, не переписывающая исходный текст прогноза (аналогично разделению insights/evaluations).
- **Ошибки и деградация:** недоступность данных для проверки — состояние остаётся «ожидает проверки», не переходит в «инвалидирован» по умолчанию.
- **Аудит:** не аудируется как критичное действие; фиксируется observability.
- **Наблюдаемость:** событие «состояние тезиса обновлено» с указанием перехода и причины.
- **Результат:** пользователь видит актуальное состояние тезиса без ручного повторного запроса анализа (UJ-033).
- **Связанные FR/NFR/UJ:** FR-063, FR-039, FR-040; UJ-033.
- **Этап:** Future.
- **Открытый вопрос:** владение этим потоком — расширение `jobs`/`evaluations` либо отдельный логический модуль `monitoring` — не решено этим документом; см. `MODULE_BOUNDARIES.md` и `docs/decisions/ADR-0012-realtime-and-background-monitoring-runtime.md` (Черновик).

- **Ошибки и деградация:** недостаточно данных для сегмента — явное «недостаточно данных для статистики», не выдуманная или экстраполированная цифра.

- **Наблюдаемость:** событие «сегментированная статистика пересчитана».
