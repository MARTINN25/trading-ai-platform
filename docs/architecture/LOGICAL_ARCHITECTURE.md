# Logical Architecture

**Статус:** Утверждён
**Владелец:** Product Owner
**Дата последнего изменения:** 2026-08-05
**Назначение:** определить логическую архитектуру AI Trading Assistant Platform без привязки к конкретному стеку.

Настоящий документ детализирует продуктовый фундамент ([`PRODUCT_SCOPE.md`](../product/PRODUCT_SCOPE.md), [`FUNCTIONAL_REQUIREMENTS.md`](../product/FUNCTIONAL_REQUIREMENTS.md)) и применяет [`ENGINEERING_PRINCIPLES.md`](./ENGINEERING_PRINCIPLES.md) к логической структуре платформы. Документ не выбирает и не подразумевает конкретные продукты, языки, фреймворки или сервисы — это предмет отдельных ADR (см. [`ADR_PROCESS.md`](../processes/ADR_PROCESS.md)). При расхождении приоритет имеет `PROJECT_CHARTER.md`; иерархия источников истины — [`DOCUMENTATION_STANDARD.md`](../processes/DOCUMENTATION_STANDARD.md), раздел 3.

---

## 1. Цель

Зафиксировать логическую структуру платформы — области ответственности, границы, потоки и правила взаимодействия — до выбора технологий и начала программирования, чтобы дальнейшие ADR и реализация опирались на согласованную структуру, а не формировались произвольно по ходу разработки.

---

## 2. Область применения

Документ описывает логический, а не физический уровень системы: логические области (раздел 6), их назначение и связи. Он не описывает конкретные серверы, контейнеры, облачные сервисы, базы данных, языки или фреймворки. Детализация модулей — [`MODULE_BOUNDARIES.md`](./MODULE_BOUNDARIES.md); потоки данных — [`DATA_FLOWS.md`](./DATA_FLOWS.md); модель отказов — [`FAILURE_MODEL.md`](./FAILURE_MODEL.md).

---

## 3. Архитектурный стиль

- **Модульный монолит как рекомендуемая начальная форма** — единое развёртываемое приложение с внутренними логическими областями, в соответствии с `ENGINEERING_PRINCIPLES.md`, пункт 11.
- **Строгие логические границы** — границы между областями (раздел 6) соблюдаются так же строго, как если бы области были отдельными сервисами.
- **Возможность будущего выделения модулей** — соблюдение границ должно делать техническое выделение области в отдельный сервис возможным без переписывания её внутренней логики (`ENGINEERING_PRINCIPLES.md`, пункт 13).
- **Запрет преждевременных микросервисов** — разбиение на отдельно разворачиваемые сервисы не вводится без конкретной, обоснованной причины и отдельного ADR (`ENGINEERING_PRINCIPLES.md`, пункт 12). Модульный монолит — не временный компромисс, а осознанно выбранная начальная форма, действующая до тех пор, пока обоснованная причина не потребует иного.

---

## 4. Контекст системы

Платформа — единая точка, через которую владелец получает собранные, проверенные и проанализированные рыночные данные и структурированные инсайты, ведёт дневник сделок и историю решений. Она работает как локально запускаемое приложение с последующим deployment на сервер, обслуживая одного пользователя через веб-интерфейс.

---

## 5. Внешние акторы

- **Пользователь** — единственный владелец платформы, инициирует запросы, отвечает на уточняющие вопросы, оценивает инсайты, ведёт дневник.
- **Источники рыночных данных** — внешние поставщики котировок и фактических данных по инструментам.
- **Источники новостей** — внешние поставщики новостных материалов.
- **Источники календаря** — внешние поставщики данных экономического календаря.
- **Внешний LLM-провайдер** — внешний поставщик AI-модели, используемой для анализа и формирования текста инсайта.
- **Будущие каналы уведомлений** — потенциальные внешние каналы доставки алертов (Post-MVP/Future), конкретный канал не выбирается этим документом.

## 7. Детализация логических областей

Для каждой области: назначение, входы, выходы, что область не должна делать.

### Web UI
- **Назначение:** отображение интерфейса, приём действий пользователя.
- **Входы:** действия пользователя (навигация, выбор, ввод).
- **Выходы:** запросы к Application API; отображение полученных данных.
- **Не должна делать:** содержать бизнес-логику анализа, обращаться к хранилищам или внешним источникам напрямую (правило 10).

### Application API
- **Назначение:** внешний входной адаптер веб-клиента — принимает и валидирует транспортный запрос, выполняет аутентификацию/авторизацию на границе, преобразует запрос в команду или query для Application Layer / Use Cases.
- **Входы:** транспортный запрос от Web UI.
- **Выходы:** команда/query для Application Layer / Use Cases; транспортный ответ для Web UI.
- **Не должна делать:** оркестрировать доменные области самостоятельно; владеть бизнес-данными; обращаться к хранилищам данных напрямую в обход Application Layer / Use Cases (правило 12).

### Application Layer / Use Cases
- **Назначение:** координация выполнения пользовательских сценариев (use case); определяет последовательность шагов, вызывает публичные интерфейсы доменных областей, управляет логическими границами транзакции.
- **Входы:** команда/query от Application API; событие от Background Jobs (для фоновых use case).
- **Выходы:** вызовы публичных интерфейсов доменных областей (Identity and Access, Market Context, Instrument Catalog, Source Integration/Ingestion, Analysis Orchestration, Insight Management, Insight Evaluation, Trade Journal, Notes and Chat, Alerting, Settings, Audit); результат для Application API.
- **Не должна делать:** содержать доменные правила, принадлежащие конкретной области; обращаться к физическим хранилищам напрямую; владеть долговременными бизнес-данными (может владеть только временным состоянием выполнения конкретного use case, включая Analysis Session Context — см. раздел «Контекст анализа» ниже).

### Identity and Access
- **Назначение:** определение владельца платформы и проверка доступа.
- **Входы:** запрос на доступ от Application API.
- **Выходы:** подтверждение или отклонение доступа.
- **Не должна делать:** реализовывать multi-tenant модель (см. `PRODUCT_SCOPE.md`, раздел 6 — вопрос не утверждён).

### Market Context
- **Назначение:** хранение и предоставление устойчивого рыночного контекста: рынок, инструмент, горизонт, таймфрейм (если применим).
- **Входы:** выбор пользователя через Application Layer / Use Cases.
- **Выходы:** контекст для Application Layer / Use Cases.
- **Не должна делать:** смешивать контекст разных рыночных направлений без явного действия пользователя (правило 20); хранить Analysis Session Context (ответы на уточняющие вопросы, явные допущения, выбранный режим, временный контекст конкретного запроса, ссылки на подготовленные данные) — это временное состояние принадлежит Application Layer / Use Cases (см. ниже), а не Market Context и не Settings.

### Instrument Catalog
- **Назначение:** предоставление списка доступных инструментов по рыночным разделам.
- **Входы:** запрос от Web UI/Application API; данные о доступности от Source Integration.
- **Выходы:** список инструментов.
- **Не должна делать:** выполнять анализ или хранить исторические данные инструмента сверх каталожных сведений.

### Source Integration
- **Назначение:** взаимодействие с внешними источниками данных, новостей и календаря.
- **Входы:** запрос на получение данных от Ingestion.
- **Выходы:** сырые данные от внешних источников.
- **Не должна делать:** передавать необработанные данные напрямую в Analysis Orchestration или LLM Gateway, минуя Ingestion/Normalization/Data Quality/Provenance.

### Ingestion
- **Назначение:** приём сырых данных от Source Integration.
- **Входы:** сырые данные от Source Integration.
- **Выходы:** сырые данные, переданные в Normalization.
- **Не должна делать:** интерпретировать или анализировать данные.

### Normalization
- **Назначение:** приведение данных из разных источников к единому внутреннему формату.
- **Входы:** сырые данные от Ingestion.
- **Выходы:** нормализованные данные для Data Quality.
- **Не должна делать:** отбрасывать provenance исходных данных.

### Data Quality
- **Назначение:** проверка согласованности, актуальности и правдоподобия нормализованных данных; дедупликация.
- **Входы:** нормализованные данные.
- **Выходы:** данные с явной пометкой состояния (доступны/устарели/недостоверны/конфликтуют — см. `FAILURE_MODEL.md`, раздел 4).
- **Не должна делать:** молча отбрасывать проблемные данные без пометки их состояния.

### Provenance
- **Назначение:** фиксация происхождения каждого значимого факта на всём пути данных.
- **Входы:** данные на любом этапе конвейера (Ingestion → Data Quality → Analysis Orchestration).
- **Выходы:** сведения о происхождении, прикреплённые к данным и к итоговому инсайту.
- **Не должна делать:** позволять факту достичь Insight Management без сохранённого происхождения (правило 9, 14).

### Analysis Orchestration
- **Назначение:** формирование структурированного результата анализа из подготовленного пакета фактов и контекста, полученных от Application Layer / Use Cases; вызов LLM Gateway.
- **Входы:** подготовленный пакет проверенных данных с provenance и Analysis Session Context, переданные use case формирования инсайта (см. раздел «Оркестрация анализа» ниже); ответ от LLM Gateway.
- **Выходы:** структурированный результат анализа (см. `FUNCTIONAL_REQUIREMENTS.md`, область 14), возвращаемый вызвавшему use case Application Layer.
- **Не должна делать:** обращаться к внешним источникам данных напрямую, минуя Source Integration/Ingestion/Normalization/Data Quality (правило 12); передавать в LLM Gateway необработанный сырой поток (`ENGINEERING_PRINCIPLES.md`, пункт 55); сохранять сформированный результат самостоятельно; зависеть от Insight Management (сохранение инициирует Application Layer после успешного результата — см. раздел «Оркестрация анализа»).

### LLM Gateway
- **Назначение:** единственная точка обращения к внешнему LLM-провайдеру.
- **Входы:** сформированный формальный запрос от Analysis Orchestration (отобранные данные, промпт, параметры).
- **Выходы:** AI-интерпретация для Analysis Orchestration.
- **Не должна делать:** обращаться к внешним источникам данных напрямую; владеть фактами или provenance (правило 9); иметь прямой доступ к секретам сверх необходимых для вызова провайдера, к пользовательским данным сверх переданного запроса.

### Insight Management
- **Назначение:** хранение и предоставление сформированных инсайтов вместе с контекстом их формирования (правило 14).
- **Входы:** структурированный инсайт, переданный Application Layer / Use Cases после успешного результата Analysis Orchestration (не напрямую от Analysis Orchestration).
- **Выходы:** инсайт для Application Layer / Use Cases (далее — Web UI через Application API), ссылки для Trade Journal, Insight Evaluation.
- **Не должна делать:** выполнять сбор данных или анализ; изменять содержание уже сохранённого инсайта по существу (аналогично запрету редактирования утверждённого ADR — `ADR_PROCESS.md`, раздел 25).

### Insight Evaluation
- **Назначение:** хранение пользовательских оценок и результатов проверки инсайтов.
- **Входы:** оценка пользователя; данные для проверки результата (от Source Integration через Analysis Orchestration или отдельный поток).
- **Выходы:** связанные с инсайтом оценка/результат.
- **Не должна делать:** переписывать исходный текст инсайта в Insight Management — оценка и результат хранятся отдельно от исходного вывода.

### Trade Journal
- **Назначение:** хранение записей о сделках пользователя, при необходимости связанных с инсайтом.
- **Входы:** запись сделки от пользователя через Application API.
- **Выходы:** записи дневника; данные для разбора сделки ассистентом.
- **Не должна делать:** изменять содержание связанного прошлого инсайта.

### Notes and Chat
- **Назначение:** хранение личных заметок и диалогов пользователя.
- **Входы:** текст от пользователя.
- **Выходы:** сохранённые заметки/диалоги.
- **Не должна делать:** становиться скрытой глобальной памятью или настройками платформы без явного отдельного действия пользователя (правило 13).

### Alerting
- **Назначение:** хранение условий алертов и инициирование уведомлений при их выполнении (Post-MVP).
- **Входы:** условие алерта от пользователя; данные для проверки условия.
- **Выходы:** уведомление для канала доставки (канал не определяется этим документом).
- **Не должна делать:** заменять собой Observability/эксплуатационные алерты владельца.

### Settings
- **Назначение:** хранение настроек платформы, управляемых владельцем (источники, язык и подобное).
- **Входы:** изменение настроек от пользователя.
- **Выходы:** актуальная конфигурация для соответствующих областей.
- **Не должна делать:** хранить секреты — это зона ответственности Configuration and Secrets.

### Audit
- **Назначение:** проверяемый журнал критичных действий (изменение настроек источников, экспорт данных и подобное).
- **Входы:** событие критичного действия от соответствующей области.
- **Выходы:** аудиторская запись.
- **Не должна делать:** использоваться как обычный диагностический лог (правило раздела 12 требований `MODULE_BOUNDARIES.md`; `ENGINEERING_PRINCIPLES.md`, пункт 28).

### Observability
- **Назначение:** структурированные логи, метрики, диагностика состояния платформы.
- **Входы:** события от всех логических областей.
- **Выходы:** диагностическая информация для владельца (раздел диагностики, `FUNCTIONAL_REQUIREMENTS.md`, FR-056).
- **Не должна делать:** хранить бизнес-состояние платформы (правило раздела 12 требований `MODULE_BOUNDARIES.md`).

### Background Jobs
- **Назначение:** выполнение асинхронных и плановых операций (например, автоматическая проверка результата инсайта, Post-MVP).
- **Входы:** запланированное или событийное задание.
- **Выходы:** результат задания, переданный соответствующей области (например, Insight Evaluation).
- **Не должна делать:** изменять production-логику автоматически на основании Future-уроков (`FUNCTIONAL_REQUIREMENTS.md`, область 31).

### Configuration and Secrets
- **Назначение:** хранение конфигурации и секретов отдельно от бизнес-кода (`ENGINEERING_PRINCIPLES.md`, пункты 40–41).
- **Входы:** значения конфигурации/секретов, задаваемые вне бизнес-кода.
- **Выходы:** значения конфигурации/секретов для областей, которым они необходимы.
- **Не должна делать:** передавать секреты в LLM Gateway сверх необходимого для авторизации вызова провайдера; экспонировать секреты Web UI.

## 7.1 Оркестрация анализа

Application Layer вызывает use case формирования инсайта. Use case координирует:

- Market Context (получение рыночного контекста);
- Instrument Catalog;
- ingestion pipeline (Source Integration → Ingestion → Normalization → Data Quality → Provenance);
- Analysis Orchestration;
- Insight Management.

Analysis Orchestration получает от use case подготовленный пакет фактов и Analysis Session Context, формирует структурированный результат и возвращает его use case — не сохраняет инсайт самостоятельно и не зависит от Insight Management. После успешного результата Analysis Orchestration use case (Application Layer) вызывает Insight Management для сохранения. Публикация логического события «инсайт сформирован» (см. `MODULE_BOUNDARIES.md`) не означает прямую зависимость Analysis Orchestration от Insight Management.

## 8. Разделение видов данных

Платформа явно различает четыре вида данных на всём протяжении конвейера:

1. **Факты** — данные, полученные от внешних источников (Source Integration → Ingestion → Normalization → Data Quality), всегда с provenance.
2. **Нормализованные данные** — факты, приведённые к единому внутреннему формату, готовые к использованию в анализе.
3. **AI-интерпретация** — вывод, сформированный LLM Gateway/Analysis Orchestration на основе нормализованных данных; явно отделяется от фактов (`ENGINEERING_PRINCIPLES.md`, пункт 59).
4. **Пользовательские данные** — заметки, оценки, записи дневника, настройки, вводимые пользователем напрямую.

Эти виды данных не смешиваются в едином неразличимом хранилище на логическом уровне — каждый вид имеет собственную логическую область владения (раздел 6).

---

## 9. Правило: LLM не обращается к источникам напрямую и не является источником фактов

LLM Gateway — единственная точка обращения к внешнему LLM-провайдеру и не имеет логического доступа к Source Integration. Факты поступают в Analysis Orchestration только через Ingestion → Normalization → Data Quality → Provenance. Это прямое применение `ENGINEERING_PRINCIPLES.md`, пункт 57.

---

## 10. Правило: Web UI не содержит бизнес-логики анализа

Вся логика формирования и оценки инсайта находится в Analysis Orchestration, Insight Management и связанных областях. Web UI только отображает результат и передаёт действия пользователя в Application API.

---

## 11. Правило: интеграции не знают о UI

Source Integration, Ingestion, Normalization, Data Quality и Provenance не имеют логической зависимости от Web UI или Application API — они предоставляют данные независимо от способа их последующего отображения.

---

## 12. Правило: аналитический pipeline работает через формальные входные данные

Analysis Orchestration не обращается к хранилищам или внешним источникам напрямую в обход Data Quality и Provenance — вход в pipeline всегда формален и проверен.

---

## 13. Правило: заметки не становятся глобальной памятью без явного действия

Notes and Chat не влияют на поведение Analysis Orchestration или другие логические области автоматически — использование заметки как контекста анализа требует явного действия пользователя, в соответствии с `FUNCTIONAL_REQUIREMENTS.md`, раздел «Правила уточняющих вопросов» (аналогичный принцип для ответов на уточняющие вопросы).

---

## 13.1 Контекст анализа

Платформа разделяет два вида контекста:

- **Market Context** — устойчивый контекст: рынок, инструмент, горизонт, таймфрейм (если применим). Владеет — Market Context (раздел 7).
- **Analysis Session Context** — временный контекст конкретного запроса анализа: ответы на уточняющие вопросы, явные допущения, выбранный режим (краткий/полный/скальпинг), ссылки на подготовленные данные текущего запроса. Владеет — Application Layer / Use Cases как состояние выполнения текущего use case (альтернативно — Analysis Orchestration как состояние текущего процесса формирования, до возврата результата use case). Analysis Session Context не принадлежит ни Market Context, ни Settings и не переживает завершение конкретного запроса без явного действия пользователя (см. правило 13).

---

## 14. Правило: инсайт сохраняется вместе с контекстом формирования

Insight Management хранит инсайт неразрывно с контекстом его формирования (входные данные и версии, provenance, временной срез, модель/промпт/параметры — `ENGINEERING_PRINCIPLES.md`, пункт 29). Это логическое требование к структуре хранения, а не к конкретной технологии.

---

## 14.1 Правило: audit и observability не создают обратных доменных зависимостей

- доменные модули не зависят напрямую от Observability;
- техническая телеметрия добавляется через инфраструктурные обёртки/перехватчики на границах вызовов, а не через явный вызов доменным модулем;
- критичные бизнес-действия передаются в Audit через Application Layer / Use Cases или через логические доменные события — не через прямую зависимость доменного модуля от Audit;
- Audit trail и Observability остаются разными механизмами (правило раздела 21, `MODULE_BOUNDARIES.md`);
- публикация логического события не означает прямую compile-time зависимость издателя события от подписчика (см. `MODULE_BOUNDARIES.md`);
- конкретная технология доставки событий/телеметрии этим документом не выбирается.

---

## 15. Синхронные операции MVP

- запрос анализа (Web UI → Application API → Application Layer / Use Cases → Analysis Orchestration → Application Layer / Use Cases → ответ; клиентский запрос MVP синхронно ожидает итоговый результат, что не означает последовательного выполнения каждого внутреннего шага в одном потоке исполнения — см. раздел «Асинхронные операции MVP» ниже);
- выбор рынка/инструмента/горизонта;
- сохранение инсайта, оценка инсайта;
- создание записи дневника, заметки;
- ручная фиксация результата инсайта.

---

## 16. Асинхронные операции MVP

- фоновый сбор данных от нескольких источников параллельно (Source Integration);
- базовое логирование и наблюдаемость.

---

## 17. Post-MVP асинхронные операции

- автоматическая плановая проверка результата инсайта (Background Jobs → Insight Evaluation);
- проверка при существенном движении цены;
- доставка алертов;
- аудит критичных действий как асинхронная запись, не блокирующая основной поток.

---

## 18. Границы транзакций на логическом уровне

Каждая логическая область отвечает за целостность собственных владеемых данных (см. `MODULE_BOUNDARIES.md`). Сохранение инсайта (Insight Management) и запись его контекста происходят как единая логическая операция — частичное сохранение (инсайт без контекста или наоборот) не допускается. Оценка/результат (Insight Evaluation) сохраняется как отдельная логическая транзакция, ссылающаяся на инсайт, не изменяя его.

---

## 19. Graceful degradation

При недоступности одного источника (Source Integration) Data Quality помечает соответствующие данные как отсутствующие, а Analysis Orchestration формирует инсайт с явной пометкой ограничения вместо отказа целиком (`ENGINEERING_PRINCIPLES.md`, пункт 21; `FUNCTIONAL_REQUIREMENTS.md`, FR-059). Подробная модель — `FAILURE_MODEL.md`.

---

## 20. Логическая изоляция рынков

Market Context, Instrument Catalog и Insight Management логически разделяют данные по рыночным направлениям (`PRODUCT_SCOPE.md`, раздел 11). Кросс-рыночный сценарий («Что если», UJ-020) требует явного действия пользователя и не является операцией по умолчанию.

---

## 21. Безопасность

- Identity and Access — единственная точка проверки доступа владельца.
- Configuration and Secrets — единственная точка хранения секретов; ни одна другая область (включая LLM Gateway и Web UI) не хранит секреты самостоятельно.
- Application API — единственная точка входа для UI; хранилища не доступны UI напрямую.
- Audit — фиксирует критичные действия отдельно от Observability.
- Ошибки, видимые пользователю, формируются без раскрытия внутренних деталей (`ENGINEERING_PRINCIPLES.md`, пункт 39) — ответственность Application API/Web UI при трансляции внутренних ошибок в пользовательские сообщения.

---

## 22. Наблюдаемость

Observability собирает структурированные события от всех логических областей (`ENGINEERING_PRINCIPLES.md`, пункт 36). Корреляционные идентификаторы связывают шаги одного логического потока (см. `DATA_FLOWS.md`) между областями для последующей диагностики.

---

## 23. Масштабируемость

Строгие границы областей (раздел 6, `MODULE_BOUNDARIES.md`) — необходимое условие возможного будущего выделения области в отдельный сервис (`ENGINEERING_PRINCIPLES.md`, пункт 13). Конкретные пределы масштабирования не устанавливаются этим документом (см. `NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-008).

---

## 24. Стоимость

LLM Gateway — единственная точка, через которую проходят вызовы к LLM-провайдеру, что даёт единую точку контроля объёма и стоимости вызовов (`ENGINEERING_PRINCIPLES.md`, пункты 53–55). Обязанность по предварительной фильтрации и дедупликации данных до LLM лежит на Data Quality/Analysis Orchestration, а не на LLM Gateway.

---

## 25. Что остаётся не определено

- конкретный технологический стек для любой логической области (предмет будущих ADR);
- физическое развёртывание (серверы, контейнеры, оркестрация);
- конкретные API-контракты между областями;
- физическая схема хранения данных;
- конкретные источники данных, новостей и календаря;
- конкретный LLM-провайдер;
- числовые нефункциональные показатели (см. `NON_FUNCTIONAL_REQUIREMENTS.md`).

---

## 26. Архитектурные риски

- преждевременное дробление модульного монолита на сервисы без обоснованной причины (митигируется правилом раздела 3 и `ENGINEERING_PRINCIPLES.md`, пункт 12);
- размывание границ между Analysis Orchestration и LLM Gateway, ведущее к тому, что LLM неявно становится источником фактов (митигируется правилами 9 и явным разделением видов данных, раздел 8);
- накопление скрытой логики в Web UI (митигируется правилом 10);
- рост стоимости LLM-вызовов без контроля (митигируется разделом 24 и `ENGINEERING_PRINCIPLES.md`, пунктами 53–55).

---

## 27. Критерии архитектурного успеха

- каждая логическая область имеет единственную зону ответственности и не дублирует владение данными другой области;
- границы областей делают возможным последующее выделение в сервис без переписывания внутренней логики;
- ни один поток данных (см. `DATA_FLOWS.md`) не нарушает правила разделов 9–14;
- модель отказов (`FAILURE_MODEL.md`) покрывает все логические области.

---

## 28. Definition of Done

Логическая архитектура считается готовой к принятию, когда:

1. Все 22 логические области (раздел 6, включая Application Layer / Use Cases) описаны с назначением, входами, выходами и ограничениями (раздел 7).
2. Правила разделов 9–14 не противоречат `MODULE_BOUNDARIES.md` и `DATA_FLOWS.md`.
3. Документ не содержит выбора технологий, физической инфраструктуры или API-контрактов.
4. Пройдено архитектурное ревью и получено явное принятие Product Owner (`PROJECT_CHARTER.md`, раздел 14; `ADR_PROCESS.md` — для последующих технологических решений на основе этой архитектуры).
