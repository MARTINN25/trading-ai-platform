# Technology Evaluation

**Статус:** Утверждён
**Владелец:** Product Owner
**Дата последнего изменения:** 2026-08-12
**Назначение:** сравнить технологические варианты для MVP по единым критериям и подготовить основания для отдельных ADR выбора стека.

Настоящий документ детализирует применение [`ENGINEERING_PRINCIPLES.md`](./ENGINEERING_PRINCIPLES.md), [`LOGICAL_ARCHITECTURE.md`](./LOGICAL_ARCHITECTURE.md) и [`MODULE_BOUNDARIES.md`](./MODULE_BOUNDARIES.md) к сравнительной оценке технологических кандидатов. При расхождении приоритет имеет `PROJECT_CHARTER.md`; иерархия источников истины — [`DOCUMENTATION_STANDARD.md`](../processes/DOCUMENTATION_STANDARD.md), раздел 3.

## 1. Назначение и статус документа

Документ является **аналитическим сравнением**, а не действующим архитектурным решением. Он:

- сопоставляет технологические варианты по единым, заранее определённым критериям (раздел 3);
- фиксирует **предварительные, необязывающие** рекомендации Solution Architect по каждой области сравнения;
- определяет дорожную карту будущих ADR (раздел 16), каждый из которых оформит ровно одно решение в соответствии с [`ADR_PROCESS.md`](../processes/ADR_PROCESS.md), раздел 11 («один ADR — одно решение»).

Ни одна рекомендация этого документа не является действующим архитектурным решением. Технологический стек остаётся неутверждённым до тех пор, пока по каждой позиции не будет оформлен, отревьюирован и принят Product Owner отдельный ADR, зафиксированный коммитом и прошедший merge в `main` (`ADR_PROCESS.md`, раздел 17). Настоящий документ **не создаёт** ни одного ADR-файла и не изменяет статус проекта на этапе «архитектура утверждена».

Claude зафиксировал предварительные рекомендации Solution Architect как есть, проверив их по критериям раздела 3, но не подменяя и не изменяя их содержание самостоятельно (`PROJECT_CHARTER.md`, раздел 11.2).

## 2. Ограничения

Сравнение проводится в границах, зафиксированных продуктовым и архитектурным фундаментом:

- MVP обслуживает одного локально запускаемого пользователя с последующим deployment на сервер (`PRODUCT_SCOPE.md`, разделы 18–19);
- Kubernetes и распределённая микросервисная инфраструктура исключены из MVP (`PRODUCT_SCOPE.md`, раздел 22);
- архитектурный стиль — модульный монолит с строгими логическими границами (`LOGICAL_ARCHITECTURE.md`, раздел 3; `ENGINEERING_PRINCIPLES.md`, пункты 11–13);
- LLM-компонент должен быть изолирован через единственную точку — `llm_gateway` — без жёсткой привязки ядра к одному провайдеру (`ENGINEERING_PRINCIPLES.md`, пункт 56; `MODULE_BOUNDARIES.md`, модуль 10);
- интерфейс и пользовательский вывод — на русском языке (`PRODUCT_SCOPE.md`, раздел 8);
- числовые NFR (задержка, доступность) не утверждены — см. `NON_FUNCTIONAL_REQUIREMENTS.md`; сравнение технологий не может опираться на неутверждённые количественные пороги;
- конкретные источники данных, их лицензии и стоимость не утверждены (`PRODUCT_SCOPE.md`, раздел 30) — сравнение по этой теме проводится на уровне подхода (`sources`/`ingestion`), а не конкретных поставщиков;
- стоимость эксплуатации оценивается наравне с техническими качествами (`ENGINEERING_PRINCIPLES.md`, пункт 52).

## 4. Backend: runtime и API adapter (два отдельных решения)

Выбор языка/runtime backend и выбор API adapter framework — два независимых решения (`ADR_PROCESS.md`, раздел 11 — «один ADR — одно решение»), не объединяемые в единый пункт «backend»: runtime исполняет `application` и доменные модули (`MODULE_BOUNDARIES.md`), а API adapter — внешний транспортный слой, не являющийся доменным модулем (`LOGICAL_ARCHITECTURE.md`, раздел 7, «Application API»).

### 4.1 Backend runtime (язык исполнения)

| Вариант | Простота | Модульный монолит | Тестируемость | Стоимость | Зрелость | Примечание |
|---|---|---|---|---|---|---|
| Python | высокая | подходит (явные модули, async) | высокая (богатая экосистема тестирования) | низкая (open source) | высокая, богатая экосистема данных/LLM-интеграций | сильная сторона — работа с данными и LLM-клиентами |
| TypeScript/Node.js | средняя (больше boilerplate для модульных границ) | подходит | высокая | низкая | высокая | единый язык с frontend, но менее развитая экосистема анализа данных |
| Go | средняя (меньше «магии», но больше ручного кода) | подходит | высокая | низкая | высокая, но менее развитая экосистема LLM-интеграций | сильные стороны — производительность, не являющаяся приоритетом MVP |

**Предварительная рекомендация (Solution Architect, необязывающая):** Python — как runtime для `application`, доменных модулей и `llm_gateway`, за счёт зрелой экосистемы данных и LLM-клиентов. Выбор конкретной версии Python и политика её обновления — предмет `ADR-0001`, не этого документа.

### 4.2 API adapter (внешний транспортный слой)

| Вариант | Простота | Соответствие роли внешнего адаптера | Тестируемость | Стоимость | Зрелость | Примечание |
|---|---|---|---|---|---|---|
| FastAPI | высокая | подходит (тонкий транспортный слой, явная валидация запроса) | высокая | низкая | высокая | популярный выбор для Python-runtime, не единственный |
| Flask + расширения | средняя (больше ручной сборки инфраструктуры) | подходит | высокая | низкая | высокая | требует больше ручной настройки валидации/схем |
| Django REST Framework | средняя (более тяжеловесный, ориентирован на monolith-с-ORM) | подходит частично (связанность с ORM Django может размывать границу «только адаптер») | высокая | низкая | высокая | больше, чем требуется для тонкого адаптера |

**Предварительная рекомендация (Solution Architect, необязывающая):** FastAPI — как внешний API adapter (`Application API`, `LOGICAL_ARCHITECTURE.md`, раздел 7). FastAPI **не является бизнес-ядром** платформы: `application` и доменные модули не импортируют FastAPI и не зависят от него (`MODULE_BOUNDARIES.md`, правило «Application API — внешний адаптер, зависящий только от application»). Выбор конкретной версии FastAPI — предмет `ADR-0002`, не этого документа.

## 8. Фоновые задачи

| Вариант | Устойчивость к рестарту web-процесса | Пригодность для критичных/долгих заданий | Дополнительная инфраструктура | Стоимость | Примечание |
|---|---|---|---|---|---|
| Отдельная очередь задач и отдельный worker-процесс (с брокером сообщений) | высокая | высокая | требует отдельного брокера и worker-процесса | дополнительная | наиболее устойчивый вариант, но с дополнительной эксплуатационной сложностью |
| Надёжная очередь/планировщик, опирающийся на основное хранилище (без отдельного брокера) | высокая (состояние задания хранится в СУБД) | подходит для MVP-объёма критичных заданий | не требует отдельного брокера, требует отдельного worker-процесса | минимальная сверх уже выбранной СУБД | задание переживает рестарт web-процесса за счёт хранения состояния в PostgreSQL |
| In-process background tasks (в рамках web-процесса) | низкая (состояние теряется при рестарте web-процесса) | не подходит для критичных/долгих заданий | отсутствует | минимальная | допустим только для коротких, некритичных операций |

**Обязательные правила (зафиксированы по итогам архитектурного ревью, ARCH-0005):**

- in-process background tasks допустимы только для коротких, некритичных операций;
- критичные и долгие задания (в том числе автоматическая проверка результата инсайта, `DATA_FLOWS.md`, DF-007) не выполняются внутри web-процесса;
- автоматическая проверка инсайтов должна переживать рестарт web-приложения — состояние задания не может существовать только в памяти web-процесса;
- фоновые задания должны иметь устойчивое (persisted) состояние;
- для критичных фоновых операций необходим отдельный worker-процесс, отличный от web-процесса, обслуживающего Application API;
- конкретный механизм очереди и необходимость отдельного брокера сообщений решаются `ADR-0006`, а не настоящим документом;
- отсутствие отдельного брокера сообщений допустимо только при условии надёжного хранения состояния задания в основном хранилище (раздел 6);
- планировщик, работающий исключительно в процессе web-приложения, **не является** предварительно выбранной production-архитектурой фоновых задач.

**Предварительная рекомендация (Solution Architect, необязывающая):** отдельный worker-процесс для критичных фоновых задач. Для MVP в первую очередь рассматривается вариант надёжной очереди/планировщика, опирающегося на уже выбранное основное хранилище (PostgreSQL, раздел 6), без добавления отдельного брокера сообщений, пока не доказана конкретная необходимость (`ENGINEERING_PRINCIPLES.md`, пункт 67). Итоговый механизм очереди — предмет `ADR-0006`.

## 10. LLM-провайдер и LLM Gateway

| Вариант | Независимость ядра | Стоимость | Зрелость API | Примечание |
|---|---|---|---|---|
| xAI как первый провайдер за `llm_gateway` | обеспечивается через `llm_gateway` как единственную точку обращения (`MODULE_BOUNDARIES.md`, модуль 10) | зависит от тарифа провайдера | развивающаяся | рассматривается как первый провайдер, не единственно возможный |
| OpenAI как первый провайдер | то же (через `llm_gateway`) | зависит от тарифа | зрелая | альтернатива, не выбранная предварительно |
| Anthropic как первый провайдер | то же (через `llm_gateway`) | зависит от тарифа | зрелая | альтернатива, не выбранная предварительно |

Независимо от выбранного первого провайдера, `llm_gateway` обязан оставаться единственной точкой обращения к LLM (`LOGICAL_ARCHITECTURE.md`, раздел 9), так что смена провайдера не должна требовать изменений в `analysis` или иных доменных модулях (`ENGINEERING_PRINCIPLES.md`, пункт 56).

**Требования к изоляции, наблюдаемости и заменимости (зафиксированы по итогам архитектурного ревью, ARCH-0005):**

- SDK конкретного провайдера изолирован внутри `llm_gateway`; доменные модули не зависят от SDK провайдера ни напрямую, ни через специфичные для него типы данных;
- конкретная модель провайдера (например, отдельная модель семейства Grok у xAI) **не фиксируется навсегда** — модель и её версия задаются конфигурацией, а не хардкодятся (`ENGINEERING_PRINCIPLES.md`, пункт 41);
- объём токенов, число запросов, задержка и стоимость вызовов LLM должны измеряться (`ENGINEERING_PRINCIPLES.md`, пункты 36, 53; `NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-029);
- лимиты вызовов задаются конфигурацией, а не хардкодятся (`ENGINEERING_PRINCIPLES.md`, пункт 41);
- fallback на другого провайдера не обязателен к реализации в MVP, но интерфейс `llm_gateway` должен допускать замену провайдера без изменения вызывающего кода (`ENGINEERING_PRINCIPLES.md`, пункт 56).

**Предварительная рекомендация (Solution Architect, необязывающая):** xAI — как первый предполагаемый LLM-провайдер, полностью скрытый за интерфейсом `llm_gateway`. Конкретная модель xAI не фиксируется навсегда этим документом. Выбор провайдера не является выбором архитектуры ядра — при необходимости провайдер заменяется без изменения `analysis` и других доменных модулей.

**Предварительная рекомендация (Solution Architect, необязывающая):** Docker Compose — для локального запуска и первоначального серверного deployment. Kubernetes не рассматривается ни для MVP, ни для ближайшего Post-MVP.

## 14. Многорыночные данные: стратегия провайдеров (Stocks / Forex / Crypto / Commodities)

Настоящий раздел добавлен по итогам Phase 0 (`PROJECT_CHARTER.md`, роли Product Owner/Claude) во исполнение решения PO-2: рынки Акции, Forex, Криптовалюта и Сырьё рассматриваются в рамках единой стратегии провайдеров данных, оцениваемой по общим критериям, с приоритетом Forex как первого расширяемого рынка после уже работающих Акций. Выбор конкретного провайдера этим разделом **не производится** — раздел устанавливает только рамку оценки для будущего `ADR-0011` (раздел 16).

### 14.1 Ограничения раздела

- для рынка Акции (Акции/Stocks) поставщики данных уже интегрированы в текущей реализации платформы — этот факт зафиксирован в `.ai-context/CURRENT_STATE.md`, не переоценивается и не заменяется настоящим разделом; предметом оценки являются Forex (приоритет), Crypto, Commodities и вопрос единообразия/расширяемости подхода между рынками;
- ни один провайдер данных для Forex, Crypto или Commodities не выбран и не сравнен по фактическим характеристикам (тарифы, лимиты, покрытие) — реальное исследование конкретных поставщиков не проводилось в рамках этой задачи и не может быть добросовестно выполнено без внешнего исследования Solution Architect;
- настоящий раздел **не называет** и не сравнивает конкретных поставщиков (например, конкретные бренды API рыночных данных) — это предотвращает фиксацию непроверенных фактов о лимитах, цене или покрытии (`PROJECT_CHARTER.md`, раздел 11.2 — Claude не изобретает факты и не подменяет решение Solution Architect);
- критерии раздела 14.2 производны от общих критериев раздела 3 и специфичны для задачи мультирыночных данных.

### 14.2 Критерии оценки провайдеров рыночных данных

| № | Критерий | Почему важен для мультирыночной стратегии |
|---|---|---|
| 1 | Модель символов/тикеров (symbol model) | разные рынки используют разные соглашения об идентификации инструмента; единообразие снижает связанность доменных модулей с конкретным провайдером |
| 2 | Котировки (quotes) | доступность актуальной цены — минимальное условие пригодности провайдера |
| 3 | История цен (OHLCV/history) | необходима для горизонт-зависимого окна данных (`TARGET_INTELLIGENCE_CONTEXT.md`, §2.4) |
| 4 | Семантика часов рынка (market-hours / 24-7) | Акции/Forex имеют торговые сессии, Crypto торгуется непрерывно — честная интерпретация «свежести» данных зависит от этой семантики (`TARGET_INTELLIGENCE_CONTEXT.md`, §2.2) |
| 5 | Новости (news) | покрытие новостей по инструменту/рынку, необходимое для `InstrumentNewsSection`-подобного функционала на новых рынках |
| 6 | Макро/календарь (macro/calendar) | доступность макроэкономического контекста, релевантного прежде всего Forex (`TARGET_INTELLIGENCE_CONTEXT.md`, §2.6–2.7) |
| 7 | Лимиты запросов (rate limits) | определяет допустимую частоту опроса без деградации сервиса |
| 8 | Задержка (latency) | влияет на своевременность отображаемых данных |
| 9 | Надёжность (reliability) | история доступности провайдера, наличие статуса/SLA |
| 10 | Лицензирование (licensing) | условия использования и переиспользования данных в продукте |
| 11 | Стоимость (pricing) | категориальная оценка, без утверждённых числовых порогов (раздел 17) |
| 12 | Тестируемость (testability) | наличие sandbox/демо-режима для интеграционного тестирования без затрат на реальные лимиты |
| 13 | Плавная деградация (graceful degradation) | явное, предсказуемое поведение при недоступности или частичном отказе провайдера, не имитация данных (`ENGINEERING_PRINCIPLES.md`) |
| 14 | Переносимость между провайдерами (provider portability) | возможность заменить провайдера без изменения доменных модулей — по аналогии с требованием изоляции `llm_gateway` (раздел 10) |
| 15 | Поддержка потоковых обновлений (streaming/WebSocket), если применимо | актуально при расширении реального времени на новые рынки |

### 14.3 Статус фактической оценки

## 17. Категории стоимости

Оцениваются категориально, без утверждённых числовых значений (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-028 — «требуется решение Product Owner»):

- **Production-сервер** — стоимость одного Linux-сервера для первого production deployment (раздел 11, `ADR-0008`).
- **Рыночные API** — тарифы поставщиков рыночных данных, ещё не выбраны (`PRODUCT_SCOPE.md`, раздел 30).
- **Новостные API** — тарифы поставщиков новостных материалов, ещё не выбраны.
- **Экономический календарь и дополнительные данные** — тарифы поставщиков календаря и прочих вспомогательных источников.
- **LLM** — стоимость вызовов выбранного провайдера, зависит от объёма токенов и запросов (`ENGINEERING_PRINCIPLES.md`, пункты 52–55; раздел 10 настоящего документа).
- **Резервные копии** — стоимость хранения и, при использовании внешнего сервиса, стоимость его тарифа (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-022).
- **Мониторинг и наблюдаемость** — минимальна на MVP-уровне (раздел 12), потенциально возрастает на Post-MVP.
- **Домен и TLS-сопутствующие расходы** — если применимо при серверном deployment; не утверждено.
- **Возможные лицензии** — лицензии источников данных или сторонних библиотек, если применимо (`PRODUCT_SCOPE.md`, раздел 29).
- **Хранение данных и исходящий трафик** — рост объёма истории инсайтов и данных пользователя со временем (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-009), а также стоимость исходящего трафика на выбранной инфраструктуре.
- **Инструменты разработки** — если платные; при выборе open source инструментов, как правило, минимальны или отсутствуют.

**Обязательные оговорки:**

- рыночные и новостные API потенциально могут стоить больше, чем аренда небольшого production-сервера — стоимость данных не следует недооценивать относительно инфраструктурной стоимости;
- итоговый бюджет платформы нельзя оценить до утверждения конкретных источников данных и ожидаемой нагрузки;
- при появлении конкретных цен они фиксируются вместе с датой проверки — цены поставщиков меняются со временем и не считаются действительными бессрочно;
- переменные расходы (LLM, трафик, хранение) измеряются фактически, а не оцениваются один раз заранее (`ENGINEERING_PRINCIPLES.md`, пункт 52);
- стоимость production-сервера рассматривается отдельно от стоимости данных (рыночные/новостные API, календарь) и отдельно от стоимости LLM — эти категории не смешиваются в одном показателе.

Конкретные суммы и бюджетные пределы не устанавливаются этим документом — они предмет отдельного решения Product Owner.

## 18. Риски

- **Риск привязки к одному LLM-провайдеру** — снижается требованием полной изоляции через `llm_gateway` (`ENGINEERING_PRINCIPLES.md`, пункт 56; раздел 10 настоящего документа).
- **Риск преждевременного усложнения** (введение кэша, векторной СУБД или Kubernetes без конкретной задачи) — снижается явным решением не вводить эти компоненты в MVP (разделы 7, 9, 11) и принципом пункта 67.
- **Риск неконтролируемого роста стоимости LLM-вызовов** — снижается принципами контроля затрат (`ENGINEERING_PRINCIPLES.md`, пункты 53–55), подлежит измерению (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-029).
- **Риск принятия предварительной рекомендации без независимой проверки** — снижается обязательным прохождением каждой позиции через отдельный ADR с архитектурным ревью и явным принятием Product Owner (`ADR_PROCESS.md`, разделы 14–15).
- **Риск неопределённости источников данных** — выбор `sources`-интеграций зависит от ещё не принятого решения о конкретных поставщиках (`PRODUCT_SCOPE.md`, раздел 30), что может повлиять на последующие технологические решения (например, формат данных, необходимость дополнительных клиентских библиотек).
- **Риск устаревания сравнения** — технологический ландшафт (особенно LLM-провайдеры) быстро меняется; сравнение должно быть проверено повторно непосредственно перед оформлением соответствующего ADR, а не считаться действительным бессрочно.
- **Риск отсутствия фактической оценки мультирыночных провайдеров** — раздел 14 устанавливает только рамку критериев, не фактическое сравнение; принятие `ADR-0011` до завершения реального исследования Solution Architect привело бы к решению на основе непроверенных или изобретённых фактов — снижается требованием, что `ADR-0011` остаётся в статусе «Черновик» до завершения исследования (раздел 14.3).

## 19. Открытые вопросы

- какой конкретно провайдер данных/новостей/календаря будет использован — влияет на реализацию `sources`, но не рассматривается в этом документе (`PRODUCT_SCOPE.md`, раздел 30);
- какая конкретно платформа/провайдер серверного deployment будет выбрана — предмет `ADR-choose-containerization-and-deployment-approach`;
- какой бюджетный предел для LLM- и хостинг-затрат — требуется решение Product Owner (`NON_FUNCTIONAL_REQUIREMENTS.md`, NFR-028);
- потребуется ли когда-либо векторный/семантический поиск — открыто, будет пересмотрено при появлении конкретной задачи (раздел 7);
- итоговый выбор LLM-провайдера остаётся открытым до оформления и принятия соответствующего ADR — xAI является только предварительной рекомендацией (раздел 10).
- итоговый выбор провайдеров данных для Forex, Crypto и Commodities остаётся открытым — раздел 14 не сравнивает конкретных поставщиков; требуется отдельное исследование Solution Architect до заполнения `ADR-0011`;
- останется ли подход к данным Акций (текущая интеграция) частью единой мультирыночной стратегии или будет пересмотрен отдельно — не решено этим документом;
- **(Phase 2.0)** итоговые источники данных для глобальных акций (EU/Asia), индексов, ставок/доходностей, макро, экономического календаря, фундаментальных данных и News Intelligence не выбраны и не оценены — раздел 14.4 фиксирует только вопросы будущего исследования (pending), аналогично разделу 14.3;
- **(Phase 2.0)** решается ли расширение `ADR-0011` или создаётся отдельный ADR для категорий раздела 14.4 — не решено этим документом;
- **(Phase 2.0)** владение логикой мониторинга состояния тезиса (`jobs`/`evaluations`/отдельный модуль `monitoring`) остаётся открытым — `ADR-0012`, раздел 28, `MODULE_BOUNDARIES.md`.

## 20. Definition of Done
