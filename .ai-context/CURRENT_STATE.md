## 4a. Предыдущая ревью-задача (теперь завершена)

**Phase 2C.1 — Canonical Live-State Domain Model** (ветка `feature/live-market-state-domain`, создана от `main` @ `d7bea77`, сразу после мерджа Phase 2B.1 через PR #51) — **завершена и смёржена в `main` через PR #52** (коммит `a1bf8cb`, merge-коммит `b9cd405`). Первый implementation-slice из Phase 2C (см. архитектурный план предыдущей планирующей задачи — «Phase 2C — Live Market Data Architecture & Implementation Plan», не создавшей ни одного файла кода/ADR).

Реализует канонический, **полностью provider-agnostic** доменный слой живого рыночного состояния — `backend/src/trading_ai/market_data/live_state.py` (новый файл) + `backend/tests/test_market_data_live_state.py` (новый файл, **61 тест** — точное число подтверждено `pytest --collect-only`, не оценено на глаз). Ни один транспорт (REST polling/Twelve Data WebSocket/любой другой будущий адаптер), ни FastAPI/SSE/httpx, ни фоновый worker этой задачей не реализованы и не подразумеваются — только чистая, детерминированная модель данных и функции перехода состояния, без сети, без `asyncio`, без скрытого доступа к часам (каждая функция, которой нужно «сейчас», принимает его явным параметром). Задача прошла одну итерацию — первоначальная реализация плюс отдельный corrective review pass, зафиксированный ниже:

- **Типы**: `InstrumentLiveState`, `Bar` (осознанно НЕ переиспользует `PricePoint` — разные концепции, см. docstring `Bar`), `PriceUpdateEvent`, `MarketState`/`ConnectionState`/`FreshnessState`/`UpdateKind`/`VolumeQuality` (все — `str, Enum`, тот же паттерн, что `ai/types.py`), `FreshnessPolicy` и `IntervalPolicy` (оба — явные policy-объекты с задокументированными значениями по умолчанию; ни одно число/якорь не зашито внутрь `derive_freshness_state`/`_floor_to_interval`).
- **`FreshnessState` — не хранится на `InstrumentLiveState`, а всегда выводится** через `derive_freshness_state(state, policy, now)` — осознанное решение, не упущение.
- **`last_closed_bar` защищён структурно, не рантайм-проверкой**: `apply_price_update` физически не имеет пути записи в `last_closed_bar`, кроме собственного rollover.
- **Символ переиспользует `watchlist.domain.normalize_ticker`** — не создан конкурирующий парсер.

**Corrective review pass** (архитектурное ревью нашло и потребовало исправить до принятия Product Owner):

- **Одинаковый timestamp у двух provisional-событий — теперь ПОЛНЫЙ no-op**, не частичный: без provider sequence/trade-identity домен не может доказать, что это разные сделки, а не повтор доставки одной и той же — ни `open`/`high`/`low`/`close`/`close_at`/`volume`/`last_price`/`last_price_as_of` не меняются, независимо от цены/`volume_hint`. Раньше `high`/`low`/объём всё же расширялись при точном совпадении timestamp — это признано неоднозначным и исправлено.
- **Genuinely-older (не равный) timestamp в том же открытом интервале** — отдельное, явно задокументированное поведение: `high`/`low`/`volume_hint` всё ещё вносят вклад (order-independent агрегаты), но `close`/`last_price` никогда не регрессируют. Явно разведено с случаем точного совпадения выше.
- **UTC-валидация ужесточена**: раньше отклонялась только naive-datetime, но **принимался любой** aware-offset (например, `+03:00`), при этом сообщения об ошибках уже заявляли «UTC» — несоответствие. Теперь `_is_utc()` требует zero-offset aware datetime everywhere (`PriceUpdateEvent.timestamp`, `Bar.interval_start`/`close_at`, `now`, `IntervalPolicy.anchor`); домен никогда не конвертирует молча — это ответственность будущего адаптера.
- **`derive_freshness_state` — MARKET_CLOSED теперь только для `MarketState.CLOSED`**: раньше любое состояние, кроме `OPEN` (включая `PRE_MARKET`/`AFTER_HOURS`/`UNKNOWN`), ложно трактовалось как «рынок закрыт». Теперь `PRE_MARKET`/`AFTER_HOURS`/`UNKNOWN` используют обычные возрастные полосы (могут быть `LIVE`) — только `CLOSED` получает специальную трактовку.
- **Новый `IntervalPolicy`** (`duration` + `anchor`, UTC-валидируемый) заменил сырой `timedelta` в `apply_price_update` — конфигурируемое выравнивание границ бара без привязки к провайдеру/бирже; якорь по умолчанию — Unix epoch (поведение по умолчанию не изменилось).
- **Документация `UpdateKind`/module docstring исправлена на честную**: раньше заявлялось, что precedence «выражен через `UpdateKind`» — фактически precedence везде чисто timestamp-based, `UpdateKind` — это routing/validation для входной точки, не независимый механизм приоритета. Никакого дополнительного механизма ранжирования не введено (самая простая корректная модель).

**Реально проверено:** 61 целевой тест → все проходят изолированно (`pytest tests/test_market_data_live_state.py -v`); backend `pytest -v` (полный набор) → **566 passed, 38 skipped** (без регрессий, было 505/38 до Phase 2C.1); `mypy src tests` → чисто (111 файлов); `git diff --check` → чисто; `git diff -- frontend` → пусто (frontend не тронут); `compose.yaml`/`docs/DOCUMENT_REGISTER.md`/`docs/decisions/**`/`frontend/package.json`/`frontend/package-lock.json`/`backend/pyproject.toml` — не изменены; поиск по новым файлам на `TwelveData`/`httpx`/`WebSocket`/`FastAPI`/`sleep`/URL/секреты — совпадений в виде реального кода нет (только объясняющие docstring-упоминания того, чего модуль намеренно избегает).

**Явно НЕ реализовано этой задачей** (следующие слайсы Phase 2C.2+, см. архитектурный план): адаптер живого провайдера (REST polling или Twelve Data WebSocket), сам REST polling, SSE/WebSocket-эндпоинт, обновления на frontend, subscription registry, фоновый worker/ADR-0006-задача. `ADR-0012` не изменён и не тронут этой задачей. Доменная модель по-прежнему полностью изолирована — ни один backend-эндпоинт/use case/frontend-компонент её не использует.

- **Горизонт (FR-006)** — `AnalysisHorizon` (`short`/`medium`/`long`) обязателен в `POST /instruments/{ticker}/analysis?horizon=...`; отсутствие или невалидное значение → `422` (никогда не подставляется по умолчанию). `ai/horizon.py` — новый модуль чисто детерминированной логики: `parse_horizon`, `history_period_for_horizon` (SHORT→существующее окно 1M, MEDIUM→новое 3M, LONG→новое 1Y — `market_data/types.py`/`gateway.py` расширены двумя новыми значениями `InstrumentHistoryPeriod`, тот же provider endpoint, только другой `outputsize`), `compute_check_after` (`generated_at` + верхняя граница диапазона горизонта: SHORT +5 торговых дней с пропуском выходных, MEDIUM +8 недель, LONG +12 календарных месяцев — не изобретается LLM), `compute_horizon_sufficiency` (качественный, явно задокументированный судейский порог: SHORT ≥5/MEDIUM ≥20/LONG ≥60 точек истории + staleness-порог котировки на горизонт — точные числа НЕ утверждены Product Owner, это Solution-Architect-style implementation judgment call, разрешённый `FORECAST_CONTRACT.md` §7).

- **`forecast_state`** — `FORECAST`/`NO_QUALITY_SETUP`/`INSUFFICIENT_EDGE`/`INSUFFICIENT_DATA`; последние три — валидные, желательные результаты (PO-2.0-8), не запасной вариант. `directional_view` (`STRONGLY_BULLISH…STRONGLY_BEARISH`, не BUY/SELL/HOLD) и `base_case`/`bullish_case`/`bearish_case`/`catalysts`/`invalidation_conditions` — `None`/`()`, когда `forecast_state != FORECAST` (структурно enforced Pydantic `model_validator`, не только промптом).

AI Quality Evaluation Vertical Slice (ветка `feat/ai-quality-evaluation`) — первый, намеренно небольшой, воспроизводимый evaluation harness для уже существующего `GenerateInstrumentAnalysis` (ADR-0007 §52 явно требует evaluation dataset до дальнейшего расширения production-использования модели). **Не пользовательская фича** — frontend не менялся вообще, ничего не выполняется в браузере, ничего не вызывает market/news provider:

- **ADR-0007 §52 требует**: evaluation dataset (создаётся отдельно, не в самом ADR — это и есть эта задача); проверку factual grounding, schema adherence, refusal correctness, prompt injection resistance, русского языка, latency/cost/stability; regression между моделями/provider на одинаковых сценариях; запрет production-изменения (модель/provider/значимый prompt) без regression evaluation; численные пороги качества ADR не задаёт. Ни LLM-as-judge, ни отдельный benchmark framework, ни новый ADR ADR-0007 §52 не требует — новый ADR **не создавался**, задача — implementation-деталь внутри уже утверждённой `llm_gateway`-границы;
- `backend/src/trading_ai/ai/evaluation/` (новый подпакет: `types.py`/`dataset.py`/`evaluators.py`/`runner.py`/`report.py`/`__main__.py`) — provider-neutral `EvaluationCase`/`EvaluationExpectation`/`EvaluationResult`/`CheckResult`, не generic benchmark framework;
- **Dataset** — 12 фиксированных, деterministic сценариев как обычные Python dataclasses (не JSON/YAML — обоснование в README), синтетический тикер `ACME` и синтетические числа (не live market values, не сырые Twelve Data/Finnhub payload); каждый case = `analysis_input` (что видела бы модель) + `expectation` (какие инварианты обязательны) + hand-authored `reference_response` (не реальный ответ модели — стенд-ин для offline-прогона на нуле стоимости);
- **Deterministic evaluators** (13 проверок на case, без LLM-as-judge — обоснование ниже): structured_output, non-empty summary/price_context/news_context, risks (min count), disclaimer, no_recommendation, no_target_price, no_system_prompt_leak, no_secret_leak, injection_resistance (только для injection-тегированных cases), missing_data_behavior (best-effort keyword-проверка, не семантика), russian_output (эвристика по доле кириллицы). `gateway.py` дал две функции публичными (`ModelOutputSchema`, `contains_forbidden_language` — были `_`-приватными) специально для переиспользования evaluation-кодом одной и той же логики, что и production;
- **LLM-as-judge STOP-условие проверено и НЕ сработало**: ADR-0007 §52 не требует model-based evaluation — перечисленные инварианты детерминированно проверяемы; judge не добавлен. Semantic factual grounding (полное "модель не выдумывает факты") намеренно не решается regex-ами — честно задокументированное ограничение baseline, не заявлено как решённое;
- **CLI** — `python -m trading_ai.ai.evaluation` (`--offline`/`--live`/`--case`/`--all-cases`), argparse, без новой зависимости (Typer/Click не добавлены). Обоснование CLI vs только pytest: разная аудитория — pytest регресс-тестирует саму grading-логику на fixtures, CLI даёт человеку читаемый summary в offline или live режиме по требованию;
- **Live evaluation — строго opt-in**: обычный `pytest`/`mypy`/offline-запуск = **0** вызовов xAI; live — либо `--live` (3 представительных кейса: normal/missing-data/prompt-injection, по умолчанию), либо `--live --all-cases` (весь датасет, печатает предупреждение с числом вызовов до первого запроса); opt-in pytest-тест `tests/integration/test_ai_evaluation_live.py` (`@pytest.mark.live_provider`, переиспользует существующую `TRADING_AI_LIVE_LLM_API_KEY`) — ровно 3 кейса, без retry;
