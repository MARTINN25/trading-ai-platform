# PROJECT CHARTER

**Проект:** AI Trading Assistant Platform
**Статус документа:** Действующая редакция
**Единственный источник истины по целям, ролям и правилам проекта.**

---

## 1. Миссия проекта

Создать персональную AI-платформу для трейдинга, которая помогает пользователю принимать более качественные торговые решения за счёт надёжной аналитики, прозрачных данных и предсказуемого поведения системы — при полном сохранении контроля решений за человеком.

---

## 2. Видение проекта

Платформа enterprise-уровня, которая:

- строится по принципу **Architecture First → Documentation First → Code Last**;
- проектируется так, будто с первого дня эксплуатируется в production и обслуживает реальные деньги реальных пользователей;
- обладает чистой, документированной архитектурой, понятной любому новому инженеру без устных объяснений;
- масштабируется и развивается месяцами без накопления технического долга;
- не содержит поспешных, недокументированных или архитектурно необоснованных решений.

---

## 3. Цели

1. Разработать полную инженерную документацию до начала написания бизнес-кода.
2. Зафиксировать архитектуру платформы до реализации любого модуля.
3. Обеспечить единый источник истины для каждого документа и решения.
4. Минимизировать технический долг за счёт продуманных решений "на берегу".
5. Обеспечить воспроизводимость и прозрачность всех этапов разработки.
6. Подготовить платформу к длительной (многомесячной) итеративной разработке несколькими участниками (человек + AI-агенты).

---

## 4. Роли участников проекта

| Роль | Участник | Мандат |
|---|---|---|
| **Product Owner** | Пользователь | Определяет продуктовые требования, приоритеты и принимает финальное решение по любому вопросу проекта. |
| **Solution Architect / CTO** | ChatGPT | Единственный источник архитектурных решений: стек технологий, структура системы, паттерны, границы модулей. |
| **Senior Software Engineer** | Claude (данный агент) | Исполняет задачи в рамках уже принятой архитектуры. Не принимает архитектурные решения самостоятельно. Готовит документацию, инженерные материалы и (на будущих этапах) код строго по утверждённым спецификациям. |

---

## 5. Зоны ответственности

**Product Owner:**
- формулирует продуктовые цели и требования;
- утверждает архитектурные решения, предложенные архитектором;
- принимает финальные решения при разногласиях.

**Solution Architect (ChatGPT):**
- определяет технологический стек;
- проектирует структуру системы и модулей;
- утверждает архитектурные паттерны и границы ответственности компонентов;
- пересматривает и утверждает изменения архитектуры.

**Senior Software Engineer (Claude):**
- реализует задачи строго в рамках утверждённой архитектуры;
- не вносит самостоятельных архитектурных решений, не меняет стек и структуру проекта;
- при обнаружении противоречий или пробелов в архитектуре — сообщает об этом, а не решает самостоятельно;
- отвечает за качество, аккуратность и соответствие стандартам исполняемой работы.

---

## 6. Основные инженерные принципы

1. **Architecture First** — ни один модуль не реализуется без предварительно утверждённой архитектуры.
2. **Documentation First** — решение считается принятым только после того, как оно задокументировано.
3. **Code Last** — код пишется в последнюю очередь, после того как архитектура и документация стабилизировались.
4. **Single Source of Truth** — для каждого вопроса существует ровно один актуальный документ.
5. **Явность важнее удобства** — неочевидные решения фиксируются явно, а не подразумеваются.
6. **Минимально необходимая структура** — не создаётся ничего "про запас" или "на будущее" без обоснованной необходимости.
7. **Обратимость решений** — где возможно, предпочтение отдаётся решениям, которые проще отменить или изменить.

---

## 7. Основные принципы документирования

1. Каждый документ имеет одну зону ответственности и не дублирует содержимое других документов.
2. Изменения вносятся путём редактирования существующего документа, а не созданием нового.
3. Документ должен быть понятен новому участнику проекта без дополнительных устных объяснений.
4. Все важные решения (архитектурные, продуктовые, процессные) фиксируются в письменном виде до их реализации.
5. Формулировки должны быть точными и однозначными — без "возможно", "наверное", "как-нибудь потом" в финальных документах.

---

## 8. Правила внесения изменений

1. Любое изменение архитектуры инициируется и утверждается только Solution Architect.
2. Любое изменение продуктовых требований утверждается только Product Owner.
3. Изменения в уже существующие документы вносятся путём редактирования файла — создание файлов-дублей (`*_new`, `*_v2`, `*_final` и т.п.) запрещено.
4. Перед внесением изменения проверяется, не существует ли уже соответствующий документ.
5. Значимые изменения фиксируются с указанием причины изменения.

---

## 9. Правила работы с Git

1. Один источник истины — основная ветка репозитория (`main`).
2. История коммитов должна быть читаемой: один коммит — одно осмысленное изменение.
3. Сообщения коммитов формулируются понятно и по существу, отражая суть изменения.
4. Деструктивные операции (force push, hard reset, удаление веток и т.п.) не выполняются без явного согласования с Product Owner.
5. Не коммитятся секреты, ключи, учётные данные и любые конфиденциальные данные.
6. На данном (документационном) этапе Git используется исключительно для версионирования документации.

---

## 10. Правила работы с документацией

1. Структура каталога документации:
   - `docs/architecture/` — архитектурные материалы (наполняется по мере утверждения архитектором);
   - `docs/decisions/` — архитектурные решения (ADR — Architecture Decision Records);
   - `docs/processes/` — инженерные процессы и регламенты;
   - `PROJECT_CHARTER.md` — устав проекта (данный документ), корневой источник истины;
   - `README.md` — общее описание проекта для новых участников.
2. Каждый документ обновляется по мере развития проекта и не оставляется в устаревшем состоянии.
3. Не создаются документы, дублирующие уже существующие по смыслу.
4. Новые каталоги документации создаются только при обоснованной необходимости.

---

## 11. Правила работы с Claude

1. Claude действует в роли Senior Software Engineer и не подменяет собой архитектора или Product Owner.
2. Claude не принимает решения о стеке технологий, структуре системы или архитектурных паттернах.
3. На этапе Architecture First / Documentation First Claude не пишет бизнес-код, backend, frontend, инфраструктурные конфигурации, SQL и не добавляет зависимости.
4. Claude обязан следовать утверждённой архитектуре после её получения от Solution Architect и Product Owner.
5. При обнаружении противоречий между запросом и текущей архитектурой/документацией Claude сообщает об этом явно, а не действует по собственному усмотрению.
6. Claude обновляет существующие документы вместо создания дублирующих файлов.

---

## 12. Что категорически запрещено

На текущем этапе проекта запрещено:

- ❌ создавать backend;
- ❌ создавать frontend;
- ❌ создавать docker / docker-compose;
- ❌ создавать базы данных;
- ❌ создавать API;
- ❌ писать SQL;
- ❌ писать программный (бизнес-) код;
- ❌ добавлять какие-либо библиотеки или зависимости;
- ❌ менять структуру проекта без обоснованной необходимости;
- ❌ самостоятельно придумывать дополнительные технологии или архитектурные решения;
- ❌ создавать дублирующие версии документов (`*_new.md`, `*_v2.md`, `*_final.md` и т.п.).

---

## 13. Общие стандарты качества

1. Каждый документ должен быть точным, структурированным и профессионально оформленным.
2. Формулировки не допускают двойного толкования.
3. Терминология используется единообразно во всех документах проекта.
4. Любое решение, влияющее на дальнейшую разработку, обосновывается, а не декларируется без объяснения.
5. Документация актуализируется синхронно с принятием новых решений — устаревшая информация не остаётся в силе.

---

## 14. Definition of Done

Для этапа документации задача считается выполненной, когда:

1. Документ создан или обновлён в правильном месте структуры каталогов.
2. Документ не дублирует содержимое других документов.
3. Формулировки однозначны и не содержат противоречий с уже утверждёнными документами.
4. Документ соответствует правилам, зафиксированным в разделах 6–13 данного устава.
5. Product Owner и/или Solution Architect имели возможность ознакомиться с результатом.

---

## 15. Порядок разработки проекта

1. **Этап 1 — Устав и базовая документация** *(текущий этап)*: `PROJECT_CHARTER.md`, `README.md`, структура каталога документации, `.gitignore`.
2. **Этап 2 — Архитектура**: Solution Architect формирует и утверждает архитектуру платформы, технологический стек, границы модулей; результаты фиксируются в `docs/architecture/` и `docs/decisions/`.
3. **Этап 3 — Инженерные процессы**: описание процессов разработки, ревью, тестирования и релизов в `docs/processes/`.
4. **Этап 4 — Реализация**: написание кода строго по утверждённой архитектуре и документации, только после завершения предыдущих этапов.

Переход к следующему этапу возможен только после того, как предыдущий этап зафиксирован в документации и утверждён Product Owner.
